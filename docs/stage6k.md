# Stage 6K: 実機不具合の修正・抽選管理・収支・コレクションの改善

## 1. 下部メニューの位置ずれ（最優先）
**iPhone 実機（ホーム画面アプリ）では未確認。** 下記は実機の診断値とコード・自動テストからの原因分析と対策。

### 原因（Stage 6J の構造が持っていた欠陥）
- Stage 6J は画面全体を `position: fixed; inset: 0` の縦flexにし、下部メニューをその最下段に置いた。
- 実機の診断値（Stage 5D〜5E で取得）: 起動直後のホーム画面アプリは `innerHeight=793 / 100vh=852 / 100dvh=793 / safe-top=59`。**レイアウト上の表示領域(793)が実際の画面(852)よりSafe Area(上)の分だけ低い**。
- `inset: 0` の入れ物の高さは「レイアウト上の表示領域」= 793px で止まるため、入れ物の下端（= 下部メニューの下端）が画面の下端より約59px上になり、その下に空白が出た。Stage 6J が外した補正（`--vp-gap`）が、まさにこの差を埋めるものだった（外した補正の裏返しが不具合になった）。
- 6J のレポートでは「入れ物は表示領域に伸縮するので補正が残らない」と分析したが、**この環境では表示領域そのものが画面より低く報告される**ため、伸縮に任せるだけでは下端が合わない。
- Safe Area の二重計上はなし: 下部メニューの余白は `max(0, safe-area-inset-bottom − 0.5rem)` の1回だけ（入れ物は画面の下端までなので、`safe-area-inset-bottom` はメニューの中の余白としてのみ使う）。ヘッダーは `safe-area-inset-top` を1回。

### 対策（構造）
- `.app-root`（globals.css）: 通常は `position: fixed; inset: 0`。
- `@media (display-mode: standalone)`（ホーム画面アプリ）のときだけ `bottom: auto; height: 100vh`（`100lvh` に対応していれば `100lvh`）。**大きい方の表示領域（画面全体）の高さ**に固定する。測定・タイマー・JS補正は使わない。表示領域が後で正しい値に直っても、`100lvh` は同じ値（画面全体）のまま変わらない。
- Safari のタブ（ツールバーあり）では `display-mode: standalone` に当たらないので、従来どおり `inset: 0`（ツールバー込みの 100vh は使わない）。
- キーボード: iOS はキーボードでレイアウト上の表示領域を縮めない（キーボードは上に重なる）ので、入れ物の高さは変わらず、下部メニューは動かない。キーボード分のボトムシート位置だけ、従来どおりイベント駆動の `--kb-inset`。
- 復帰・モーダル: 入れ物の高さは CSS の単位（`lvh`）だけで決まり、イベントや状態に依存しない。

### 計測
| 項目 | 結果 |
|---|---|
| 修正前（6J）の想定 | 入れ物 793px → メニュー下端は画面下端(852)の約59px上（診断値からの算出。実機で再確認が必要） |
| 修正後の想定 | standalone: 入れ物 = 100lvh = 852px → メニュー下端 = 画面下端（診断値からの算出。実機未確認） |
| 自動テスト（Chromium、幅 320/375/390/430px） | 入れ物の上端=0・高さ=画面全体、メニュー下端=画面下端、横スクロールなし、画面高さを変えても（キーボード・回転の模擬）下端に接し続ける |

standalone の挙動はブラウザの自動テストでは再現できない（Playwright で `display-mode` を切り替えられない）。

## 2. 地域フィルター（全47都道府県）
- 地域の行に「都道府県: すべて ▾」ボタン。タップすると選択画面（ボトムシート）が開き、北海道・東北／関東／中部／近畿／中国・四国／九州・沖縄に整理した47都道府県をチェックボックスで複数選択。地域ごとの「地域を選択／解除」、「すべて選択」「選択解除」、選択数（n / 47）を表示。

## 3. 全情報タブの「20」「28」
- 定義: 薄い数字（`count`）= 全情報タブに出ている抽選の件数（既定の絞り込み「受付中・未応募」＋スルー除外）。青いバッジ（`newCount`）= **絞り込み前**の全抽選のうち「まだ確認していない（新着）」の件数。
- 原因: 集計の母数が違った（絞り込み後 20 件に対し、受付終了・応募済みの新着を含む絞り込み前 28 件）。重複・キャッシュの不一致ではない。
- 修正: 新着は件数と**同じ集合**（既定の絞り込み・スルー除外後）の中の `isNew` だけを数える。必ず件数以下。表示は「新N」（aria: 新着N件（表示中のうち未確認））。

## 4. 日付入力の表示（iOS）
- 原因: appearance を外した固定高さの日付欄で、WebKit の内側の値の表示部（`::-webkit-date-and-time-value`）が上寄せになる。
- 修正: 日付・日時・月・時刻の入力欄を `display: flex; align-items: center` にし、内側の値の高さ・余白・行の高さをそろえる（全フォーム共通のCSS）。支出登録の日付欄から `appearance-none`/`block` を外した。他のフォーム（抽選・購入・売却・カード・対戦記録など）にも同じCSSが効く。**iPhone 実機未確認。**

## 5・6. 支出の品目区分
- 支出登録の先頭に「品目」: ポケモンカード／カード周辺グッズ／経費。説明文（「購入した商品を登録します…」）は削除。
- 品目で入力欄が変わる:
  - ポケモンカード: 従来どおり（商品マスター・数量・単位・購入方法・定価からの金額計算）。購入実績・商品別数量に反映。
  - カード周辺グッズ: 品名（自由入力）・数量・金額。マスター非連携。
  - 経費: 内容（自由入力）・金額のみ（数量・単位・購入方法なし）。
- DB: `purchases.category`（文字列。形式のみ制限。品目を増やすときは `src/lib/expense-category.ts` に1行足す）。**既存の支出はすべて `pokemon_card`**（既定値。金額・日付・購入履歴は変更なし）。
- 集計: 収支（月間支出・一覧）には全品目が入る。品目別の内訳（月間）と品目での絞り込み。購入実績・商品別数量・購入条件（過去の購入実績）・売却原価の候補・コレクションの数量には**ポケモンカードの購入だけ**を使う（周辺グッズ・経費は混入しない）。

## 7. コレクションの光の演出が消える
- 調査: 詳細を開く・閉じるときに IntersectionObserver が外れる経路は無い。原因として確定できたのは、演出の定期的な光が `:not(:hover)` と `data-touch` に依存していたこと。**iOS はタップ後に `:hover` が残る**ため、タップして詳細を開いたカードは詳細を閉じたあとも「ホバー中」と判定され、定期的な光が止まる。また保留中の位置更新（rAF）が指を離したあとに `data-touch` を付け直す競合があった。
- 修正: `:hover` はホバーできる端末（`@media (hover: hover)`）だけに限定。定期的な光の条件から `:not(:hover)` を外した。指を離す・キャンセルしたときに保留中の更新を取り消して `data-touch` を確実に外す。IntersectionObserver による画面外停止・省電力・動きを減らす設定・画像の色味は変更なし。
- **iPhone 実機未確認。**

## 8. カードの状態別相場評価
- 相場計算の状態区分（記録は変えない）: A（良好）= A+・A／B（軽微な傷・使用感）= B+・B／C（傷や状態不良が目立つ）= C。未選択・旧表記は推測せず A（補正なし）として計算し、その枚数を表示する。
- 価格: ①状態B・Cの**実際の販売相場**が取得データ（ポケカ価格比較CSV）にあればそれを使う（取得時に状態B／Cの掲載があるカードだけ別に保存。無いものは作らない）。②無ければ**基準相場（手動の参考相場）× 倍率**。買取相場は状態の区別がないので常に倍率。
- 倍率の初期値: **A 100% / B 85% / C 65%**。コレクション右上「その他」→「状態別の評価倍率」で変更（1〜200の整数）。世帯ごとに保存。
- 計算例: 基準10,000円・状態B・倍率85% → 評価額8,500円。
- 保存・表示: 基準相場（補正前）と状態補正後の評価額を区別して表示（カード詳細「状態別の評価額」）。取得相場・手動価格・購入額・お気に入りは変更しない（評価額は導出値）。コレクション全体の「参考価値」は補正後。
- DB: `condition_multipliers`（世帯別・RLS）、`card_market_prices.condition_grade`（既存行は `A`）。

## 9. 長押しドラッグ並び替え
- カード一覧（画像・テキストとも）で、長押し（約0.4秒）でドラッグ開始。指に追従し、重なったカードの位置へ入れ替わる（FLIPで滑らかに移動）。離すと確定。画面の端では自動スクロール。長押し前に指が動いたら縦スクロールとして扱う。ドラッグ直後のクリック（詳細表示）は抑止。iOS の長押しメニュー・選択を無効化。
- 保存: お気に入り表示（並び順が標準／お気に入り順）では順位を保存（再読み込み・他の並び順に切り替えて戻っても復元。絞り込み中は表示されないお気に入りの位置を保つ）。それ以外は一時的で、並び順・絞り込みを変えると解除し、保存しない。
- ドラッグ操作はカード情報を変更しない（並びの変更のみ）。

## 10・11. 抽選カードの日付
- アイコン: 購入期間 = 財布、受取期間 = 買い物袋（従来の購入の買い物袋を受取へ）。簡易・詳細・各タブで共通部品。応募期間・発表日などのアイコンは変更なし。

## 14. 複数端末のログイン
- 原因（確定）: ログアウトが `supabase.auth.signOut()` の既定である `scope: "global"` で、そのユーザーの**全端末のセッションを失効**させていた。夫婦で同じアカウントを使うと、片方のログアウト（または不要なログアウト）でもう片方が再ログインを求められる。
- 対策: `signOut({ scope: "local" })`（操作した端末のセッションだけ）。認証の無効化・無期限トークンは使わない。リフレッシュトークンのローテーション（reuse interval 10秒）は変更なし。各端末のプロフィールの選択は端末内保存（変更なし）。
- 未確認（利用者の操作）: Supabase ダッシュボード → Authentication → Sessions の「Single session per user」が**無効**であること（有効だと後からのログインで先のセッションが失効する。Pro プランの設定で、このリポジトリからは確認できない）。
- 検証: 実Supabase・2つのブラウザコンテキストで同じアカウントにログインし、片方をログアウトしても、もう片方が再読み込みを繰り返してもログイン済みのままであることを確認（E2E）。
