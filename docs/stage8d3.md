8D-2 の実装との照合で**直したもの**:
1. **検索の費用が過小だった**: 検索は別の問い合わせ（トークン費用あり）で行うのに、検索1回の固定概算（1.5円）しか加算していなかった → 実際の使用量（検索回数×料金＋トークン料金）を報告して加算（`searchCostJpy`）。キャッシュから返した検索は0円。
2. **トークン上限の既定（6万）が累計に対して小さすぎた**: 各ステップで会話全体を再送するため累計は数十万に達する。実際の安全装置は費用上限 → 既定を30万に変更し、費用上限（15円）を主とした。
3. **Haiku 5.5 は思考が既定でオン**: ツール呼び出しの応答の思考ブロックを次の要求へ**原本のまま戻す**必要がある → 応答の原本（`raw`）を保持して再送。`effort` を明示（既定 medium）。`max_tokens` を4000に（思考を含むため）。出力が `max_tokens` で途切れた応答のツールは実行しない。
4. 検索の `pause_turn` に対応（最大3回で打ち切り）。検索結果の要約に、引用文（`cited_text`）を取り込む。`allowed_domains`/`blocked_domains` を指定可能。
5. 検索結果・取得ページの再利用（キャッシュ。同じ検索語・同じURLは再取得しない。空の結果・失敗は保存しない。期限24時間。評価ではファイル保存）。
6. 長いページは、冒頭と「店舗名・住所らしい行・会社概要・閉店/移転」の前後だけをAIへ渡す（トークン削減・住所の見落とし防止）。

## 2. 公式サイトの自律的な発見（`official.ts`）
**8D-2 の制約**: `store_url` が未登録だと、正しい住所を取得しても「確認済み」になりにくかった。**8D-3**: AIが公式サイト候補を発見し、取得したページの内容から**根拠で**公式性を判定する。AIの「公式だ」という主張は、入力にも根拠にもならない。
| 状態 | 条件 |
|---|---|
| trusted | 店舗マスターに登録済み（`store_url`。**同じ系列の他店舗に登録されたものを含む**） |
| verified | すべて満たす: ①ページの見出しに系列名（または系列の別名）がある ②そのドメインの取得済みページに、店舗マスターの同じ系列の他店舗の名前が2つ以上（または他店舗1つと対象店舗）載っている＝公式の店舗一覧との一致 ③会社概要・運営会社・著作権表記が系列名の近くにある（運営元との一致）**または**信頼済みサイトからそのドメインへのリンクがある |
| candidate（公式候補） | 根拠が不十分。住所の「公式の裏付け」には使わない。理由（不足している根拠）を保存 |
| rejected | SNS・まとめ・地図・口コミ・ブログ・通販モール・検索・百科事典などの第三者ドメイン（系列名・店舗一覧・運営会社の記載があっても公式にしない） |
- 公式（trusted/verified）の情報源に支えられた住所がちょうど1つなら、非公式の異なる住所があっても公式を採る（理由に残す）。公式が複数の住所を示す、または公式が無ければ矛盾のまま確定しない。
- エージェントの動き: 検索 → 店舗一覧ページを取得 → **同じサイト内のリンク（会社概要など）をたどる**（取得できるURLは、検索結果・登録済み公式ドメイン・取得済みページと同じサイト内のリンクのみ）。システムプロンプトに「公式サイトの店舗一覧と会社概要で裏付ける」「あなたの判断は根拠にならない」と明記。
- 保存: `store_location_research.official_sites`（ドメイン・状態・満たした根拠・不足・URL。マイグレーション `20261213000095`。**開発用DBのみ適用・本番未適用**）。**`stores.store_url` は更新しない。**
- **限界**: 公式の店舗一覧と会社情報をそっくり複製した悪意のあるサイトは、この条件だけでは見分けられない可能性がある（その場合も、住所は地図の照合・複数情報源・閉店の確認を通らなければ確認済みにならない）。実在サイトでの精度は未計測。
- 系列の別名（`chain_aliases`。例: ふるいち＝古本市場）を、系列名の表記ゆれの吸収に使う。
