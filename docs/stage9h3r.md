## 2. 実地検証で判明した問題と修正（個別の店舗名・系列名・検索語は固定していない）
1. **既存の再発見を新規と誤計上**: 店舗名の表記揺れ（先頭の系列名・括弧書き・屋号つき）と、屋号違いの系列名で既存に一致しなかった → 店舗名・系列名の一般的な正規化（`storeKeyOf`・`sameStore`・`chainsRelated`）。
2. **原文の照合が厳しすぎる**（12件中9件が除外）: AIが表の項目を並べ替えた／記号を整えた引用が通らなかった → 記号・空白を除く一致、または断片の85%以上がページにあること（作られた内容は通さない）。除外理由に、引用の直し方を明記。
3. **費用の関門による停止を「AIの障害」と記録** → `cost_limit` として記録。
4. **二次情報の扱い**: まとめサイトの記載が要確認にならなかった → 情報源の分類（既存の `classifyCaseSource`）で二次情報を要確認に。
5. **系列共通・店舗選択式の告知が成果として残らない** → プロンプトに、scope を指定して記録するよう追記（実AIでの再確認は未実施）。
6. **マスターに無い未知の店舗が、登録経路で止まる**（再解析が店舗名を読めず、店舗を特定できない）→ 既存の収集と同じ基準の仮登録（名称が明確で近い候補が無い）＋ 解析が店舗を読めない場合だけ、検証済みの店舗名を使う（`storeHint`）。
7. **実行時間が60秒（Cronの上限）を超えた（62秒）** → ミッションの時間上限をCronでは35秒に。
8. **本番での有効化・費用管理** → 次節。

修正後の確認: 自動テスト（モック）。**実AIでの最終確認は、予算の都合（累計85.35円）で、修正1（表記揺れ）の一部以降は再実行していない**（修正2〜7は実AIで未確認）。

## 3. 本番での有効化・費用管理（実装。本番の設定は変更していない）
- 有効化条件: 開発環境（`TOREMANE_ENV=local`）、または **`AUTONOMOUS_COLLECTION=on`**（本番の環境変数で明示）。無い場合は、設定が自律型でも従来方式で動く（保存値は保持）。`autonomousAllowed`／`resolveEffectiveEngine`。設定画面の選択も同条件。
- 本番の費用管理（`autonomous-hook.ts` の `budgetRemainingJpy`）: 調査履歴（`discovery_runs.cost_jpy`）から、**今日（日本時間）・今月の残り予算**を計算（`AUTONOMOUS_DAILY_CAP_JPY` 既定30円／`AUTONOMOUS_MONTHLY_CAP_JPY` 既定300円）。残りが1件の上限（`COLLECT_AUTONOMOUS_PER_MISSION_JPY` 既定8円）に満たなければ開始せず、理由を記録。読めなければ開始しない。本番ではファイルの台帳が使えないため、費用はDBに記録（例外・途中終了でも消費分を記録）。
- キー: `AUTONOMOUS_ANTHROPIC_API_KEY`、なければ既存の `ANTHROPIC_API_KEY`（追加契約なし）。モデル: `AUTONOMOUS_MODEL`（既定 Haiku 5.5）。
- 既存の安全制御はそのまま: 取得できるURLの範囲・robots・SSRF・同一サイト頻度・重複拒否・収穫逓減の打ち切り・上限はAIが変更不可。
- 戻し方: 設定で「既存ロジック主体」を選ぶ（次回の実行から）、または `AUTONOMOUS_COLLECTION` を外す（即時に従来方式）。データ・応募・当選は削除されない（DBテストで確認）。

## 5. 残る課題
- X（Twitter）はrobotsで取得できず、収集元の多くがXのため、起点の告知を読めない（まとめサイト経由の二次情報が中心）。公式Xの扱いは既存の方針（X連携）に依存。
- 二次情報（まとめサイト）由来の採用候補は、公式の告知での確認が必要（要確認として登録される）。
- 実際のページでの登録経路（再解析・仮登録）は、実AIの出力ではなく架空のページで検証。実運用の初期に観察する。
