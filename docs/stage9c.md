## 1. 9項目の原因と修正
| # | 原因 | 修正 |
|---|---|---|
| ① 系列名の表記揺れ | 照合の正規化が「ブックオフ/bookoff」など一部の語の前方一致だけで、記号（・）、括弧書きの読み、通販の語に未対応 | `src/lib/chain-normalize.ts`（記号・括弧書きの読み・法人格・チャネル語を除く共通の正規形）。マスター照合・重複判定・除外ルール・別名の衝突検査・手動の新規系列作成（表記違いだけの同じ系列は作らず別名追加を案内）で共通利用。**系列の統一と通販チャネルは区別**（チャネルは別に返し、店舗は統合しない）。部分一致はしない（イオン/イオン九州は別） |
| ② アカウントから店舗が分からない | 表示名だけが根拠 | `account-evidence.ts`: 表示名・ユーザーID・プロフィール・投稿本文・公式サイトのドメインを重み付きで照合。系列は重み2以上（または単独で競合なし）、店舗は1つに絞れるときだけ。競合・同名複数は決めない。店舗不明でも抽選は登録 |
| ③ 店舗選択式なのに「店舗不明」 | 後段の登録判定が `storeResolved=false` で店舗を空に上書き（`isReady` が店舗選択式を見ていなかった） | `ready.ts`・`attention.ts` で店舗選択式を解決済みとして扱う。AIに `apply_unit`（応募単位）を追加し、`understanding.ts` の `decideApplyUnit` で AI と構造検査を突き合わせ（構造の根拠が高確度で食い違うときだけ固定ロジックが変更し理由を残す）。**候補の draft に `understanding.trace`（ai→match→form→fixed→final）を保存** |
| ④ 店舗選択式と個別店舗の二重登録 | 重複判定が「同じ情報源URL」だけで、別URLの告知を拾えなかった | 「選べる店舗にその店舗が含まれる」を根拠に追加。**同系列・同商品・同締切だけでは重複にしない**（確認待ちも増やさない。既存テストの方針を維持） |
| ⑤ 重複対象に選べない | 画面（`storeDiffers`）とサーバー（`exclusion-reasons.ts`）の両方が、店舗選択式の抽選を「店舗が異なる」として拒否 | 両方で店舗選択式（登録の方式・候補の方式・プレースホルダ名）を例外に。統合先の更新は情報源URL追記のみで、応募・当選・購入の記録は変更しない |
| ⑥ 一部の情報が新規候補に | 商品が読み取れないと重複判定を行わなかった | 商品なしでも情報源URL一致（high＝補完）・同店舗かつ同締切（medium）で既存の抽選と関連づける。別店舗・別開催回は関連づけない |
| ⑦ 商品名の認識不良 | 販売条件（シュリンクなし等）が商品名に残る | `product-name.ts`: 括弧内・末尾の販売条件/数量語を分離（`conditions`）。商品を区別する語（特別版）は消さない。商品区分・シリーズ名の接頭辞を除いた本体名も候補に |
| ⑧ キデイランド | 「1店舗のみ」の制限は構造の証拠でないとして一律に断定を避けていた | `lottery-form.ts`: **店舗をまたぐ応募制限の記載**＋（店舗別の応募ページ、または系列の傾向）で店舗選択式（`cross_store_limit`）。制限の記載だけ／URLが店舗別だけ／系列の傾向だけでは決めない。受取だけの制限は対象外 |
| ⑨ 楽天ブックス複数商品 | 商品ごとの告知が別カードになる | `multi-product.ts` + `addProductsToLottery`: 同系列・同店舗・同締切・同条件分類＋根拠（同じ情報源／複数商品の記載／系列の傾向）で既存の1枚に商品を追加し、応募方式未確認の注意を付ける。商品別応募・期間/条件違い・手動登録・応募記録あり・手動編集済みは統合しない |

## 2. 情報の理解と追跡（§2）
`understanding.ts`: 系列／店舗・チャネル／商品（複数）／応募単位／期間／条件／当選発表／受取方法／情報源／根拠／未確認項目に整理し、`decidedBy`（AI か固定ロジックか）と `trace` を候補の draft に保存。`disposition.ts`: 新規／補完／更新／重複／追加調査の判断を記録（既存データは変更・削除しない）。

## 3. 自律型の情報収集計画（§3）
`src/lib/agent/collection-planner/`（既存のエージェント基盤を使用）。
- AI は `get_signals`（新商品の発売・発見状況・不足している抽選・取得失敗・未監視の系列）を読み、調べる対象を**自分で選び**、`check_official_site` → `follow_external_link` → `match_existing_lotteries` と結果を見て次を決め、根拠つきで提出する。`search_public_web`・`read_announcement_image` は**検索・画像解析が承認・設定された世界でだけ登録**（既定では存在しない）。
- 安全: ツールは読み取り専用（書き込み・投稿・SQL等は登録時に例外）／回数・検索・取得・トークン・費用・時間・再試行・重複の上限／`HostThrottle`（ホストごとの回数・間隔、同一URLの再取得、内部アドレス・認証情報つきURL・取得制限のホストを断る。制限は回避しない）／外部文面はデータとして囲み命令は実行しない／**検証層**（`reviewPlan`）が、存在しない対象・根拠なし・取得していないURLを根拠にした発見を不採用に。
- 出力は「調査計画と発見（提案）」で、監視対象の追加・抽選の登録・データ変更はしない。`collection-planner-world.ts`（読み取り専用）が信号を作る。**画面・定期実行には未接続**（§7）。
- 検索API・取得手段の比較: 取得は既存の公開ページ取得（無料・robots尊重）。検索は未導入（有料サービスは承認まで導入しない）。
