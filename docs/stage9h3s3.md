# Stage 9H-3S-3: 自律型AIによる一括再調査・名寄せ・抽選統合

9H-3S-2 の再調査基盤を、運用できる形（本番用の関門・費用の上限・実行画面・候補への対応）と、名寄せ・応募構造・店舗別カードの統合まで広げた。**本番は未変更**（PR #4 への追加コミット。DB・マージ・デプロイ・大規模な再調査は承認後）。

## 1. 名寄せ（系列・商品）
固定ロジックは「候補の発見」と「検証」、判断はAI。個別の名称は書かない。
- `master-identity/reading.ts`（純関数）: ひらがな/カタカナ・全角半角・記号・空白の吸収（ふるいち⇔フルイチ）、かな⇔英字の厳密な読みの一致（ゲオ⇔GEO）、音の近さ（ジラフル⇔GIRAFULL。**候補の発見にだけ**使い、同一とは扱わない）。漢字を含む名称は読みを機械的に決めない（古本市場⇔ふるいち はAIがWebで確認）
- `resolveName`: 上記を組み込み。独立管理の系列（イオンオンライン等）は読みが近くても寄せない。**同じ名称が仮登録名と正式マスターに当たるときは正式マスターへ**（自動収集の仮登録名が優先されない）
- `agent/name-judge.ts`: AIが、検索結果（タイトル・URL・要約）だけを根拠に「同一／別／判断できない」を判断。**同一にできるのは、両方の名称が併記された原文が検索結果に実在するときだけ**（捏造した引用・片方だけの引用は根拠にならない）。独立した2つ以上のドメインで併記＝別名学習の根拠。1つだけのときは、読み・音が近い系列名に限り「読みの近さ＋併記の原文」を根拠にする（`reading_with_source`）。音が離れた名称は1つだけでは関連候補止まり。独立管理の系列・商品の型番/数字/版/BOX・パックの食い違いは、AIが同一と言っても同一にしない
- 別名学習（`learning.ts`・`alias-service.ts`）: 根拠が足りなければ関連候補として保持／**AI推定の別名は一覧から取り消せる**（`/settings/reevaluation`）。取り消した名称・マスターの組は却下として記録し、同じ根拠で再学習しない。人が確定した別名・正式名・表示略称は変更しない
- 通常収集への反映: `resolveName` は `saveLottery`（手動・自動収集・自律型AI）の共通入口なので、読み・正式優先は全経路に効く。**AIによる名称判定は再調査の経路のみ（通常収集の中では未接続）**

## 2. 本番用AI一括再調査
- 関門 `reeval-ai-hook.ts`: 開発（`TOREMANE_ENV=local`）または本番で **`REEVAL_AI=on`**（自律型収集の許可 `AUTONOMOUS_COLLECTION` とは別）のときだけ動く。無効なら DB にもAIの部品にも触れない。AIの部品は関門のあとに動的に読み込む（`production-disabled` と同じ作り）
- 費用: 利用者が**累計の上限（6〜100円。環境の `REEVAL_AI_MAX_JPY` が最大）**を指定。通常収集の予算（日額100円・月額1,500円・1件15円）とは**別枠**で、バッチに積み上げる。残り6円未満は開始しない。上限・権限はAIが変更できない。キーは `REEVAL_ANTHROPIC_API_KEY` → `AUTONOMOUS_ANTHROPIC_API_KEY` → `ANTHROPIC_API_KEY`（既存の契約）
- 実行: 画面（`/settings/reevaluation`）で「見積もり→上限を指定→5件調べる（続きから再開）」。1回は200秒で区切る（`maxDuration=300`）。実行中の印で二重実行を防ぎ、調査済みの項目は再調査しない。通常収集の実行中は**適用**しない（調査は読み取り＋別名・店舗所在地の蓄積のみ）
- 対象: **全抽選＋抽選候補**。日付の補完・期限切れ・地域外・名称（マスター候補・候補の系列名）・店舗別カードの統合。抽選候補は下書き（系列・店舗・商品・締切・情報源）を入力にして、期限切れ・地域外をAIが確認（確認できなければ未適用のまま）
- 結果: 変更前後・根拠・費用を項目ごとに画面で確認（「AIの調査結果」）。適用は**AI確認済みのみ**・区分ごと・25件ずつ。**元に戻す**はバッチ全体
- 見積もり（1単位の実測 3〜8円。`UNIT_COST_JPY`）。本番の書き出し（2026-11-18）での未調査は 日付24・期限切れ39・地域外12・候補22・名称ほか。**全件の実行は概算250〜600円**（取得できない情報源が多いと調査済みにならず費用だけが出る）。最初は100円まで

## 3. 応募構造（抽選形態）と店舗別カードの統合
- 判定: AIが情報源（調査エンジン）から店舗選択式／店舗別独立／その他を判断（`assessForm`。LivePocketなどは本文の構造解析）。**正解・系列の傾向は渡さない**。食い違い・記載なしは不明のまま
- 統合の候補（計画）: 同じ系列・同じ商品で、**同じ情報源URL**、または**短縮URL（t.co等）だけ・URLなしで締切が日時まで一致**する店舗別カード（2店舗以上）
- 適用（`consolidate_lotteries`。AIが店舗選択式と確認したものだけ）: 統合先を**店舗選択式の1件**（`selectable_stores`＝統合した店舗）に変え、統合元は非表示（物理削除しない）。**対応関係は `lottery_exclusions.duplicate_of_lottery_id`**、変更前の状態は項目の `before_state` に記録。元に戻せる（統合先は店舗固定へ、統合元は表示へ。その後に利用者が変えたものには触れない）
- 保護: ★・応募/当落/購入の記録・確認済み・人が登録/確認・通知/ルール/メモの参照あり・利用者が手動で設定した抽選形態は、統合先にも統合元にもしない。店舗別独立と確認されたもの・取得できなかったものは適用しない

## 4. 店舗所在地
9H-3S-2 の仕組み（公式の店舗一覧に住所があるときだけ確認済み→店舗マスターへ蓄積、不明は不明のまま）を、抽選候補にも適用。収集中のWeb調査は未接続（蓄積済みの所在地は以後の収集の地域判定に効く）

### 従来方式（9H-3S）との差
- 候補の発見: 店舗別カードの統合候補（従来0→1組）、音の近い系列（従来検出なし）
- 判断: 従来の固定ロジックは名称・日付・地域を「暫定」で出すだけ。AI確認済みで適用できたと言えるのは、地域外1店舗（二子玉川）と日付補完1件（いずれも検証用で本番には未適用）
- **実データでの改善は小さい**: 取得できない情報源（X・t.co・一部サイト）が多く、情報自体が無いものも多い。応募構造の判定（ふるいち×ハドウシーカー）は確認できなかった
