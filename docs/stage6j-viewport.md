# iPhone 下部メニューの不具合：なぜ過去の対応で直らなかったか／現在の構造

**iPhone 実機（ホーム画面のPWA）では未確認。** 下の「事実」はコード・履歴・自動テストで確かめたこと、「推定」は実機で確かめる必要があること。実機で直った、とはまだ言えない。

## 1. 不具合（再発している症状）
起動時に下部メニューが一部隠れる／キーボード開閉後に位置がずれる／画面下端のオーバースクロールで位置がずれる／バックグラウンド復帰時にも発生しうる。

## 2. 過去の対応と、なぜ直らなかったか（履歴の調査）
| 時期 | 対応 | その後に起きたこと |
|---|---|---|
| 5D/5E〜 | 診断モード（`?diag=1`）で実機の値を取得 | 実機: `innerHeight=793 / 100vh=852 / safe-top=59`。起動直後は表示領域が上のSafe Area分だけ低く、操作すると直る |
| c5c2910 | `--vp-gap = 100vh − innerHeight` を**起動・復帰・最初のtouchstartの瞬間に1回だけ**測り、`position:fixed` の下部メニューの `bottom` を `−gap` に | 表示領域は**イベントなしで後から直る**。直ったあとも補正値だけが残り、メニューの下側59pxが画面の外へ出る（＝一部が隠れる） |
| c541432 | 起動・復帰・操作の後4秒はフレームごとに測り直す／キーボード分のシート位置（`--kb-inset`） | 4秒を過ぎてから表示領域が変わると、また補正が残る |
| 5P (ae8e7d3) | `--vv-shift`（見えている下端とレイアウト上の下端の差）で固定要素を実際の見える下端に合わせる | 最下部・最上部のゴム紐バウンスでも `visualViewport.offsetTop` が動くため、**バウンスの分だけメニューが浮く** |
| 5Q / 5V | 過剰補正の防止（`stabilizeShift`: 指が触れている間は更新しない／同じ値が10フレーム続いたときだけ採用）、`touchend` の取りこぼし対策 | 0.5秒ごとのポーリング（`setInterval`）が常時動く構造になった。補正の判定自体が複雑になり、タイミング次第で補正が残る／効きすぎる |

### 根本原因（事実に基づく分析）
過去の対応はすべて、**`position: fixed; bottom: 0` の下部メニューを、測定値（`innerHeight` / `100vh` / `visualViewport`）で動かして表示領域に合わせる**という同じ構造の上に、条件を足していったものだった。
- iOSのホーム画面アプリでは、起動直後・復帰・キーボード開閉・バウンスのたびに、`innerHeight`・`100vh`・`visualViewport` が**互いに食い違う一時的な値**を取る（実機の診断で確認）。しかも値の変化は**イベントを伴わないことがある**。
- 「測る→補正する」は、常に動く標的を追う形になる。補正が**残る**（下が隠れる）か、**効きすぎる**（浮く）のどちらかになり、一方を直すと他方が出た（上の表の「その後に起きたこと」）。
- さらに、ページ全体（ドキュメント）がスクロールする構造のため、バウンスやキーボードの出入りで**ドキュメントのスクロール位置・visualViewport が動き**、`position: fixed` の要素が基準にする「レイアウト上の表示領域」と「実際に見える領域」がずれる余地が残っていた。

つまり、補正値の調整では直らず、**測定に依存する構造そのもの**が原因だった（と推定される）。タイマー（4秒のフレーム測定・0.5秒のポーリング）による一時補正を重ねたことも、状態を複雑にした。

## 3. 現在の構造（Stage 6J）
測定・補正をやめ、**レイアウトの構造**で下部メニューの位置を決める。

```
<div class="fixed inset-0 flex flex-col">         ← 画面全体を固定の入れ物にする（上下左右を表示領域に固定）
  <header class="shrink-0">…</header>              ← 動かない
  <main id="app-scroll" class="flex-1 overflow-y-auto overscroll-y-contain">…</main>   ← スクロールするのはここだけ
  <nav class="shrink-0 …">…</nav>                  ← 入れ物の最下段（固定配置ではない）
</div>
```
- ページ全体（`window` / `document`）はスクロールしない。スクロール領域は `main` の中だけ。ゴム紐のバウンスも `main` の中の動きで、ヘッダーと下部メニューには伝わらない（`overscroll-behavior-y: contain`）。
- 下部メニューは固定配置ではなく入れ物の最下段。入れ物は表示領域に固定されるので、メニューは**測定なしで常に表示領域の下端に接する**。`--vp-gap`・`--vv-shift` と、4秒の測り直し・0.5秒のポーリング・`stabilizeShift` による運用は、メニューについては不要になったので外した。
- `--kb-inset`（キーボードが隠す高さ。ボトムシート・登録フォームの位置用）は残したが、**イベント駆動のみ**（`visualViewport` の resize/scroll、フォーカスの出入り。キーボードの出入りの約0.6秒だけフレーム追従して止まる）。常時のタイマーは無い。
- 起動直後に表示領域が一時的に低くても、入れ物は**その時点の表示領域に合わせて伸縮**し、メニューも一緒に動く（補正値が残らない）。メニュー背景は下へ延長してあり、表示領域が画面より低い間も下に空白は出ない。
- スクロール領域が `main` に移ったことに伴う変更: ページを移ったら `main` を先頭へ戻す／カードの詳細を閉じたときのスクロール位置の復元は `main` の位置を使う／`sticky` の上端オフセットは `main` 内で `0`（`--header-h` を `main` の中だけ `0px` にした）。

## 4. 確認できたこと／できていないこと
- 自動テスト（モバイル幅 320/375/390/430px、Chromium）: 下部メニューが表示領域の下端に接する／ページ全体がスクロールしない／スクロール領域を動かしてもメニューの位置が変わらない／最後のカードがメニューに隠れない／`window` の高さを変えて（表示領域の変化を模擬）もメニューが下端に接し続ける。
- **未確認（実機が必要）**: iPhone のホーム画面アプリでの、起動直後・キーボード開閉後・画面下端のオーバースクロール・バックグラウンド復帰。直った、とは判断しない。実機で問題が続く場合は、診断（設定 → 診断、または `?diag=1`）の値を共有してほしい。
- 副作用の可能性: ステータスバーのタップで先頭へ戻る動作は、`main` がスクロール領域になったため効かない可能性がある。ブラウザの「戻る」でのスクロール位置の自動復元も効かない（ページを移ると先頭から）。

## 5. Stage 6K での修正（6J の構造の欠陥）
6J の `fixed inset-0` は、起動直後の iOS ホーム画面アプリでは「レイアウト上の表示領域（innerHeight/dvh=793）」で止まり、画面（100vh=852）の下に約59pxの空白が出た。standalone のときだけ入れ物の高さを `100lvh`（画面全体）にする CSS に変更（`.app-root`、測定・タイマーなし）。詳細・計測・未確認事項は [stage6k.md](stage6k.md) §1。
