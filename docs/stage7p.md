# Stage 7P: 抽選情報の重複解消・キーボード後のタップ判定ズレ

## 1. 抽選情報の重複登録

### 根本原因（実データで確認）
有効な抽選 114 件のうち、系列・店舗・商品が同じ組が 10 組あった。重複の大半は **店舗が未確定（store_id なし）の自動登録**。

1. **店舗が未確定だと重複判定そのものを行わなかった**（`findDuplicates` が「店舗IDなし かつ オンラインでない」なら即 `[]` を返す）。
   ヤマダデンキ（ストームエメラルダ）・GEO（ハドウシーカー＋30th）・ホビーステーション・ドラゴンスターは、いずれも「受取店舗が確定していません」の注意つきで自動登録された抽選で、同じ告知が別の投稿・別のアカウント経由で再収集されるたびに新しいカードが作られた。
2. 判定が「同じ情報源URL」「同じ締切日」「どちらかの締切が不明」に限られ、応募期間・URLが違うと同一の抽選でも登録された（Luruna Card など）。
3. 重複判定は収集開始時のスナップショットに基づく。ヤマダ（06:20 に 2 件）・GEO（18:25 に 2 件）は同じ分に登録されており、**並行処理（同時に動く収集）でも二重登録され得た**。DB側の防止がなかった。
4. 複数商品の抽選は「商品が 1 つでも共通」だけで同一判定されていた（誤統合の危険）。

### 判定ルールの変更（`src/lib/lottery-match.ts` の `findDuplicates`。自動収集・確認待ちの再評価・手動登録・一括登録で共通）
| 条件 | 判定 |
|---|---|
| 同じ情報源URL（同じX投稿ID・フォーム・URL） | high |
| 系列・店舗・商品構成が同じ（応募期間・URLが違っても） | high（開催回を判断できない場合は重複を優先） |
| 明確に別の開催回（応募期間が重ならない／既存の締切が過ぎていて新しい締切がそれより後） | 登録を許可 |
| 商品の一部だけが共通（商品構成が違う） | 同じ締切日・不明なら medium（確認待ち）、締切が違えば対象外 |
| 双方とも店舗が未確定（応募時に店舗選択を含む）で、商品構成・締切が同じ | medium（確認待ち。別店舗の告知の可能性があるため自動統合しない） |
| 店舗が確定していて別の店舗（店舗別抽選。ドラゴンスターなど） | 別カードのまま |
| 未登録の商品（ID なし）を含む | 商品構成が同じとは見なさない |

- medium は `decideRegistration` で確認待ち（C）になるため、新規カードは作られない。
- 系列名の表記ゆれは `chainKey`（通販・オンライン等の語を除いた名称）と系列ID で照合。

### 並行処理の防止（DB）
- `supabase/migrations/20261205000091_stage7p.sql`（追加のみ）: `lotteries.auto_dedupe_key` と部分ユニーク索引 `lotteries_auto_dedupe_key_uq (household_id, auto_dedupe_key) where auto_dedupe_key is not null and archived_at is null`。
- キーは `autoDedupeKey()`（系列｜店舗｜商品構成｜応募締切日）。自動登録の直後に設定し、並行して同じ抽選を登録した側は 23505 で弾かれ、その抽選をアーカイブして既存の抽選へ統合（情報源URLを追記、候補は「重複」）。収集（`run.ts`）・再評価（`reevaluate.ts`）の両方に適用。
- 手動登録・既存の抽選（キーなし）は対象外。

### 既存の重複データの整理（`scripts/dedupe-lotteries-7p.mjs`）
- 調査のみ（既定）／`--execute`（バックアップ取得後に実行）／`--restore <ファイル>`。物理削除はしない（アーカイブ）。
- 自動整理の条件: 系列同じ・商品構成が集合として同じ・締切日が同じ・店舗が同じ（または双方オンライン）。店舗が双方とも未確定のときは、さらに「締切時刻が同じ」かつ「情報源/応募URLが共通、または同じ収集回（作成が10分以内）」。
- 残す側の選定: 手動登録・手動修正・情報量で採点。消す側に応募記録・★・手動登録・手動修正・通知・メモなどがあれば統合せず「要判断」。
- 調査用: `scripts/investigate-duplicates.mjs`（読み取り専用）。

### 実施結果（本番）
- 実行前に `npm run backup`、整理時のバックアップは `backups/dedupe-7p-2026-11-10T23-57-00-194Z.json`（復元可）。
- 整理: 5 組・抽選 5 件をアーカイブ、情報源URLを残す側へ統合、収集候補 12 件を「重複」へ付け替え（応募記録を持つ抽選は対象外。アーカイブした 5 件に応募記録は 0 件）。
- 有効な抽選 114 → 109 件。

## 2. キーボード開閉後のタップ判定ズレ

### 原因（調査結果・仮説。実機での最終確認は未実施）
- iOS はキーボードを出すとき、入力欄が隠れないようにページ（レイアウトビューポート）を押し上げる（`window.scrollY` / `visualViewport.offsetTop` が 0 でなくなる）。
- 閉じるときに押し上げが元へ戻らないことがあり、残ると **描画位置とタップ判定の位置が食い違う**。
- このアプリは画面全体が固定の入れ物（`.app-root`）でスクロールするのは内側の `#app-scroll` だけ。ページ自体は動かせないため、**スクロールでは直らず**、再びキーボードを開閉すると iOS が位置を再計算して直る（報告された症状と一致）。同じ構造の別アプリでも起こる。
- 既存の `--kb-inset`（ボトムシートをキーボードの上へ上げる）は、閉じたあとの 0.6 秒だけ追従する設計で、ページの押し上げ自体は戻していなかった。

### 修正（共通。`src/lib/use-keyboard-inset.ts`・`src/lib/viewport-insets.ts`。AppShell が呼ぶため全画面・全モーダルに適用）
- 入力中でないのにページが 0 からずれているとき（`needsViewportReset`）だけ、`window.scrollTo(0, 0)` でページの位置を戻す。確認のタイミング: `focusout` の 150 / 450 / 900ms 後、`visualViewport` の resize / scroll。
- 入力中の判定は「入力欄にフォーカス **かつ** キーボードが実際に出ている」。フォーカスが残ったままキーボードだけ閉じた（スワイプ）場合も戻す。入力欄から別の入力欄へ移るだけのときは戻さない。ピンチ拡大中は触らない。
- アプリ内スクロール位置（`#app-scroll`）・入力内容・ダイアログの開閉状態は変えない。再描画・再読み込み・強制レイアウトはしない。
- `AppShell` の固定レイアウト・Safe Area は変更なし（フックの切り出しのみ）。

### テスト
- `src/lib/keyboard-viewport.test.tsx`（10 件）: 判定の純粋関数と、`visualViewport` を模擬した開閉の再現（押し上げが残る／iOS が自分で戻す／入力欄間の移動／スワイプで閉じる／5 回の繰り返し／アンマウント後に残らない）。
- 実機の WebKit のキーボードは自動テストで再現できないため、挙動の最終確認は実機（下記）。

### iPhone 実機での確認方法
1. ホーム画面アプリ（PWA）と Safari の両方で、対戦記録 → 「対戦を記録」を開く。
2. 入力欄をタップ → キーボード表示 → 完了／外側タップで閉じる。これを 10 回以上、入力欄を替えながら繰り返す。
3. 閉じた直後に、画面下部のボタン・カード・下部メニューをタップして、表示位置どおりに反応するか。
4. 画面を少しスクロールした状態・ダイアログ内（抽選登録/編集・購入記録・収支登録・設定）でも同じ操作を行う。
5. 症状が出た場合は、Mac に接続した Safari の Web インスペクタで `visualViewport.offsetTop` と `scrollY` が 0 でないかを記録する。
