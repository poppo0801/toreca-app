# 開発ログ（重要な決定・不具合の原因と再発防止）

作業ログではなく、**将来の開発判断に役立つ情報**だけを残す。新しい記録は各節の先頭に追加する。

## 記録するもの／しないもの
- 記録する: 重要な設計判断／UI/UX 原則の変更／不具合の原因と再発防止策／AI の判断方式の変更／DB 構造の重要な変更／従来方式から変えた理由／未解決の矛盾・リスク。
- 記録しない: 軽微な修正、日々の作業内容（それは Git 履歴と `docs/stage*.md`）。
- 書き方: 日付・内容・理由・根拠（コミット/文書）。**確認できていないことは「未確認」と書き、推測で確定しない**。実機（iPhone）で確認していないことは明記する。
- 初期データ（下記の2026-10-26〜11-11分）は、2026-11-11 に Git 履歴（192コミット）と各 Stage の文書から確認できた事項を整理したもの。理由が文書に無いものは「理由未確認」とした。

| 2026-11-12 | **実API評価で見つかった検証層の汎用的な不具合（8D-3）**: 実在店舗5件の実API評価で、AIが正しい住所を見つけても検証層が不採用にする偽陰性が続いた（住所の地名＝店舗名の語、営業時間表示の「営業終了」、引用が「…」でつながれる、運営法人名が系列名と違う、引用が住所の後半だけ、最終提出の形式不正）。**原因は多くが検証・採点側。AIの誤りではなかった。** 汎用的に修正（特定店舗の例外なし）し、実ページ（保存済み）で回帰テスト。実API再検証で R1〜R3・R5 は確認済み、R4 は候補。誤住所・誤公式は0。**正解データも誤っていた**（R5を「別店舗」と想定）→ 取得し直して `revision` つきで修正。再発防止: 評価の不採用は、まず検証・採点・正解の側を疑う／不採用の候補と閉店ヒントを記録する／結果を見て正解を直したら成功率を割り引いて報告する（詳細 `docs/stage8d3.md` §7・§10）。 |
