# 開発ログ（重要な決定・不具合の原因と再発防止）

## 記録するもの／しないもの
- 記録する: 重要な設計判断／UI/UX 原則の変更／不具合の原因と再発防止策／AI の判断方式の変更／DB 構造の重要な変更／従来方式から変えた理由／未解決の矛盾・リスク。
- 記録しない: 軽微な修正、日々の作業内容（それは Git 履歴と `docs/stage*.md`）。
- 書き方: 日付・内容・理由・根拠（コミット/文書）。**確認できていないことは「未確認」と書き、推測で確定しない**。実機（iPhone）で確認していないことは明記する。
- 初期データ（下記の2026-10-26〜11-11分）は、2026-11-11 に Git 履歴（192コミット）と各 Stage の文書から確認できた事項を整理したもの。理由が文書に無いものは「理由未確認」とした。

## 6. DB 構造の重要な変更（マイグレーション94本。主なもの）
- Stage 1: 世帯・プロフィール・マスター・監査・RLS（複合 FK `(id, household_id)`）。Stage 2〜3: 抽選・応募・購入・スルー規則・応募制限。Stage 3.5: 複数商品・仮登録マスター。
- 5T: AI 予算の予約（`reserve_ai_budget`）。5T-3・7R: 系列の区分（直営/その他）・カードボックスの2系列。
- 7P〜7Q: 重複登録の DB ガード（`auto_dedupe_key` ほか）、情報元の保存。
- 7S（`20261211000093`）: `store_reference_counts`・`delete_store`・`merge_store_masters`。住所変更でトリガー `stores_geo_reset` が座標をリセットする（座標を同時に更新すれば維持）。
- 注意: `service_role` から使えない RPC・テーブルがある（`_repoint_store`、`member_numbers`、`chain_conditions`）。整理は SQL（postgres）で行う。

## 7. 従来方式から変えた理由（まとめ）
- 測定補正 → 構造で解決（下部メニュー）。日次 AI 上限 → 月額予算の予約。ページ再描画（`revalidatePath`）→ 構造共有と楽観的更新（★のみ）。JSON バックアップ → SQL ダンプ＋全 Storage の完全バックアップ。個別の重複判定 → `findDuplicates` に集約。店舗名の表記ゆれ → 正規化に集約。
