# Stage 7D: iPhoneアプリ切替エラーの再調査・自動フォーカスの全面廃止

DB変更なし。

## 1. iPhone復帰時エラーの再調査

### 症状の整理
「https://toreca-app.vercel.app/settings/masters で問題が繰り返し起きました」＋Safariの表示が黒くなる、は **Safari（WebKit）自身のメッセージ**で、Webコンテンツプロセスが終了（クラッシュ・メモリ超過・ウォッチドッグ）し、自動で再読み込みしても繰り返し終了したときに出る。アプリのJavaScriptのエラー（Stage 7Cのエラー境界・自動復旧の対象）ではなく、**JavaScriptでは捕まえられない**。Stage 7Cが効かなかったのはこのため。

### 調べたこと（実測）
計測: `e2e/perf-resume.supabase.spec.ts`（実Supabase・マスターを本番規模=系列60・店舗120・商品55にして、Chromiumの `Performance.getMetrics` で JSヒープ・DOMノード・イベントリスナー数を測定。復帰を10回繰り返して増加を確認）。

| 画面 | JSヒープ | DOMノード | リスナー |
|---|---|---|---|
| 抽選一覧 | 6.4MB | 302 | 358 |
| コレクション | 6.2MB | 432 | 361 |
| 設定 | 6.0MB | 349 | 361 |
| マスター管理（Stage 7C時点） | 8.5MB | 2,241 | 726 |
| **マスター管理（7D: 40件ずつ描画）** | **7.8MB** | **1,587（-29%）** | **611（-16%）** |
| 収支 | 6.0MB | 260 | 354 |

- **JSのメモリは原因として小さい**: 最大でも約8MB。復帰を10回繰り返してもノード数・リスナー数は増えない（リーク・リスナー重複なし）。ヒープの増減は+1〜2MBで、再取得したデータの置き換え。
- **データ量も小さい**: /settings/masters が一度に取得するマスターは合計約264KB（系列35KB・店舗99KB・商品38KB・名義アカウント80KB 他）。画像は系列ロゴ46枚（192×192px・計1.1MB、展開後約7MB）・商品サムネイル38枚（最大419×288px・計1.1MB、展開後約12MB）で、いずれも軽量。重い画像・大量データの一括読み込みは見つからなかった。
- **復帰処理の過剰さ**: 復帰ごとにアプリ全体のデータを1回再取得していた（設定画面でも）。取得の嵐・無限ループはない（復帰1回につき取得1回）。バックグラウンド中も1分ごとの再描画タイマーが動いていた。
- 重い描画効果（`backdrop-filter`・`filter` 等）はマスター管理には無い（コレクションの光沢効果のみ）。Service Workerはキャッシュせず、原因ではない。

### 結論（未特定）
**原因は特定できていない。** 計測できた範囲（JSヒープ・DOM・リスナー・データ量・画像サイズ・取得回数）には、WebKitのプロセスを終了させる材料は見つからなかった。メモリ不足とは断定しない。iOSのジェットサム（メモリ上限）・GPU/描画メモリ・WebKitの不具合・特定のデータの組み合わせなどは、Chromiumでの計測では再現・排除できない。**今回の修正で解消したとは言えない。**

### 実施した改善（原因の解消ではなく、負荷の低減と、次回に原因を特定できる手がかり）
- **マスター管理を40件ずつ描画**（`masters-view.tsx`）: DOM・イベントリスナー・画像の数を削減（上表）。種類・検索・絞り込みを変えると先頭に戻る。
- **設定画面では復帰時に全データを取り直さない**（`resilience-watcher.tsx`）: 設定・マスター管理は開くたびに自分のデータを取得するため。計測で、設定画面での復帰10回のデータ取得が10回→0回。
- **バックグラウンド中は「いま」のタイマーで再描画しない**（`app-provider.tsx`）: 戻ったときに1回だけ更新。
- **画面の終了の検出**（`lifecycle.ts`・`client-resilience.ts`）: WebKitのプロセス終了はJSで捕まえられないため、**次の起動時**に前回の終わり方を判定して記録する。端末に「表示中／バックグラウンド／閉じた」と最後の画面を残し、`pagehide` なしに表示中のまま終わっていたら「表示中に終了した可能性」（=クラッシュ・メモリ超過の疑い）、バックグラウンドのまま戻らなければ「バックグラウンドで破棄」（=iOSの通常のメモリ回収）として記録（設定 > 表示設定の「接続の記録」と、Vercelの実行ログ）。次に症状が出たあと、この記録で「どの画面で・表示中に落ちたか」を確認できる。
- 自動の全画面再起動は追加していない（プロセスが終了した場合JSでは復旧できないため）。

### iPhone実機で確認が必要なこと
1. 症状が出た直後に、設定 > 表示設定 > **接続の記録** を開く。「表示中に終了した可能性」か「バックグラウンドで破棄」か、画面（/settings/masters など）を確認する（どちらも出なければ、記録の保存前に落ちている）。
2. Mac の Safari > 開発 > [iPhone] > トレマネ（Web Inspector）に接続し、/settings/masters を開いて **タイムライン > メモリ**・**レイヤー**（描画メモリ）・**ストレージ**を確認。別アプリへ切り替えて戻す操作を繰り返し、メモリの増え方を見る。iPhoneの設定 > プライバシーとセキュリティ > 解析と改善 > 解析データ に `JetsamEvent` ログがあれば、トレマネの Web Content プロセスがメモリ上限で終了させられたか確認できる。
3. 特定の画面だけで起きるか（/settings/masters 以外でも起きるか）、ホーム画面アプリとSafariのどちらでも起きるか、低電力モード・他の重いアプリの使用中か。

## 2. 自動フォーカス・自動選択の全面廃止

### 原因
コードに `.focus()` や `showPicker()` の呼び出しは無く、`autoFocus` は2か所（コレクション・BOXの検索欄）だけだった。ダイアログを開いたときに最初の入力欄へフォーカスが入っていた主因は、**Radix UI の Dialog が開いたとき最初のフォーカス可能な要素へ自動でフォーカスする既定動作**（全ダイアログ・シートに共通）。

### 修正
- `components/ui/initial-focus.ts`（`usePanelFocus`）を `DialogContent` と `SheetContent` に適用: 開いたとき入力欄・セレクト・テキストエリアへフォーカスせず、**パネル自身（コンテナ）へフォーカスを移す**。フォーカストラップ・Escで閉じる・タイトルの読み上げは維持。閉じたときは、開く前にフォーカスがあった操作ボタンへ戻す（制御型で Trigger を持たないダイアログでも。直前が入力欄なら戻さない）。全画面のダイアログ・シート（抽選登録、マスター編集、系列/商品の統合・削除、支出登録、各種設定ほか）が対象で、個別の修正は不要。
- 検索欄の `autoFocus` を削除（コレクション・BOX）。検索アイコンをタップしても欄へは入らず、欄をタップして入力する。
- 残している `onFocus` の全選択（数量入力）は、利用者が欄をタップしたときだけ働く。クリップボードコピー用の一時要素の `select()` は画面の入力ではない。
- 例外なし。

## 3. キーボード表示時のレイアウト
- 中央のダイアログ（`DialogContent`）の位置と最大高さを、キーボードを除いた表示領域（AppShell が visualViewport から更新する `--kb-inset`）基準にした。入力欄・確定/キャンセルがキーボードに隠れず、本文は内部でスクロールできる（`overscroll-contain`）。個別ダイアログが持っていた固定の `max-h-[90dvh]` は削除。
- ボトムシートは既存の `--kb-inset` 対応のまま。
- 既存デザインの全面変更はしていない（入力項目の多いダイアログのシート化は不要と判断）。
