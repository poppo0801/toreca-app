# Stage 9H-3H: LivePocket解析の調査への接続・肯定否定の双方向学習・系列傾向の判断

開発環境のみ（`COLLECT_UNIFIED=on` かつ `TOREMANE_ENV=local`）。マイグレーションなし。**有料API・実AIは未使用（費用 0円）**。本番へは接続していない。無効時の収集は従来と同一。

## 1. LivePocketの調査への接続（`agent/case-investigator/tools.ts`）
- 調査エージェントが**取得した**LivePocketページの本文を、その場で構造解析（`analyzeLivePocket`）する。**追加の取得・検索は行わない**（取得済みの本文だけを使う。回数の上限は従来のまま）。応募操作・ログインはしない。
- 解析結果（A 店舗選択式／B 店舗別独立／C 不明／食い違い）は、(1) AIへのツール結果に「参考」として付く、(2) **調査の終了時**に、**同じ抽選と確認できたページ**（identity=same）の構造が台帳の「抽選形態」「選べる店舗」の根拠になる（AIの報告より後に足すので、AIが根拠の原文つきで報告した値が優先される）。
  - AIが抽選形態を報告しなかった → 構造から補う。AIの報告と食い違う → **両方を残す**（別の値として保持。黙って片方を捨てない）。台帳の既存規則で、主催者を確認できた本文（一次）が優先される。
  - C・食い違いは**反映しない**（不明のまま保持）。別の抽選のページの構造は反映しない。複数のLivePocketページは、ページごとに同一抽選かを判定して区別する。
- 根拠の抜粋（`quote`）はページ本文の実在する部分。判断履歴（`to-case.ts`）に、反映した／しなかった理由を残す。結果は `CaseInvestigationResult.livepocket`。
- 調査の指示文に、A/B/Cの区別・確認項目・「傾向だけで店舗選択式と報告しない」を追加（9H-3G）。

## 2. 双方向学習のデータ構造（`case-model/form-learning.ts`）
`FormRecord { key, chain, form(store_select|store_independent|online_only|undetermined), platform?, caseIds[], setId, evaluatedAt, corrected?{from, wasEstimate}, status(active|invalidated) }` と、履歴 `FormLedgerEvent { action(added|updated|invalidated|ignored), key, reason }`。`HumanKnowledge.forms` に保持。
- 採用する実績: 評価ツールの**抽選形態欄**の訂正（店舗選択式／店舗別独立／通販のみ／判断不能）、店舗欄の同様の訂正（従来の評価も読める）、「不明なだけ」＝判断不能、**表示した候補の形態を「正しい」とした項目**（候補に形態が明示されているときだけ）。
- **採用しない**: AIの出力・推定そのもの（人間が確定していなければ記録しない）、未評価・判断できない・`usableAsGold=false`、抽選形態の確定がない評価（推測で補わない）。
- 重複・更新: 同じ抽選（系列・商品・締切日・店舗。足りなければ事例ID）は**1実績**。別の評価セット・転載・別の事例IDでも統合し、**新しい評価で更新**（古い評価を二重計上しない。読む順序に依らない）。
- 無効化: `backups/review-answers/` の `invalidate` を持つJSON（`{"invalidate":[{"caseId"|"key", "reason"}]}`）で個別に取り消す。取り消した実績は傾向に使わない。追加・更新・無効化・無視は履歴に残る。
- 評価ツール（`tools/review`）: 抽選形態欄の入力候補（店舗選択式／店舗別独立／通販のみ／判断不能）を追加。店舗選択式と店舗別独立の両方を明示的に訂正できる。
- 保存済みの評価JSON（9F〜9H-3F）から作られた実績: 16件（店舗選択式 13・通販のみ 3）。**否定（店舗別独立）の実績は、既存の評価JSONに明示がなく0件**（推測で補っていない）。今後の評価で蓄積される。

## 3. 系列傾向の判断（`form-learning.ts` の `chainFormTendency`、`form-inference.ts`）
- 重み付き（応募方式が同じ=1・不明=0.7・違う=0.4。推定を訂正された実績は×1.5）の割合から、Wilson下限で評価。単純な多数決・固定の閾値だけではなく、件数・割合・応募方式で決める。
- 強さ: 実績1件は**弱い**。強い=下限≥0.55かつ実効件数≥3。評価に使う件数は**上限10**（実績が増えても無制限に強化されない。信頼度は推定では「高」にならない）。
- 例外: 店舗選択式が多く店舗別などの例外もある系列は「例外あり」（信頼度は低に下げ、強い傾向でなければ『提案』止まり）。割れている系列（半々）・店舗別独立に傾く系列は、**店舗選択式と推定しない（不明）**。
- 人間の実績が1件でもあれば、系列の傾向の辞書の実績は数えない（同じ評価から作られているため二重計上しない）。辞書だけのときは弱い補助。
- 推定は**今回の情報が無いときだけ**。今回の一次情報（構造の根拠・LivePocketの構造解析・AIの読み取り）が明確なら、傾向で上書きしない。参照した実績（キー）は trace に残る。

## 4. 実際の収集経路への接続
`server/collector/run.ts`: 系列名の解決 → （調査: 取得 → LivePocket構造解析 → 台帳 → 共通モデル）→ 既存の店舗選択式の判定 → 実績の傾向を参照した推定 → 登録候補（推定は確認が必要）。人間の評価の知識は `loadHumanKnowledge` が収集のたびに（ファイルの更新時刻が変われば再読み込み）読み、訂正が次回以降の判断に反映される。
結合テスト（`tests/stage9g3.integration.test.ts` 18件・実Supabase・有料AIなし）で、全段階が次へ渡ることを確認: LivePocket選択式の構造→調査（取得1回）→店舗選択式・選べる店舗→確認済み（推定でない）／実績があっても今回が店舗別独立なら今回を優先／実績が割れた系列は推定しない／実績だけの推定は『推定』と記録され確認が必要・AIの推定は再学習されない。

## 5. 安全対策
AIの推定を正解として蓄積しない／同一抽選の重複評価を1実績に／評価の訂正は更新・古い評価の無効化／件数の上限／判断根拠と参照実績の記録／低信頼の推定を確認済みにしない／推定だけで既存抽選の削除・統合をしない／手動確定の分類・項目は上書きしない（既存の保護を維持）／未評価・判断不能を数えない。

## 6. 未解決・次回の実AI検証
