# Stage 9H-3Q: 自律型AIの実システム統合・収集方式の切り替え

開発環境のみ。本番DB・本番環境・本番デプロイの変更なし。**新たな有料AI・検索の呼び出しなし**（実Web接続は部品の接続と、模擬の世界・モックAIでの検証まで。有料の実地確認は9H-3Rで少額予算を設定して行う）。復元点: タグ `pre-9h3q`（9H-3P のコミット `dff3f3c`）。

## 1. 既存実装の確認結果
- 自律探索エンジン（`src/lib/agent/discovery/`）は純粋なロジック。DB・実Webには未接続だった。
- 既存の登録経路: 収集（`runCollection`）→ 候補（`collection_candidates`）→ ワーカー解析 →（自動）登録。別系統として9Dの調査（`investigation-world.ts` の `analyze`＝URLの再解析＋重複照合＋安全条件 → `applyPreviews` → `saveLottery`）があり、これを**再利用**した。
- 定期実行: `/api/cron/collect`（Supabase Cron が数分おきに呼ぶ。1回約60秒以内）。設定は `collection_settings`（世帯に1行、`saveCollectionSettings` で保存、画面は `settings/collection`）。
- マイグレーション: ローカルDBは 099〜103 適用済み。**104 は今回新規作成**（指示文の「099〜104」のうち104が本ステージの新規分）。本番は 099〜 すべて未適用。

## 2. 実Webへの接続（安全制御は迂回しない）
`src/lib/server/agent/discovery-world.ts`（`createRealDiscoveryWorld`）:
- 取得: 既存の安全な取得（`SafePageFetcher` → SSRF対策・内部アドレス拒否・リダイレクト先の再検査・robots.txt・サイズ/時間・ログイン非回避）。さらに探索ツール側で、**起点・公式サイト・検索結果・取得済みページのリンクだけ**を取得対象にし、同一サイト4回・間隔・重複拒否・収穫逓減の打ち切りを適用（`discovery/controls.ts`、AIは変更不可）。
- 検索: 実検索（Anthropic web_search）は、費用の台帳（`RealRunGuard`）つきの部品を渡したときだけ検索ツールが登録される。
- 既存データの読み取り: 登録済みの抽選（出どころ＝従来の収集／手動登録／過去の自律探索、人間確認済みか）、店舗マスター、系列の公式サイト（店舗URLの最多サイト）。**既存の収集対象リスト・履歴だけに探索範囲を限定しない**（公式の店舗一覧から未知店舗を見つける）。
- 取得したページは世界の中に保持し、登録経路の再解析が同じ内容を使う（二重アクセスなし・AIが見た内容と同じ内容を解析）。
- 実AI・実検索の関門（`discovery-real.ts`）: 開発環境・`AGENT_REAL_API=allow`・開発専用キー・`COLLECT_AUTONOMOUS_CAP_JPY`（累計上限）・`COLLECT_AUTONOMOUS_CONFIRM=yes`。台帳に書き込めなければ開始しない。**関門が未設定なら、実行せず「開始できなかった」理由を調査履歴に記録する**（従来方式へは自動で切り替えない）。

## 3. 既存の抽選管理との統合（`discovery-service.ts` の `intakeRecord`）
AIの発見（`note_lead`）→ 固定の検証（根拠の原文の実在・重複・地域・店舗選択式）で `adopt` になったものだけを、次の順で既存の登録経路へ:
1. 取得済みページを既存の解析で**再解析**（`createInvestigationWorld().analyze`）
2. **AIの報告と照合**（`collector/intake-check.ts`）: 系列・店舗・商品・店舗選択式が一致しなければ登録しない（別店舗の告知・別の抽選の誤登録を防ぐ）。店舗を読み取れない場合は一致と見なさない
3. 既存の重複照合（既に同じ抽選があれば新規登録しない。AIの新規発見には数えない）
4. 既存の安全条件・自動登録（`applyPreviews`→`saveLottery`。注意付き。人間が編集した抽選は補完しない）
5. **根拠の保存**: `lottery_discovery_origins`（情報源URL・取得経路・原文の抜粋・経緯・要確認項目）。抽選カードの内容は変えない
- 系列共通情報と店舗固有情報は `fields.chainCommon`／`fields.storeSpecific` に分けて保持。店舗選択式は店舗ごとに展開しない。
- 地域: 対象地域の外と確定したものだけ除外。不明は除外せず要確認（根拠に残る）。
- 自動登録の設定（`auto_register`）がOFFなら、登録せず確認待ち（記録のみ）。

## 4. 収集方式の切り替え
- 設定: `collection_settings.collection_engine`（`legacy`｜`autonomous`、既定 `legacy`）。世帯ごとにDBへ保存され、PC・スマホで共有。設定画面（`settings/collection` の「⓪ 情報収集方式」）で選択・保存（`setCollectionEngineAction`）。変更は**次回の収集実行から**反映（実行中の処理は変更しない）。
- 解決（`collector/engine-setting.ts`）: 設定を実行ごとに読み直す。**読めない・不正な値 → 従来方式**（設定は書き換えない。理由を画面に表示）。自律型は開発環境（`TOREMANE_ENV=local`）のみで、本番は設定が `autonomous` でも従来方式。AIの一時的なエラーで設定を変更しない（失敗は調査履歴に残るだけ）。
- 定期実行（`/api/cron/collect`）: 方式が自律型の世帯は、従来の「収集元の取得（`runCollection`）」を自律探索に置き換える（ワーカー・位置情報など他の処理は共通）。1回の呼び出しでミッション1件、同じ時間枠で最大3回（`MAX_RUNS_PER_SLOT`）。従来方式の世帯の処理は変更なし。呼び出し口は `collector/autonomous-hook.ts`（本番では何もせず、探索のコードは本番で読み込まれない。`production-disabled.test.ts` の既存規約に合わせた）。
- 二重起動・二重登録の防止: ①世帯ごとの期限つきロック（`autonomous_lock_until`、5分で自動解放）②実行中の記録は世帯で1つ（部分一意索引）③従来方式の収集が実行中なら開始しない ④同じ枠で実行済みのミッションは繰り返さない ⑤登録は既存の重複照合を通る。
- 失敗の隔離: 例外・AIの障害・上限は調査履歴に記録し、応募・既存の抽選・方式の設定に影響しない。ロックは必ず解放。

## 5. データの共通管理
抽選・応募・当選・通知は共通のDB（従来と同じ表）。方式を切り替えても削除・初期化しない（テストで確認）。情報元の区別: `lotteries.source_kind`（auto/manual）＋`lottery_discovery_origins`（自律探索が登録した抽選）。既存ロジックが取得済みの抽選をAIが再発見しても、AIの新規発見に数えない（`credit: already_known`）。AIが先に登録したものを従来方式が後から取得しても、既存の重複照合で重複登録しない（従来方式側の変更なし）。

## 6. 調査履歴・探索実績の永続化
- `discovery_runs`: ミッション単位の実行記録（`DiscoveryRunRecord`＝調査対象と理由・情報源と取得経路・追加調査の経緯・手がかり（採用/保留/除外とその理由・既存との重複）・終了理由・時間・費用・未確認の対象）。件数（新規発見・登録・重複・除外・保留・既存が先に持っていたもの・照合の不一致）も保存。ページ全文・個人情報・認証情報は保存しない。
- `discovery_strategy`: `StrategyMemory`（系列ごとの新規発見数・既存と重複した数・新規なしの連続回数、情報源ごとの取得失敗・新規発見数）。次のミッションの参考情報として渡す（「未確認」は開催なしの意味ではない旨を明記。事実として確定しない）。
- 保持方針: 60日・最大300件を超えた記録を削除（実行中は残す）。保存する記録は切り詰める（原文300字・経緯160字、全体60,000字超は手がかり・経緯を間引く）。

## 7. 設定画面・運用状況
「⓪ 情報収集方式」: 方式の選択・保存、現在の方式、最終実行日時・結果（開始できなかった理由を含む）、新規発見（登録）件数、重複・除外件数、AI費用（直近）。開発環境のみ「自律型を今すぐ1回実行」。折りたたみの既存部品（`Block`）を使用。
