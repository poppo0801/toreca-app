状態: **評価の仕組みと安全制御は完成。評価データ（実在の抽選）が未確定のため、実API実行の承認待ちの前に「データの書き出しと正解の確認」が必要。** 実APIは一度も実行していない（費用 0 円）。本番DB・本番データは触っていない。

## 1. 評価の設計（8F の判定ロジックをそのまま使う）
- 判定: `evaluateGrouping`（8F）。AIが読み取り専用ツールで調べ、検証層（固定ロジック）が auto／suggest／hold／single を決める。この評価は判定ロジックを変えない。
- 評価単位: ケース＝「対象の抽選＋同じ系列の既存の抽選・グループ＋保存済みの情報源の文章」のスナップショット。AIは外部に接続しない（グループ判定は検索・取得の上限が0。追加調査は保存済みの情報源の文章を読み直すこと）。
- 入力は `eval/lottery-grouping-real/cases.json`、正解は `gold.json`（別ファイル）。正解は AI にも判定ロジックにも渡さない（テストで、AIとの会話に正解が現れないことを固定）。
- 結果の種類を混ぜない: `kind = real`（新規の実API）／`replay`（保存済みの提出を現在の検証層でやり直す。API・AIなし。**新規の精度評価ではない**）／`mock`（模擬）。ロジックを変えた後の再判定は replay として別に扱う。

## 2. 評価データ（実在の抽選）の作り方
**正解の根拠を、利用者自身の判断に限る**（AIの判定結果は使わない。独立した根拠）:

| 正解 | 根拠 | 由来 |
|---|---|---|
| auto（同じ企画としてまとめるのが正しい） | 利用者が手動でまとめたグループ（origin が manual／save_and_duplicate／duplicate） | 1件を対象にして残りを相手にする（3件以上なら「既存グループへの追加」） |
| none（まとめてはいけない） | 利用者が手動で外した・解除した記録（理由つき） | 分離の記録そのものは入力に入れない（AIの素の判断を測る） |
| unknown（正解不明） | 人が判断していない組・根拠が足りないもの | **別集計**（正解率の分母に入れない） |

- 書き出し（本番は読み取りのみ。利用者の端末）: `npm run prod -- scripts/export-grouping-eval.mjs --yes-production --out=eval/lottery-grouping-real --max=30`。抽選IDは連番に置換。住所・個人情報・鍵は含まない。情報源のURLと取得日時（収集時の記録）を各ケースに保存する。
- 分類（`CATEGORIES`）: 同一系列・同一商品・同一期間の複数店舗／応募期間が異なる／応募条件が異なる／複数商品／情報源が異なる（X投稿と公式サイト等）／既存グループへの追加／重複投稿・再収集／情報不足／手動で分けた組。書き出しは分類を自動で付ける。「重複投稿」「情報不足」は自動では作れないため、実データに該当が無ければ**不足として報告**する（作り物で埋めない）。
- Claude Code は本番を読めない（`.env.production-ops`）。そのため書き出しは利用者が実行する。公開情報（Web）から作る場合は、公式告知など一次情報で正解を確定し、`basis.kind=official_announcement` と URL・確認日を記録する。調査では、一部のまとめサイトが取得を拒否し（HTTP 403）、一次情報で正解を確定できる複数店舗の事例は短時間では揃わなかった。このため、**利用者の手動のグループ化を正解の主要な根拠**とした。
- 検査（`validateDataset`）: IDの対応・分類・情報源のURL/取得日時・根拠のない正解の拒否・入力に正解らしきキー（`label` など）が無いこと。
- 凍結: 正解を確定したら `npm run eval:grouping-real-freeze`。入力・正解のハッシュを `frozen.json` に保存し、実行時に照合する（凍結後に変えたら実行を拒否）。

## 3. 実API評価の安全制御（実装済み・テスト済み）
- 関門: 8D と同じ `checkRealApi`（開発環境・`AGENT_REAL_API=allow`・開発専用キー・本番キーと別・費用/回数の上限）。
- 費用: **合計 500 円・1ケース 15 円**。実行前に最悪ケース（実行数×15円）を計算して表示。実行中は「残りが1ケースの上限（15円）に満たなければ開始しない」ため、**最悪でも合計を超えない**。1ケースのAI実行には「15円と残りの小さい方」を費用上限として渡す（超えると実行基盤が停止）。
- 回数・時間・トークン: 既存の `GROUPING_LIMITS`（ステップ10・トークン12万・60秒）。追加調査は既定1回（同じ予算の中。同じ状況の繰り返しは打ち切り）。同じ情報の再検索は断る（8D-2 の重複拒否）。
- 停止: 連続2件で実行が完了しなかった（認証・通信障害）→ 即停止。エラーメッセージのキーらしき文字列は記録しない。
- 承認の範囲: `--approved-max-jpy=<円>`（500以下）・`--approved-runs=<回>`。計画の実行回数が承認回数を超えれば拒否。
- 記録: 1実行ごとに、提出（検証前）・最初の提出と最終・区分・信頼度・使用量（ステップ・トークン・推定費用・時間）・追加調査の回数。結果は `eval/runs/lottery-grouping-real/`（Git管理外）。キーは含まない。
- 手順: `npm run eval:grouping-real-preflight`（接続なし）→ 承認 → `npm run eval:grouping-real -- --approved-max-jpy=… --approved-runs=… [--repeats=N] [--followups=N]`。

## 4. 評価指標（`summarizeRuns`）
1. 正しいグループ化の割合／2. 誤グループ化の件数／3. 見逃し率（`proposal`: AIの提案そのもの。検証前）。
4. 自動確定・候補提示・保留・単独の割合（`gated`: 独立検証を通過した結果）。**誤った自動確定（autoHarm）は 0 であること**。
5. 追加調査による改善率（最初の提出を検証した区分 → 最終の区分）。
6. 1実行あたりの費用・時間・トークン。
7. 安定性（`--repeats=N` で同じ入力をN回再評価し、区分と組の構成が一致する割合）。
- 誤判定・見逃しの原因分類（`CAUSES`）: AIの情報理解不足／情報源の不足・矛盾／系列・店舗の識別／商品・期間の解釈／既存抽選との照合／検証が厳しすぎる／検証が緩すぎる。汎用的な改善のみ検討し、特定店舗の例外処理は作らない。評価途中でロジックを変えたら、変更前後を区別し、同じデータの再判定は replay として別に扱う。
- 注意: 正解 auto は「同じ企画としてまとめるのが正しい」の意味。検証層が候補止まり（suggest）にしたものは `autoToSuggest`（保守的で誤りではない）。
