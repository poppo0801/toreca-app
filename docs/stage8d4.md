## 4. 見つかった問題と汎用的な改善（特定店舗の例外はなし）
原因の多くは AI ではなく、検証・採点側だった。
1. **郵便番号つきの住所**（N07・N13・N15・N16）: 「〒561-0821 大阪府…」が「都道府県から始まらない」と判定され、地図の照合も外れた。→ `cleanAddress` で郵便番号を取り除いた住所を検証・保存する。
2. **「三重県」が常に不完全と判定される**（N15・N16）: 共有の `normalizeForMatch` が漢数字を変換し「三重県」が「3重県」になっていた。→ `isCompleteAddress` で都道府県名も同じ正規化をかけて比べる（`src/lib/geocode.ts`。店舗住所の座標取得にも使われる共有関数で、同じ潜在不具合の修正にもなる）。
3. **店舗一覧ページで、隣の店舗の「移転」を取り違える**（N13・N15・N16 ほか）: 引用の前後300字を見ていたため。→ 範囲を、その店舗の名前から次の店舗・次の住所の手前までに限定。自分の記載の「移転」は引き続き検出する（N11・N17 は安全側で候補のまま）。
4. **語順の違う店舗名**（N09「マルイ海老名」と「海老名マルイ」）: 文字種ごとの部分がすべて近くにあれば同じ店舗とみなす。別の店舗名は一致しない。
5. **登録済みの公式サイトが別ドメインへ転送**（N14: cardbox.nextone-iga.co.jp → cardbox.online）: 転送は公式サイト自身が行うので、転送先を公式（検証済み）とする。登録も転送もないドメインは公式にしない。
6. **採点**: 上記 ②。正解データは変更していない。
- 取り消した変更: 「独立した2つの情報源のうち1つは系列自身のサイトであること」への締め。U02・U08 のような第三者だけの一致を防げるが、既存のモックの正解（独立した2サイトの一致は確認済み）と衝突し、実害（誤住所の確定）も観測していないため、方針変更として未採用（§6）。
- 判定基準を緩めた変更はない。誤住所の確定は 0 のまま（初回の出力で、改訂採点の誤確認 0。修正後の再判定でも 0）。

## 5. 反映候補の承認フロー（開発環境のみ。本番には反映しない）
調査結果 → 反映候補 → 承認 → 開発DBの店舗マスター。**調査結果（ログ）と確定データ（店舗マスター）は分離**し、承認するまで店舗マスターは変わらない。
- **DB（マイグレーション `20261214000096`。開発DBのみ）**: `store_location_proposals`（候補。対象店舗・候補作成時の登録内容・取得した住所・情報源・公式性・信頼度・理由・既存との差異・反映前の値）／`store_location_proposal_events`（操作履歴。追記専用）。認証済みユーザーは参照のみで、書き込みは DB 関数（`propose_/decide_/apply_/revert_store_location_proposal`。security definer）だけ。店舗の更新は既存の監査ログ（audit_logs）にも残る。
- **画面**: 調査画面の「反映候補にする」→ 一覧（差異・情報源・公式性・信頼度・理由・履歴）→ 承認・保留・保留を解除・却下・反映を取消。
- **誤登録・重複登録の防止**: 調査1件につき候補1件／同じ店舗・同じ住所（全角半角・ハイフン類を同一視）の有効な候補は1件／反映は承認待ち・保留からの1回だけ（反映済み・却下済み・取消済みは再反映不可）／候補作成後に店舗名・系列が変わっていたら拒否（別店舗への誤反映防止）／店舗の住所が編集されていたら拒否／既存の住所は「置き換える」を選ばない限り上書きしない／住所のない調査結果（失敗・情報不足）は候補にできない。
- **取消**: 反映前の値（住所・都道府県・座標）へ戻す。反映後に店舗が編集されていたら戻さない（編集を守る）。
- **本番での拒否**: アクションは `TOREMANE_ENV=local` の開発環境でのみ動く（`canApplyToStoreMaster`）。`next dev` だけの環境や本番（Vercel）では DB に触れる前に拒否。エラー時は既存データを変更しない（DB関数は拒否理由を履歴に残して何も更新しない）。
- **テスト**: DB結合 `tests/stage8d4.integration.test.ts`（9件: 正しい住所の承認・誤りの却下・保留後の再確認・二重反映の防止・取消・他店舗への誤反映の防止・API障害の結果は候補にできない・世帯の分離と直接書き込みの拒否・本番での拒否）、E2E `e2e/stage8d4.supabase.spec.ts`（2件）。

## 6. 残存リスク・未解決
1. **第三者だけの2サイトで「確認済み」になる**（U02・U08）: ドメインが別でも、地図・口コミ・まとめは同じデータの転載の可能性がある。正解のあるN系では実害（誤住所の確定）なし。締めるには、独立した2つのうち1つは系列自身のサイトを条件にする方針変更と、モックの正解の改訂が必要。**8D-5 で利用者が判断する。**
2. **店舗マスターに同じ系列の他店舗が無い・都道府県別の一覧しかない場合、公式サイトの判定が「候補」止まり**（N07・N08・N20・N12 ほか）。基準を緩めると複製サイトに弱くなるため、緩めていない。
3. 評価の規模: 正解あり20件・正解不明10件で、統計的な優劣は言えない。**改善は同じ30件の分析から作った**ため、修正後の数値（③）は同じ30件への当てはめを含む。新規の別店舗（未使用）での再評価が必要。
4. 正解は Claude が作成し、利用者の再確認は未実施。
5. ③はAIの出力と取得ページを固定した再判定で、AIの調査行動（検索の選び方）の変化は測っていない。実行ごとにAIの出力は変わりうる。
6. 慎重に候補止まりのもの: N11（同じ建物内の移転の記載で信頼度5）・N17（移転オープンの記載）・N08（旧ブランド名）。
7. 本番へ適用する前に、マイグレーション `…094`・`…095`・`…096` の承認・`backup:full` が必要。承認フローは、本番の店舗マスターへ反映する権限設計・旧方式との比較・利用者の承認のあとに、別の段階で検討する。
8. `db:env` は `.env.local` を上書きして開発用キーを消す（`docs/DEV_ENVIRONMENT.md`）。

## 7. Stage 8D-5 への移行可否
**条件つきで可（全面的な自動運用は不可）。** 誤住所の確定が実APIの初回で0・修正後も0、費用は1件約3円・約19秒と実用範囲で、承認フロー（人が承認する運用）は開発環境で検証できた。一方、改善は同じ30件への当てはめを含み、規模も小さいため、次は ①未使用の新規店舗で修正後の再評価（承認のうえ実API）②第三者のみの確認済みの方針決定 ③承認フローの運用設計（本番への適用はマイグレーション承認・バックアップ後）を行い、AIが提案し人が承認する運用に限る。
