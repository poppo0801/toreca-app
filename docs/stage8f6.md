## 1. 抽選形態の定義（`src/lib/lottery-form.ts`）
抽選を、応募受付の**構造**で分類する。

| 形態 | 意味 | カード | グループ化 |
|---|---|---|---|
| A 店舗選択式（`store_select`） | 1つの抽選企画に対し、応募時に複数店舗から1店舗を選ぶ（応募フォームに店舗選択欄）。選択店舗はプロフィールごとに保存（既存: `applications.applied_store_*`） | **1件** | **対象外** |
| B 店舗別独立抽選（`store_independent`） | 店舗ごとに独立した応募受付・応募記録。複数店舗へ応募できる場合もある | 店舗ごとに別カード | **対象**（同系列・同商品・同期間・同条件・同方式・異なる店舗）。表示整理のみ |
| C その他（`other`） | 通販・単独店舗など | 既存のまま | 対象外 |
| 未確認（`unknown`） | 構造を確認できない | 既存の登録を尊重 | 確認候補（自動にしない） |

**最重要: 店舗選択式と店舗別独立を混同しない。**「1店舗のみ応募可」「複数店舗への応募は無効」は応募の**制限**であり、店舗別独立抽選にも付く。制限だけでは店舗選択式と断定しない（`restrictionOnly`。構造が不明なら unknown＋候補）。決め手は構造の記載:
- 店舗選択式の根拠: 応募時に店舗を選ぶ旨の記載（選択欄）／選べる店舗の一覧（2店舗以上）／店舗選択式としての登録。
- 店舗別独立の根拠: 店舗ごとに受付・応募する旨の記載／店頭での応募・受付。店舗ごとに別の情報源URLがあることは、**構造の根拠があるときの裏づけ**にとどめる（別の投稿が同じフォームを紹介していることがあるため、単独では根拠にしない）。
- 両方の構造記載がある（食い違い）→ 確定せず unknown（conflict）。

## 2. 判別の仕組み（AI＋固定ロジックの分離は維持）
- **固定ロジック**（`judgeForm`）が、登録された条件・取得した情報源の文章・選べる店舗・タグ・手動の設定から形態を決め、根拠（シグナル・確度）を返す。AIの自己評価では決めない。
- **AI**（グループ判定のエージェント）には、各抽選の `form`（判別結果・根拠・制限の有無）を参考情報として見せ、指示文で形態の区別を明記した（制限だけで店舗選択式と言わない・構造が不明なら断定せず `missing` に書く・手動の設定は覆さない）。最終の区分は検証層が事実で決める。
- **優先順位**: 利用者の手動の分類 ＞ 構造の根拠 ＞ 登録済みの方式。手動の分類と構造が食い違うときは手動を採用し、食い違い（`manualDisagrees`）を記録する。
- **自動収集・手動登録の両方**: 収集（`collector/run.ts`）は、店舗を1つ特定できても、告知に店舗選択欄の記載があり店舗ごとの受付の記載が無ければ、店舗選択式の1件として登録する（特定できた店舗は選べる店舗の1つ）。手動登録は、画面の既存の「店舗の指定方式」の選択がそのまま利用者の分類になる（UIの変更なし）。
- 情報不足は無理に確定しない（unknown）。

## 3. 手動修正と上書きの防止（マイグレーション101・開発DBのみ）
- `lotteries.lottery_form`（store_select / store_independent / other / NULL）と `lottery_form_source`（manual / rule / ai）。追加のみ・NULL許容。既存の行・`store_mode`・応募・当選・購入・通知・期限には触れない。
- 利用者の保存: 店舗の指定方式を**変えた**とき、または店舗選択式で新規登録したときだけ「manual」として記録（初期値の「店舗固定」のまま保存しただけでは記録しない）。
- 収集・AIの保存: 手動の分類がある抽選には**一切書かない**（`nextFormColumns`。DBテストで確認）。
- `setLotteryForm`（サービス）: 手動で設定・解除（null で構造からの判別に戻る）。分類の記録だけを変え、応募・店舗の指定方式・期限は変えない。変更時、その抽選の承認待ち候補は無効化（`form_changed`。キーを退避して、新しい分類で出し直せる）。判断の記録キーにも抽選形態の記録を含め、過去の単独・保留を再評価する。
- 誤判定からの復旧: 画面の「店舗の指定方式」で戻す、または `setLotteryForm(null)`。

## 4. 店舗選択式の重複登録対策
1. 検出: 収集時に構造から店舗選択式を検出（§2）。
2. 登録済みの確認（`findDuplicates`）: 同じ情報源URLの**店舗選択式がすでに登録済み**なら、店舗別の新規候補は**新しいカードを作らない**（high。既存の統合ガード `reconcileAutoRegistered` が、応募記録のない自分のカードだけをアーカイブして情報元を記録）。逆（店舗別に登録済みの同じ情報源へ店舗選択式の新規）は要確認（medium。自動統合しない）。情報源が別・明確に別の開催回は別の抽選のまま。
3. 既存の複数登録の整理: `findSelectFormCleanup` / `auditSelectFormDuplicates`（**読み取りのみ**・AIなし・費用なし）。構造のある店舗別カード、店舗選択式と同じ情報源の店舗別カードを整理候補として示す。**応募・当選・購入の記録があるカードは `protectedIds` に分け、自動で削除・統合・アーカイブしない**。手動で店舗別独立と設定されたものは候補にしない。
4. 自動で行わないこと: 削除・統合・店舗の指定方式の変更。整理は利用者が判断する。

## 5. グループ化判定の改善（`verify.ts`）
- 8F-5の「イベントID・URLは必須でない」「情報不足を一致とみなさない」「AIの自己評価で決めない」を維持。
- 抽選形態を `judgeForm` で判別: 構造が店舗選択式 → **対象外（single）**（理由に「1つの抽選を店舗ごとの別カードで登録している可能性。グループ化ではなく重複登録の整理の対象」）。手動で「その他」→ 対象外。構造が不明で制限の記載だけ → 候補（suggest。「制限だけでは店舗選択式と断定しない」と明記）。店舗別独立の構造がある、または手動で店舗別独立 → 制限があっても対象（auto になりうる）。
- 8F-5 で「1店舗のみ」の記載・タグを店舗選択式の疑い（候補）としていた判定を、制限と構造の区別に置き換えた（制限だけの場合の区分は同じ suggest）。構造の記載（店舗選択欄）がある場合は、候補ではなく対象外（single）になる。
- 商品略称・系列名・日時の正規化は、8F-5 の固定ロジック（同名の正規化＋AIが「共通」と判断し名称が近い場合は候補）を維持。情報不足（応募開始など核心の不明は保留、周辺は候補）も維持。
