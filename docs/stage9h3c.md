# Stage 9H-3C: 実AI接続・判断結果の反映検証

開発環境のみ。マイグレーションなし。**有料API・実AI・実検索・実ネットワークの呼び出しなし（費用 0円）**。本番DB・開発DBの実データへの書き込みなし（テスト用の世帯のみ）。**実AIの判断精度が上がったかは未測定**（保存済みの結果の再生とモックの試験）。

## 1. 実AI接続（`src/lib/server/agent/case-bridge.ts`）
9H-2の実AI調査（Haiku 5.5＋Anthropic web_search＋安全なページ取得）を、9H-3Bの調査フック（`investigation-hook.ts`）から呼べるように接続した。新しい並列の収集経路は作っていない（収集 → 調査要否 → 調査 → 既存の登録経路の入口へ合流）。
- 接続の条件（すべて必要。どれかが欠ければ未接続＝従来の経路）: `TOREMANE_ENV=local`・`COLLECT_UNIFIED=on`・`COLLECT_INVESTIGATE=on`・既存の関門 `checkRealApi`（`AGENT_REAL_API=allow`・開発専用キー・1回/1日の上限）・**`COLLECT_INVESTIGATE_CONFIRM=yes`**（実行ごとの確認）・**`COLLECT_INVESTIGATE_CAP_JPY`**（累計上限の円。未設定は接続しない）。
- 費用: 呼び出しの前に最大費用を確認（累計・1件15円 `COLLECT_INVESTIGATE_PER_CASE_JPY`）。台帳 `backups/eval-9h3c/ledger.json`（検索料金を含む）。超える見込みならAPIへ送らない。
- 調査の自律性は9H-2のとおり（不足の特定・検索語の作成・情報源の選択・取得・追加調査・照合・同一抽選の判断・統合・終了）。AIの入力に、参考情報パケット（過去の人間の判断・確認済みの公式Xアカウント・系列の傾向）が「参考」として入る。
- 失敗時: 調査の例外・時間切れ（180秒）・費用上限・未接続は、確認済みの情報を一切変えず従来の経路へ戻る（結果が無ければ何も合流しない）。
- **今回の検証は台本のクライアント**（Messages APIの応答の形・tool_use・usage）。実APIは呼んでいない。

## 2. 保存済み実AI結果の再生（`tests/stage9h3c-replay.integration.test.ts`、結果 `backups/eval-9h3c/replay.json`）
保存されているもの: 9H-2の13事例の調査結果（項目の採用値・状態・根拠の抜粋・情報源・行動の記録・検証の拒否の詳細）と、A（従来の抽出結果）。**保存されていないもの（再現不能）**: AIへの入力本文・実際のAIの生出力・取得したページ本文・A側の入力本文。よってAIの入力・出力を推測で作っていない（Aは抽出結果の再現、Bは保存された台帳を現行コードで共通モデルへ変換）。
再生の経路: 保存B → 案件ファイル → 実際の `processQueue`／`processCandidate`（応募単位の判定・店舗照合・重複・登録判定）→ 登録候補。各項目を「残る（kept）／理由つきで保留（held）／理由なく消えた（lost）／調査不要のため未使用（not_used）」に分類し、lost が0であることをテストで確認する。

## 3. 固定ロジックによる上書きの解消（今回の修正）
| 問題（9H-3A・再生で確認） | 修正 |
|---|---|
| 調査の応募単位が既存の判定に届かない（3Bで修正済み） | 維持 |
| 日時の境界表現（12:00と11:59）・日付のみと時刻つきを、別の値として「保留」「変更」にしていた（再生で発見: フルコンプの応募締切） | 同じ意味として扱い、安全側（早い方・時刻つき）に揃え、理由を記録（9Gの規則を合流・判断履歴にも適用） |
| 検証で拒否されたAIの判断が、どの項目・なぜ、が残らない | 項目単位で記録（`rejected`: 例「当選発表（開始）: 日時の形式が正しくない」「店舗: 根拠の原文が本文に見つからない」「統合しない: 同じ抽選と確認できない」） |
| ページ・文章の入力に参考情報（過去の人間の判断）が入らない | X投稿以外の入力にも、告知本文と区別して付与（フラグ有効時） |
| 固定ロジックが応募単位を変える2箇所に理由がない（3B） | 維持 |
原則: AIの判断を単純なキーワードで上書きしない／根拠が確認できた値は保持／相違は記録／根拠不足は勝手に別の値にせず未確認として保持（未反映情報に残す）／人間確定は保護。ただし、根拠の不存在・別の抽選との混同・データ不整合は保留（拒否の記録つき）。

## 4. LivePocketの主催者本文の一次情報判定（`organizer.ts`）
ドメイン全体は一次にしない。応募サービスのページごとに主催者の同一性を確認し、**確認できたときだけ、主催者本文（organizer_body）の項目を一次情報**として扱う。確認の根拠: ①主催者欄（主催者/販売元/運営会社/出品者）が対象の系列・店舗と一致 ②登録済みの公式サイトへの記載・リンク ③登録済みの公式Xアカウントの記載。見出しや本文中の店名の言及だけでは確認しない。確認できなければ未確認（二次のまま）。サービス側の受付表示（販売受付期間など）は、確認できても一次にしない。分類（一次/二次・主催者本文/受付表示・主催者の確認結果）は、台帳 → 案件ファイル → 判断履歴まで保持される。テスト: 確認できる／別主催者・見出しだけは確認しない／公式サイトへのリンク・公式アカウント／受付表示は一次にしない／同じサービスの別ページは別判定。
**限界**: 9H-2で保存されたページ本文が無いため、フルコンプの実ページが確認できたかは再生できない（未検証）。実際のLivePocketページに主催者欄があるかは未確認。

## 5. 調査起動条件・抜き取り再確認
起動条件は3Bのとおり（取得失敗・不足・矛盾・系列/店舗不明・店舗選択式の判断不能・重複疑い・根拠が弱い）。調査に失敗しても従来経路へ戻る。**正常と判断された案件の一部をAIで再確認する設計**: 案件IDのハッシュで対象を決める `spotCheckEligible`（割合 `COLLECT_SPOTCHECK_RATE`、既定0）。対象かの判定を判断履歴に記録するだけで、再確認は実行しない。

## 6. 人間評価・過去知識の利用
参考情報パケット（`case-model/reference.ts`）: 過去の人間の判断（系列の別名・店舗選択式・店舗名の訂正・登録/除外/重複の判断・コメント）＋確認済みの公式Xアカウント（`xLinks`）＋系列の傾向（`chain-knowledge.json`）。すべて「参考。今回の告知の記載を優先」。応募期間・当選発表日・応募条件の情報は渡さない。実際の評価30件のファイルから、キデイランド・フルコンプの店舗選択式の判断がAIの入力に入ることを、実際の収集経路で確認した。**未実装**: 「店舗ごとの抽選傾向」は系列の傾向（5系列の静的JSON）のみ。過去の応募方式の実績の蓄積は未実装。
