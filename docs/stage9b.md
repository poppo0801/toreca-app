# Stage 9B: 自動更新・日時不明の扱い・発見の改善

開発環境のみ。本番DB・本番データには触れていない。新しい有料API呼び出しなし（費用の発生なし）。**マイグレーション102は開発DBのみ適用・本番未適用**（§8）。9A の方針（情報不足でもまず登録）は維持。グループ化は変更なし。

## 1. 現行の発見処理の分析（コード・既存文書から。今回、本番データは読んでいない）
- **発見の方式**: X は「監視アカウントのタイムライン」（キーワード検索ではない）を `judgeXPost` で関連判定→AI解析。まとめサイト一覧・ブックマーク・優先収集メモ・登録済み情報源ページの再確認が別経路。
- **区別して見た原因**（`auto-collection-audit.md` §8 の分類を引用。数値は 2026-11-05 時点）: ①取得できない（robots・JS描画・削除・X取得失敗）②検索（監視）対象に入っていない（アカウント・系列の偏り）③解析で落ちる（関連判定で「ポケカ」と書かれていない告知を捨てる・日時が読めない）④登録処理で除外（地域・商品未登録・重複）。
- **今回特定した穴**: (a) 関連判定が「ポケモンカード」等の語に依存し、**商品名・略称だけの告知を捨てていた**（略称・表記揺れ）(b) 既存抽選の**変更告知は常に人の承認待ち**で、応募に影響しない延長も自動反映されなかった。反映の履歴・復旧が無かった (c) **日時不明の抽選**に長期間の扱いの定義が無かった（9A は新規の登録を止める案だった）(d) 再確認の優先順位に「重要情報が不足している抽選」が効いていなかった。実装時に、**jsonb の包含検索が配列を Postgres 配列として送っており一致しない不具合**に気づき修正した（9A で入れた再確認の優先順位の問い合わせが、実際は効いていなかった）。

## 2. 実装
| 項目 | 内容 |
|---|---|
| 商品名・略称での発見 | 商品マスターの名称・本体名・別名から関連語を作り（`productTerms`。4文字未満・単独で意味を持たない語は除外）、X投稿の関連判定で「ポケカ」と書かれていなくても関連ありとして解析に回す。他のTCGが主題の告知は対象外のまま。解析の上限（1日約30件）・古い投稿の除外は不変。 |
| 自動更新 | 既存抽選の変更を検出したとき、**自動収集で登録され・手動編集されておらず・公式（または登録時と同じ情報源）の更新**で、**応募機会を減らさない変更**（不明な日時を埋める／応募締切・購入期限の延長／当選発表日の変更）は人の承認なしに反映（`planAutoUpdate`・`tryAutoUpdate`）。1日3回まで。 |
| 自動では反映しないもの | **応募締切・購入期限の短縮**（応募機会に直接影響）、過去の日時への変更、開始日・受取方法の変更、中止、公式でも登録時と同じ情報源でもない更新、手動編集された抽選、自動収集でない抽選 → 従来の「更新の提案」（人の確認。理由を表示）。新しい情報に値が無いこと（取得失敗・記載なし）を理由に、確認済みの値を消さない。 |
| 履歴・復旧 | `lotteries.update_history`（マイグレーション102）に、更新前後の値・情報源・公式か・時刻を保存（30件まで）。詳細画面に「自動更新の履歴」（折りたたみ・履歴がある抽選だけ）と「元に戻す」。その後に値が変わっていれば戻さない。**戻した内容と同じ変更は再び反映も提案もしない**。応募・当選・購入・通知の記録は更新しない（日時の列だけ）。競合・失敗時は何も変えず提案に回す。 |
| 日時不明の抽選 | 登録後に日時が長く（21日超）確認できない自動登録の抽選には「終了候補」の注意（`end_candidate`）を付ける。**非表示・アーカイブ・削除・終了日時の推測はしない**。手動編集された抽選・新しい抽選には付けない。日時が入れば（自動補完・手動入力とも）注意は自動で外れる。告知から21日超で日時不明の**新規**告知も、9A の「登録しない」をやめ、登録して終了候補の注意を付ける。 |
| 再確認の優先順位 | 日時が未確認の抽選の情報源を先に再確認（jsonb 検索の不具合を修正。件数・時間の上限は不変）。 |
| 手動編集の保護 | 手動編集の検出（9A で修正）を、自動更新・補完・終了候補で共通に使う。 |
| 情報源の網羅性の分析 | `analyzeCoverage`（純関数・読み取りのみ）: 実績のある未監視の系列、日時未確認の抽選、取得制限のある情報源（回避せず再試行をやめる）、新着の無い情報源（間隔を空ける）を、関連性・コストで順位づけ（上限10件）。**まだ画面・自動実行には接続していない**（§7）。 |

守っていること: 外部ページの文面はデータとして扱う（解析の既存の安全策。新しい命令実行なし）。取得制限・robots・ログインの回避なし。認証情報・個人情報は送らない。

## 3. 評価（測定できたこと／できていないこと）
- **できていない（実データの比較）**: 候補・ログの保存データは本番にのみあり、開発環境に無い。**発見した候補数・登録数・見送り数・重複数・情報取得成功率・項目別の抽出精度・自動補完成功率・API費用・実行時間の改善前後の比較は、今回も未測定**。発見率は「独立して確認した実際の告知」の正解データが無く算出できない。推測では出していない。
- **測定できたこと（架空データ・DB統合）**: 自動更新の判定が方針どおりか（単体9件）、DB上で、延長の自動反映・履歴・復旧・二重復旧の拒否・戻した内容の再反映の防止・短縮と手動編集と手動登録の不反映・応募の記録の不変・終了候補の付与と解除（`tests/stage9b.integration.test.ts` 5件）。商品名・略称での関連判定（単体）。登録方針の適合（`eval/collection-9a/`。17件・架空。R06 を終了候補付きの登録に更新。旧方式3件→新方式9件）。いずれも**精度ではなく仕様への適合**。

## 6. API費用・実行時間
新しい有料API呼び出しなし。関連判定の拡張で、商品名だけの告知が解析に回るため、**解析件数が増える可能性がある**（1日約30件の上限で頭打ち。未測定）。再確認・終了候補の付与は無料の処理で、1回の件数・時間の上限は不変。

## 7. 次に必要な実API評価の計画と予算（提案・未実行）
1. **本番の読み取り分析（無料・利用者の端末）**: 確認待ち・保留・除外・更新の提案の現状を読み取り、新方針で再判定した場合の件数を見積もる。独立して確認した実際の抽選告知（30件程度）を正解として作れれば、発見率・登録率・誤登録率・自動更新の正確性を測れる。
2. **実API評価（承認制）**: 対象は上の正解セット30件程度、AI解析は1件約0.3〜0.5円（8F-7 の実測）→ **想定15〜30円、上限は100円・1件15円**。停止条件は費用上限・連続エラー2回・誤登録または誤更新が1件でも出たとき。
3. **AIが調査対象を選ぶ探索**（`analyzeCoverage` の結果をAIが読み、追加の情報源・調査方法を選ぶ）は、上記の評価で固定ロジックとの差（発見率・費用）が確認できてから。
