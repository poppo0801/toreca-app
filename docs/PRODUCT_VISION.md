# トレマネ 開発方針・自律型AIの構想

出典: 「トレマネ開発方針 引継ぎ資料」（2026-11-11。利用者作成）と、現行コード・Stage 8A の調査。
**表記**: 【実装済み】コードで確認できたもの／【一部】一部だけ実装／【構想】未実装の方針・案。【構想】を実装済みとして扱わない。精度・効果の数値は、計測していないものは「未計測」と書く。

## 1. 目的
- 便利な TCG 抽選管理アプリを完成させるだけでなく、**AI を活用して、人間がどこまで介入せずに高度な情報収集・判断・分析・提案・自動操作を実現できるか**を追求する。
- 現状の機能・使い勝手には満足している（維持が前提）。一方、情報収集・重複判定・地域除外・店舗住所の取得で、固定ロジックの追加や人手の修正が想定以上に必要。
- 方向: **「人間が処理手順を細かく指定する」から「人間が目的を与え、AI が必要な処理を考えて実行する」へ**。

## 2. AI と固定ロジックの役割分担（原則）
AI 化は目的ではない。精度・安全性・費用・速度・利用者の手間で総合評価する。

| 領域 | 方針 | 現状 |
|---|---|---|
| 判断の柔軟性が要るもの（情報の読み取り、表記ゆれの解釈、情報不足の補完調査、店舗・住所の調査、矛盾の検出、先回りの提案） | AI に任せる方向 | 読み取りは【実装済み】（Anthropic API。既定モデル `claude-haiku-5-5`）。調査・補完・提案の自律化は【構想】 |
| 数値計算・データ整合性・応募管理（応募可否判定、集計、金額、期限計算、通知、重複の一意制約、RLS） | **固定ロジックを維持**。AI は計算を代替しない | 【実装済み】 |
| システム制御（保存・削除・マイグレーション・デプロイ） | 確実な処理。AI の権限は段階的（§5） | 【実装済み】（AI は保存権限を持たず、人が確定する流れが基本。自動登録は条件付き） |

## 3. 現在実装されているもの（自律化の出発点）
- 【実装済み】**AI 解析**: 文章・画像・URL・X 投稿から抽選情報を読み取る。項目ごとの根拠（出典・原文）、フィードバック記録、マスター照合、重複検出（`docs/ai-import.md`、Stage 4B/4B.5）。
- 【実装済み】**自動収集**: 5分ごとのワーカー（pg_cron → Vercel）が収集元（Web・X 公式 API）から候補を作り、AI 解析し、4分類（自動登録／自動除外／自動再試行／要手動確認）に振り分ける。月額予算の予約制御、保留・再調査、情報源の信頼性管理、除外ルール（`docs/stage5t.md`、`docs/stage4c.md`、`docs/stage7a.md`）。
- 【実装済み】**重複判定・店舗の正規化**: `findDuplicates` への集約、並行登録の DB ガード、「通販」への正規化、カードボックスの系列統合（Stage 6C・7P〜7S）。
- 【実装済み】**店舗の所在地**: 住所→座標は国土地理院の住所検索（無料）で変換し、直線距離・手動交通費（Stage 5B）、燃料費の計算を持つ。**住所そのものの取得は自動化されていない**（Stage 7S の調査で、住所未登録の約48店舗のうち反映できたのは5件。公式サイトへの到達が難しく、第三者サイトの情報は単独では反映しなかった）。
- 【一部】**収益の把握**: 収支・購入記録・コレクション・相場取得（BOX・カード）がある。抽選ごとの期待利益・移動費込みの利益算出は【構想】。
- 【実装済み】**安全面の既存策**: AI 費用の月額予算、SSRF 対策（`safe-fetch.ts`）、AI に渡す情報の最小化（住所・認証情報は送らない。`architecture-decisions.md`）、操作履歴（監査ログ）、冪等性。
- 自動収集の現行仕様の詳細は `docs/auto-collection-audit.md`（2026-11-05 時点。その後の修正との照合は**未実施**）。

## 4. 目指す機能（すべて【構想】）
### 4.1 自律型の情報収集エージェント
X 投稿・公式サイトから抽選情報を取得 → 不足・矛盾・重複を AI 自身が検出 → 必要なら Web 検索・公式サイト確認・DB 照会 → 店舗の正式名称・住所・所在地を調査 → 情報源を照合し信頼性を評価 → 結果・情報源・確認日時を DB に蓄積 → 過去の調査結果を再利用して検索を減らす → 自力で解決できない問題だけ人に確認。

### 4.2 初期の重点: 店舗所在地の取得（基盤は Stage 8D-2 で開発環境に実装。実API・本番導入は未）
- 住所を AI の推測で補完しない。**検索サービス・公式情報・地図 API を使い分け、取得情報を検証する**構造にする。
- 検証の考え方（7S で有効だった手法）: 公式・一次情報を優先／国土地理院の住所検索で番地まで厳密に一致したものだけ採用／既存の正しい値を上書きしない／出典と確認日を記録する／単一の第三者情報は反映せず「未確認」として残す。
- 「所在地を取得」ボタン案（店名・系列からの一括取得）は**未実装**。Google Places（有料・保存条件に制約）/ OSM Nominatim（無料・一括利用の制限）等は、費用・無料枠・利用規約・精度を**未調査**。有料 API の契約は利用者の判断（無断で導入しない）。

### 4.3 分析・提案
1. 抽選ごとの利益・費用分析（購入価格・買取相場・店舗所在地・自宅からの距離・交通手段・交通費・燃料・高速・駐車・その他）。**不明な費用は推測値と明示し、取得できない情報は確定しない。**
2. 抽選の推奨度（見込み利益・移動負担・応募条件・過去の当選実績）。**当選確率が不明なとき、当選時の利益と期待利益を混同しない。**
3. 近隣店舗・移動経路を考慮した提案（受取予定の周辺の抽選・買取店舗）。
4. 蓄積履歴（応募・当選・購入）からの傾向の発見。
5. ユーザーごとの行動傾向（応募・スルー・購入）の学習。

### 4.4 継続的な改善
AI の判断履歴の蓄積、ユーザー修正の学習、判断基準・検索方針の改善、改善前後の精度比較。フィードバック記録（Stage 4B.5）が出発点。

## 5. 権限管理と安全性（設計方針）
原則（利用者の指示）: **AI の調査・分析の自由度と、データ変更・システム変更の権限は区別する。過剰な制限で自律性を失わせない。** 以下の段階表は、この原則を具体化した**設計案**（採用は Stage 8C 以降の設計時に確定）。

| 段階 | できること | 条件 |
|---|---|---|
| 0 読み取り・調査・分析 | Web 検索、公式サイト確認、DB の読み取り、分析 | 自由。回数・費用の上限内 |
| 1 提案 | 候補の作成、推奨、住所案（情報源・確認日・信頼性つき） | 人が確定するまでは「確認済み」にしない |
| 2 低リスクの自動登録 | 既存の自動登録（条件に合う抽選。注意付き）。調査結果の「候補」欄への記録 | 出典・理由を記録、取り消し可能 |
| 3 変更・削除・一括更新・重要設定・コード変更・マイグレーション | 利用者の承認＋事前バックアップ＋検証 | **AI の実験は開発用 DB（Stage 8C で分離済み）で行う。本番データを変更する AI のテストは禁止** |

共通の安全策: API 費用・検索回数・再試行回数の上限／検索結果への情報源・確認日時・信頼性の記録／外部情報（Web・X 投稿）内の指示は実行しない（データとして扱う）／個人情報・API キーを外部に渡さない／推測値の確定禁止／操作履歴（監査）と取り消し手段／AI の自己改善が既存機能を悪化させないよう、改善前後を比較検証してから導入。

主なリスク: 誤情報の自動登録・更新／正常データの誤削除・上書き／判断の連鎖（誤りの増幅）／無限検索・再試行による費用増大／外部情報による指示誘導（プロンプトインジェクション）／情報漏洩／自己改善による劣化。

## 6. 検証の方法（新旧比較）
- 新しい自律方式は、既存システムと**分離した環境**で試験し、旧方式と比較して、十分検証してから段階的に本番へ導入する。
- 比較項目: 精度（正しく取得・登録できた率／人手の修正が要った率）・費用（API 費用）・速度・利用者の手間・誤登録の件数。いずれも**現時点で基準値は未計測**。基準の計測が最初の作業になる。
- 実行形態の案: 本番に書き込まない「影（シャドウ）モード」で旧方式と並走させ、結果だけ比較する。
