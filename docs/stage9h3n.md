## 1. 系列横断の調査（`collector/chain-sweep.ts`）
- **開催機会（Opportunity）**: 系列＋商品＋時期のまとまり。開始日が7日を超えて離れる／発売時と再販など種類が違う／時期を比べられない抽選は、**別の開催機会**（誤って統合しない）。店舗ごとの応募期間・条件・URL・発表日は店舗ごとに独立（他店の値で補わない）。
- **系列の傾向の発見**: 蓄積した履歴から、系列ごとに店舗の参加率・同時性（開始日が3日以内に揃う割合）・時期のずれを計算（系列名の固定ルール・辞書なし。未知の系列も、標本が少なければ信頼度を下げて発見する）。全系列の傾向で標本の少ない系列を補う。
- **関連店舗の調査計画（`planSweep`）**: 起点の抽選から、まだ見つかっていない店舗のうち開催の可能性が高い店舗を、上限つきで選ぶ（起点あたり5・実行全体15・同じ店舗は3回まで・最低の可能性0.4）。複数の開催機会に一度も参加していない店舗は選ばない。応募期間が終わった開催機会は調べない。傾向が無い系列は調べない（根拠の無い調査を増やさない）。
- **台帳（`SweepLedger`）**: 調査を始めたら記録（重複実行の防止）。見つからなくても**「開催なし」とは記録せず**、1→2→4日と間隔を広げて未確認のまま継続。上限回数・応募期間の終了で `closed_unconfirmed`（未確認のまま終了）。見つかれば `found`。調査の記録（`agent_investigation_runs.result.sweepLedger`）に蓄積し、次回の判断に使う。
- **既存の自律型の収集計画（9C）へ接続**: 調査の種類 `chain_sibling` を追加。手がかり `signals.siblings`（根拠つき。開催の可能性であり確認ではない）をAIが読み、調べる対象を選ぶ。検証層は、手がかりに無い対象を拒否する（`reviewPlan`）。登録・グループ化は既存の検証を経る（AIの提案は登録しない）。
- **検証（保存済みデータ・費用0。`BUILD_9H3N=1`）**: 本番候補プール（1,380候補）から履歴536件・77系列。傾向を発見できた系列11（キデイランド＝同時性78%・開始日のずれ中央2日、カードラボ＝71%・2日、など）。複数店舗（3店以上）の開催機会45件で、その開催機会を除いた履歴だけから起点以外の店舗を予測: **適合率47%・再現率9%**（予測43・的中20）。系列で差が大きい（キデイランドは的中14/21、TSUTAYAのような店舗数が多く参加率の低い系列は選ばない）。**この適合率は、履歴で観測できた店舗だけを正解にした下限**（観測できていない開催店舗＝取りこぼしは誤りに数える）。開催機会の区別: 同じ系列・商品で複数の開催機会に分かれたのが23組・**誤統合0件**。実際に取りこぼしを見つけられるかは、実調査（有料AI・実サイト）での検証が必要（未実施）。

## 2. 抽選予告の内部管理（`collector/announcement.ts`・`teaser-filter.ts`・`teaser-summary.ts`）
- **総合判断（`judgeAnnouncement`）**: 日付の欠落ではなく、募集内容が実際に公表されているかを、応募先（URL・フォーム）・受付開始・締切・当選発表・条件・商品・公式性・「受付開始」等の言い回しと、「抽選予定」「近日」「詳細は後日」「模様」等の未発表・憶測の言い回しの重みづけで判断し、根拠・信頼度・確認事項を記録。1項目の欠落だけでは予告にしない（受付開始日＋応募先＋条件があれば、締切が無くても正式発表）。応募開始前でも、公式が具体的な内容を発表していれば正式発表（登録対象）。迷うときは予告のまま継続して調べる。
- **内部管理**: 予告（teaser・有効/延期）は `draft.tracking`（announcement・outcome・carried・lastJudgement）に保存し、**通常の抽選候補の一覧・件数（下部ナビのバッジ）に含めない**（`NOT_INTERNAL_TEASER`。DBの結合テストで確認）。通知は抽選本体が対象で、候補の件数は含まない。
- **正式発表への昇格**: 続報で `formal` と判断したら `outcome=promoted`（履歴・昇格日時を保存）。予告段階で取得した系列・店舗・商品・予告元URL・抜粋は `carried` に保持し、正式発表後の調査・補完に再利用（`carryOver`: 新しい告知の値を優先し空の項目だけ補う）。
- **中止・延期・終了**: 告知が中止を明示したら、自動で除外せず**要手動確認**（他店・他商品の記載を拾う誤判定を避けるため）。延期は日程の再発表まで保持。続報なし60日・予定日を過ぎて7日以上続報なしで「未発表のまま終了」（履歴は残す）。
- **確認画面**: 設定 → 収集 の診断領域に「抽選予告の内部管理」（追跡中・開始7日以内・昇格・延期・中止・終了の件数と、確認待ちの予告・未発表の項目）。
- 本番へ入れるとき: `draft` のJSONだけで、スキーマ変更なし。本番の既存の追跡（判断なし）は、従来どおり表示される（`announcement` が無い）。

## 3. 地域判定の問題（原因と改善）
- **事例の特定**: 報告の「ドラゴンスター宮店」ではなく、**キデイランド三宮店（兵庫県）**（候補 `k-b2cc23a6`）。ドラゴンスターに兵庫県の地域除外の記録は無い。除外理由「対象外の地域です（東京都）」・根拠「告知に記載された都道府県（東京都）」。
- **原因**: 「キデイランド各店」の告知（X投稿→LivePocket）には複数店舗が並ぶ。AIの抽出で、先頭の店舗「吉祥寺店（東京都）」の都道府県が、抽選対象の三宮店に紐づいた。判定は `店舗マスター → 住所 → 告知の都道府県 → 店舗名` の順で、**告知の都道府県が店舗名の地名（三宮＝兵庫県）より優先**されたため、東京都として除外された。同じ告知の他の店舗（大阪梅田・神戸・京都四条など）は登録されている。
- **改善**: 告知の都道府県と店舗名の地名が**食い違う**ときは、どちらも採用せず「不明」（`basis=conflict`・両方の根拠を記録）→ 地域外として除外せず**要確認**（店舗の所在地の確認）。店舗マスター・住所があれば従来どおり最優先。一致するとき・片方だけのときは従来どおり。除外の記録（`exclusion.conflict`）に食い違った根拠を残す。収集・再評価の両方に適用。**対象地域の設定値は変更していない**。既存の地域除外（東京都の店舗など）は維持（テストで確認）。
- 残る課題: 食い違い時に、店舗の所在地を信頼できる情報源（店舗マスター・公式ページ）で確認する追加調査の自動化（9C/8Dの店舗所在地の調査基盤を使う案）。

## 4. 自律性・学習
- 系列の傾向は、固定ルールでなく履歴から毎回発見（未知の系列も）。台帳・予告の経過・人間の評価（9H-3M の履歴）が次回の判断に使われる。
- 安全な上限: 起点あたり5・実行全体15・同じ店舗3回・応募期間終了で停止・間隔の指数的な拡大・重複実行の防止・予告の追跡期限。AIの推測（開催の可能性・予告/正式の判断）は確定情報にせず、根拠・信頼度・確認事項を記録。人間確認済みの情報は上書きしない（書き込みはしない）。
