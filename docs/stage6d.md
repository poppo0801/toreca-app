# Stage 6D: 複数情報源の項目別統合・情報充実度A〜E・確認待ち画面の改善

## 1. 複数情報源の項目単位の統合

### 方式（`src/lib/collector/fields.ts`）
候補全体を上書きせず、**項目ごと**に「採用した値・情報源URL/投稿ID・取得日時・公式か二次情報か・確定/未確認/矛盾」を `draft.fields` に保持する。対象項目: 系列・店舗・商品・応募開始/締切・当選発表日・発表方法・応募方法・応募URL・応募条件・購入期間・受取期間・受取方法・所在地。
- **情報源の優先順位**: 公式サイト(4) > 公式X(3) > Xまとめ(2) > まとめサイト(1)。公式Xは、利用者が登録した対応づけ（`x_account_links`）のアカウントだけ。収集元のまとめアカウントは「Xまとめ」。まとめサイトのホスト（pokeso.jp・torecabiyori.com）は最下位。
- **補完**: 主（情報の揃った方）に値が無く、他にあれば補う。既に値がある項目は上書きしない。
- **同じ値**: 独立した出どころ（元の投稿・ページ）が2つ以上になれば「確定」（公式は1つでも確定）。**同じ元の投稿を引用した情報は、独立した裏付けにしない**。
- **違う値**: 同じ情報源（同じアカウント・ホスト）の新しい情報は更新。手動確定（`manual`）は上書きしない。それ以外は**矛盾として記録**し、どちらにも決めない（優先順位の高い値を仮に残す）。矛盾した候補は自動登録せず確認待ちに残す。誤検出を避けるため、短縮URL（t.co 等）と実URL、受取方法「どちらも可」と限定した記載は矛盾にしない。
- 抽選側（`lotteries`）には書き込まない。登録済みの抽選への反映は従来どおり「更新の提案」。系列の抽選条件（Stage 5R・手動のみ）は AI が変更しない。

### 同一抽選・補足投稿の照合（`supplement.ts`）
- 同一抽選（`matchOpen`）: 系列・商品が一致し、店舗は双方が分かっていれば一致。**応募締切・開始が双方に分かって違えば別の抽選回（関連候補）**（追跡中の予告は日付が変わりうるため例外）。商品と締切日だけでは統合しない。複数に該当すれば自動確定せず**関連候補**（`draft.related`）。
- 補足投稿（商品・締切が無く、条件・発表方法などだけの投稿）: **引用元・返信元／共通の応募URL／同じ公式アカウント×同じ系列×24時間以内**のいずれかで対象が**一意**に決まるときだけ補完。同じアカウントというだけでは統合しない。
- 取り込み位置: ① 新しい候補の解析時（`processCandidate`。保存済みの解析結果だけで統合、AI追加なし） ② 既存候補への適用（`merge-pass.ts`。AI・X APIは呼ばない。双方向に一意なものだけ）。統合された側は削除せず「統合済み」として除外状態で残す（`draft.mergedInto`。元の内容も残る）。
- 返信は X API の取得対象外（`exclude: replies`）のため、返信元の紐付けは、取得できた引用・URL・アカウントで行う（返信の取得は費用が増えるため未実施）。

## 2. 情報充実度 A〜E（`completeness.ts`）
件数ではなく、**重要項目**（系列・店舗の識別／商品の識別と既存マスターとの一致／応募期間（締切）／応募先・応募方法）で、ルールベースに判定する。AIの自己評価は使わない。保存済みの候補から**表示のたびに再計算**（最新のマスターで再照合）するので、古いランクが残らない（解析時・統合時にも `draft.assessment` に保存）。
| ランク | 条件 |
|---|---|
| A 登録可能 | 重要項目がすべて揃い、マスター照合の未解決が無い。収集条件の判定が「要確認」（地域・受取方法が未確認）でない |
| B ほぼ完成 | 重要項目は揃い、未解決が1項目（商品マスター確認など）、または収集条件の判定に必要な情報（地域・受取方法）が未確認 |
| C 一部不足 | 系列・商品は分かるが、店舗・締切・応募先のどれかが不足（またはマスター未解決が複数、複数商品の方式未確定） |
| D 大幅に不足 | 系列と商品だけで、応募期間と応募先がどちらも不明（抽選予告など） |
| E 識別困難 | 系列・商品・応募先がほとんど得られていない |
- **矛盾**はランクを下げず「情報は揃っているが矛盾あり」として別に表示。判定理由（何が効いたか）は詳細に表示。補助情報（当選発表・購入/受取期間・受取方法・条件・所在地）は不足の要約にだけ使う。

## 3. 対応優先度（`priorityOf`）
A〜Eとは独立。**本日/明日締切の受付中**＞締切間近＞受付中＞締切不明＞自動追跡（受付前・予告）＞急がない（A/Bで締切が2週間超）＞低優先（D/E・根拠不明）。★系列・優先収集メモ・公式に近い情報源は同条件で先に並ぶ。画面には短い表示（「本日締切」「自動追跡」「急がない」など）だけを出し、数値は見せない。

## 4. 低情報量（D・E）の扱い
- 要手動確認へ送らず、低優先度の自動追跡・再調査（`triage=auto_retry`、24時間間隔）にとどめる（`lowInfoOverride`）。
- 要手動確認に残すもの: 商品マスター未登録・矛盾（利用者の判断）、締切が24時間以内。**低情報量だけでは自動除外しない**（受付終了・明確な対象外は従来どおり）。公式の予告・優先収集メモは追跡を続ける。

## 5. 確認待ち画面（`auto-collect-view.tsx`）
- 各候補: ランク文字（A〜E）・系列/店舗・商品・「不足：…」・対応優先度・受付状況・情報源・「矛盾あり」を1〜2行で表示。詳細に項目別の出典（確定/未確認/矛盾）と判定理由。
- 絞り込み: すべて/A/B/C/D/E（件数つき）。並び順: 対応優先度順（初期）／締切順／情報充実度順／新着順。
- 主操作は「編集して登録」。編集画面には、不足項目・矛盾項目の注意（`flags`）を優先して表示し、取得済みの情報は入力済み。商品マスター未登録は従来どおり商品選択・新規登録。
- **即時除外**: 行の「除外」でその候補だけを除外（収集元の除外ルールは作らない・物理削除しない）→ 約3.5秒の「元に戻す」通知。取り消しは直前の状態へ復元（利用者が除外した候補だけ）。
- **一括操作**: 選択を除外（対象件数を表示して確認→成功・失敗の件数）／選択を再調査（成功・失敗の件数）。除外は選択した候補だけ。
- 連続確認: 登録後は一覧を更新し「次の候補を開く」を表示。処理済み候補は一覧から消える。失敗時は成功として表示しない。通知はAppShell・下部ナビを変更せず、Safe Areaを考慮して配置。

## 6. 既存候補への適用（運用API）
`POST /api/cron/merge`（CRON_SECRET。既定は調査のみ）: 統合（`execute`・`ids`で少数件に限定可）／`lowInfo`（低情報量の追跡への移行）。統合後の登録判定は既存の再評価に任せる（AIなし）。
