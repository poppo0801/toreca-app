## 最小限の承認（Stage 10F のシャドー経由・2026-11-21 更新）
人が30件の正解（gold）を作ることは**前提にしない**。実データの新旧比較は、抽出した原文を新方式のシャドー（`ShadowController`）に流し、旧方式の保存結果との**差分を人が見る**運用で始める。必要な承認は次の3つ（重複なし）:

| 承認 | ゲート | 決めること | 省略できない確認 |
|---|---|---|---|
| ① 本番DBの読み取り | **A** | 対象列・期間・最大30件・抽出コマンド（読み取り専用） | `npm run backup:full`、接続先（project ref）の確認 |
| ② 外部AIへの実原文の送信 | **B（人の目視）＋C（送信）** | B: 全文を目視して「送ってよい」を記録する担当。C: Anthropic への送信範囲、ローカルの保存・30日以内の削除 | **送信前の全件目視（B）**と、**Anthropic API の保持条件の確認（C。未確認。承認前に公式規約・組織設定を確認）** |
| ③ 費用・キー・比較範囲 | **E** | 総額50円・1件3円、専用キー、旧方式の比較は構造のみか項目抽出も含めるか | 事前予約で上限を超えない。共用キーの実請求はConsoleで確認 |

- **D（正解データ）は任意**: 「正解率」を断定したいときだけ、確認シート（提案つき・承認するだけ）で作る。コード上も、課金評価（`paid_eval`）は A・B・C・E で足り、D が要るのは正解率の断定（`paid_eval_with_gold`）だけ。
- 本番DBの読み取り（A）と外部AIへの送信（B・C）は**別のゲート**。A の承認だけでは送信できず、B・C が揃うまで原文は送られない（`assertMaySend`）。
- 通常収集へのシャドー配線（Stage 10F）は、ローカルの開発DB・モック用で、**この承認とは独立**。実データ評価は通常収集を通さず、抽出した原文を直接シャドーへ流す評価ランナー（未実装。承認後に実装・レビュー）で行う。
- 実施順序: ①→（目視）→②→③→評価→分析→削除。いずれかが欠けた時点で停止。

## 実施順序（承認後）
1. 承認記録（A〜E）→ 2. `npm run backup:full`、接続先（project ref）確認 → 3. 抽出の dry-run（件数・層の分布のみ確認）→ 4. 抽出（接続コードの実装・レビュー後）→ 5. 伏せ字・漏洩検出→全件の人手確認 → 6. 正解の作成・固定 → 7. 費用見積もり（API非接続）→ 8. 評価（1回）→ 9. 分析・報告書 → 10. 原文・記録の削除（30日以内）と削除記録。
**どれか1つのゲートが欠けた時点で止まる**（コード上も、承認記録が無い・不備なら拒否）。Stage 10F は別承認。
