# Stage 9H-3P: 自律型AI主体の情報収集基盤

開発環境のみ。本番DB・本番環境・マイグレーションの変更なし。**新たな有料AI・検索の呼び出しなし**（模擬の世界とモックAIで検証）。復元点: タグ `pre-9h3p`（9H-3O のコミット `01dc9a4`）。

## 1. 9H-3O で「16件調査して新規発見0件」だった原因の切り分け

| 仮説 | 判定 | 根拠 |
|---|---|---|
| 検索回数が単に足りない | **主因ではない（副因）** | 1件あたり検索1〜2回・取得3回の割り当ては小さいが、調べた店舗の7/9は既に収集済みだった。回数を増やしても、見つかるのは既存の再発見になる |
| 探索対象の選定 | **主因** | 対象は「過去の抽選履歴にある店舗」から選ばれた（履歴ベース）。履歴にある＝すでに収集の網に掛かっている店舗なので、未知店舗は構造上、候補にならない。対象地域内で候補が無い店舗は1件しか無かった |
| 調査の単位 | **主因** | 調査エンジン（case-investigator）は「1つの抽選の項目を埋める」設計。「この系列に他の開催店舗があるか」という探索は、店舗を1件ずつ指定しないと表現できない |
| 情報源へのアクセス | **副因** | 起点の告知（X）が、登録外のURLとして取得を拒否され、複数店舗が載る告知を手がかりにできなかった。公式の店舗一覧を探索の入口にする手段が無かった |
| 追加調査の自由度 | **副因** | 調査方針（検索語・情報源）はAIが選べたが、「次にどの店舗を調べるか」は固定の計画（履歴の統計）が決めていた |

結論: **探索の「範囲」が履歴で固定されていたことが主因**。AIの自由度は項目の補完に限られ、未知店舗の発見に使われていなかった。ただしこれは9H-3Oの観測からの推論であり、実AIでの検証は未実施（次のステージ）。

## 2. 新しい自律探索の仕組み（`src/lib/agent/discovery/`）

```
ミッション（何を調べるか: 商品／見つかった抽選の周辺／系列）
   │  ※店舗名・検索語・順序は含まない
   ▼
AI（AgentLLM） ── 自分で選ぶ ──▶ 調査対象・検索語・情報源・未知店舗の探し方・追加調査・終了
   │ 読み取り専用ツール
   ├ declare_focus          調べる対象と理由の宣言（履歴に残る）
   ├ search_public_web      公開検索（有料。未承認なら未設定）
   ├ fetch_source_page      起点・公式サイト・検索結果・取得済みページのリンクだけ取得可
   ├ list_known_stores      店舗マスターの店舗（公式の店舗一覧との突き合わせ用）
   ├ lookup_existing_lottery 既存の収集・手動登録との照合（出どころ・人間確認済みも分かる）
   ├ check_store_region     対象地域の内外（外と確定したものだけ除外）
   ├ note_lead              抽選の手がかりを記録 → 固定の検証が採用・保留・除外を返す
   └ get_progress           成果・停滞・残りの余力（続けるか終えるかの判断材料）
   ▼
固定ロジック: 上限／URLの範囲／根拠の実在／重複／地域／保護／収穫逓減の打ち切り／記録
   ▼
DiscoveryRunRecord（調査履歴）→ 共通の候補（EngineCandidate）→ 既存の登録経路の入口
```

- **特定の店舗名・系列名・検索語・順序を固定しない**。プロンプトにも手順の固定は書かない（`engine.ts`）。
- **上限はAIが変更できない**（`controls.ts`）: ミッションあたり 検索8・取得16・ステップ30・費用25円・120秒・同一ホスト4回。セッション全体 6ミッション・60円。ツールの入力・出力に上限を変える項目は無い。
- **自律的な終了**: AIは `get_progress` で成果と費用を見て終える。さらに、新しい情報が5回続けて増えない／費用の70%を使っても手がかり0件なら、固定ロジックが継続を断る（`diminishing_returns`）。確認できなかった対象は **未確認**であり「開催なし」と断定しない。
- **実費の計上**: 検索の実費は費用の上限に数える。費用を記録できない実行は、有料の実行を開始しない（`runDiscoverySession`）。

## 3. 系列横断（未知店舗の発見）

履歴ではなく、**公式の店舗一覧・店舗ページ・告知**から店舗を発見し、店舗マスター・既存の抽選と突き合わせて「まだ手がかりが無い店舗」を探す。系列の全店舗を無条件には調べず、対象地域・過去の探索実績（`StrategyMemory`）・残りの余力で優先する（この判断はAI。モックでは対象地域の店舗を順に調べる）。店舗ごとの応募期間・URL・応募条件は `fields.storeSpecific` と `fields.chainCommon` に分けて保持し、店舗選択式は店舗ごとの抽選として展開しない。

## 4. 既存ロジックとの役割分担

| 担当 | 内容 |
|---|---|
| AI | 探索の主導（対象・方法・順序・追加調査・終了） |
| 固定ロジック（補助・確定処理） | 上限・アクセス制限、根拠の実在検証、重複（既存・実行内）、地域判定（`region.ts`）、人間確認済みの保護、記録、登録経路（既存の解析・登録の入口がURLを独自に再解析する） |
| 既存の収集方式 | **残す**（削除・変更なし）。`createLegacyEngine` は既存の収集の呼び出しを包むだけ |

「従来の収集結果をAIが解析する」構造には戻していない。ただし、**既存が先に持っていた抽選はAIの発見実績に数えない**（`credit: already_known`）。

## 5. 切り替えの土台（9H-3Q用）

`src/lib/collector/engine-contract.ts`: 収集エンジン（`autonomous`／`legacy`）が共通の `EngineCandidate` を返し、共通の登録経路は中身を解釈しない。`EngineRegistry.resolve(setting, env)` は、未設定・不正・開発環境以外では **legacy（現在の挙動のまま）**。autonomous は `TOREMANE_ENV=local` で明示したときだけ。設定画面・設定の保存は9H-3Qで実装する。

## 6. 調査履歴・評価基盤

`DiscoveryRunRecord`: 調査対象と理由（`focus`）／使った情報源と経緯（`sources`: seed・search・link・official_site）／追加調査の経緯（`followUps`: 行動・直前の結果を踏まえた理由・結果）／検索語／手がかり（根拠の原文・採用/保留/除外とその理由・既存との重複・要確認項目）／終了理由（AI・システムの別）／継続を断った記録／実行時間・費用／確認できなかった対象。`StrategyMemory`（plain JSON）は、系列ごとの新規発見数・既存と重複した数・新規なしの連続回数と、情報源ごとの取得失敗・新規発見数を持ち、次のミッションの参考情報になる（事実の確定ではない）。**DBへの保存は未接続**（呼び出し側が `saveMemory`／記録の保存を実装する。マイグレーションなし）。

## 7. 検証（模擬のWeb世界。27件）

- 未知店舗の発見（店舗マスターに無い店舗を含む）・対象地域外は調べない・起点が取得できないときの代替探索・未確認の扱い

- 地域不明は除外せず要確認／店舗選択式／系列共通と店舗固有の分離／根拠なし・別店舗の告知・確認できない日付の不採用／同一抽選の二重記録
- 何も無い世界での終了・貪欲なAIの打ち切り・繰り返しの拒否・費用の上限・検証を破ろうとするAI・命令文の混入・書き込みツールの登録拒否

- エンジンの切り替え（既定は legacy）・共通の候補への変換・探索実績の保存

**限界**: モックAIと架空の世界での検証であり、実AIの探索能力・実Webでの精度は未測定。モックAIの探索手順（対象地域の店舗を順に調べる）は、実AIの判断の代わりではない。旧方式との比較は、同じ模擬の世界での構造的な差の確認であり、実運用の再現率の改善を示すものではない。
