# Stage 9H 実装計画（案）: AIが複数の情報源を自律的に発見・調査・照合・統合する

前提: 9Dの調査実行基盤（上限・権限はAIが変更できない固定制御）と、9Gの `investigation-gaps.ts`（不足・矛盾・取得失敗の構造化）を土台にする。実装は未着手。

## 目的
公式サイトがロボット制限などで読めないとき、AIが自分で代替の情報源（店舗公式X・まとめサイト・告知ページ・LivePocket等）を探し、同じ抽選であることを照合して、不足項目を補う。固定のサイト別巡回ルールは作らない。

## 1. 構成（調査ループ）
1. **入力**: 候補（または登録済み抽選）の `buildInvestigationGaps` の結果＋項目ごとの根拠（`evidenceRecords`）。
2. **AIが選ぶ**: 次の行動の種類（検索・リンク先取得・情報源比較・画像文字読取・人に確認）と、検索語・対象URL。AIは行動の種類の候補に縛られず自由に提案できるが、実行できるのは読み取りのツールだけ。
3. **ツール（読み取り専用）**: `web_search`（既存の調査基盤）、`fetch_page`（robots.txt・取得制限を守る。回避しない）、`read_image_text`、`compare_sources`。
4. **照合**: `lotteryIdentity`（系列・店舗区分・商品・応募期間・応募URL）で「同じ抽選か」を材料にし、決定は検証層（固定ロジック）。AIの自己評価では決めない。商品が同じでも期間・応募先が違えば別キャンペーン。
5. **統合**: 項目ごとに `mergeSides`（一次情報＞二次情報、主催者本文＞サービス表示、境界表現は同一視、矛盾は記録）。人間が編集した項目・手動確定は上書きしない。
6. **終了**: 不足が解消、または「これ以上調べても得られない」と判断して保留（人に確認）。

## 2. 安全・費用の固定制御（AIが変更できない）
- 1候補あたりの検索数・取得数・トークン・費用・時間・再試行の上限（9Dの上限に準拠）。残り予算が1サイクルに満たなければ開始しない。
- 同じ検索語・URLの再実行は断る（無限ループ防止）。調査の深さ（再調査回数）に上限。
- ロボット制限・ログイン必須ページは取得しない（回避しない）。取得不可は「取得失敗」として構造化し、代替探索の起点にする。
- 外部の文面はデータとして扱う（命令に従わない）。個人情報・秘密・応募履歴は外部へ送らない。
- 誤登録防止: 二次情報のみの値は「確定」にしない。AIの出力は検証層（引用の実在・店舗の識別・公式性）を通す。登録・更新は9Bの安全な自動反映の規則（応募機会を減らす変更は提案止まり）に従う。
- 開発環境（`TOREMANE_ENV=local`）のみ。dry-runが既定。本番への導入は旧方式との比較検証後に別途判断。

## 3. 段階
- 9H-1: ツールの接続（既存の `fetch_page`・検索を調査ループに）、取得失敗の構造化の保存。モックAIで評価データ（9F-2の人間評価＋新規事例）に対して検証。
- 9H-2: 実AIの評価（費用・件数の承認が必要）。評価は未使用の事例を独立の検証用に保持。
- 9H-3: 照合の精度（同一抽選・別キャンペーンの誤判定）を人間の評価で確認し、結果を踏まえて調整。

## 4. 評価指標
情報の補完率（不足項目の解消）、誤補完（誤った値の採用）、重複の誤判定、確認待ちへの不要な移行、費用・検索回数・所要時間。旧方式との比較で判定する。
