# Stage 10J 書き込みなし本番シャドー運用の実装方針（提案・未実装・未承認）

状態: **提案のみ**。本番有効化・本番DBの変更（マイグレーション含む）・9H系のローカル限定の解除は、ユーザーの個別承認まで行わない。評価の実測値は `docs/reports/2026-11-21-stage10j-evidence-holdout.md`。10Fのローカルシャドー（`docs/AI_REDESIGN_10F_SHADOW_ROLLOUT.md`）の延長。

## 1. 目的と、書き込みなしの意味
新方式（統合AI判断）を、本番の通常収集と**同じ入力**で並走させ、旧方式の結果と比較できる記録だけを残す。**抽選・候補・応募・当選・購入・マスターへの書き込みはしない**（旧方式の結果・画面・通知・費用に影響を与えない）。記録は、新設の追記専用の記録先にのみ書く（§4）。記録先を作るにはDBマイグレーションが要るため、その適用はユーザーの承認が必要。

## 2. 10Fのフックを本番サーバレスにそのまま有効化できない理由
| 項目 | 現状（10F） | 本番サーバレスでの問題 |
|---|---|---|
| 実行寿命 | 通常収集の処理中に並行して開始し、最後に `settle`（最大25秒）だけ待つ | AI判断は1件10〜60秒（実測）。収集のcron（`maxDuration=180`）の末尾で待てるのは数件。待たずに関数が終了すると、実行中の判断は打ち切られる（結果も費用も記録できない） |
| 起動条件 | `TOREMANE_ENV=local` でのみ有効（9H系の安全弁） | 本番では動かない（意図どおり）。解除は設計と承認が必要 |
| 記録先 | ローカルファイル（`LocalFileSink`） | サーバレスにはローカル保存がない。本番用の記録先が必要 |
| 予算・停止 | 設定の再読込で緊急停止が即時に効く（環境変数） | 環境変数の変更は再デプロイが要る。実行中の関数に即時には効かない |
| 鍵 | 開発用の共用キー（評価用） | 本番キーの分離・上限が必要（開発用キーを本番に流用しない） |

## 3. 推奨アーキテクチャ（段階導入）
**案B（推奨）: 追記専用の記録先＋専用の非同期ワーカー（cron）**。通常収集は何も待たない。
1. **投入（通常収集側）**: 旧方式が候補の処理を終えたら、`shadow_jobs` に1行を**追加するだけ**（候補ID・保存原文の参照・投入時刻）。AI呼び出しはしない。失敗しても収集は続行（例外を握りつぶし、件数だけ数える）。投入の可否は設定（既定OFF・世帯単位のフラグ）で制御。
2. **ワーカー**: 専用のcron（収集とは別の関数。`maxDuration` 60〜180秒）が、`shadow_jobs` を1回に最大N件（例: 3〜5件）だけ処理。1件ずつ「保存原文を読む→伏せ字・漏洩検出・公開告知確認→（リンク先の公開ページを取得）→判断→記録」。**リース（期限つきの占有）**で二重処理を防ぎ、関数終了前に必ず状態を残す（処理中のまま消えない）。時間切れは「次回に再投入」。
3. **記録**: `shadow_judgments`（追記専用）。非機微の要約（10Fの `ShadowRecord` と同じ: 連番ハッシュ・列挙値・件数・費用・遅延・状態）。原文・URL・個人情報は**コピーしない**（比較で原文が要るときは、既存の `collection_candidates.last_good.evidence` を、権限のある画面・スクリプトで参照）。
4. **旧方式との分離**: 別のテーブル・別の関数・別の予算プール。旧方式のテーブルへの書き込み権限を持たない専用のDBロール（または、書き込み先をアプリ側で固定し、テストで保証）。ワーカーの失敗・遅延・費用超過が、収集・通知・画面に波及しない。
5. **一覧投稿**: 10Iの焦点・分割（`list-split.ts`）をワーカー側で使う。通常収集の候補は「その候補の対象案件」があるため、焦点（対象に関係する項目だけ）が既定。一覧全体の候補発見（新規の項目の抽出）は別のジョブ種別として分け、最初は無効。

**案A（最小）: 記録先を作らず、構造化ログだけを残す**（Vercelのログ）。DB変更が不要で最短だが、集計・保持・比較が難しく、ログの保持期間は短い。**実測の集計用には不十分**で、案Bへの前段の短期の確認にとどめる。
**案C（現状の延長）: 本番は読み取りのみ（SELECT）で、ローカルで再判定**（10G〜10Jの方式）。本番に何も足さず安全だが、リアルタイム性・継続性がなく、収集直後のデータでの比較ができない。**案Bの承認前の継続手段**として有効。

## 5. 機密情報・データ保護
- 外部AIへ送るのは**公開告知の伏せ字後の本文のみ**（既承認の保持リスク受容の範囲）。伏せ字・漏洩検出・公開告知確認を通らない候補は投入しても処理しない（記録は「除外」）。
- 応募・当選・購入の記録、世帯・プロフィール・メモ、人が確定した値は**外部AIに送らない**。保護された抽選の情報は、保護の有無（列挙値）だけを入力に含める。
- 記録は非機微のみ（`assertSafeRecord`）。ログに原文・URL・ID・キーを出さない。

## 6. 本番シャドー開始の判定基準（案）
次をすべて満たしたときに、案Bの実装・マイグレーションの承認を依頼する。
1. 未知データ（10J）で、**構造・応募機会の暫定ラベルとの重大な矛盾がない**（人が確認した少数のラベルでも再確認）。
2. 一覧の**誤集約・取りこぼしが検出されない**（項目対応の検査で missing/merged が基準内）。
3. 判断の**完走率が高い**（目安95%以上）・1件あたりの費用が上限（3円）内・遅延が非同期ワーカーの時間内。
4. 保護された対象への変更提案が0、機密情報の漏洩検出が機能していること。
5. 旧方式との分離（書き込み先・予算・失敗の波及）が、統合テストで確認済み。
6. 費用の月次見込みをユーザーが承認（候補数×約0.4〜1円の見込みで、日次・月次の上限を設定）。

## 7. 最短の次工程
1. （本Stage）ローカルでの実装・検証・本方針の整理 — 完了。
2. 人が確認した少数のラベルで、未知の一覧の対象を再検証（精度の確認）。
3. **ユーザーの承認**: 案Bのマイグレーション・ワーカーの実装着手、本番専用キーと日次上限、9H系の限定解除の設計。
4. 実装（ローカルDBでの統合テスト・RLS・リース・緊急停止・予算）→ PR → CI → レビュー。
5. 本番マイグレーション適用（別承認・直前に完全バックアップ）→ 少数（例: 1日10件）で開始 → 監視 → 段階的に拡大。
6. その後、旧方式との比較の結果を見て、切替の判断（別承認）。
