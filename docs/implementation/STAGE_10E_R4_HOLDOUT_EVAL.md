1. PR #36に最新mainを取り込み、評価コード・料金・ゲート・モデル名・r4版・ホールドアウトH01〜H06を確認する。
2. **評価前**にH06のgoldの注記「別系列」と、入力の「同系列・別商品・別締切」の矛盾を訂正する。**正解の関係値 independent は変更しない**。注記以外のgold・採点基準・ケース入力・プロンプトは評価前後で変更しない。注記変更と評価実行のコミットを分け、変更理由を記録する。
3. `JUDGMENT_REAL_SET=holdout` で **H01〜H06の6件のみ**を、`10e.2-r4` と `claude-haiku-5-5` で評価する。goldはモデルに渡さず、Web検索・実原文・本番DB・本番デプロイ・10Fには触れない。
4. 実行前にローカル環境・明示オプトイン・モデル利用可能性・既存開発キーの出所・確認フラグを検査する。キー値は表示・保存・コミットしない。**総額5円、1事例2円を事前予約で厳格に制御**。最悪時の予約見積もりが上限を超える場合、勝手に上限を増やさず、実行可能な件数や再試行上限の調整案を報告して停止する。費用上限内であっても承認外の追加事例・反復評価は行わない。
5. 構造ラベル、機会数、既存カードとの関係、誤統合・誤分割、保留、`products`形式エラー、再判断成功率、保護履歴、根拠、API回数・実測費用・遅延を事例ごとに集計。**受理されなかった出力の構造情報のみ**（フィールド名、型、検証エラー）を秘密・原文・キーなしで記録し、原因分析可能にする。生出力全文や機微情報は記録しない。
6. 今回のH群は初回の実AI評価なので結果を見てからプロンプト・採点基準・goldを修正しない。問題があれば修正提案を報告するが、同じH群を再び「未見」と扱わない。既存のK/J群は回帰として別扱い。
7. 型検査・lint・単体・DB結合・build・CIを確認し、`docs/reports/2026-11-21-stage10e-r4-holdout-eval.md` に実行条件、事例別結果、前回との比較の限界、費用、残課題、次の実データ評価の承認事項を記載。**実AI精度の一般化はしない**。
8. 結果と必要な最小コード変更はPR #36に追加し、**PR #36は未マージ**のままレビュー待ちにする。
