# Stage 10F：新旧並行評価（シャドーモード）への移行指示

## 方針と承認範囲
ユーザーは2026-11-21、Stage 10Eの架空データ検証を一区切りとし、実データ評価のために開発全体を停止せず、**Stage 10Fの安全な統合実装へ進む方針**を承認した。既存PR #36のマージ、本番データへのアクセス、実原文の外部AI送信、追加の課金API、本番デプロイ/設定切替は**この承認に含まれない**。

Stage 10Eの評価報告とPhase2準備報告・承認票を踏まえ、過度な追加ホールドアウト検証は行わず、実際の運用に近い環境で比較できる仕組みを優先する。

## 一括実装
1. **PR #36の最終レビュー**: 最新mainを取り込み、型・lint・単体・DB結合・build・CI、保護履歴、冪等性、重複・応募機会の境界、費用ゲート、原文漏洩対策、既存機能への回帰を確認。問題があればPR #36で修正し、報告。**PR #36をマージしない**。
2. **Stage 10Fのシャドーモード基盤を別実装ブランチ/PRで作成**。旧方式を唯一の正式な判断・登録経路として維持し、新方式は同一入力に対して比較用の判断のみ行う。新方式は抽選カード・応募履歴・当選履歴・通知・保護対象の登録/更新/削除に一切作用させない。初期状態OFF、環境/フラグで明示的にON。実行先・実データ・AI課金の承認ゲートは既存の制約を維持。
3. 新旧の比較を、構造・機会数・関係・保留・根拠・誤統合疑い・誤分割疑い・費用・遅延に分けて記録。**旧方式が表現できない構造は不正解と混同しない**。比較結果だけからgoldや精度を断定しない。保存は最小限の非機微メタデータに限定し、原文・ID・URL・認証情報をログやPRに出さない。
4. **無課金・架空データのローカルテストを先行**し、通常経路への副作用ゼロ、シャドー側エラー時の旧方式継続、タイムアウト、重複実行防止、レート制限/回数上限、コスト上限、緊急停止・旧方式への即時切戻し、初期OFF、無許可の本番接続/AI送信拒否を検証。必要ならモックの新方式で比較する。既存のPhase2ゲートA〜Eを迂回しない。
5. 将来の段階的切替の設計（OFF→ローカルシャドー→承認後の実データシャドー→限定適用→全面切替）と、各段階の停止条件・復旧方法を作成。**この指示で許可するのはローカルの無課金シャドー実装・テストまで**。実データシャドー実行や新方式を正式な登録経路へ切り替えるのは別承認。
6. Stage10EのPR #36と10F実装PRの依存関係を明記し、レビューしやすい分割にする。Stage10F実装PRも未マージ。レポート `docs/reports/2026-11-21-stage10f-shadow-readiness.md` に実装・テスト結果・残課題・**次に必要な最小限の承認事項**をまとめる。

- Stage10EのK03/H06のような保守的なunknownは、誤統合より安全な挙動として当面許容。不要なプロンプト修正・再評価を繰り返さない。

- 本番DB読取、実原文取得、Web収集の追加、課金API、本番反映、PR #36および10F実装PRのマージは今回の対象外。
