# Stage 10D 実行指示：共通データ基盤・移行準備・履歴保護

状態：**ユーザーがStage 10Dへの進行を承認した実行指示**。本書は `docs/implementation/STAGE_10D_to_10H_DRAFT.md` の10Dを正式化・具体化したもの。**本番DBへの変更、稼働中エンジンの切替、外部AIの有料実行、保存期限による削除は承認していない**。

## 0. 最優先原則
- 最終目標は**AI主体の意味判断・自律調査・継続改善**であり、既存固定ルールへの小手先の追加ではない。Stage 10Dはそのための安全な土台作り。旧方式の恒久維持を目的としない。
- 既存の応募・当落・店舗/商品選択・スルー・通知・手動修正・購入・コレクション・A/B/C・地域条件・継続抽選を守る。**既存の `lotteries.id` と参照関係を壊さない**。応募記録がある抽選の自律統合・削除・ID変更は禁止。
- 新しい論理5層（Evidence/Case/Opportunity/View/User records）は5つの物理テーブルを要求しない。**案A**（`lotteries`をOpportunityとして維持、`cases`と`case_judgments`を追加、必要な関連列を追加）を**設計・開発実装の第一候補として採用**。実測で問題が見つかれば代案と根拠を示す。破壊的な案Bへ独断で切り替えない。
- 安全な技術判断・実装・テスト・PR作成はまとめて自律実行してよい。ユーザーの既存合意にない基本設計変更・本番DB/本番設定変更・費用増・個人情報の外部送信は事前承認。

## 2. 作業の進め方
- 最新mainから作業ブランチを作り、開始コミット・未コミット差分・既存テスト状態を記録。既存の未追跡ファイルは勝手に削除しない。
- **ユーザーへの細切れ確認は不要**。下記の安全な作業を設計→実装→テスト→PR→報告まで一括で進める。承認ゲートに到達した部分だけを明示して止め、他の安全な作業は継続。
- 本番読み取り計測は、既存の許可された読み取り手段に限定し、権限・接続先を事前に確認する。**本番のマイグレーション状態の照会は元ドラフトのとおり事前承認**。未承認の項目は未確認と記録して他を進める。接続できない場合は推測で埋めず、ローカルDB/マイグレーション定義から可能な範囲を進める。
- 本番接続時のSQLはSELECT等の読み取り専用。機密値・個人データの本文をログやPRへ出さず、集計値とスキーマ情報に限定。新しいDB操作スクリプトに本番書き込み経路を作らない。

## 3. 必須作業と成果物

### A. 現状実測と依存関係の確定
1. `lotteries`、`collection_candidates`、既存9Z原文保存の件数・容量・増加ペースを測定可能な範囲で集計。時点、接続先、計測方法、未取得値を明記。保存量を勝手に0とみなさない。
2. `lotteries`を参照するFK・複合FK・ユニーク制約・RLS・通知の冪等キー・手動修正保護の経路を洗い出す。通知が締切/発表日/構造変更時に再評価されるかをコードで確認。
3. 現行マイグレーションの定義と開発DB適用状態を確認。本番の適用状態は許可範囲でのみ確認。9Hのlocal-only関門と既存の `collection_settings.engine` の意味の違いを保持。
4. 既存機能の回帰テストの欠落を列挙し、少なくとも履歴破損・応募ID保護に関わる欠落は10D内で補う。

### B. Case/判断履歴/証拠のデータ基盤
1. 案Aを基本に**追加のみ・既存データ非破壊**のスキーマ/マイグレーションを作る。必要な `cases`、`case_judgments`、`lotteries.case_id`、`collection_candidates.case_id` 等の具体設計を既存スキーマと照合して決定。必要性が証明されない新規テーブル・列を増やさない。
2. Caseに未確定の応募構造を保持でき、根拠のない複数Opportunityを生成しない。1企画の複数独立応募機会、店舗選択、商品別独立、関連告知、既存Opportunityとの関連を将来表現できること。未確定Caseを既存抽選IDに強制変換しない。
3. 判断履歴に少なくとも根拠参照、取得時点、事実/推論/不明の区別、判断の版・モデル/プロンプト識別、修正の由来、費用、再評価の理由・結果を**将来検索・比較できる形**で保存できるようにする。すべてを巨大JSONに閉じ込めて検索不能にしない。AIが後から過去判断・訂正を検索参照する経路の設計も明記（10Eで活用）。
4. 9Zの保存原文と `collection_hard_sources` を再利用可能な参照にする。原文のハッシュ重複排除、サイズ・保存期間・個人情報マスキングの設計案を提示。**未承認の保存期限・自動削除は有効化しない**。取得不能・未取得・取得成功だが読解失敗を区別。
5. 家庭・アカウントの分離（RLS、household_id、アクセス権）、外部取得本文によるプロンプトインジェクション対策、秘密情報を含む証拠の保存・ログ/AI送信制限をテストする。実AIの呼び出しは行わない。

### C. 履歴保護・正規化・移行互換
1. 応募記録・当落・手動修正等のある抽選を自律変更/統合/削除できない共通の**検証・保護層**を実装し、失敗理由を記録。単なるUI側チェックにしない。人手確定値をAIが後から上書きしないための根拠/優先順位を設計。
2. 系列・店舗・商品名の正規化経路（TS/DB/別名マスター）の違いを洗い出し、一本化する設計・安全な実装範囲を提示。既存の手動紐付け、スルールール、購入履歴を推測で再紐付けしない。意味的な名寄せの最終判断は10EのAIへ。
3. 旧判定/新判定の**一時的な切替設計**を作成。既存 `collection_settings.engine`（自律探索の併用設定）と混同しない。10Dでは新エンジンを本番で有効化しない。旧方式は追加列を無視して動作できるようにする。切替設定・旧コードは10Hで廃止する前提。
4. バックアップ・復元・再適用/ロールバック手順を文書化。「旧コードが新列を読まない」ことと「DBマイグレーションの逆操作が安全」は別問題として検証。**本番での逆操作・削除を実行しない**。

### D. テストと受入
- 開発DB/ローカルSupabaseで新スキーマを適用し、FK・ユニーク制約・RLS・既存ID不変・複数Case/Opportunity・判断履歴・不確定状態・再実行の冪等性を検証。開発DBの利用ができない場合は代替テストを実施し未検証範囲を明記。
- 応募A/B/C、店舗/商品選択、当落、スルー、通知、地域判定、手動値、購入・コレクションの回帰テストを追加/実行。**重要な履歴破損はゼロ**。
- `lint` / `typecheck` / `tests` / `build` と既存CIを実行。環境依存で未実行の場合は理由・代替・残リスクを報告。必要なら既存テストの失敗と新規失敗を区別。
- 旧方式の精度改善やAI推論の性能は10E以降の評価対象。**10D完了を「新AIの精度向上確認済み」と記載しない**。
