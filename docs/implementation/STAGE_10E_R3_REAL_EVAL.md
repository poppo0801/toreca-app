## 実施手順
1. PR #36 `feat/10e-unified-judgment` に最新mainを取り込む。直近報告書 `docs/reports/2026-11-21-stage10e-accuracy-prep.md` と `docs/AI_REDESIGN_10E_PHASE2_PLAN.md`、評価スクリプト・費用ゲート・`eval/judgment-10e/unseen` のgoldを確認する。
2. **正解を固定**したK01〜K12を実AI評価対象とし、J01・J13を加える。新プロンプト版 `10e.2-r3` を使用。採点用goldはモデルに送らない。Web検索・実ページ取得・本番DB接続なし。J21等、対象外の事例を追加しない。
3. 実行前にAPIモデル利用可否・料金・環境（`TOREMANE_ENV=local`）・キー出所・`JUDGMENT_REAL_EVAL=allow`・既存キー再利用オプトイン・実行ごとの確認を検証する。**既存のキーを使用し、新しいキーを要求しない**。キー値を表示・保存・コミットしない。
4. **上限12円・1事例2円を強制**。見積もりの「全件3回で最大約19.1円」は12円を超えるため、事前予約式のゲートが実行を拒否する場合は**勝手に上限を引き上げず停止**し、何件なら実行可能か・再試行上限を減らす安全な案を報告する。個別の再試行・失敗も同一累積予算で計上し、上限到達見込みで停止。再実行や診断も12円に含める。費用の見積もりと実測を区別する。
5. `scripts/eval-judgment-real.mjs` の既存ゲートを用いて、実AI評価を実施。K群とJ群を区別し、**未見K群の結果を中心に**構造・機会数・関係の正解率、誤統合・誤分割、再判断での修復、保留、根拠なし断定、履歴保護、API回数、費用、遅延を評価。J01/J13は既知の回帰確認として別集計する。採点基準を結果に合わせて改変しない。
6. 既存の台本テストと実AI結果を混同しない。修正が必要なら原因と影響範囲を報告し、**有料の追加実行は累積12円以内のみ**。未見K群の正解を見てプロンプトを修正した場合、その後のK群を「未見」として扱わない。新たな独立ホールドアウトを用意するまで一般化の結論を出さない。
7. 型検査、lint、単体、DB結合、build、CIを確認。結果を `docs/reports/2026-11-21-stage10e-r3-real-eval.md` に記録。実AI未実行・一部のみ実行の場合はその理由と残予算を明記。実データ評価へ進むか、追加修正が必要かの判断材料を整理する。
8. 実装・報告は**PR #36へ追加**し、PR #36は未マージのままレビュー待ち。本番データ評価や10Fは着手しない。
