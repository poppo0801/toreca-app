# Phase 3 — 実行基盤の正確性と実案件の判断改善
起点: main #157 および docs/reports/2026-11-26-phase3-foundation-recovery.md。前回の成果（事前取得、構造化出力、検索接続、地域除外）を維持し、残存する基本欠陥を順に解消する。目的は自律型AIが十分な証拠を自ら調査し、実用的な正しい判断を安定して出すこと。テスト件数や保留率の見かけを目標にしない。
## 承認と運用
- 今回の修正・安全確認・PR/CI・本番反映・実データ再評価を一括で進める。既存キー、家族1世帯、シャドー隔離、自動登録禁止、期限11/28 13:45 JSTを維持。現行収集・登録・通知を維持。
- 現在の日次30円、通算100円、1件10円を起点に、上限に達する/次の必要な試行が入らない場合はClaude Codeがユーザーに直接、対象上限・現状の実費/引当/残額・必要増額・用途を提示し明示承認を得て変更し続行する。ChatGPTへの伝言は不要。承認なしに増額せず、期限延長も別承認。起点・過去台帳をリセットしない。予算不足時も無料の調査・修正は継続。旧文書の固定上限は最新のユーザー承認で更新する。
- 開発に使うClaude CodeのOpus 5.5と、アプリ内APIの調査/判断モデルを混同しない。モデル名、対応パラメータ、価格、利用可能性を実際のSDK/APIと公式仕様で確認。
## 1. F1: 時計の分離
- mainの generate.ts が deps.now（basisClock: 収集時刻に固定）を ResearchTools.now に設定し、research-loop.ts がこれで経過時間を計算している。収集時刻/評価基準時刻、実際の取得・ログ時刻、単調増加する経過時間を独立させる。評価基準時刻を変えて過去案件を期限切れにしない。
- 入口からrunXPostReplay/runResearchまで追跡し、固定基準時刻でも実時間が進み、残時間表示・タイムアウト・取得時刻が正しいことをテスト。Vercelの実行上限、外部呼出しのタイムアウト、残時間による開始可否、キューでの安全な継続を確認。時間切れ0件という旧報告を根拠に差を無視しない。必要なら時間枠内の再開可能な処理にする（大規模な新機構は不要なら作らない）。
## 2. F2: 費用の正確性と上限
- research-ai.ts withOneRetry は合算とコメントするが、失敗時null、再試行後のbだけを返している。各実API呼出し（成功・形式不正・拒否・再試行・例外・検索・画像等）の利用量と費用を一度ずつ記録し、成功した出力に依存せず合算する。料金不明/中断は保守的に引当、非課金が確認できる拒否は0、曖昧なエラーを一律0にしない。再試行も呼出し前に個別の費用予約を行う。実行中の予約が並列処理から漏れないことを検証。
- proposal-job.ts の judgeReserveFor（9,000/1,500）と実際の最大入力/出力、preflightRun の reserveBelowWorstCase が警告に留まる点を確認。異なるモデルの各呼出しの最悪費用、実際のトークン上限・検索/画像費用を用い、日次/通算/1件枠を越える可能性を残さない。必要ならユーザーへ増額を直接申請。
- 前回の約16円の誤計上は履歴を削除せず、確認可能な証拠と追記型の調整記録で訂正できる設計を検討する。実費確認ができないものは推定と明記、勝手に実費を確定しない。既存台帳が適切に使えない場合は予算承認と整合を取る。
## 3. F3: API互換性と推論
- Sonnet 5.5の400拒否（strict有無の両方）を診断から特定。research-ai.ts の output_config.effort=low 固定、強制tool_choice、strictスキーマ、max_tokens、モデルID、SDK/APIバージョン、thinkingとの組合せを公式仕様と実際の要求に照らす。拒否理由の記録が先頭40字で特定不能なら秘密を伏せた有用なエラー情報を残す。最小の実APIリクエストで互換性を確認してから案件を再評価。未確認の原因を決めつけない。
- アプリ内の調査モデル・判断モデルを別々に評価し、適切な推論設定を利用できるようにする。上位モデルなら必ず優れるとみなさず、同じ証拠、基準時刻、出力仕様で判断品質・安定性・費用を比較する。低推論固定が目的達成を妨げている場合は解消。判断失敗時の無目的な繰り返しを避け、適切なモデルを選択する。
## 4. 調査と判断の成果
- 検索が提示されても0回しか使われていない原因を、実際の入力、道具の説明、判断された不足、終了理由、残予算/時間、検索後の流れから特定する。検索利用回数を目標にせず、必要な際に自律的に利用し、取得可能な根拠を集めることを確認。不足を認識した場合に調査へ戻る経路、保存済み情報の活用、ページ内リンク、画像の扱いを精査する。不要な固定ルールは増やさない。
- 初回3件について、案1は実資料にある店舗選択式・応募先・地域適合を正しく理解し登録案に、案2は適切な地域除外を維持、案3は投稿と公式ページの対応・応募機会の実在を追加調査して登録可否を決定する。口数等の任意項目不明だけで保留にしないが、不明を捏造しない。根拠が不足すれば保留の妥当性と調査内容を明示。事例固有の分岐・期待する正解の埋込・検証緩和は禁止。過去版を保全し、同じ入力の再評価結果が消えないことも確認する。
- LivePocket以外の少数の実案件も確認する。根拠の確定を先に行い、実AIを用いた本番共通経路での成果を、コードテストの合格と別に報告する。
## 5. 完了基準・報告
- F1/F2/F3の原因・実装・回帰テスト・本番での確認を別々に明示。現行の正常な機能を維持。最終変更後の型検査、lint、単体、DB統合、関連E2E、build、CI。DB変更ならバックアップ/安全なplan/後方互換を確認。安全を保証できない場合はシャドーのみ停止する。
- 本番実データで成果が未達なら未達とする。具体的な失敗箇所・原因・次の対処を示し、同じ方式の漫然とした再試験はしない。作業中に追加で発見した関連欠陥も自律的に是正する。GitHubへ報告書をpush、PRで共有、既存スマホ通知。指示の矛盾や目的からの逸脱が必要なら報告し、黙って機能を制限しない。
