# Stage 10Z 実装指示：通常収集と新AIの接続・人間承認プレビュー・本番導入直前の検証

作成日：2026-11-22。基点：Stage 10Y 報告 `docs/reports/2026-11-22-stage10y-real-e2e-and-release-gates.md` と PR #92。目標：今まで独立した実験用の10U〜10Y新AIを、**開発・ローカル環境で通常収集の入力から登録案の保存と人間の確認まで**一気通貫で接続し、限定運用を始めるための実証と本番移行案を完成させる。新しい抽象基盤を量産しない。小Stageに分けない。既存の収集・記録・AI・シャドー資産を最大限再利用。

## 実施範囲と安全境界（重要）
今回のユーザー承認は**開発・テスト・PR作成・文書の完成まで**。本番のDB閲覧・変更、migrations適用、PR #84/#86/#88/#89/#90/#92等をmainにマージ、Vercel本番反映、Supabase Cron登録・新機能ON、ユーザー履歴・抽選データの本番変更、**有料Anthropic AI/web_search/X APIの新規呼び出し**は含まない。これらは費用/対象/手順/影響を提示して個別に承認を得る。既存の過去の費用承認枠を再利用しない。
安全な無課金の公開Web読み取りは、現行のrobots・SSRF・アクセス頻度・認証不要の制限下で許可。秘密情報・実投稿本文・ユーザー識別情報をGitに入れない。開発機能OFFが既定。自動登録・通知は一切しない。

## 1. 通常収集→AI→登録案のローカル専用パイプラインを実装
- `src/app/api/cron/collect/route.ts` → `server/collector/run.ts` → 現行の `collection_candidates` / Xエビデンス / `shadow-hook` を調査。**本番旧収集の挙動を変更せず**、この入力をローカル・明示フラグON時だけ10U〜10Yの`planXPost`/`runResearch`に接続するアダプタを実装する。収集済み公開データの再生やローカルDB候補を利用できるようにする。
- 本番の収集が出す構造と新AIが必要とする`post.text`、親投稿のlinkMap、項目内URL・本文範囲、出典/店舗/商品/応募期間・日時の関係が、実際に適切に渡ることをテスト。**既存entity→linkMapの短縮URL展開は再実装禁止**。共通リンクを別店舗へ機械的に流用せず、AI自身が追加調査・意味判断できる構造を維持。
- 同じ投稿内の複数店舗・複数商品、店舗選択式と店舗別独立、応募条件不足、URLなし/終了、重複系列、追加調査中断を通す。公開ページ取得は `live-fetch` の既存安全ゲートを再利用し、外部由来のHTMLや検索抜粋は命令ではなくデータとして扱う。
- **無課金で動作を確認できるようにagent/judge/searchの依存を注入**して、保存済み入力＋モックAI→候補→登録案までE2E。実AIは承認前に呼ばない。判断ロジックを名前一致・系列別固定ルールの過剰な追加で代替せず、自律調査の自由度を保つ。

## 2. 登録案の保存と人間の承認プレビュー
- **既存の`shadow_opportunities`等の追記専用・RLS資産を優先して調査**し、既存テーブルに用途が合うかを正確に評価。用途が違う場合は**開発ブランチのmigration案**を作る（本番適用禁止）。source/リンク/判断根拠、未確認事項、候補のフィールド値、応募単位、同一機会の可能性、取得・判断の時刻、モデル・費用・停止理由、申請者/人間確認状態、元候補を追跡できるようにする。秘密情報と元投稿の不要な複製は避ける。
- ローカルのみの一覧・詳細プレビューまたは既存の候補確認UIへの非破壊的統合で、**人が「保留／修正して承認／却下」できる流れ**を示す。ここでの「承認」は新方式の登録案に対するレビュー記録であり、**自動で`lotteries`を追加・更新しないし、応募/当落/購入履歴・通知に触れない**。明示的な本登録アクションは別の本番承認の段階に残す。UXは既存のトレマネの候補確認に自然に馴染ませ、不要な管理画面を増やさない。
- 候補ID・投稿ID・項目番号・出典URL等を使い、再取得・再評価の際に**応募の機会が失われる誤統合／同一フォームの重複候補の誤分割／同じ登録案の大量重複**を防ぐ。人間の判断/修正をAIが上書きしない。既存のA/B/Cユーザー個別応募・スルー・通知、手動編集を保護。監査ログ・ローカル削除/再起動・停止・再開・費用ゼロモードも検証。
- 既定OFF、ローカル環境と個別フラグが揃うときに限ってプレビューを有効化。本番ブランチに含まれても、誤設定だけで勝手に新方式が有効になることを防ぐ。プレビューと自動登録の区別を維持。

## 3. AI判断の実用的評価を可能にする
- Stage10X A（12件）は検証通過9件でも正答率ではない。**引用が実在するか**と**その引用/ページから候補値・応募単位が実際に導けるか**を分け、人間が閲覧できる記録を残す。誤統合/誤分割/未発見/過剰保留/根拠なし確定を独立評価。
- Cの3 goldと根拠不足6件の分類を引き継ぐ。人間が既存原文・ページ・出典を確認して独立goldを追加できるレビュー手順を用意し、**AIの旧出力や検証通過を正解扱いしない**。十分なgoldが揃わなければ精度を断定せず、現実の有用性を事例ごとに評価する。
- B2はライブの安全な公開取得モードでURLの候補→ページ→応募単位を再生・観測。**検索が有料なら検索APIは呼ばない**。実検索が無い場合は「候補与件の再生」であり自律発見の成功と報告しない。
- Cの予算ミス2度の防止：`preflightRun`による各対象ごとの総額・1件・調査+判断予約、web_search料金、実費超過のテスト。API請求の絶対保証を誇張しない。出力中断の `max_tokens` 改善はmockのみであることを記録。
