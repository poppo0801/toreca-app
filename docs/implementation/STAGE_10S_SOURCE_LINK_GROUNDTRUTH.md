# Stage 10S — 応募先URLの項目単位対応・実データの正解検証

## 目的と背景
Stage10R報告 `docs/reports/2026-11-22-stage10r-flexible-hint-reasoning.md` を前提に実施。Stage10Rは51機会（除外38・非除外13）/55項目で自動登録プレビュー0、暫定候補1、直接根拠0。応募ページ取得15回中4回成功したが、全て別店舗ページで、項目への誤対応9件をscope_mismatchで除外。t.coの11回はrobotsで拒否。人間の正解確認は0。Stage10Sは**プロンプトの追加調整より、正しい一次情報の取得と人間の実データ検証を優先**する。

## 絶対方針
- AIの判断は自由。参考知識は少数・関連する判断観点のみ。系列/プラットフォームに対する結論の固定ルール、単純加点、ヒントの絶対視は追加しない。
- **リンクが取得できたことと、該当応募機会のリンクだと証明できたことを分ける**。リンクがない・不一致・複数候補のとき、他店舗のURLを流用しない。AIの推測やURL文字列の類似だけで確定しない。
- 人間が確認していない推論を正解率に算入せず、確認結果を自動で「正解」登録しない。正解の独立性を保つ。
- 本番DB、マイグレーション108〜113、既存の抽選/応募/当選/購入/通知/設定、PR #36/#46のマージ、本番デプロイ、cron有効化には触れない。ローカル・読み取り専用の検証に限定。

## 実施内容（一括で進める）
1. Stage10Rの現行実装・収集経路・`linkMap`・X投稿のURL entities/展開済みURL・親投稿と項目の分割・`pageMatchesItem`・`investigateStructure`・`decision.ts`・レビューUIを確認し、リンクの出所、親子関係、取得日時、対応根拠が追跡できる形にする。新規収集分において**項目ごとのURLを展開済みの状態で保存し、推論まで引き継ぐ**経路を実際に走らせて検証する。t.coをrobotsに反して追跡しない。既存の保存データに展開URLが無い場合は復元不能を明示し、新しい公開データで検証する。
2. **項目と応募ページのスコープ判定**を強化する。店舗名一致だけを絶対条件にせず、系列・店舗・商品・開催回・応募期間・フォームの対象範囲・URLの発生位置（項目内/親投稿共通）を複数の証拠で照合。共通応募ページや店舗名がページ本文に出ない正当なケースを誤除外しない一方、別店舗・別商品・別開催回の誤対応を防ぐ。マッチ確定/候補/不一致/不明と根拠・反証を記録。項目が複数リンクを持つケース、親投稿に1リンクだけあるケース、店舗別リンクが混在するケースをテスト。複数項目へ同じリンクを流用する際はページの適用範囲を検証し、無根拠の一括流用は禁止。
3. 実際の公開ページ取得を少数の**新規収集データ**でエンドツーエンド実測（X投稿→項目分割→URL展開情報→安全取得→項目対応検査→AI判断→登録プレビュー）。取得不可なら理由（投稿データ不足/robots/認証/消失/URL未記載/スコープ不明等）を分類。公開ページから応募単位、店舗選択時点、店舗グループ、商品別・回別、応募制限を根拠箇所付きで抽出。フォーム送信・ログイン・CAPTCHA回避・robots回避は禁止。新規データが取得できなければ、取得可能な実公開資料で経路を部分検証し、エンドツーエンド成功と混同しない。
4. **実データの人間確認用レビューを実用的に整備**する。Stage10Rの12件に加え、新規データから店舗選択/店舗別/グループ別/商品別/回別/当選後受取/不明等が可能な範囲で分散する10〜20件程度を用意。偏りを満たせなければ不足内訳を明記。原文・応募ページ・リンク出所・AI仮説と代替案・根拠・不明点を1件ごとに示し、ユーザーが「正しい/誤り（正しい方式を指定）/判断不能」を簡単に記録できるローカルUI/出力を整える。**架空例を実データの正解確認に混ぜない**。レビュー資料はユーザーがアクセス可能なローカル出力として生成し、実データ/個人情報/非公開URLをGitにコミットしない。
5. **人間の確認を勝手に代行しない**。確認が未実施ならレビュー待ちの件数と操作方法を報告し、正解率・再現率等は未測定と明示。人の確認後にのみ、応募単位・店舗/商品/回の独立性・受取選択時点の一致率、誤った統合/分割、false auto-register、false exclusionを評価できる仕組みを作る。正解データの保存は根拠・確認者・日時・訂正履歴を持たせ、AI未検証の自己強化を禁止。
6. 応募単位以外の阻害要因（TCG不明4/混在3、重複疑い3、地域不明2、系列欠落/未確認2、応募先欠落1、複合理由）を実例ベースで分類。一次情報で解決できるもの、商品/系列/地域マスターの不足、AI抽出の誤り、真に人間判断が必要なものを分け、改善策と期待影響を示す。既存のマスターを無断で変更せず、推論で勝手に既存抽選を統合/分割しない。
7. **同じ51機会/55項目の10P→10Q→10Rとの比較**と、新規収集データの評価を**別表**にする。応募先リンク取得率、項目スコープ適合率、直接根拠あり件数、応募単位分布、確認待ち、暫定候補、自動登録プレビュー、阻害理由、AI費用を記載。母数や取得条件が異なるものを単純比較しない。少なくとも別店舗リンク誤対応・共有フォーム・店舗名非掲載・短縮URL取得不可・同一系列別開催回・同名店舗・情報欠落の回帰テストを行う。
8. 型・lint・build・単体・DB統合・CIを確認。既存のSSRＦ/robots/リダイレクト/タイムアウト/回数制限、非公開情報遮断、冪等性を保持。API費用/公開ページ取得のハード上限をStage10R同等以下に設定（AI最大90回、¥50、公開ページ最大60取得、対象最大30件、1件¥3予約）。上限超過前に停止。実データやAPI鍵はGitに残さない。
9. `docs/reports/2026-11-22-stage10s-source-link-groundtruth.md` に、実測と仮説、取得成功/失敗、誤対応防止の実例、レビュー資料の場所と実行方法、**人の確認が必要な事項**、10P〜10Rとの比較、費用、安全確認、次段階の推奨を記載。小刻みな承認を求めず、実施可能な範囲を一括実装・検証・報告する。

## 完了基準
「URLがある」ではなく「その応募機会の根拠である」と確認できる収集・対応経路を実データで示す。AI推論の自由度は保ち、実データに対する人間の検証導線を用意する。人間の確認未実施なら精度は主張せず、次の人間作業を明確に示す。**本番反映の判断は別途承認を待つ。**
