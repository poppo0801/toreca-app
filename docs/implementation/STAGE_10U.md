# Stage 10U 実装指示：応募情報の取得・自律調査・登録判断の接続と実例評価

作成：2026-11-22／状態：ユーザー採用方針に基づく正式な実装指示書（**本番稼働・実課金実行・本番DB適用は未承認**）

## 0. 目的と優先順位
AIが抽選情報を実際に読めることを出発点に、**情報取得→証拠と事実の整理→AIの仮説→必要時の自律追加調査→調査終了判断→独立した登録判断→安全検証→開発用プレビュー／候補保存**を一本の検証可能な流れとして実装する。登録済みの案件も必要なら新証拠に基づき再評価できるようにする。

**AIの意味判断を固定ロジックで上書きしない。** 固定処理は安価な索引・整形・キャッシュ、根拠の検証、費用・権限・履歴の保護、停止・復元を担当する。LivePocketその他のサイト名や今回の例を決め打ちの判定ルールにしない。実際の有効な応募機会を、早く、正しく、費用を抑えて把握することが目的。確認待ち件数を減らすだけで誤登録を増やさない。安全側に保留しすぎて応募機会を失うことも成果としない。

このStageは**開発環境での一体的実装・検証**を対象とし、本番の通常収集・DB・Cron・Vercel設定や既存のユーザーデータを変更しない。実装PRはレビュー待ちとし、マージや本番反映は別承認を受ける。

## 2. 情報取得とAI入力の接続
- Xの元投稿・スレッド・画像、公式サイト、公開応募ページ、Googleフォーム、LivePocket、関連イベント、過去の原文・調査履歴を、出典・取得日時・項目スコープを保った共通の観察データに整理する。URLの発見・展開から応募項目への紐付けまで追跡し、親投稿URLを別店舗の応募URLに無根拠に流用しない。
- Stage 10Tの**ページ内受付枠と「同じ販売元のイベント」の区別**、店舗・商品・開催回・選択タイミング・横断応募制限の実際に取得できた情報を再利用。ページのHTML／描画構造→抽出事実→AI入力→AI解釈→登録案を事例ごとに可視化する。入力が欠けた失敗と、入力はあったがAIが誤解した失敗を分離。
- サイトごとに必要な取得アダプタを設けても、判断そのものはサイト固定ルールに委ねない。robots・CAPTCHA・ログイン・認証制限・SSRF対策・レート制限を回避しない。見えない情報は確認済みと書かない。取得不能と未取得と読解失敗を区別。
- 既存の9Z原文・取得結果・同内容のハッシュ・人間の訂正を検索再利用し、同一原文の反復解析を避ける。個人情報・秘密情報は収集・AI送信・ログへの出力を防止。

## 3. AIの仮説形成、検証と自律追加調査
- AIは応募機会の実在性、応募単位（独立した応募／当選権利・状態追跡）、店舗選択タイミング、商品・回、期限、条件、系列、重複関係を統合的に推論。**観測事実／推論／不明**、根拠の箇所と適用範囲、反対仮説、重要な不明点を明示し、複数ソースが単なる転載なら独立の裏付けと数えない。
- AI自身が「何を追加で調べるべきか」「どの手段・情報源が有益か」を選ぶ。X投稿へ戻る、公開応募ページ、同系列の関連告知、公式店舗ページ、商品／店舗名での検索等はヒントであり、必須順序や固定の5工程ではない。
- 必要性は **誤判定した場合の被害（応募漏れ、重複、誤通知、地域誤り等）×不明点の重要性×情報獲得の見込み×締切までの時間×費用** の観点で理由を出す。機械的なスコア・固定項目チェックリストで意味判断を置き換えない。
- AIの自己評価だけで結論を確定しない。根拠の実在、項目との対応、出典・時点、矛盾、権限・履歴ガードを別層で確認する。不足・不整合があれば理由をAIに返し限定的に再評価させ、別の固定意味判定器で結論を黙って上書きしない。
- 既存の履歴・判断メモリを検索して、訂正済みのAI推測を正解として再利用しない。人間の確定情報と既存応募・当落・購入・スルーを保護する。

## 4. 調査継続・終了・監視・再開
**「調査終了」と「登録可否」と「更新監視終了」は別々の判断と状態**として扱う。
- 重要な不明点について、新しい証拠獲得が見込め、時間と費用に見合う場合だけ調査を継続。十分な根拠がある、進展しない、同一取得失敗が続く、情報源にアクセス不可、締切・時間・費用上限に達した等の場合は調査を終了し、その時点の証拠で別途登録判断を行う。
- 同一URL・同一本文の無益な再取得、転載の巡回、取得不能なXへの反復アクセスを抑止する。取得履歴、内容ハッシュ、時点、失敗原因、試行費用、進展の有無を記録。AIが次の調査方法を変更する余地は残す。
- 調査終了後でも、新しい公式告知／応募URL、ページ更新、ユーザー訂正、締切接近による重要性変化を契機として**必要な部分だけ再評価**する。ただし締切接近のみで同じページを際限なく取り直さない。更新監視は価値・応募期間・費用に応じて終了できる。
- 本登録済みでも不足情報（発表日等）の後日補完を検討。重要な更新で通知や応募状態が変わる場合は冪等性と履歴保護を確保。定期発見の予算を追加調査が枯渇させない。
- AIの調査裁量は維持しつつ、システム側で回数・同時実行・経過時間・トークン・費用・再試行・ループと緊急停止を強制。既存上限を黙って変更せず、費用が不明な処理を0円扱いしない。再開時も上限を回避しない。

## 5. 登録判断（本登録／暫定候補／除外）
- **情報が全項目揃うことは本登録条件ではない。** 「応募機会が存在する根拠」「利用者が正しく応募行動できるか」「誤登録時の被害」「不明点が登録判断に影響するか」をAIに総合評価させる。項目ごとに未確定値・根拠を保持し、無根拠な推測を確定事実として書き込まない。
- 例：発表日だけ未確認で応募先・商品・期間・応募単位に十分な根拠があるなら本登録を検討。店舗別受付か店舗選択式かが不明で応募漏れ・誤統合に直結するなら調査や暫定候補を優先。住所不明でも地域が確認できるなら登録可能な場合がある。応募URLが直接得られなくても信頼できる公式の応募案内へ到達できるなら案件ごとに判断。**いずれも固定ルールではなく評価例**。
- 本登録に必要な根拠の水準は、情報項目そのものではなく誤った時の影響に応じて変える。軽微な不明点による過剰保留と、根拠不足の早期誤登録を双方評価。
- 独立した応募機会と表示カードを混同しない。店舗別応募を誤統合して機会を消したり、店舗選択式を店舗ごとに誤分割して重複応募を促したりしない。Case/Opportunity/View/User recordsの論理分離を守り、既存ID・A/B/Cの応募／通知／購入記録を推測で付け替えない。
- 登録・補完・統合・削除の実行前に共通の根拠検証、世帯RLS・権限、履歴保護、重複操作防止を通す。AIは意味判断と提案、システムは実行の安全性を検証。自動破壊的統合・履歴移動・ユーザーの確定値上書きは禁止。安全検証に失敗したら具体的に保留し、架空の別結論に置き換えない。
- 暫定候補のままでも応募機会の兆候をユーザーが把握できるようにし、必要な行動・不明点は明示する。実行上の新しいUIは本Stageに無断混入せず、開発用の表示／プレビューで評価する。既存の本番公開画面は変更しない。

## 6. 検証設計・達成条件
**実際の公開抽選の根拠を中心**に、同一入力で旧／新の発見力・取得率・判断精度・登録判断・所要時間・正確な応募機会1件あたりの費用・確認待ち・人手負担を比較。mockテストや自動生成正解データを実AIの精度証明としない。
1. 「取得できたか」「AI入力へ渡されたか」「AIが正しく意味判断したか」「登録・除外・暫定候補が適切だったか」「安全検証で何が止まったか」を分離して追跡。誤判定ごとに**取得欠落／抽出・スコープ誤り／AI推論誤り／登録判断誤り／実行層の誤り**を分類。
2. LivePocketの単一受付、複数店舗枠、関連イベントの別ページ、明示的な横断制限、商品・開催回別、当選後受取店舗選択に加え、Googleフォーム、公式サイト、X起点、地域、系列・商品名揺れ、重複、期限変更、公開後の更新、会員限定・取得不能を含める。既存10Sのユーザー30件レビューは、実際の回答が取得できた範囲で分析。**元URL不明・人間未確認の例は正解率の分母に入れない**。
3. 本登録したものだけでなく、**確認待ち／暫定候補／除外／見逃した抽選**を集計。「安全側の過剰保留」「根拠不足の早すぎる本登録」「調査無限延長」「調査終了後の再開不能」を失敗として検出。推論が偶然正しくても根拠が無ければ適切な判定としない。
4. 正解データは人が検証した原文・公開フォーム・画像から別管理。旧方式の出力・AI自己申告・保存済みAI回答を正解扱いしない。入力とgoldを隔離しAIにgoldを渡さない。実例不足、実X API不可、ブラウザとの一致未確認はそのまま未検証と報告。
5. **相殺不可の安全条件**：重大な応募機会誤統合、ユーザー履歴破損、権限逸脱、費用上限突破、停止不能ループ、重大な通知重複・欠落、秘密情報漏洩がテスト対象内でゼロ。既存応募・当落・通知・購入・地域除外・A/B/C・継続抽選の回帰を確認。
6. 合格数値を捏造しない。初めに測定可能な旧方式ベースライン・評価対象母数・母集団の限界を示す。実AIの精度・費用については**有料API利用の具体的承認が無い限り実施せず「未検証」**とする。重大な性能低下があれば原因を報告し、比較指標・受入判定の案を示す。
7. lint／typecheck／単体／DB統合／E2E／build／PR CIを順に確認。開発用のローカルSupabase・架空DBで安全な再生を行い、外部サイトは公開範囲の読み取りに限る。

## 7. 実装順序・既存PRとの境界
- 最初に、10E（PR #36）・10F（PR #46）・10Tの**実装状態と依存先**を監査し、再利用／未接続／未マージを表にして報告書へ。**「10Tの指示書が存在する」だけでは10T完了と断定しない**。欠けている実装は必要な範囲で開発ブランチに取り込み、依存PRは勝手にマージしない。
- 可能であれば「取得→AI入力→判断→追加調査→登録案→安全検証」を同一開発フローに接続。対象ブランチの機能と未マージ依存を混同せず、テストだけのmock接続と実運用接続を明確に区別する。通常収集を本番切替する操作は実施しない。
- ユーザーが既に合意した目標設計を、現行コードの制約を理由に縮小しない。大規模な新DB構造・追加コスト・基本設計変更が必要なら影響と代案を記し**承認待ち**。技術的に合理的な非破壊開発は一括で進め、細かな確認を求めない。
- Stage 10Uの作業を、PR #36/#46の未承認マージ・本番DB migration108以降の適用・実AI本番有効化・本番ユーザーデータのAI試験の許可と読み替えない。既存の開発用AI gateと本番操作入口を維持し、本番秘密鍵を開発環境に移さない。

## 9. 完了判定と次の着手条件
- 開発環境において、実際の公開情報からAIに渡す証拠と登録案までが追跡可能で、必要時の再調査・終了・監視・再開と登録判定の独立性をテストできる。
- 根拠付きの実例で、少なくとも**取得の問題と推論の問題を切り分け**、重大な誤統合・履歴破損・費用制御等の回帰がないことを示す。正解例が不足すれば数字を盛らず限界を記載。
- 実AI／X起点の実データE2E・本番実用性が未検証なら完了の範囲を限定し、ユーザー承認が必要な次の実測段階を提案する。
- **本番登録・デプロイ・旧方式廃止は本Stageの自動実行範囲外**。前段の未マージPRの整理と段階的な移行計画を提示したうえで判断を待つ。
