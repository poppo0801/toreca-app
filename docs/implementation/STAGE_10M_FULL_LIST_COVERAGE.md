## 一括実装・検証
1. `feat/10f-shadow-integration` に最新mainを取り込み、既存Stage10Lの画像検証、公開ページ処理、旧方式の非干渉を保持。**収集元→候補抽出→一覧分割→機会判断→重複判定→保存／シャドー**を実際のコードで追跡し、どこで最初の項目だけに限定されるかを明示。旧本番方式と新シャドーの違いを報告。
2. **一覧全体を対象とする発見処理を実装**：一つの投稿に異なる系列・店舗・商品・開催回・URL・締切が複数ある場合、全項目を漏れなく列挙し、出典の原文範囲と親投稿ID・一覧項目番号を保持。単なる行数・商品数を機会数と混同せず、各項目について「独立抽選」「同一応募で複数商品」「店舗選択式」「複数店舗別応募」「判断不能」を根拠に基づいて判定する。ひとつの抽選で複数商品を選ぶ構造を不必要に分割せず、別系列・別店舗・別開催回を安易に統合しない。情報不足の項目も捨てず候補として保持し、明確な非抽選は除外する。画像・公開リンクを各項目の出典に正しく結び付ける。
3. **長文・大量項目の堅牢性**：段階的な分割・小バッチ・再試行・処理済み項目の再利用、項目ごとの状態（完了／保留／失敗）、カバレッジ照合を実装。モデルの出力件数だけで完了判定しない。途中で予算・回数上限に達した場合、未処理を明示して安全に再開できるようにし、処理済み分を重複課金しない。ハードなAPI呼び出し回数上限を追加し、**画像文字起こし、再試行、再評価をすべて合算**して上限を超える前に停止。費用上限も併用。
4. **実データ#1を必須回帰テストに**：ユーザーの#1は8項目の一覧。最低限、8項目を独立に発見・追跡できることを検証（ただし8応募機会と決めつけない）。各項目の系列・店舗・商品・応募方法・応募単位・日時・根拠・保留を確認し、全8項目が処理済みか保留かを明示。別の複数系列一覧、同一系列の複数店舗、同一応募の複数商品、単独告知、非抽選、リンク・画像中心の告知も検証。新規ホールドアウトは開発・調整に使った後は独立評価として数えない。人による少数の正解確認が未完なら正解率を主張しない。
5. **ローカル確認画面を改善**：一覧は親投稿の下に全項目を分けて表示し、各項目の原文範囲・店舗・系列・商品・応募方法・応募単位・期間・AI判断・根拠・未解決事項を並べる。項目ごとに「妥当／誤り／判断不能」を付けられるようにし、親投稿全体の「全件発見／不足／判断不能」も別途評価。acceptedは処理成功であって正解ではないと明記。人の確認を大量に要求せず、#1と代表的な数件で十分に問題が発見できる画面にする。確認結果はGit管理外。
