# Stage 10I：一覧投稿の分割処理・対象案件への焦点・精度検証

## 背景・目的
`docs/reports/2026-11-21-stage10h-improvements.md` を参照。Stage10Hは自己照合質問13→4、高重要度質問39→25、公開ページ取得後のunknown 3→1など改善した一方、一覧投稿が長いと出力上限9,000トークンでも途切れ、対象案件1件の検証なのに一覧全体を応募機会として展開した。再実行に約11円を消費し、正解率は未測定。**新システム移行を急がず、この問題を解消してから限定運用を判断する。**

## 実装・検証を一括して進める
1. `feat/10f-shadow-integration` に最新mainを反映。10Hの入力設計・保留基準・公開ページ取得は維持し、既存の判断器と実データ評価を再利用。不要な追加承認や細かな往復を作らない。
2. **一覧投稿の事前分割**：一投稿に複数の独立告知がある場合、本文の見出し・店舗・日付・応募リンク等の根拠を保持して、小さな塊（目安5〜8項目、出力量に応じて動的調整）に分けてAI判断する。1件の巨大JSONを要求しない。各断片に原文の引用位置・共通注意書きの対応を持たせ、全体での重複排除・関係判断を行う。断片ごとの誤分割や共通条件の脱落を検証する。
3. **対象案件に焦点**：再判定対象の `currentCase` と原文の項目を照合し、対象に関係する告知・応募機会を優先して評価。無関係な店舗・開催回・商品を勝手に対象案件へ追加しない。一覧全体の新規発見が必要なら別の候補抽出タスクとして明確に分ける。対象が一意に特定できない場合は理由を残し、推測で結び付けない。
4. **出力途切れ対策**：長文/多機会のときに分割・縮約して再試行し、同一巨大リクエストを繰り返さない。リトライ回数・トークン・費用上限を守り、部分結果が有効なら採用して失敗箇所だけ再試行。引用の実在確認・店舗関係の整合・原文の不足情報を推測しないルールは維持。
5. **少数の正解データ**：10G/10Hの同一28件のうち、単純告知・一覧・店舗選択式・商品別・unknownを含む代表的な少数（目安8〜12件）を、公開告知原文と保存済み登録値を混同せず根拠付きで独立にラベル化。AI自身が出した答えをそのまま正解にしない。人の判断が不可欠な曖昧なものは判定不能として別扱いし、無理に正解を作らない。比較可能な構造・応募機会・対象案件対応・誤統合/誤分割を測る。**正解ラベルを十分に確立できない場合は正解率を主張せず、確認可能な一致と未確定を報告**。
6. **再評価**：10Hと同一対象の一覧投稿を優先して、分割前後の出力完走率、対象外機会の混入、unknown、未解決質問、引用検証、誤統合/誤分割疑い、費用・遅延を比較。10Hのフェーズ1が混合版だった点や追加取得による情報差を明示し、同条件比較を優先する。軽微な改善で数値だけを良く見せない。
7. **収集原文・画像の取得品質調査**：X/t.coアクセス制限の回避をせず、既存の保存原文が短くなる原因と、公開ページ本文・画像説明・既存取得経路で得られる情報を調査。実装可能な低リスク改善は同工程に含めてよい。画像解析は費用・著作権・プライバシー・取得元を考慮し、公開で取得可能な素材だけを扱う。新たな外部サービスや有料APIの導入はしない。36件のXのみ対象を取得できたと見なさない。
8. **実行条件**：本番DBへの書き込み・既存データ更新・統合・削除・アーカイブは行わない。実装PR #36/#46のマージも行わない。既存Anthropic APIキーと既承認の公開告知の伏せ字・漏洩検出・保持リスク受容を流用。追加実AI評価の上限は**50円、30対象、90呼び出し、公開ページ取得60回、1件3円**。機密漏洩・無限再試行・予算超過を防止。ローカル保存済みデータを再利用し、本番の読み取りが不要なら行わない。
9. **成果物**：`docs/reports/2026-11-21-stage10i-batched-list-evaluation.md` に変更点、再評価の実測、一覧の対象案件対応、正解ラベルの独立性と比較可能範囲、未解決問題、費用、限定運用へ進めるかを記載。Gitに原文・内部ID・秘密情報を載せない。変更部分のテストを実施し、不要な承認票を増やさない。

## 判断の優先順位
目的は**実用的に正しい抽選カードを少ない手間で作ること**。保留率を見かけ上減らすことや全情報を無理に分割することではない。新方式の自律性を高めつつ、応募・当選・購入履歴の保護と誤統合防止を維持する。
