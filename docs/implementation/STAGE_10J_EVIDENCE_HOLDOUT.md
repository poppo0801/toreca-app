# Stage 10J：収集証拠の保存改善・一覧の取りこぼし防止・未知データ評価

## 背景
`docs/reports/2026-11-21-stage10i-batched-list-evaluation.md` を参照。10Iでは一覧78項目の処理完走、対象案件の焦点改善、判断失敗0。ただし暫定ラベルはAI作成17件・開発に使用したため未知データの精度は未測定。保存原文179件中、展開済みリンク92件・取得済み画像70件。公開ページ41件中22件は本文120字未満。画像から読んだ情報は後の再判定へ渡っていない。別店舗の同一内容の一覧項目を集約する危険がある。

## 目的と進行
**Stage10Jを一括実装・検証し、新AIを本番の書き込みなしシャドーに進めてよいか判断できる材料を揃える。** 本番DBへの更新・登録・削除・統合・マイグレーション、実装PR #36/#46のマージは行わない。ローカルでのコード実装と検証を行い、本番反映は別判断。

1. `feat/10f-shadow-integration` に最新mainを取り込み、10Iまでの機能を再利用。既存の通常収集パイプラインで、公開告知の**原文・展開済みリンク・取得済み画像由来の説明/読み取り内容**がどこで失われるかを追跡する。外部AIに再送信する本文は公開告知だけ、伏せ字・漏洩検出を維持。
2. **収集証拠の品質改善**：公開ページの要約・ボタン文言だけではなく、既存の安全な取得部品で本文/詳細告知を優先。保存済みの展開済み公開httpsリンクを活用し、X/t.coや認証・robots制限は回避しない。取得できた画像のAI解析結果が既に存在する場合、出典・画像由来の区別・引用可能性を保持して判断へ渡す。画像の追加解析が必要な場合は、既存の処理で許容される公開素材に限定し、費用上限内で行う。新たな有料APIやサービスは導入しない。本文と画像由来情報を混同しない。**保存形式の変更は互換性と移行影響を確認し、ローカルで実装・テストまで**。本番データへの書き込みはしない。
3. **一覧の誤集約防止**：店舗・開催回・応募先・商品・締切の根拠を保持し、同一文面でも別店舗・別開催回の独立応募権をまとめない。単なる同文重複は根拠があるときのみ統合。対象案件への焦点と一覧全体の候補発見を分離。10Iで7項目→2機会となったケースを重点回帰テストし、実際に7機会か2機会か根拠不足なら保留して報告する。
4. **未知データの検証**：10Iの開発・ラベル修正に使っていない新しい公開抽選事例を、単純・一覧・店舗選択・商品別・開催回別・曖昧を含めて可能な範囲で選ぶ。ラベルは原文根拠と別の検証経路で作り、既存登録値や新AIの出力を正解として流用しない。人の確認なしなら「独立の暫定ラベル」と明示し、正解率とは呼ばない。人が確認しなければ解決できない曖昧さは未確定として区別。開発用と検証用を分離し、検証データを見て修正したらそのデータは開発用へ移し、別の未知データで再検証する。
5. **実測比較**：10Iとの比較で、入力の情報量・公開リンク取得成功・画像情報の引継ぎ・構造unknown・応募機会の対応・店舗/開催回取りこぼし・未解決質問の質・引用整合・処理失敗・費用/遅延を集計。正解が不足なら誤統合・誤分割の具体的な疑いと未検証を報告。数値をよく見せるための推測確定や保留隠しは禁止。
6. **安全・費用**：既存Anthropic APIキー、既承認の公開告知送信条件を流用。実AI追加評価は**合計50円、対象最大30、AI呼び出し90、公開ページ取得60、原則1件3円**。画像再解析を含め上限を厳守。API費用の異常、無限ループ、情報漏洩、本番DB変更を防ぐ。ローカルの保存済みデータと取得可能な公開ページを優先し、追加本番読取が必要なら最小限・SELECTのみ。個別の承認票や全件目視の儀式は増やさない。
7. **本番シャドー準備の評価**：本番サーバレスでは10Fのローカルシャドーフックをそのまま有効にできない。非同期キュー/実行寿命・予算/緊急停止・旧方式からの完全分離・機密情報・監視を踏まえ、**書き込みなし本番シャドーの実装方針と必要な変更を提案**する。実際の本番有効化はしない。重大な誤統合・誤分割が疑われるなら保留理由を明記。
8. **成果物**：`docs/reports/2026-11-21-stage10j-evidence-holdout.md` に実装差分、未知データの独立性、検証可能な精度と限界、収集証拠の改善、費用、残課題、本番シャドー移行の可否と最短の次工程を記載。Gitに原文・内部ID・URL・秘密情報を含めない。変更範囲のtsc/lint/テストを実行。

## 優先順位
過度なゲート・人手チェックより、実用的な自律収集と正確な応募機会の判定を優先。ただし履歴の保護、誤統合の防止、秘密情報とAPI費用の管理は維持する。ユーザーが別途希望しているUI変更は本Stageの対象外とし、別ブランチで扱う。
