# Stage 10R — 自由なAI推論と参考知識の適用検証・応募先調査

## 背景
Stage10Q報告 `docs/reports/2026-11-22-stage10q-ai-apply-unit-inference.md` を参照。51機会中38除外、非除外13、12仮説（11 store_select・1 one_form_one）、直接根拠0、自動登録プレビュー0、暫定候補1。経験則による店舗選択式への偏り、応募先ページ取得0、人による正解確認0が課題。10Q最終の`K-RULE-NO-CROSS-STORE`変更後の再評価も未実施。

## 中核原則（固定ルールへの回帰を禁止）
- **推論は自由、実行は安全制御**。参考知識は判定命令・強制重み・許可リストではない。AIは関連するヒントを採用・反論・無視・再解釈し、未想定の応募方式や新仮説を提案できる。参考知識と結論が異なるだけで差し戻さない。
- 「多店舗系列＋店舗受取⇒店舗選択式」「LivePocket⇒1店舗」などの条件分岐、加点スコア、プロンプト内の結論強制を設けない。**今回の具体的な情報が過去の傾向より優先**。情報が無いことは否定根拠にしない。
- **ヒントは判断観点**として表現する。「この条件でXを検討し、YやZの可能性も確認する」「適用の前提」「反例」「何を確認すると区別できるか」。過去の確認済み実例・ユーザー提供の一般的経験則・AIの未検証仮説を区別。
- 複数仮説の比較は曖昧なケースでのみ柔軟に行う。全候補を機械的に列挙する義務はない。明確な告知では簡潔に決められる。応募の独立単位・店舗選択の有無・選択時点・店舗グループ・商品/開催回を混同しない。
- AIの未検証推論を「正解」として知識ストアへ自己増殖させない。人の訂正（理由つき）や独立した一次資料で裏付けた事例を区別して蓄積。人が訂正した内容も絶対ルール化しない。

## 実装・評価を一括実行
1. `feat/10f-shadow-integration`（PR #46）上のStage10Q実装を起点に、最新mainの指示書を取り込む。現行の`knowledge.ts`、`apply-unit.ts`、`ai-unit.ts`、`decision.ts`、`investigateStructure`、`linkMap`、収集パイプラインを確認し、旧ルールの隠れたバイアス・固定判定を点検。既存手動確定や保護データは変更しない。
2. 参考知識を「結論の推奨」から「適用条件・確認観点・対立仮説・反例・反証条件・情報源の信頼度/確認状態・更新日」へ再構成。関連する系列/プラットフォーム/方式のヒントのみを少数選択。選択した理由と適用条件を満たすか/不明かを記録。**条件未確認のヒントを既知の事実扱いしない**。無関係な一般知識を毎回大量投入しない。ユーザー例：LivePocket・イトーヨーカドーのグループ別例外・ドラスタ・竜のしっぽ・他店舗同時応募禁止・多店舗系列の店舗受取・ヨドバシ当選後選択を保ち、具体的な対象条件を精緻化する。
3. 推論を「今回の観察事実抽出 → 関連ヒント取得 → AIの自由な仮説と必要な対立仮説の比較 → 必要なら追加調査 → 最終判断」に整理。結論と支持/反対/不明な根拠、採用/無視したヒントと理由、選択時点、独立応募回数、確信度、調査必要性を構造化。AIの自由な仮説は受け付け、未知の方式は既存型に無理に押し込まず安全な暫定状態にする。明示根拠の機械検証は維持し、根拠にない断定を防ぐ。
4. **応募先ページの取得を実動作させる**。10Qで0件だった理由（保存済み一覧に応募リンク無し）を調査し、実際の公開情報から応募URLの抽出・短縮URLの安全な展開・`linkMap`接続・`investigateStructure`への受け渡しを検証。X等の元投稿から取得不能なら原因を分類し、公開で取得できる代替の告知/応募ページを限度内で探索する。応募先フォームの選択欄、店舗別URL、応募制限、グループ分割、応募時/当選後の受取方法を観察。ただしログイン・CAPTCHA回避・応募送信・非公開データ取得は禁止。公開ページが取得できなかったら「未確認」として扱い、推測で埋めない。SSRF/robots/リダイレクト/取得深さ/時間制限を厳守。
5. **偏り検証**：10Q最終知識修正を反映し、同じ51機会/55項目で比較。単位推論の内訳（特にstore_select集中）、根拠別、暫定候補、確認待ち、除外、自動登録プレビュー、他の阻害理由を10P/10Q/10Rで比較。さらに①ヒント無し②関連ヒントのみ③無関係ヒントを意図的に混入、の比較で結論の不当な誘導を測る。ユーザー例と反例を実告知優先で検証。少数の架空ケースはテスト用途と明記し実測の正解率に混ぜない。
6. **人の検証**：実データから10〜20件を、店舗選択/店舗別/店舗グループ/制限記載/受取時点/情報不足に偏りなく抽出し、ユーザーが判断・訂正しやすいレビュー資料を生成。人の確認が無ければ正解率は出さず、「人による検証待ち」と報告。人の訂正を理由付きで知識へ取り込む導線を確認するが、ユーザーの確認前に勝手に正解登録しない。
7. **応募単位以外の阻害要因**：TCG不明・混在、地域不明、系列欠落/未確認、重複疑いを観察し、根拠のある追加調査で改善可能なものは調査する。応募単位の仮説だけを解消しても自動登録0の原因を分解する。既存の地域設定・系列/店舗マスターを勝手に拡張・上書きしない。
8. **安全境界**：実装PR #36/#46のマージ、本番DB/マイグレーション108〜113の適用、本番デプロイ/cron、本番書き込み、抽選・応募・当選・購入・通知の更新/削除は行わない。ローカル/非書込シャドープレビューまで。AIには個人情報を渡さない。再試行を含め費用とページ取得のハード上限を設定（Stage10Q相当を基準：AI最大90回・¥50、公開ページ最大60取得、対象最大30件、1対象¥3予約。超過前に停止）。実原文/URL/ID/鍵をGitに含めない。
9. 型・lint・build・単体・DB統合・安全境界・冪等・根拠の実在・知識の適用条件・ヒント無視/反論・反例・未知方式・URL取得不可・取得上限・プロンプト誘導をテスト。レポートを`docs/reports/2026-11-22-stage10r-flexible-hint-reasoning.md`に作成し、変更点、実データ比較、偏り、応募先取得成功率、費用、人手未確認事項、次の判断を記載。CI状況も確認する。細かい承認を求めず可能な範囲を一括実行。

## 完了条件
固定ロジックを増やさず、AIが経験則を参考として採用・反論・無視できることを反例で示す。実際の応募ページ取得が成功したか/失敗した理由を実測で明示し、推論の改善を正解率と取り違えない。本番反映は別途ユーザー承認を待つ。
