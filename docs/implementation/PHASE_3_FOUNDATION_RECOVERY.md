# Phase 3 基本機能の立て直し
起点: main（#152報告書）。ユーザーは予算引き上げと早急な根本修正を承認。初回3件の成功条件は根拠で支持される利用者向け判断（案1登録、案2除外、案3は追加調査で登録可否を確定）。正解の強制や事例固有ルールは禁止。
## 運用境界
既存キー、家族1世帯、自動登録禁止、現行の情報収集・登録・通知の継続、試行期限11/28 13:45 JSTを維持。費用上限は日次30円、通算100円（既支出29.01円を含む、起点リセット禁止）、1候補10円とする今回の実務上の設定。予算を使い切ることが目的ではない。期限延長・更なる増額・新規キー発行は不可。永続引当と多重実行防止、失敗・中断時の課金記録を維持。設定変更だけでなく実際の全階層の上限（許可証5円、run cap、予約・モデル・検索等）を調べ、矛盾をなくす。通常稼働が予算を消費する場合はシャドーのみ制御。安全確認後の通常PR/CI・本番反映・残予算内の少数実評価まで一括で進める。
## 1. 現行とAIの比較、テストの欠陥監査
現行の実際の収集・解析・登録経路とAIの経路を同じ実候補で照合。動作している取得・正規化・地域判定・保存などの共通基盤を再利用する。固定ロジックを全面的に再実装したり旧方式を正解扱いしたりしない。#152の各欠陥がテストを通過した理由（fixtureの偏り、モックの出力保証、入口の差、判定項目・結果保存の欠落等）をコードとテストから特定し、実際に再現する回帰テストを追加。モックではAIの精度を証明できないことを明記。既知の欠陥を一覧化し、重大度・原因・修正・本番確認の状態を追跡する。事前検証を無限に拡張せず、少数の実データで成果を確認。
## 2. 出力処理の安定化を最優先
fields_string / invalid_fields / agent:invalid_next の発生経路、実際のAPI stop_reason、tool_useの構造、スキーマ、SDK、出力上限、使用トークンを確認し、形式不正と推論失敗を分離。値・秘密を不用意に記録せず、型・長さ・終了理由など診断を十分残す。プロバイダの構造化出力・厳密なツール入力スキーマ等の利用可能性を実際のモデル/SDKで検証。正当な形式揺れの安全な解釈、必要時の限られた再試行、検証済み部分の保持、失敗理由の明示。失敗した再確認で成功済み出力を消さない。壊れたJSONの恣意的補完、根拠の緩和は不可。修正が確認されるまで同じ入力の無目的な有料再試験を繰り返さない。
## 3. 情報取得・全文保存の共通基盤
カード候補の取得元ページを収集段階で取得・保存しない経路を調査し、安全な既存取得機構を共通化。取得元URL・応募先URL・遷移の由来を区別し、必要な公開ページ本文、リンク、取得時刻、画像参照、失敗・切り詰め理由を永続保存してAIが利用できるようにする。既存収集に必要な追加取得/保存の変更は許可するが、既存登録・除外・通知の判定方針は変更しない。現行の収集が追加取得の失敗・遅延に巻き込まれない非同期化/独立処理を検討。重複取得回避、鮮度、SSRF・robots・公開情報・秘密保護・サイズ/時間・頻度上限を維持。保存済み情報を再利用でき、短文や取得不能な場合は自律的な追加取得へ進めることを実証。実際の取得/保存/提示/読取の量と由来を確認する。 
## 4. 調査・判断能力の改善
- 安全な限定検索を承認済み上限内で本番共通経路へ接続。既存の検索・取得・画像の能力を最大限使い、必要な情報をAIが自律的に調べられるようにする。テスト/本番の残る差（時間等）を解消または明示。既知候補の調査を優先し、未知店舗の大規模探索は今回対象外。
- 判断モデルのみ上位モデルへ変更する案を優先検討。実際に利用可能なモデルと料金を確認し、同じ証拠・基準時刻・道具で現行モデルと上位モデルを少数比較。費用、根拠、判断、形式異常を評価し、性能が良ければ採用。モデル変更だけで基盤不具合を隠さない。回数を増やす合議は必要性が確認された場合のみ。
- 案1の応募先と地域適合の根拠、案3の応募単位/口数の不足を実証拠で確認。応募機会の実在、利用者適合、登録に必須な情報と任意情報を区別。口数不明が本当に登録を阻むべきか既存仕様と利用目的に照らして再検討し、不明値を捏造せず扱える汎用設計にする。案2の正しい除外を回帰させない。単なる保留率削減ではなく正しい判断を目標にする。
## 5. 検証・反映・報告
各工程で原因→修正→再現テスト→結果を確認して次へ進む。重大問題がなければ途中承認不要。最終変更後の型検査、lint、単体、DB統合、関連E2E、build、CIを実施。データ保全、移行時の最新バックアップ・安全なplan、旧機能の回帰を確認し本番反映。初回3件は過去版を保持し、実際の本番共通経路で再評価。追加でLP以外の少数の実候補も確認（残予算内）。正解は実証拠で確定し、確認不能なら未達と明示。登録率のための強制登録や事例固有の分岐は禁止。成果が出ない場合は理由・次の必要手段を提示し無目的な再実行を止める。報告書をGitHubへpushし、PRで共有。原因・各工程の結果・実データの判断・費用/残額・残る欠陥・実行経路の差を明記。スマホ通知を使用。実運用レビューUIの拡張は基本機能の修正後に別工程とする。
