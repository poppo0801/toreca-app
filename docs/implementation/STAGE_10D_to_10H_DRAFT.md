## Stage 10D：共通データ基盤・移行準備・履歴保護
**目的**: Case層と判断履歴・証拠の保存を、既存ID・履歴を壊さず追加する。
**成果物**
1. 読み取り計測（本番は `npm run prod` の読み取りスクリプトのみ）: `lotteries`・`collection_candidates` の行数/容量、原文保存の実容量、`lotteries` を参照するFKの全一覧（IMPLEMENTATION_MAP §1の実測版）、通知の再評価の現行実装の有無。`TODO(根拠)`: 本番の適用済みマイグレーションの確認（利用者の承認のうえ読み取り）。
2. マイグレーション案の確定（MAP §6のA案を基本。新規2テーブル＋追加列。追加のみ・既定値つき・可逆）。**適用はユーザー承認後**: バックアップ→本番適用→復元手順の確認（`docs/RELEASE_FLOW.md`）。開発DBで先に適用・テスト。
3. 履歴保護の仕組み: 応募記録のある抽選行を自律変更しない検証層（共通関数）、判断の系譜（根拠・版・費用）の保存、原文の保存方針（ハッシュ重複排除・サイズ上限・保存期限・個人情報マスキング）。
4. 正規化の一本化設計（系列・店舗・商品。DB `norm_name` とTSの差の解消案。マイグレーションが要る場合は提案→承認）。
5. 旧⇄新の切替の設計（設定キー・互換アダプタ。既存の `collection_settings` の engine＝自律探索併用とは別の設定として定義。旧エンジンは新列を読まない/書かない）。
**テスト**: DB統合（FK・RLS・追加列の可逆性・既存E2E無影響）。**禁止**: 本番適用の自動実行・新構造の有効化。
**ロールバック**: 追加列・テーブルを参照しなければ旧動作に戻る。

## Stage 10E：統合AI判断・追加調査・同一性・マスター・証拠再利用
**目的**: 意味判断を1つのAI判断に一本化し、検証層で安全性を担保する。
**成果物**
1. 単一の意味判断（共通入出力＝SPEC §3）。入力は実際の証拠・関連案件・マスター・過去判断・人手修正・取得失敗履歴・地域条件（個人履歴は最小限）。出力は案件種別・応募機会構造・日程条件・店舗/商品/系列候補と根拠・既存機会との関係（同一/独立/同企画の別機会/不明）・未確定事項・次の処理。観測事実と推論を区別。
2. 検証層（出典の実在・参照整合・履歴保護・権限・費用）。不合格は理由つきで限定再判断。**後段の別判定器で意味結論を上書きしない**。9H `case-model`/`integrate`/`relation-judge`/`verify.ts` の再利用可否を評価して決める（MAP §3）。
3. 非同期の追加調査層（締切を待たせない）。調査は具体的な未解決事項と次の行動を持ち、同じ失敗経路を繰り返さない。停止条件（進展なし・取得不能・費用/回数上限・締切）と新証拠での再開。9Z原文・`collection_hard_sources` を通常収集へ接続。発見の枠を再調査が圧迫しない予算分離。
4. 実AI評価は**承認制**（費用・上限を報告）。再生評価（保存証拠）で旧/新を比較し、既知6課題と例外事例（ACCEPTANCE_PLAN §5）の回帰テスト化。
**禁止**: 本番有効化、費用上限の変更、AIによる予算/権限/履歴の変更。`TODO(根拠)`: 9H local関門の本番対応方式（関門の設計変更はユーザー承認事項）。
