# Stage 10Q：応募単位のAI推論・経験知識の活用・暫定候補の実証

## 目的と基本方針
Stage 10P報告（`docs/reports/2026-11-21-stage10p-evidence-first-shadow-readiness.md`）では新規51機会の自動登録0・確認待ち13、一覧55項目中54で応募単位unknown。**「明記がない＝判定不能」という設計を改め、情報を総合して人間のように推論する**。ただし固定ルールに回帰せず、例外を考慮し、AIの判断根拠・不確実性・誤統合リスクを残す。公式性は引き続き登録の必須条件ではない。

## ユーザー提供の経験則（必須ルールではなくAIに渡す参考知識）
- LivePocketで複数店舗が選択肢として表示される場合、原則としてその応募機会では1店舗のみ応募可能。ただしイトーヨーカドー等では同じ商品・期間でも店舗グループA/B/C/Dごとに1回ずつ応募できる例外がある。**同じプラットフォームだからと一括りにしない**。
- ドラスタ・竜のしっぽなど同じ抽選システムを使う系列では店舗ごとの独立応募が多い。
- 「他店舗へ同時応募すると落選」等の制限記載があれば、その抽選固有の応募制限を優先。記載がなければ店舗別応募を基本仮説の一つとするが、禁止記載が見つからないことを応募可能の証明とは扱わない。
- 店舗受取が前提、複数店舗を持つ系列、かつ実施店舗が特定されず応募時の店舗指定も明記されていない場合、**店舗選択式を有力な仮説**とする。店舗マスターが不完全なので「登録店舗が1つ＝単店舗系列」とは推論しない。公開情報や既存履歴から多店舗性を補助確認。
- ヨドバシのように当選後に店舗受取/配送を選べるものも、**アプリの管理上は店舗選択式として扱ってよい**。ただし内部には「応募時店舗選択／当選後受取先・配送選択／選択タイミング不明」を区別し、応募時に選択必須と誤表示しない。
- 同一商品・同一期間・同一系列でも、店舗グループ別の独立応募、店舗別独立応募、全店舗共通1応募、店舗選択1応募、商品別フォーム、複数商品同時応募、開催回別応募などの可能性がある。**応募可能回数と応募時の選択肢**を分けて推定する。

## 一括実装指示
1. **現行経路の確認**：`feat/10f-shadow-integration`に最新mainを取り込み、Stage10Pの`resolveApplyUnit`、`decision.ts`、一覧分割・URL`linkMap`、クラスタ・AI照合、登録カード/店舗選択式UI、既存応募管理を追跡。現行の応募単位の型を確認して必要な最小拡張を設計。既存の手動確定や保護データは変更しない。
2. **経験知識ストア**：上記のユーザー提供例を、出典「ユーザー提供の運用知識」・適用対象（系列/プラットフォーム/抽選方式）・例外・観測日時・信頼度・反例・有効期限を持つ編集可能な参考事例として保存。一般化された傾向と特定イベントの実例を分離し、系列名の表記揺れを吸収。コードに`if (chain===...)`のような絶対判定を埋め込まない。後日の人手訂正理由を蓄積・再利用できる構造を用意。人手未確認のAI判断を正解事例として自己強化しない。
3. **AI推論の入出力**：今回の告知原文、店舗/系列、商品、応募URL・フォーム構造、店舗グループ、応募制限の文言、過去の関連する実例、経験知識、店舗マスターの網羅性不明を、必要最小限の文脈としてAIに渡す。出力は「応募の独立単位」「選択可能店舗/グループ」「商品別応募の可否」「店舗・受取方法の選択タイミング」「推論された方式」「代替仮説」「根拠抜粋・参考知識ID」「確信度と不明点」「追加調査候補」の構造化データ。**今回の明示的な根拠が経験則より優先**。情報に無いことを事実として引用させず、直接根拠/類推/未確認を区別。AIが推論できることと根拠の機械検証可能性を分ける。推論の数値スコアだけで無条件に登録しない。
4. **多段階の判断と安全**：明示情報・応募先の構造・URLの違い・系列傾向・既存事例を総合。曖昧でも合理的な仮説がある場合は`unknown`一律で止めず、**暫定候補（未確定の応募方式を明記）**として保持できるようにする。十分な根拠がある場合のみ自動登録プレビューへ。店舗選択式と店舗別独立抽選を誤統合・誤分割しない。確信度が低い場合は通知・応募済み管理に誤った案内を出さず、確認待ち/候補にする。既存の`candidate_with_gaps`の意味と衝突する場合は状態設計を整理し、UI上で未確定を分かりやすく区別。保留理由は複合条件を残す。
5. **補助調査の自律化**：必要に応じて公開の応募ページや規約、系列の過去抽選、URL・店舗グループを限度内で追加調査。robots・SSRF・ログイン回避禁止・リダイレクト/回数/深さ制限。フォームを実際に送信・応募しない。追加調査で矛盾が判明すれば推定を覆す。ページ取得不可でも即座に捨てない。
6. **実データでの前後比較**：10Pと同一の51機会・一覧55項目を可能な限り同じ入力で再評価。応募単位の明示/推定/不明、暫定候補、自動登録プレビュー、確認待ち、除外、重複疑い、TCG/地域不明の分布を比較。**応募単位だけ解消しても他の条件で止まる件数を明示**。比較母数が変われば理由を説明。ユーザー提供例（LivePocket、イトーヨーカドーのグループ例外、ドラスタ、竜のしっぽ、他店舗応募禁止、店舗受取の多店舗系列、ヨドバシ）を対立仮説込みで評価する。例外・不確実な事例を優先してレビュー用画面に出し、可能な範囲で人の正解確認を得る導線を作る。**人の確認0なら正解率は主張しない**。
7. **安全と費用**：本番DB変更、PR #36/#46のマージ、本番デプロイ、cron/本番シャドー開始、既存抽選・応募・当選・購入・通知の書き込み/削除・自動統合は禁止。実行はローカル/シャドーの**非実行プレビュー**まで。既存のユーザー別履歴・手動修正・保護設定を不変にする。外部AIに個人情報や応募/当選/購入履歴を送らない。費用はStage10Pと同等以下のハード上限（追加AI90回、50円、公開ページ60取得、対象30件、1対象3円予約）。既存の運用予算との二重計上を避け、再試行も全て計上。実データ/原文/URL/秘密情報をGitに含めない。
8. **テスト・報告**：型検査/lint/build/単体/DB統合/CI、経験則の反例、店舗マスター欠落、LivePocketグループ分割、店舗横断応募禁止、受取タイミング、別フォーム・別開催回、AI出力の検証、同一入力の再現性、誤統合・誤分割、冪等・保護不変・費用停止をテスト。結果を`docs/reports/2026-11-22-stage10q-ai-apply-unit-inference.md`に報告。実測・仮定・人の検証を区別し、次段階で本番シャドーへ進めるかを根拠付きで提案する。作業は可能な限り一括で進め、細かな確認往復を不要にする。

## 優先順位
**応募単位の推論を柔軟にすることが主目的**。マスターの大量手作業拡充や公式性の再強化を主題にしない。正確性の保証できない仮説は「仮説」として保持し、根拠が更新されれば再判定する。
