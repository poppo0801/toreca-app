## 2. X応募URLの取得と出所の保存
1. **短縮URLと展開URLの対応**を、元投稿ID、元テキスト中の位置・項目番号／項目境界、展開方式（X API entity / 安全なリダイレクト / 既存保存情報 / 人手確認）、取得日時、成功/失敗理由、リンクのスコープと共に保持する。URL自体の存在・到達可否・抽選項目への意味的な適用を区別する。
2. X APIが現在提供するentityの短縮URL・展開URL対応が取得できる場合は第一候補。取得できないときも、**公開範囲・許可された安全なHTTP手段**で展開可能性を検討。リダイレクト先・各ホップのSSRF（内部IP/DNS再解決/localhost/メタデータアドレス）・robots・アクセス制限・サイズ・時間・回数・スキーム・機密URL・ログの扱いを検証し、安全性が担保できなければ無理にアクセスしない。ログイン/CAPTCHA/認証回避はしない。実X APIや有料検索を承認なく発火しない。
3. 既存 `buildItemLinks` / `itemScopedUrls` を再利用し、項目自身のリンクと親投稿共通リンクを別扱いにする。**項目への対応が不明なURLはAIの追加調査の手掛かりにできるが、無根拠な確定応募URLとして扱わない。** AIが調査して得た公開ページの店舗・商品・応募単位と元投稿の項目を照合し、根拠が揃えばAIが対応付けを提案できるようにする。曖昧なときは候補・要確認にして、リンクが無いから無条件に応募機会を捨てない。
4. 保存先は既存の非破壊的な収集エビデンス構造・開発用ファイル・評価fixturesの活用を優先。**本番DBの新規列・migrationが不可欠なら、その理由・DB影響・後方互換・切り戻し・代替案を仕様案として提示するに留め、承認前に本番適用しない。** 開発DBの変更が必要なら既存の許可・安全運用規則に従い実施し、未適用の本番状態を明記。
5. 同一URLのキャッシュ、リンク展開結果の再利用、転載の判別を維持。登録値やユーザー応募履歴に破壊的書き込みを行わない。原文・URL・ID・APIキー・個人情報をパブリックGitへ流出させない。

## 3. 実データ再生を可能にする（条件B）
- 現状の `research-10v-real.test.ts` の条件Bは「linkMapのfixtureが無いことをassertしているだけ」で、**実際の発見能力のテストではない**。fixtureを後から作成するとテストが失敗する構造を廃止し、「例がないときはskipped／評価不能」とし、存在すれば正常に評価を走らせられるハーネスへ修正。
- **次の検証を分けて計測**：
  (B1) 投稿から項目別の展開済みリンクを抽出・保存し、店舗・応募ページに対応付けできるか（リンクの「入力取得・scope」評価）。
  (B2) 入力に直接の応募URLが無い場合に、AIが公開情報から探索・追加調査してURLに到達・対応付けできるか（AIの「自律発見」評価）。

- 可能なら現に保存されている179投稿/382項目を、法的・技術的に許される範囲の非課金の再処理（保存済みentity、公開安全リダイレクト、検証済みユーザー提供例）で再生する。**再処理した件数・成功・未展開・リンク無し・項目対応確定・候補・mismatch・取得拒否・元データの欠損**を独立して報告。実際の対応先の正解を人間や独立原文で確定できない場合は精度値を計算しない。

## 4. 条件Cの正解データと採点を是正
- 10Sの「correct/wrong」は**以前の回答・旧判定への評価**であって、必ずしも新AIが選ぶべき正しい応募単位そのものではない。これを単純に比較したり `wrong` から反対の応募方式を自動導出しない。
- 根拠付き原文・公開応募ページ・人間が明示的に示した正しい応募方式（例 `correctUnit` 等）と対象となる店舗・商品・開催回・時点を照合し、**独立したgoldラベルが確定できた例だけ**正解率の分母へ入れる。過去のAI回答と同じ/違うだけの事例は「判定への評価のみ」であり正解ラベルなし。判断不能・URLなし・ページ取得不可・矛盾・範囲不明は別集計。
- goldは入力から隔離し、評価用原文とground truthを同じプロンプトに混ぜない。評価の正解、判断不能、不足根拠、人手確認が必要な例を一覧表示する**ローカル限定の安全な確認資料**を作る。正解が無いときは新AIの正答率を出さない。根拠なしの断定・登録と、過剰保留を別々に計上。
- 保存済み人手レビューの資料がない場合は再度一から人間に質問を重ねず、存在する評価資産を利用し、不足と選択肢を報告する。
