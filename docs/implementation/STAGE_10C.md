# Stage 10C 実行指示：AI再設計の正本化・既存実装対応監査

状態：Claude Code向け実行指示 / 2026-11-20
**このStageは文書・設計監査のみ。アプリコード、実行設定、DB、ジョブ、収集挙動、本番データを変更しない。**

## 0. 最初に必ず読むもの
1. このファイル全文。
2. `docs/AI_AUTONOMY_PRINCIPLES.md`、`docs/AI_REDESIGN_SPEC.md`、`docs/AI_REDESIGN_DECISION_HISTORY.md`。
3. 既存の `CLAUDE.md`、`docs/SPEC_GOVERNANCE.md`、`docs/CURRENT_SPEC.md`、`docs/DECISION_REGISTER.md`、`docs/ACTIVE_ROADMAP.md`、`docs/PRODUCT_VISION.md`、`docs/UI_UX_GUIDELINES.md`、`docs/RELEASE_FLOW.md`、`docs/DEVELOPMENT_LOG.md`、`docs/SPEC_ALIGNMENT.md` の存在と実内容を確認。
4. Stage 10A/10B、9X/9Y/9Z等の報告書を必要箇所だけ参照。古いStage文書を現行仕様として無批判に採用しない。
5. 既存リポジトリ内に `AI_AUTONOMY_PRINCIPLES.md` がすでにある場合は内容を比較し、ユーザー合意事項を失わず統合する。

## 1. 目的
- 設計合意を、Claude Codeが将来のStageで誤読しない正本仕様にする。
- Stage 10A/10Bで見つかった実装と仕様の乖離を、**現在のコードとDB定義を再確認**して対応表にする。
- Stage 10D〜10Hの実装・移行・受入テストを、既存機能の保護と総合精度改善の両立を前提に具体化する。
- 古い `CLAUDE.md` の肥大化、矛盾、古い未デプロイ記述などを整理し、古い履歴が新設計を上書きしないようにする。

## 2. 必須作業
### A. 現状の安全な確認
- 作業開始時のGitブランチ/コミット、未コミット差分、文書の実在、現在のDBマイグレーション定義、関連実装ファイルを記録する。
- 既存の実行系に変更を加えない。必要なら読み取り専用のコード調査・静的検査のみ。秘密情報、ユーザー個人データ、生の認証情報を報告書へ転載しない。
- 既存の設計原則文書がリポジトリに反映済みかを確認する。未反映・矛盾があれば、提供された合意内容と整合させる。

### B. 正本文書の再構築
- `docs/AI_REDESIGN_SPEC.md` を正式な**目標仕様**として整備。未実装を実装済みと書かない。
- `docs/AI_AUTONOMY_PRINCIPLES.md` の理念を保持し、重複・矛盾を整理。理念を削って旧実装優先にしない。
- `docs/CURRENT_SPEC.md` は現時点で実装・提供中の機能と、将来目標を明確に区別する。現状と将来の混同を防ぐ。
- `docs/DECISION_REGISTER.md` に、Case/Opportunity分離、単一AI意味判断、履歴保護、短期旧新切替→旧方式廃止、3本柱の完成条件、Markdown指示書運用等の決定を追記。
- `docs/ACTIVE_ROADMAP.md` にStage 10C〜10Hの目的・依存関係・完了条件・承認ゲートを整備。工程の統合提案は可、実装に先行して勝手に実行しない。
- `docs/SPEC_GOVERNANCE.md` と `docs/PRODUCT_VISION.md` を整合させる。優先順位はユーザーの最新明示決定→正本仕様/決定記録→ビジョン/過去設計→コードは現状把握の根拠、という原則を明示。コードの現状を理由に合意した将来設計を取り消さない。
- `CLAUDE.md` を短く保守可能な運用入口に整理し、最初に必読の正本文書とStage指示書の読み込み手順、作業承認境界、Stage報告義務を明記する。古いStage履歴の長文貼り付けは除去。既存の有効な安全・Git・CI・権限ルールは失わない。
- 古い資料は知見抽出後にアーカイブまたは現行参照対象から除外。**一括削除・Git履歴改変はしない**。ローカルバックアップが必要なら復元方法と保存場所を記録し、必要なら追跡可能なアーカイブを作る。

### C. コード・DB対応表（読み取り専用）
- Evidence/Case/Opportunity/View/User recordsの各論理層を既存テーブル・ID・外部キー・アプリ処理に対応付ける。
- 応募、店舗/商品選択、当落、スルー（今回/常時）、継続抽選、地域判定、通知、購入・コレクション、編集/手動修正の参照経路と破損リスクを洗い出す。
- 9H（case-model, investigator, integration, relation-judge, planner, grouping）、9Z証拠保存、現行の各種重複判定/正規化、既存切替設定を実コードで確認し、再利用/変更/廃止候補と理由を表にする。9Hのlocal-only制約や本番環境のフラグ前提を明示し、無検証で本番有効化しない。
- マイグレーション案は**提案のみ**。新規テーブル数を最小化する代替案も比較。既存抽選ID・履歴を保持する移行/逆戻し手順、切替互換アダプタを検討。
- 判明しない実稼働状態や本番DBの設定値は「未確認」と明記。推測で断定しない。

### D. 受入テスト設計と性能評価計画
- 既知の6課題だけでなく、従来方式との**総合精度比較**を必須とする。発見力、抽出精度、登録/対象判定、網羅性、更新、同一性、遅延、費用/正確機会、人手負担、安定性を定義。
- 旧方式の出力を正解とみなさず、検証可能な原文/フォーム/画像を根拠に正解事例を構築する方法を設計。取得不能事例は「検証不能」と分離。過去保存証拠と新着本番事例の双方を扱う。
- 例外事例：店舗選択式と店舗独立、1フォーム複数独立機会、商品一括と商品別、別開催回、締切延長、中止再開催、既存応募履歴ありの分割/統合、通知再計算、地域一部対象、X取得不能、会員限定、手動修正の保護。
- 必須安全条件：重大な誤統合ゼロ（テスト対象内）、履歴破損なし、費用上限突破なし、権限逸脱なし、通知の重大な重複・欠落なし、切替での破壊的再解釈なし。
- 根拠のない精度閾値や費用上限を捏造しない。ベースライン、測定方法、後から設定すべき閾値を区別。長期シャドー運用を必須にしない。
- 新方式が目立った問題なく運用できれば旧方式は早期廃止。恒久互換のために新方式を制約しない。

### E. Stage 10D以降の具体化
- Stage 10D〜10Hの成果物、依存関係、移行/承認ゲート、テスト、ロールバック、廃止対象を記述。
- 後続StageのMarkdown指示書は、確定できる範囲で**ドラフト**作成してよい。ただし、実コード監査で未確定の箇所はTODOとして根拠を付す。承認なしに後続Stageの実装を開始しない。
- 技術的選択肢は自律的に比較・提案してよいが、ユーザーの合意済み原則の変更は提案に留める。
