## 0. 開発姿勢と承認境界

既知の修正可能な問題は、Claude Code側で原因究明→修正→回帰検証→再監査を一括で完了し、解消可能な既知問題を未解決リストに並べたまま終了しない。個別の小さな実装方針・途中修正に確認を求めない。**ただし正解データの最終的な人による真偽確認、有料APIの明示的な実行・予算承認、本番変更、外部サービスの契約・課金は勝手に行わない。** 本番DB/Storage/Vercel/cron/環境変数・自動収集/通知/登録の本番挙動は変更せず、新AI系PRをmainへマージしない。外部の実サービスへの負荷試験や有料AI・X API・有料Web検索の無承認実行をしない。開発用DB、保存済みの公開ページの再生、モック、ローカルのテストは可。

## 1. 独立goldをブラウザで確認・修正できる開発専用UI

現状R1の `eval/phase2-compare/r1-worksheet.local.md` と `r1-gold-pages.template.local.json` を人が行き来し、JSONを直接編集する必要がある。**最小限のレビュー画面を実装し、通常の抽選UIへ混入させない**（開発専用、ローカルDB/環境ゲート、本番ではアクセス不可）。

- 案件一覧と確認進捗（未確認／確認済み／除外／要再確認）、各ページ原文の抜粋・出典URL・取得時刻/版、公式ページを別タブで開くリンク、店舗・商品・応募締切・応募単位・対象地域・開催回・応募枠・引用の確認・修正、原文の別位置を参照する導線。
- 機械抽出した候補は明確に**未確認**として表示し、公式ページの独立確認による明示的な人の確定がある場合だけgoldにする。未確認・不明な値をAIが推測して補わない。人がどのページ版を見たか・検証日時・根拠・訂正履歴を残し、引用と保存された原文の実在を自動検査。AI・旧方式・既存登録案・モック回答をgoldへ流用しない。簡単な項目一括承認が正確な確認抜きにできる設計は禁止。
- 1ページに複数枠・複数商品・複数店舗がある場合の応募機会を取り違えない。現行R1の「1ページ=1機会」に合わない事例は除外理由つきで残し、別試験の対象にできる構造とする。
- 保存はGit管理外の開発用ローカルデータ/DBのみ。世帯・人の認可、入力検証、CSRF/URL安全性、権限分離、他機能への非干渉。データ消失防止・バックアップ/エクスポート/インポートを備える。Vercel Previewや本番での公開を禁止。iPhone幅390pxとPC画面の操作をテスト。
- 完了時はユーザーが**JSON編集なしで12ページの確認を進められる**ようにし、レビューで確定したgoldを既存の `r1-build` と比較試験ランナーに連携。未確認が残る場合は有料試験を止める。必要なユーザー操作は短い手順で提示する。

## 2. 実際の複数リンク投稿の不足を解決

保存済み実X投稿30件では複数リンク投稿が1件、しかも短縮URL未展開・複数の取得済み本文ゼロ。これを単なる「データがない」で終わらせず、**新規発見、既存保存、短縮URL展開、元投稿/引用/スレッド/フォームへの到達まで経路別に原因を調査**。過去に最初の1件しか取得されない構造問題があったことを踏まえ、収集・保存・テストデータ選定のどこが不足しているのか切り分ける。

- 保持済みの公開データ、許可された無課金の参照元を優先し、**本物のX投稿を含む、実際に複数応募リンクがある例**の発見・保存・検証可能な資料化を進める。新たな有料X API/検索の無承認実行は禁止。Xアクセス・第三者規約・認証の回避をしない。取得できなければ検証事例の不足を明記し、実例が揃ったふりをしない。
- 合成R1と実投稿R1を**明確に別のデータセット・結果として管理**。実在するLivePocket12ページを合成投稿に組み合わせる方式は初期の構造検証には利用可だが、ページ重複・サイト偏り・独立性不足を統計的な精度の主張に使わない。実投稿の初期検証は可能なら異なる系列・店舗・応募形式を含める。
- 複数店舗・複数商品・URL順序入替・短縮URL展開・引用元・別開催回・フォームへの2段リンク・同名店舗などをテスト。実例が少ない場合は契約テストを補強し、実際の運用評価が未完了であることを残す。

## 3. 情報の上限・実AIの全文参照の追跡を強化

前工程の `limits-audit.ts` は無言の欠落6種類を発見修正したが、**上限に当たらないこと、全文を保存したこと、AIが重要箇所を実際に読んで判断したことは別**。今後の比較試験ごとに以下を測り、結果に載せる。

- URL発見数/未取得・追跡成功数、投稿文字数、ページ本文の分布とp50/p95/最大、6,000字抜粋の上限到達率、12,000字の全文先行提示、20,000字の統合入力、14,000字リンク配分、目次/分割/read、リンク取得24+6、ページ30、台帳80等、上流から下流の実際の値・上限と、記録のある欠落/ない欠落を監査。限度が現実に不足していれば自律的に改善（無条件の巨大トークン投入ではなく、全文保存・段階的read・再取得・ページング等）。
- エージェントの `read` / `fetch` / `search` や引用の証拠範囲をイベントで記録し、**保存済みの全文のどの区間を実際にAIが読めたか**、正解の重要条件の存在位置を読み飛ばしたかをgoldと突き合わせる。情報が収集されていない／保存されていない／AI入力に届いていない／届いたが読んでいない／読んだが誤判断した、を分けて評価する。
- 取得できなかったリンクの自動再調査キューと結合し、上限到達率や再取得回収率・古い証拠が再収集で失われるリスクも継続監査。重要条件の未読を「記載なし」にしない。機密や個人情報・長文原文をログへ無制限出力しない。
- モック・長文/多リンク/障害系/回帰テスト、次の実AIで測定する項目まで整える。

## 4. 独立gold確認→小規模R1実AI比較

R1の優先目的：旧「先頭1リンク」対新「複数リンク」の応募機会再現率と、誤登録・他店混同・無効引用の差を測る。

- まず12ページのレビューUIから人が確認できるようにし、独立gold・引用の原文照合・校正/評価データの独立性を保証。`r1-build`→`plan`→`mock` までは無課金で進める。
- 予算は前回の見積**約37円、関門上限60円・1案件5円**を参考とするが、実行直前に使用モデルの料金、実際の試験件数、最大予約額と呼出し数を再計算して表示する。
- ユーザーはR1実AI試験への意向を表明しているが、**金額と確認文の明示的な承認は未取得**。 `APPROVE C <総額>JPY` を勝手に作成・入力・迂回しない。**承認まで有料実AIは実行しない**。人が確定したgoldと金額承認が得られたときだけ、承認された対象・件数・予算でR1を実施する。
- 誤登録・混同の悪化が1件でもあればその結果を隠さず停止・原因修正・無料の回帰試験。再度の有料呼出しは追加承認が必要。統計的に不十分な少数例は効果を断定しない。
- R1結果を見てR2（全文）・R3（画像）・R4（経験ヒント）の順序を再提案する。**R2〜R4の有料実行はこの指示の承認範囲外**。
