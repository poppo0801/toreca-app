# Stage 10T — 応募ページの構造取得・応募単位の判定検証

## 背景と目的
Stage 10S（`docs/reports/2026-11-22-stage10s-source-link-groundtruth.md`）では公開応募ページ36件中32件取得、18件の判定で直接根拠15件・自動登録プレビュー2件。ただしX投稿からの実データE2Eは未実施。ユーザーはレビュー30件を確認し、元URL不明の大半を判断不能、LivePocketで店舗別応募を店舗選択式とする誤認が多いと報告した。従って、**人がブラウザで見える応募枠・店舗・関連イベント・制限事項を、取得処理がどこまで読み、AIへ何を渡しているかを検証すること**を最優先する。精度改善の数値自体を完了条件にしない。

## 判定対象を分ける
1. **ページ/フォームの受付単位**：独立イベント・独立応募ページ・1ページ内の複数チケット枠・商品別/回別/店舗グループ別。
2. **応募可能な独立単位**：同系列・同商品・同時期の店舗ごとにそれぞれ応募できるか、1フォーム内の選択か、系列横断の応募制限か。
3. **選択時点**：応募時/当選後/選択不要/不明。受取先の選択と応募単位を混同しない。
4. **応募条件**：一人1回、1チケット1回、複数店舗禁止などの制限は適用範囲を特定する。「お一人様1回」だけで系列横断禁止と断定しない。
5. **情報の状態**：観察事実、出典・抜粋、ページと抽選項目の対応、AIの解釈、代替仮説、不明点を別々に保持。

## LivePocketで特に調べること
- ページの「受付・チケット情報」の**受付枠数・カードごとのタイトル/店舗/商品/回/期間/説明**を抽出。ページ内の「抽選を希望する店舗を選んで下さい」「1店舗のみ応募可能」等の注意書きとカード構造を併せて解釈。
- **同じ販売元のイベント**に表示される別イベントのタイトル・店舗・URLを、ページ本体の応募枠とは**別の情報構造**で取得。関連イベントが同商品・同時期・同系列かを照合し、必要なら公開リンク先を安全に調査。単なる関連イベント表示だけで応募可否を確定しない。
- ユーザー提供の実例を判定の観点に含める：(A) ページ内の受付枠1件・店舗選択の記載なし → 当該ページは店舗別受付の有力根拠、他店舗の存在は必須でない。(B) 同一ページ内に八王子本店・立川南口店・町田店など複数店舗別チケット枠＋「1店舗のみ応募可能」 → 店舗選択式。(C) 「同じ販売元のイベント」に名古屋大須店・広島店・なんば店など店舗別の独立イベント → 別応募ページがあることを支持。(D) 別々の応募ページでも明示の系列内重複禁止があればその制限を優先。
- 同時期・同商品・同系列で店舗別の独立応募ページがある場合、**明示的な横断制限がなければ店舗ごとに応募可能と推論してよい**。ただし絶対ルール化せず、個別の応募条件が優先。1店舗しか記載されないページを「他店舗の選択式」と推測しない。単一ページ内の複数カードも商品別・回別・店舗別を区別する。
- 通常のHTML取得でJS描画のカードが欠ける場合、許可された公開手段で取得可能性を検証。ログイン・CAPTCHA・robotsを回避しない。取得不能は未確認とする。

## その他の情報源
- **Googleフォーム等**：公開フォームの設問、店舗/商品/開催回選択肢、説明、回答制限の文言。フォームの回答送信やログインはしない。
- **店舗・系列公式サイト**：店舗別告知、応募リンクと各店舗の対応、商品・期間・応募制限・系列共通条件。
- **X/SNS**：投稿本文・添付画像の公開範囲・スレッド・店舗別告知・項目単位の展開URL。親投稿のURLを別店舗へ無根拠に流用しない。開発用X APIキーがなければE2E未実施と明示し、鍵の提供を要求せず代替の公開データで部分検証する。
- **抽選専用サイト/その他公開フォーム**：チケット/応募枠、店舗選択、商品・開催回、重複応募制限を調査。
- **会員専用ページ**：公開範囲のみ。認証が必要なら未確認として扱う。
- サイトごとの取得処理は必要に応じて設けるが、出力は共通の観察データ構造に正規化する。特定サイトの名称だけで応募単位を確定しない。

## 実装・検証順序
1. 既存の`investigateStructure`、`linkMap`、`item-links.ts`、`link-scope.ts`、`apply-unit.ts`、`ai-unit.ts`、`decision.ts`、レビュー資料の入出力を追跡。**取得したHTML/構造化情報 → 抽出した事実 → AIへ渡した内容 → 判定結果**を実例ごとに比較し、取得欠落とAI解釈誤りを切り分ける。
2. LivePocketの受付枠と関連イベントを構造的に抽出・対応づけ。表示されるカード件数、各カードの店舗/商品/回、制限文言、関連イベントのURL/店舗を記録。ページ自身の受付枠と「同じ販売元のイベント」は別扱い。実際のブラウザ表示との一致状況を人が確認できるローカル比較資料を作る。スクリーンショット等が自動で取れなければ人手で対照できる原文・URL・取得項目一覧を示し、表示一致を推測で断定しない。
3. 他サイトも同じ観点で取得可否を点検・必要な改善を実装。元URL不明やスコープ不一致のサンプルは**正解率の評価対象にしない**。取得不能率・判定不能率を別指標で計測。無関係な関連ページを根拠として流用しない。
4. Stage10Sのユーザー回答30件がローカルに保存されていれば`scripts/eval-review-10s.mjs`等で集計し、**判断不能/誤り/正しいの件数と理由**を報告。保存が見つからなければ再回答を要求せず、その旨を明記。人の回答をAIの仮説に置換しない。
5. 公開されている実ページで最低限、独立した店舗別ページ、1ページ複数店舗の選択式、別店舗の関連イベント、明示的な横断応募制限、商品別・開催回別、当選後の受取先選択を検証。実例が見つからなければ「未検証」と明記し、架空ケースは回帰テストに限定。**正解率は人が根拠を確認した実例のみ**で計算。
6. 応募単位以外の阻害要因（地域、店舗・商品マスター、TCG、系列、重複）も観察するが、今回は情報取得と誤判定の切り分けを優先。既存マスターや保護データは変更しない。
7. 型・lint・build・単体・DB統合・CIを確認。安全取得のSSRF/robots/リダイレクト/サイズ/タイムアウト/レート制限を維持。AI最大90回、¥50、公開ページ最大60取得、対象最大30件、1対象¥3予約の上限を超えない。鍵・原文・URL・ID・個人情報をGitに含めない。実装PR #36/#46のマージ、本番DB/マイグレーション108〜113、本番デプロイ/cron、既存データ書込は禁止。
8. `docs/reports/2026-11-22-stage10t-application-page-structure.md` に、情報源別の取得項目と欠落、LivePocketのカード/関連イベント取得実測、ブラウザ表示との比較資料の場所、ユーザー30件レビュー集計、誤判定の原因分類、実データ検証、費用、安全、次段階への提案を記載。可能な範囲を一括で実装・検証し、細かな確認は求めない。

## 完了条件
**人が見ている応募ページの重要情報をAIも取得できるか**を実測で説明し、情報取得の欠落と推論誤りを分離する。数値上の正解率改善は完了条件としない。本番反映は別途承認を待つ。
