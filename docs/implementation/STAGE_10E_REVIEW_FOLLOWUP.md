## A. マージ前に必須の安全対策
1. **migration108未適用時の互換性を実証**。`src/lib/server/master-identity/reeval-service.ts` の `lotteryProtection` → `commonProtection` がDB関数 `lottery_history_blockers` 不在時（PostgRESTの関数未登録、404/PGRST202等）に従来の確認へ安全に戻るテストを追加。関数正常時は新保護が有効になること、権限拒否・接続障害・未知のRPCエラーを「関数が存在しない」と一律にみなして**保護なしで続行しない**ことも検証。特に保護対象の非表示/統合/削除が失敗時に通過しないことを確認。互換性と安全性を両立できない場合は、影響範囲を明記してマージ前に停止。
2. **追加調査URLの安全性**。`src/lib/judgment/investigate.ts` の `fetchPage(target)` 前に、AIの返すURLを信用せず、http/https、資格情報なし、内部/loopback/link-local/プライベートIP・localhost・メタデータ宛先・不正なポート等を拒否する。DNS解決、IPv4/IPv6表記ゆれ、リダイレクト先、DNSリバインディングを含むSSR Fの防止は、**実際の取得アダプタ/ネットワーク境界で保証**し、事前の文字列検査だけで安全と主張しない。10Eで実ネットワーク取得を接続しない場合でも、実行境界の型・安全契約・拒否テストを追加し、10Fの取得アダプタに必須条件として残す。外部本文の命令をツール呼び出し権限として扱わない。
3. **費用・ループ・履歴の回帰**。予算予約・精算の二重計上/未知費用/並列実行、再判断上限、同一取得の反復、取得失敗、手動確定値、応募/当落/通知/スルーの保護を再検証。既存の `lotteryProtection` が確認するDB参照が失敗したときに0件として扱う箇所も評価し、保護の判定不能を安全側で止める。破壊的操作に関わるテストを優先。
