# Phase 3 — 初回3件の根本原因解消・実用性の回復
## 目的・承認境界
報告書 2026-11-25-phase3-shadow-tentative-analysis.md および 2026-11-25-phase3-runtime-parity.md §7 を起点とする。初回3件が追加取得後も全件暫定だったことを未解決の欠陥として扱う。機能が動いたことではなく、根拠に基づく正しい最終判断を成果とする。3件の正解は現行の結果を盲信せず実資料で確定する。期待は案1・3の登録案、案2の地域外除外だが、実際の根拠と基準時刻が支持する場合に限る。実登録はしない。修正・無料テスト・通常PR/CI・安全確認後の本番反映まで一括で進める。既存キー、家族1世帯、自動登録禁止、日次15円・通算45円、期限11/28 13:45 JSTを維持。増額・延長・新キー発行は禁止。残予算が足りない場合は必要額・理由を提示し、有料再評価のみ承認待ちとする。予算待ちを理由に無料の原因究明・修正を止めない。既存の現行収集・抽選・応募・購入・通知を変更しない（共通収集経路の欠陥修正が必要なら既存結果への影響を確認し、破壊的変更や現行登録方針の変更は別承認）。本番書き込みはシャドーの隔離領域と必要な安全設定のみ。
## 1. 最初に3件の証拠を確保し、原因を確定
- 初回v1・再評価v2の候補ID、原文、保存された last_good・取得元・全文保存表、取得時刻、取得URLと最終URL、実取得結果/本文長/切り詰め/失敗理由、AIが実際に参照できた証拠、抽出値と引用（証拠ID・位置・種別）、検証結果、AIの判断、訂正回数・理由・結果、停止理由・予算を版別に照合する。保存されていないものは未確認とし、推定を事実と混同しない。公開告知の必要箇所だけを報告に引用し、秘密・個人情報・非公開URL等は記録しない。既存データ・過去版を保全。
- v2の3件のどれが検証済み暫定、どれが引用不一致かを特定する。報告書の集計では判別できない部分を補う。各件の当時の正解、現在の状態、地域適合性を区別。期限切れのページを現在の状態だけで過去の正解にしない。取得元が変化・消失した場合は保存済み証拠を優先し、確認不能なら明記。
## 2. 案1 LivePocket 28店舗 — 抽出値・根拠・自己修正の共通欠陥
- 原文の店舗記載、AIの抽出値、引用、引用を照合した実際の証拠本文を並べ、何が違うかを文字単位・意味単位で説明する。正規化・空白・Unicode・別名・複数店舗・見出しと表の構造・証拠IDや切り詰めの誤り、実際の捏造/誤読を区別する。店舗名を正規化して登録することと、原文の逐語引用を忠実に保持することを分離する。意味的裏付けを維持し、曖昧な部分を安易に通過させない。
- 不一致時にAIが具体的な検証エラーと該当証拠を再読し、抽出値・引用・証拠IDのどれを直すべきか自律的に判断し訂正できるようにする。既存の訂正経路が実行されなかった/失敗した原因を調べ、必要に応じて回数・時間・費用を効率よく配分する。全件一律の追加呼出しや店舗固有の正規表現追加を避ける。複数店舗選択式の実際の応募範囲を証拠で確定し、条件を満たせば verified register を出せること。
## 3. 案2 佐賀県の店舗 — 実在と利用者適合を両立
- 現行の地域設定（兵庫・大阪・京都等、オンライン可否は実設定を確認）、店舗所在地、店頭受取/通販、応募と受取の条件、複数店舗や選択の可能性を根拠で確認する。機会の実在判定を壊さず、利用者向けの最終判定へ適合情報を正しく反映する。既存の地域条件は固定の店名/県名ルールではなく設定から渡す。地域外店舗限定で利用可能な通販等がないことが確認できれば、利用者向け exclude（実在と適合は別記録）。曖昧なら追加調査、根拠がなければ保留。旧固定ロジックを正解扱いしない。地域外の表示だけで機会の実在を否定しない。
## 4. 案3 通販公式サイト — 71文字の原因と取得/保存/活用の完全性
- 71文字は初回に保存された card_or_context であり、再取得後の本文長は未報告。収集の入口→URL抽出/展開→HTTP取得→本文抽出→全文保存→AIへの読み込み→リンク探索→判断の各段階を、実際のログとコードで追う。未取得、取得失敗、本文抽出失敗、保存漏れ、読取漏れ、意図した切り詰め、AIが読まなかった場合を区別する。どのURLのどのコンテンツを取得したのか、取得/保存/提示/読取文字数を比較。71文字が短い告知そのものだった場合と、長い取得済み本文が欠落した場合も区別する。
- 取得済み情報を漏れなく利用できる共通経路に是正し、取得元URLを起点に公式告知・関連ページ・応募先を自律的に探索できるようにする。既存の全文保存・安全取得・リンク展開・画像参照・再調査機能を優先利用する。短文を機械的に失敗扱いする文字数ルールは作らず、不足項目に応じて調べ方をAIに選ばせる。取得できない情報を捏造しない。
- 検索は現在の予約額2.5円＋調査判断1.2円が1件3円に収まらず提供できない。既存の許可済み・安全な低コスト経路、予約額と実課金根拠、情報取得の効率化を検討し、必要な限定検索を提供できるなら共通の道具契約で実装。予算超過や安全策の迂回は不可。検索が必要なのに提供できないなら必要費用と代替手段を明示し、原因解消済みとはしない。Vercelの時間制約も、必要なら既存キューでの継続調査などを検討し、無限ループを防ぐ。 
## 5. 検証と完了条件
- テストと本番は同一パイプライン。3件の実証拠を匿名化した再現fixtureで、修正前の失敗を再現し修正後の根拠・判断・訂正を確認する。他情報形式にも適用できる汎用的な回帰例を必要最小限追加（LP以外も含む）。合成データの大量作成や全件手入力は不要。最終変更後の型検査・lint・単体・DB統合・関連E2E・build・CIを実施。DBテスト前は評価記録保全。本番DB移行が必要なら安全なplan・最新バックアップ・後方互換確認。
- 本番シャドーを安全に切替し、承認済み残予算・日次枠内で3件を再評価。必要なら通常稼働と調整して二重実行を防ぐ。費用の永続引当、失敗記録、期限、自動停止を維持し、既存の承認条件を変えない。旧版を保持し、結果を比較。再評価が予算や期限で不可能ならその時点を明示し、実運用合格とはしない。
- 成功条件は、根拠で支持される正解を3件で確定し、AIが本番の共通経路でそれに到達すること。案1・3は登録条件を満たすなら検証済み登録案、案2は地域条件を満たさないなら適切な除外案。根拠が本当に不足する場合の保留は認めるが、何を調べたか、なぜ取得不能か、残る機能不足を明示する。登録率を上げるための強制登録・検証緩和・事例固有の分岐・正解のプロンプト埋め込みは禁止。
- GitHubに報告書とPRを必ず共有。各件の原因（確定/仮説）、原文と抽出値/引用の差、71文字の経路別文字数、地域根拠、修正内容、修正前後の判断、自己修正履歴、道具/費用/残予算、本番実績、残る差・未解決を示す。既存のスマホ通知を使用する。
