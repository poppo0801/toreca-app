# Stage 10G：全情報・抽選候補の一括再判定／整理プレビュー

## 目的と承認範囲
ユーザーは2026-11-21、Stage 10F実データ30件評価の結果（構造unknown 10/30、未解決事項あり29/30）を踏まえ、次の既存抽選再整理テストへの進行を了承した。本指示では `docs/AI_REDESIGN_10F_REFRESH_PLAN.md` の **R0（読み取り）＋R1（再取得・AI判定・差分プレビュー）を一括実行**する。R2/R3の本番DB更新・統合・アーカイブ・削除は**行わない**。PR #36/#46のマージも対象外。

## 進め方
1. `feat/10f-shadow-integration` を継続し、最新mainを反映。既存の9X/10Fの抽出・バックアップ・シャドー・比較部品を最大限再利用する。不要な承認票・人手での30件個別レビュー・過剰な段階分けを増やさない。
2. 現時点の「全情報」相当と「抽選候補」の対象を、既存画面の抽出条件に沿って本番DBから**読み取り専用**で取得。プロフィール依存の画面件数との差は明記。応募・当選・購入の記録は**保護有無の判定に必要な最小限のみ**扱い、外部AIには送らない。バックアップの接続先検証は既存の安全な仕組みを再利用。
3. 全対象の件数・保存原文あり割合・状態・保護・取得可否を集計（R0）。**R0の集計後に承認待ちで停止せず**、保存原文あり・保護なし・取得可能な公開ページを優先して初回最大30件のR1に進む。原文なしは既存の公開取得部品で再取得を試み、X/t.co等のアクセス制限は回避しない。
4. 既存Anthropic APIキーを流用し、公開告知の伏せ字本文だけを送信。既にユーザーが承認した通常・例外的なデータ保持リスクの受容方針を適用し、組織設定の再確認や全件個別目視は求めない。個人情報・秘密情報の自動除去・検査と送信先制限は維持。上限：**対象30件、AI呼び出し90回、公開ページ取得60回、API費用合計50円・1件3円**。予算・回数を超えないようにし、連続5件の取得不能なら理由を記録して次の取得可能対象を優先する（無限リトライしない）。
5. 新方式の構造・応募機会数・関係・重複・開催回・系列別名・店舗別/商品別と、**実際の既存登録値・保存済み旧方式の出力**を比較する。旧固定判定が全件unknownだった問題を再発させない。比較可能な項目と比較不能な項目を明示。判断の正確性を差分だけで断定しない。
6. **構造unknownと未解決事項を重点分析**。30件評価でunknown 10件、保留あり29件だった原因を、(a) 告知本文が不十分、(b) 抽選でない投稿、(c) 取得不足、(d) AIの過剰保留・判断能力、(e) その他に分類。人手確認を増やすのではなく、AIによる再調査・軽微な不一致の自律解決・実際に必要な保留だけ残す改善案を検討。元の30件と今回の対象が異なる場合は、混同せず別集計。
7. 差分プレビューは**書き込みなし**。応募・当選・購入・人が確定した情報に影響する提案は参考表示のみ。保護なし対象への低リスク修正案（店舗情報補完、重複候補、期限修正等）と要確認を分け、変更件数・期待効果・誤判定リスクを報告する。復元手段の実装は更新段階まで不要。
8. `docs/reports/2026-11-21-stage10g-refresh-preview.md` に、R0全件統計、R1最大30件の実測、AI費用、unknown/保留の原因、具体的な改善策、次に実際のデータ整理を行うべきかをまとめる。原文・URL・ID・秘密情報を公開報告書に載せない。テストは変更箇所中心に実施。PR #36/#46は未マージ。

## 方針
**開発効率・自律性を優先**。公開情報の取得・解析・差分比較はまとめて実施し、軽微な不確実性や事前の追加承認票作成で止めない。ただし本番の履歴破損、意図しない書き込み、機密情報送信、API異常課金・無限ループの防止は維持する。取得できない情報を取得済みと偽らない。実行に必要な権限・接続が実際に不足する場合だけ具体的に報告する。
