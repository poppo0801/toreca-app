# Stage実行指示書の運用ルール

## 位置づけ
- 大規模なStageの実装指示は、**Git管理するMarkdown（`docs/implementation/STAGE_<番号>.md`）を正本**とする。チャットには「最新の `main` を取得し、`docs/implementation/STAGE_XX.md` に従って実施」という短い指示だけを送る。小規模な修正はチャットの指示でよい。
- 指示書は ChatGPT（または利用者）がPRで追加する。**PRの作成やマージは実行開始を意味しない**。Claude Code の起動・実行は利用者の別の指示で始まる。
- 指示書が `main` に無いうちは、正本に反映済みとみなさない。実行前に `git fetch` で最新の `main` を取得する。

## 実行者（Claude Code）の手順
1. 指示書全文と、そこに列挙された必読文書を読む（`CLAUDE.md` §1 の順）。
2. 開始時のブランチ・コミット・未コミット差分を記録する。
3. 指示書と他の文書が矛盾したら、優先順位（`CLAUDE.md` §2）に従い、判断できなければ報告書に「未解決」と書く。ユーザーの合意済み原則を変える提案は提案にとどめる。
4. 作業・テスト・PR・CI を通常フローで行う。本番反映・本番DB変更・費用発生・基本設計変更は事前承認。
5. 新規の報告書を `docs/reports/` に保存し、チャットは報告書パスと要点（変更要約・確認できた事実・未確定・判断待ち・次Stage着手条件）のみ。

## ドラフト指示書
- `STAGE_10D_to_10H_DRAFT.md` は **ドラフト**（未承認）。10C報告書の保存と、ユーザーの「10D開始」の指示があるまで実装を開始しない。確定した版は `STAGE_10D.md` のように個別ファイルとして別PRで追加する（ドラフトは履歴として残す）。
- ドラフト内の `TODO(根拠)` は、実コードの監査で未確定の箇所。確定前に当該Stageの冒頭で読み取り調査して埋める。

## 指示書の書式（推奨）
目的／必読／必須作業／成果物／禁止・承認境界／完了と報告／次Stage着手条件。
