# Phase 3 — 証拠活用・調査能力・自律探索の実用化
起点 main #176、docs/reports/2026-11-26-phase3-production-parity.md、#174。Claude Code は Opus 5.5 継続。判定の改善は大きいが、未見12/13は小標本、項目72.9%、本番8案は登録0・除外4・仮登録4（未検証3）、収集由来全文295文書に対し新AI提示8ページのみ。実用上の成果を優先し、同じ案件の反復や評価基盤だけの肥大化を避ける。AIの自律的な調査・判断・改善を重視し店舗固有ルールを増やさない。
## 承認境界
通常シャドー通算380円（報告時190.58）、日次140、1件25、期限12/3 23:59 JST。隔離評価通算1250円（報告時1089.21）、日次400、1件25。最新残高を確認し、必要な増額/期限延長/DB変更等は用途・必要額・残高・見積を示して利用者に直接承認を求める。既存キー・家族1世帯・現行機能維持・新AIの本登録/変更/削除/応募/通知禁止。未知情報元の探索は隔離評価で実証し、本番常時探索への変更は別承認。標準モデルの恒常的費用増も別承認。通常の修正・テスト・安全確認後の本番反映は一括で進める。無課金作業は承認待ちでも継続。
## 1. 前回の本番未確認事項を最初に確認
parity-prod-check 等の実データで、Web告知全文保存、X API停止期間（11/23 06:40 JST〜11/26 22:10 JST）の投稿補完（取得可能な期間/件数、重複排除、期限切れは現行の通知/登録を発生させない）、取り直し時の全文引継ぎ、画像参照→取得→解析の実績、未取得リンク25件の完了/失敗理由、再評価抑制、待ち102件の処理実績・最古時間・残予算、自律型発見の失敗1件を確認。既存のAUTONOMOUS_COLLECTIONの実際の機能と費用（前回10日632.01円、別予算）を把握して新AIの探索と混同しない。収集停止や予算切れ、取得・保存失敗が画面/運用で分かるか点検。再発の横断監査は必要箇所に継続し、開発限定フラグ・依存注入・本番権限・キュー・時間/費用で機能が実質停止していないか確認。安全な意図的制限は維持。新規案件不足なら未確認とし、実データの隔離再生で補う。
## 2. 保存済み全文の活用（最優先）
- generate.ts fetchPage は collector文書に structure.links が無い場合にlive取得を優先し、リンク先も短いlast_goodの擬似HTMLを先に返し構造・時刻を失う場合がある。collected-store.ts は structure:null、textLoss:null。取得時点のページ構造（受付枠・見出し・リンク・フォーム・日時の対応・画像参照等）と原文の整合を確保し、保存済み証拠をAIに再利用させる。不要な再取得を避け、過去時点評価と現時点の鮮度確認を分ける。必要なら再取得し、版・取得時刻・由来を保持。loadBestDocument の長さ優先で古い版が選ばれる問題も検討。収集時の生の意味を失わない整形テキストを保持（無断の原HTML永続保存は不要）。
- Xの長文・引用元が上流で切られたのにcollector_postが全文扱いされる可能性、保存済みpost全文が種に利用されるか、再取得リンクの更新が本文hashだけの重複判定で新AIに届かない可能性（link-recheck→shadow enqueue）、同じ本文でも画像・リンク・受付枠が変わる場合を点検し是正。失敗時に既存証拠を失わず、取得上限と実測を明示。
- 利用者の要望: 将来的にはヘッダー、フッター、共通メニュー等の無関係な文字を削減して効率化。今回は取得原文を不可逆に削除せず、原文とAI提示用の関連情報ビューを分離する設計・小規模実証を行う。DOMの意味/構造、反復する共通部分、関連セクションを活用し汎用化。特定店舗向け固定ルールを増やさない。ナビゲーション中の応募リンク、フッターの店舗住所・条件・注意、画像、動的受付枠等を誤って除外しない。原文への位置対応、除外文字数・理由、未提示の明示、AIによる全文read/復元経路、根拠照合を保つ。既存の本文整形・索引機能を調査し再利用。削減率、実際のトークン/費用/時間、重要項目の欠落/正答、追加readの効果を同一証拠で比較。精度を犠牲にする圧縮は採用しない。効果が小さい場合は後続に回し本工程の主目的を遅らせない。
- 取得→保存→提示→判断の実測: 取得成功/失敗、整形後文字数、保存文字数、提示したユニーク文字数/範囲、追加read、入力トークン、ページ構造の保存と利用、重要項目の根拠の位置。上限値や同じ文字の繰り返しを実績にしない。HTMLバイト等未記録なら必要最小限の計測を追加。直近本番のX/Web別・画像・長文別に評価。
## 3. 調査・判定能力の改善
- 前回未見の全項目72.9%を改善。公式情報への到達、二次情報の適切な補助利用（確定と区別）、所在地・購入/受取・発表期間・応募方法/条件、ログイン必須でも公開告知で判明する情報の活用、複数機会、長文後半の条件を優先。検索1回で不足するなら2回以上や再開を比較。情報があるのに取得/提示/判断/検証で消える原因を区別し、追加調査の必要性をAIに判断させる。期限や予算で常に不可能な設計は調整。取得できない公開情報は推測せず、ログイン等を迂回しない。任意項目不足のみで保留しない。
- 前回のモデル比較はHaiku＋適応型17/21、Sonnet全段18/21、項目111対100、費用115対235円で適応型維持が妥当。ただし調査モデル単独の効果、調査effort、検索回数増加は未検証。同一初期証拠・時刻・ツール・予算条件で必要最小限の比較を行い、調査で得る証拠と同一証拠での判断を分離する。Sonnet調査＋Haiku判断、Haiku調査＋Sonnet判断等を比較し、有望構成を未見で確認。Haiku優先に固執しない。SonnetのAPI互換性（強制tool_choice等）と実際のモデル/effort・予算切れ・失敗を確認。現状の採用構成を変えるなら根拠・費用を提示し必要な承認を得る。残額約160円で不足なら直接増額承認。無意味な全組合せの反復は避ける。
- 収集対象はポケモンカードBOX/パック/シングル等及びポケモンカードを含む福袋・セット。カード以外のみ/他TCGのみは除外。福袋の封入が不明なら追加調査し確定不能を示す。混在告知は対象機会を拾う。research-ai.ts のaskHuman例にカード以外を管理するかという既に解決済みの方針が残るので修正し、調査・判断・既存発見経路で整合させ、実例で検証。人への再確認は不要。
- worker.ts の12時間再評価制限は期限直前・締切変更・新規公式リンク・重要条件変更・人の修正等まで遅らせないようにする。表示上の微差による重複費用は抑えつつ、意味のある証拠更新を優先し、期限/優先度・待ち時間・予算を考慮。無制限再試行禁止。待ち102件を一律再実行せず、期限切れ・重複・変更・新規/重要案件を判別、正常な現行抽選データは削除しない。
## 4. 採点と正解の信頼性
- intensive-score.mjs のmissedOppsで判断だけ数え、未取得機会の項目を分母に入れない問題を是正。機会の漏れ・余分・誤分割/誤統合、誤った追加登録、すべての記載あり項目（未取得機会もmissing）を採点し、対応した項目だけの精度と全体の取得率を区別。単一機会は一致0でも対応する、語の部分一致で異なる店舗/商品/受付回を対応させる、sameOppRecsを無条件に許容する、extraRecsの誤登録が判断誤りに入らない等を監査。機会の同一性は原文・受付構造・URL・商品/店舗/期間を照合し、不確実な対応を明示。捏造0は記載なしの観察値に限定した指標と区別し、誤値/根拠なし推定も測る。全試行費用・失敗を含める。既存の保存済み評価結果を無課金再採点して前回値の訂正を示す。
- 全項目の正解入力は必要時のみ。unknown_fields 16件・snapshot 4000バイトのDB制約が実用上障害なら安全な移行を検討して別途承認。切捨て禁止、拒否時の説明、証拠版・原文・時刻・判断・修正値の保持を確認。人への依頼は公開情報で解けず有益な案件だけ。全項目/期間/複数機会の確認を可能にするが、利用者の入力を開発の前提にしない。
## 5. 未知情報元の自律探索と実用化
- 既存の自律型発見133完了の内容・失敗・費用・既存収集との関係を調べ再利用。AIが既存の情報元に限定せず未知の系列・店舗・応募サイトを公開情報から探索し、公式確認・対象地域/通販・商品適合・開催回・重複を判断して新しい機会を見つける隔離実証を進める。過去・現在の実告知を活用し、新規抽選が少なくても評価可能にする。発見数、既存にない実在機会、重複/誤発見、公式到達、費用・時間を示す。完全な母集団が不明なら発見率を断定しない。既存候補内判断と未知情報元発見を分ける。評価での検索は安全・予算内、公開アクセス規約遵守。本番自動登録・常時探索の解禁は今回行わない。
- 新しい未見案件（既知系列・開催回との重複に注意）で独立した正解を作成し、同じ条件の改善前後比較を優先。前回12/13は候補単位かつ小標本。正確な機会単位、重要項目・全項目、不要保留、誤登録/誤除外、画像・長文、未確定、モデル・費用を測る。実用化の暫定目安（重要95%、全項目85%、不要保留20%以下等）と安全性・母数を踏まえ、次の人確認付き登録への段階移行に必要な条件を示す。無理な数値達成や過剰な基盤開発ではなく具体的な実運用改善を優先。
