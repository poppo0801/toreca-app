# Phase 2 P2 原因究明・実用性改善：応募単位unknown／保留過多／自律検索の不達

作成日 2026-11-23。基準: PR #98 `feat/phase2-real-ai-preview`、`docs/reports/2026-11-23-phase2-p2-real-ai-results.md`。ユーザー要請：**応募単位の確定が2/15にとどまり、unknown 13/15・保留8/15だった原因を徹底的に調査・試験する**。検索0/3・根拠なし除外1件も同一工程で原因まで追う。

## 重要：ChatGPTによるコード確認で特定した優先不具合
- PR #98 の `src/lib/judgment/xsource/x-origin.ts` にある `cachedTools(tools)` は `fetchPage` と `now` しかオブジェクトにコピーしておらず、受け取った **`tools.search` を返却していない**。
- `runXPostReplay` が `cachedTools(a.tools)` を `runResearch` へ渡し、`research-loop.ts` は `searchAvailable: !!args.tools.search && L.maxSearches > 0` を用いている。よってP2の実行経路では検索ツールが消失し、**AIには検索不可と通知される／選んでも実行されない**と読める。「AIが検索を選ばなかったのは文言のせい」という過去の原因分析は未立証。**まず実行時の `searchAvailable`、検索ツール到達性、予算予約、実呼出しを証拠で確認し、配線を修正する。**
- `cachedTools` 修正後も同一URLキャッシュ・安全な検索境界・回数制限・機密保護を保つこと。**検索を常に実行する固定ルールにせず、AIが検索の価値を判断できるようにする**。P2後の「検索しなければ到達不能不可」という強い指示が検索の無駄打ちを生まないか対照テストする。

## 安全境界・費用
- 実施範囲: **原因分析、Git管理外の既存P2記録・実候補・証拠のローカル読み取り、保存ページの無料再生、開発DB、擬似AI/検索ツールの注入、改善実装、単体/統合/E2E、独立gold作成の補助、非本番PR・報告書**。
- **有料Anthropic推論・web_search・X APIの新規呼出しは今回未承認。P2の20円枠・P3提案10円を流用しない。** 無料の公開ページ取得は既存 robots/SSRF/頻度制限を守る場合のみ。外部APIを無料と思い込んで実行しない。
- 本番DB/Storage/cron・Vercel・環境変数・通知・応募/購入履歴・実装PRのmainマージ・自動登録は変更禁止。作業はPR #98の最新headを起点に積み上げる**別の開発PR（baseは #98 ブランチ）**。ユーザーの途中承認は不要（上記の安全範囲だけ）。本番に影響しない既存のテストを壊さない。個人情報・原文・gold・APIキーはGit/ログに出さない。

## 1. P2の15件を項目単位で再現・原因分類
- `eval/real-data/proposal-real-result.json`、`proposal-real-audit.jsonl`、`p2-review.md`、保存済み原文、評価DBの提案15行を調査し、**入力に含まれた原文／構造化情報／AIに見せた抜粋／AIの調査手順と終了理由／判断フィールド／検証issues／最終decision**を区別（秘密を伏せてGit管理外に記録）。
- 13件の `apply_unit=unknown` は「原文にも情報なし」「原文にはあるが取得・抽出失敗」「parseApplyPage/structureToObservations の読み落とし」「EXCERPT_CHARS=2500による切断」「AIが読み取ったが出力しない」「フィールド名・enum・basis変換/検証の落下」「scope/quote/textLossなどの検証が保留」「根拠のない推測を正しく拒否」の**どの段階か**、証拠で分類。未確定のままが正しい例も数える。AIに毎回確定させない。
- `register/tentative/exclude/none` と `verified/held` と応募単位 unknown を別の軸で数える（保留8/15に至る複数原因の分解）。**registerなのに応募単位unknownの3件**、`lp/4`（9枠）`lp/11`（7枠）`lp/12`（2枠）、`lp/1,2`、gold 3件、`r10:2`（根拠なしexclude）、`r10:4`（fields欠落）を優先し、原文に十分な根拠があるのにunknownかを個別に検証。
- 同じイベントに複数受付枠があっても「複数応募できる」とは限らず、選択式・店舗別独立・商品別・1フォーム1応募等、**実際のフォーム上の権利単位**を人が原文から判定する。URL／応募単位／表示カード数を混同しない。
- `proposal-real.mjs` の試験は15件で **検索0回**という事実と、配線欠陥の説明を区別する。AI側のプロンプト原因と結論づける前に配線/ツール到達/プロンプト変化の効果を切り分ける。

## 2. 根本原因を再現・修正し、回帰防止
- 検索ツールを注入した `runXPostReplay` の結果で、agent入力 `searchAvailable=true`、`next.kind=search`、検索呼出し1回、取得した検索結果から適切な候補ページへ進めることを**偽検索プロバイダーを使った実際の通しテスト**で確認。検索を注入しない場合は従来どおりOFF、検索の上限/予算枯渇/重複の禁止/host安全検査を維持。直接 `runResearch` を試すだけでは不十分。
- P2でAIに実際に届いた文脈、予算・上限、検索可否、原文抜粋、募集枠構造と各候補の対応を確認。**調査側**と**判断側**の入力差分を可視化し、応募単位の重要な根拠が後者に渡っていない場合は修正。
- 検証で重要な根拠が落ちていたか（対応未確認/本文欠損/引用一致/正規化/列挙値変換）を試験。検証の基準を緩めるのではなく、正しい証拠の渡し方、引用、構造の読み取りを改善。
- 既存の `exclude_without_evidence` が **実際の登録案状態で安全に保留・人間確認へ回るか**を検証。issue記録だけでexcludeとして運用処理に伝播するなら、機会喪失を避ける停止策を提案・開発側でテスト。人が確定した履歴・応募機会は保護。
- `fields` 省略を空として扱う変更で**「判断成功」と誤カウントしない**。取得不可・出力不備・エビデンス不足を分けた診断を整備し、API利用がなくても試験可能にする。
- 一時しのぎの店舗別/販売元別の固定判定を加えず、応募フォームの意味解釈はAI主体。AIに過度な保留や乱暴な推測を促さない。

## 3. 評価セット・対照実験（無課金）
- 既存の P2 15件を回帰セットにする。これに応募単位を確定しやすい明示事例、原文に何もない正当なunknown、店舗選択式・店舗別独立・複数商品・複数受付枠・応募締切/終了・親URL共通・リンク展開不能・日付変更・同一系列別店舗など**幅広いケース**を追加。
- 原文とAI・旧方式の過去出力から独立して、人が根拠を確認したgoldを追加できるワークシート・証拠位置を用意。AIの出力をgoldに流用しない。根拠が確認できないケースは `unverifiable` と区別し正答率の分母に混ぜない。ゴールド数が少ない間は一般化しない。
- 無課金の擬似agent/judgeの比較で、検索修正前後、文面変更前後、入力情報の有無、受付枠構造有無、調査回数・検証の有無を**一因子ずつ**対照。可能なら保存済みP2のAIレスポンス（秘密は伏せる）をオフライン再生して判断後工程の差を測定。**モックが成功したことを実AIの精度改善と称さない**。
- 具体的な前後差を「検索が実際に届くか」「unknownになる経路の件数」「根拠のある確定を保てた件数」「不確実なものを保留できた件数」「根拠なしexcludeの防止」「誤統合/誤分割」「推定コスト・遅延」で報告。再試験対象/必要な承認額は原因修正後に見積もる。
