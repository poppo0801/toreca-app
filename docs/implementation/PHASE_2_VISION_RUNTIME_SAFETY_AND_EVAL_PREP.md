# Phase 2：画像実解析接続・収集負荷の安全化・DB移行整備・実AI比較試験準備

- 作成：2026-11-24

- 開発起点：未マージ PR #113（`feat/phase2-post-ui-collector`）。積み上げ元：#98 → #100 → #102 → #104 → #113。
- 背景：PR #113 は「X投稿のリンク先が最初の1件しか取得されなかった」構造的欠陥を修正し、最大24件＋追跡6件の取得、全文保存、画像読み取り結果の注入・再利用、経験から読む位置を提案する仕組みをモックで検証した。**ただし本物のビジョンクライアントは未実装、収集負荷未実測、実AI精度改善も未検証。** 本番115未適用で116〜118適用済み、119も未適用。

## 0. 原則・安全な進め方

1. 新AI基盤専用の開発作業。**PR #113 を基点とする新ブランチ**を作り、実装PRのbaseも原則 #113 にする。#98/#100/#102/#104/#113 の積み上げを壊さない。最新mainのUI・相場管理変更とのコード/DB/テスト互換性を確認し、単純に未マージAIブランチをmainへ統合しない。
2. ローカルDB、無料モック・保存済みデータ、静的検証・テストは一括実行可。**Anthropic等の有料推論、ビジョン、Web検索、X APIの実行は禁止（実接続のコード作成は可）。** 本番DB/Storage/Vercel/cron/環境変数/既存収集/通知/自動登録の変更、新AI本番ON、AI実装PRのmainマージは禁止。実行に必要な外部のキーはコードやログに出さない。
3. 実装詳細・ツール選定・テスト方針はClaude Codeが合理的に設計。目標は**実AI試験を安全に実行できる状態を完成**させること。見せかけの完成宣言を避け「実装済」「モック検証済」「実API検証済」「本番反映済」を厳密に分ける。
4. 既存機能、ユーザーの登録・履歴・通知を保護。構造的な情報欠落をAIの判断のせいにしない。情報が取得できない場合は「存在しない」でなく未確認と理由を残す。

## 1. 画像解析を実際のAPIに接続できる状態まで完成させる

PR #113 の `VisionClient`、`image-evidence.ts`、`evidence_image_observations`（migration 119）を活用し、X投稿・公式告知・応募ページの公開画像に対して実運用可能な取得・ビジョン処理を実装。

- **画像の安全な取得**：許可されたHTTP(S)、SSRF保護（DNS解決・リダイレクト先・内部IP含む）、robots/アクセス利用条件、認証・私的URL回避、content-typeと実バイト形式の検証、サイズ/ピクセル数/形式/時間/画像枚数/リダイレクト上限、並列数・ホスト別間隔、取得失敗の分類。必要なら加工（縮小/向き修正/安全な形式変換）。不適切なファイル・偽装レスポンス・過大画像でのOOMや無限ループを防止。
- **AI接続の実装**：プロバイダの正式API・既存Anthropicクライアント等の適切な方式を調べ、画像バイトを実際にモデルが参照できる実クライアントを開発。応募日程、店舗/系列、対象商品、申込方法・応募制限等を抽出。複数画像それぞれの画像ID/出所/位置の説明/原文の抜粋と解析の信頼度・失敗理由を関連付ける。画像内文言の抽出結果を証拠原文と混同しない。
- **本文・画像の照合**：日時・店舗・商品・応募単位などの一致/矛盾/未確認を具体的に記録。画像が重要情報の唯一の情報源でも黙って排除しない。既存の安全な登録検証を弱めない。
- **再利用と費用制御**：既存読み取りや保存済み画像解析結果は安全に再利用し、画像内容・版が違う可能性やURLの再利用時の鮮度も扱う。モック結果と実解析結果は絶対に混ぜない。画像費用・入力/出力トークン・最大枚数・総予算・停止/二重実行防止・失敗時の再試行を、既存のリアルAIゲートに統合。キーを持つだけで有料APIを発火させない。
- 実APIアクセスは禁止。**モックビジョン・ローカルのテスト画像のみで、画像取得 → 解析入力 → 根拠/未確認 → 保存 → AI調査 → 登録案まで検証**。画像データを公開Gitや機密を含むログへ載せない。保存期間・著作権・個人情報・容量方針を比較し、実装方針と未解決事項を報告。

## 2. 複数URL取得の実運用上の負荷・安全性

PR #113 の最大24リンク＋深さ1の6リンク、1投稿90秒、抽出テキスト、`linkLedger`、`evidence_documents`を土台に、**投稿単位の上限と同時に収集が走った場合の全体上限**を横断監査・修正。

- ホストごとの取得間隔/同時接続上限、複数投稿にまたがるレート制御、キュー/キャンセル/締切超過、robots/SSRF/リダイレクト、失敗時停止・リトライ/バックオフ、DB容量/全文保持、タイムアウト、課金推定、収集スケジュールの締切、Vercel等の実行時間制限との整合を確認。
- 大量リンク・遅いホスト・429/403・応答不正・画像大量・URL順序変更などの保存済み再生/モック負荷試験を実施し、**実際のURL取得を必要としない負荷・アクセス数・時間・保存量の見積**を提示。必要なら取得計画・再利用・段階的処理を変更するが、**候補リンクと未取得理由を捨てない**。
- 取得範囲をむやみに縮めて取りこぼしを隠す設計は禁止。取得できた全文の保管と後段AIへの到達・出所/店舗対応付けの保証を維持。段階的取得を採用する場合も、未取得分の追跡可能性・再調査経路と利用者に見える未確認を保つ。

## 3. DBマイグレーション115／119の順序問題を解決

本番には116〜118が適用済みで115・119は未適用。タイムスタンプ順の問題があるため、**既存履歴に破壊的な変更を加えず、将来の本番適用を安全に実行できる具体的な方法とコードを整備**。

- 本番相当のスキーマ・migration履歴をローカルに再現し、115依存の119のテーブル・FK・RLS・復元を検証。移行の先行条件、失敗点、番号の付け替え／新しい順序での再定義／適切な手動適用等を比較して、一つの安全な方法を選ぶ。
- 必要な場合、未適用のAI migrationだけを整える。既に本番適用済みの116〜118の履歴・実データを壊さない。古いブランチとの衝突も整理する。**勝手に本番へ適用しない**。バックアップ・復元・ロールバック（適用後のデータとの整合も含む）リハーサルをローカルで実施。
- 本番反映時の段階的な安全な導入・OFF制御・既存本番機能との共存手順を明確に報告。

## 4. 実AI比較試験を実行可能にする（有料実行はしない）

単なる試験案ではなく、**同条件の比較を実際に実行できるスクリプト/評価コード/独立gold基盤**を用意。

比較対象：
1. X投稿の複数URL旧方式（1件）vs 新方式（複数取得）による応募機会・根拠の取りこぼしと混同。
2. 長文の先頭抜粋vs全文+readによる応募条件・応募単位・上限の抽出。
3. 画像ありvsなしによる応募条件の復元と矛盾検出。
4. 応募単位、店舗、商品、受付期間、対象地域、URL、登録/保留/除外の正しさ。
5. 経験ヒントなしvsありによる網羅性・最初に読めた条件の位置・費用・時間・人の修正率。

- 保存済み実データと、可能なら人が根拠を確認した**独立gold**を使う。モックAIの自己採点を精度としない。独立gold不足は明示し、必要な追加件数を提案。固定ルールへの過学習を避け、初期の幅広い探索を維持。
- 全条件で同一の案件・証拠・設定・モデル（比較対象以外）・費用算出法を使用。登録案が根拠の引用と正しい項目に紐づくか検証する。
- 試験の停止条件：総額/1案件予算、画像枚数、最大取得回数/時間、誤登録防止、実行ロック。**事前に dry-run で件数・費用見積・API呼出し計画を提示し、実行には別途承認を必須**。
- 実装したテストランナーをモックで実際に動作確認し、実API試験時に使う手順・件数・比較表・合否基準を報告。
