# Phase 3 — 適応型判断と実運用の正解蓄積
## 目的・優先関係
起点 main #164、docs/reports/2026-11-26-phase3-runtime-correctness.md。今回の成果はHaikuが初回3件中2件、Sonnet判断が3件中3件の期待結果に到達したこと（案3は推定であり独立の正解確定は未完）。少数・反復改善に使った案件であり一般性能を証明しない。次は同じ3件を延々と再試験せず、多様な実案件に対する精度と費用を改善し、日常利用から正解を蓄積できる仕組みを整える。AIの調査・推論・判断を自律的に行わせ、個別店舗向けの固定判定を増やさない。既存の正常な機能・資産を最大限再利用する。最新の本指示と明示承認を過去文書の相反する条件より優先。
## 承認・運用
- Claude Code は当面 Opus 5.5 を使用（アプリ内APIとは別）。難しい設計/原因調査を先に一括で実施し、後続が通常UI等になった段階でSonnetへの切替候補を報告。開発モデルの自動変更は不要。
- 現在承認済みは1件25円・日次85円・通算130円、期限11/28 13:45 JST、家族1世帯、既存キー、新AIの本登録/変更/削除/応募/通知は禁止。現行の収集・登録・通知は継続。実装・検証・安全確認後の通常PR/CI・本番反映・少数実評価まで一括で進める。費用不足時は必要額・用途・現在の実費/引当/残額を提示してユーザーに直接承認を求め、承認後に更新し続行。ChatGPTを経由しない。期限延長は別承認（期限で実評価が阻まれるなら明示して直接求める）。起点や台帳をリセットせず、新規キー不要。予算不足でも無課金作業は継続。
## 1. 判断モデルの適応型選択（最優先）
- 実際の本番共通経路、モデル指定・許可証・各呼出しの費用予約・保存・再開機構を確認する。調査は当面Haikuを基準とし、判断はHaikuで通常処理、重要な情報の未確定・矛盾・検証失敗・複雑な応募構造等でより高い判断能力が必要な場合にSonnetを選ぶ方式を実装・検証する。これらは選択理由の例であって、店舗固有の固定ルールではない。明らかに複雑な場合の直接Sonnetも比較し、機械的に全件二重実行しない。既に十分な根拠があり登録/除外できた案件も少数抽出して誤判断を監査し、保留だけを見る選択バイアスを防ぐ。情報そのものが不足・取得不能ならモデル変更だけでは解決しないため追加調査または適切な保留。APIのOpusやeffort引上げは必要性を示せる場合の比較に限り、標準化を前提にしない。
- 前段の取得済み証拠・調査結果を再利用し、無用な検索・取得・画像解析の再課金を避ける。Sonnetが異なる結論を出しただけで正解扱いせず、根拠・対象・時刻・矛盾と検証で評価。失敗/予算不足/時間不足で検証済みの前段結果を消さない。選択理由、モデル/effort、証拠の版、各段の判断と根拠、検証・費用・時間を保存。既存の単一モデル運用への切戻しを用意。
- 前回の判断から調査へ戻る機能は本番未発動。必要な場合に検索、リンク追跡、画像等を活用して調査へ戻れるか確認する。複雑案件を見つけるために調査モデルを上げる必要があるかも検討するが、結論は実証に基づく。既存の安全・予算・時間上限を維持。無限ループや全件Sonnet化を避ける。
## 2. 残存欠陥の重点レビュー（新規の過剰な設計は不要）
- research-loop.ts の推定応募単位の検証は観察用の語彙検査を外しただけに見え、引用なし/無関係な引用/単一ページに複数受付枠などでも register が通らないか実コードで調査。推定は認めるが構造的根拠と対象対応を要する。口数の不明を自動的に保留理由にしない。登録必須項目の欠落や検証成功の意味も確認。検証済み＝人が正解確定とはしない。
- 追加調査・再判断で前の検証済みの出力を失う経路、store.ts の旧版supersede→insert失敗/中断/同時実行で現行版が無くなる可能性、各試行の結果・費用の保存（同じ結果を重複表示しなくても試行記録は残す）、基準時刻と実時刻の分離、実行上限直前の呼び出し、費用の最悪予約とモデル別入力/出力/ツール定義/検索/画像/再試行の整合を調査。概算で保証できない場合は実際のトークン計測等の適切な手段を使い、上限を守る。重大な実害のある欠陥のみ今回是正し、理由とテストを示す。
- 旧誤計上約16円は実費確認なしに減額しない。既存履歴は保持し、追記型調整が必要なら証拠と権限を検討。予算の増額で解決できるだけなら大規模な台帳再設計は延期。
## 3. 実運用レビュー・正解入力（既存UIの拡張）
- 既存 src/components/proposal-preview.tsx、src/lib/server/proposals/review.ts、store.ts、experience-store.ts、gold-review 等を実際に調査し再利用。現在のプレビューは候補詳細中心で店舗/商品/締切/応募単位の4項目しか修正できず、hold/approve_with_edits/rejectだけではAIの保留を登録すべき等の正解を十分表せない可能性がある。
- 管理者向けに「AI評価・要確認」等のコンパクトな一覧を既存の管理画面/候補UIに自然に追加（独立した大規模管理アプリ不要）。現行で既に登録・除外済みの案件も含め、AIの保留・失敗・現行との食い違い・根拠不足・多様な情報形式を優先。絞込は未確認/確認済・AI判断・情報元等、優先度は締切や不確実性。全件確認を強いない。正しい登録案や除外案も任意でレビュー。候補から登録案を作れなかった/取りこぼした機会も簡潔に記録できる入口を設ける（既存管理機能を流用、現段階では現行が見つけた候補との比較が中心、AI独自発見は未実装と区別）。
- 詳細では取得元・応募先へのリンク、取得時刻・原文/画像または保存済み証拠、AI判断・理由/検証指摘・現行判断、使用モデル・必要な版を比較できる。原文は長くても折りたたみ、確認操作を簡潔に。スマホ向け既存UIの余白・操作様式を守り、入力の自動フォーカス/自動プルダウンは行わない。
- ユーザーは「正しい（変更なし）」「正解を修正」「まだ不明/後で確認」を選べる。正解の判断（登録/除外/保留、機会の実在と利用者適合）、必要な項目（系列/店舗/商品/応募期間/発表/受取/条件/応募URL/応募単位等は既存アプリのスキーマを優先）、不足した商品・店舗・応募機会の追加/誤分割・誤統合、明示的不明を表現できる設計。変更箇所だけ入力、正しい項目まで再入力させない。未確認と確認済みを混同しない。根拠は参照・短い補足でよく、毎回全件の引用転記を強制しない。人が示した正解とAI出力を別に保存。レビュー操作で実際の抽選登録/削除や通知が発生しないことを明確に表示。
- 正解記録に候補/応募機会/版・証拠版・時刻・修正者・判断と項目単位の確認状態・変更前後・根拠・未確認を保持。再評価で旧正解を失わず、内容が変われば再確認対象へ。正解を過去データに直接上書きしない。AIが自ら正解を確定したり人の修正を上書きしたりしない。既存レビューとの互換と世帯/RLS/権限・モック/実AIの分離を確認。
- review.ts の recordHumanExperience は利用者セッションで呼ばれ失敗を握り潰す構造、experience-store.ts は既定 mode=mock、書込みはサービス権限のみという記述、未編集項目を人が確認済みとみなす実装がある。実際に本番レビューが経験/正解として保存されているか、確認していない項目や別ページ版をhuman扱いしていないかをコード・RLSで検証し必要なら是正。レビューからモデルの重みが自動更新されるとは称さない。人の確定情報を汎用の経験・評価データへ活用するが、特定案件の正解を未見評価へ漏らさない。
- Claude Codeが数日分の失敗傾向を分析できる読取専用の集計/エクスポート（既存機能を活用）を用意。正解確定数、判断精度、重要項目、取りこぼし、不要保留、誤除外/誤登録、形式別、モデル選択・追加調査の効果、費用を区別。未確認を正解/不正解に数えない。原因分析・修正の自動化/学習用の大規模機構は今回は不要。
## 4. 実案件による検証・本番反映
- 現在のLINE合言葉応募、家電量販店の会員限定福袋を含む実運用の異なる形式を少数選ぶ（公式サイト・フォーム・画像等、実候補があれば）。実証拠で正解を確認し、確認不能は未確定とする。LINEの非公開トークやログイン等の制限を迂回しない。告知から応募方法/対象条件が確認できる場合は応募先の中身まで確認できないだけで一律保留にすべきか、実用上必須の情報と区別して判断する。過去3件は回帰用であり、新規精度評価から分離。
- 同じ証拠・基準時刻・出力仕様で必要最小限のHaiku/Sonnet比較（判断段階だけの比較と実運用全体の比較を区別）。適応型選択が安価なモデルの正解を維持しつつ不足を補うか、選択理由・追加費用・時間・失敗を示す。少数の試験で統計的優位を断言しない。実案件で発動しない機能は未検証として扱う。
- 最終変更後の型検査・lint・単体・DB統合・関連E2E・build・CIの結果を件数と実施版で報告。モックの合格をAI精度の証明にしない。特にレビュー保存/再評価/別世帯/失敗/スマホ画面をE2Eで検証（実機は未確認なら明記、実画面スクリーンショットを報告書から参照できるようにする）。DB変更時はバックアップ・plan・互換性確認。本番反映後に実データで動作確認、現行に影響しないことを確認。ユーザーによる実レビュー前に架空の正解を本番に保存しない。
- 完了報告をGitHubにpushしPRで共有、スマホ通知。各要件の実装・テスト・本番・実データの状態を分け、残る欠陥・未確定・費用・追加予算の承認・期限・次に必要な操作を記載。目的を満たせない場合は完了扱いせず原因を示す。次の開発が主に通常UI/操作改善・軽微な保守となったかも報告し、Claude CodeのSonnet切替判断に使う。未知店舗の自律探索や全面自動登録は今回の検証を踏まえて別工程とする。
