# トレマネ：UI改修後に実施するAI情報収集基盤の追加改善（保留中の実装指示）

作成日：2026-11-23
状態：**指示書のみ。作業開始はUI改修完了後。現在は実装しない。**
対象：PR #98 → #100 → #102 → #104 の新AI基盤（現時点すべて未マージ）。特に #104 の `feat/phase2-evidence-coverage` を後続の起点とする。
目的：収集段階の情報欠落、画像証拠の未連携、経験の再利用不足を解消し、AI自体の性能と構造由来の精度劣化を区別する。

## 0. 開始条件・作業ブランチ
- **UI改修を先に実施する。** 本文書を作成・mainに保存することはAI改修の実行許可ではない。
- UI改修開始時は最新 `main` を起点にUI専用ブランチ/PRを作成。既存の未マージAI系PR #98/#100/#102/#104 を勝手に統合・削除・改変しない。UI改修にマイグレーションやAI側共通部品の変更が必要な場合、差分・衝突・本番影響を検証し、人の承認なしに本番設定や機能OFF状態を変更しない。
- UI改修後に本指示を実行する際は、最新のPR #104を検査し、最新mainとの競合、UI側で変更された同一ファイル/スキーマ/契約の差を最初に確認する。**単純に旧ブランチをmainへマージしない。** AI系の積み上げ関係・未適用migration 115を考慮し、最適な作業順序を決める。原則 #104を起点に新しい実装ブランチを作り、実装PRのbaseを #104ブランチとする。UI差分によって変更が必要なら根拠を報告し衝突を解決。
- 開発/ローカルDB/無料の保存済みデータ再生・モックAI・テストは実施可。**有料Anthropic推論/web_search/X API、本番DB/Storage/Vercel/cron/環境変数、新AIの本番ON、自動登録・通知、AI系実装PRのmainへのマージは別承認。** 既存個人データ・本番機能非干渉。API費用を暗黙に発生させない。

## 1. まず「X投稿リンクの最初の1件だけ取得」の事実関係を徹底確認
最重要。以前、X投稿内の複数店舗・商品・リンクと候補の対応付けを改善した経緯がある。PR #104報告書は `x-rich.ts` の収集で **外部リンクの最初の1件のみ取得**と記載するが、これが全収集経路共通か一経路のみか、以前の修正との関係はまだ未確認。

**先入観なくコードと実動作を追跡**：
- X本文のURL/entitiesと展開後URL、親/スレッド、リツイート/引用、複数店舗・複数商品のリンク、linkMapと候補分割、関連する抽選ページへの到達を、取得・保存・判断まで系統立ててトレース。リンクを「発見できる」「項目に紐付けられる」「本文を実際に取得する」「原文を保存する」は別々に検証。
- `x-rich.ts` およびその他すべての収集経路、旧方式・新AIの検索/再取得・キャッシュ・リンク展開の違いを実コードで確認。過去の複数URL修正が壊れていないか。最初の1件のみ取得する動作が確定したら、**具体的な処理箇所、影響範囲、導入経緯、未取得の他リンクがどこで失われるか**を報告。
- 同一投稿内で（A）店別応募URL3件、（B）共通親URL＋個別店URL、（C）URL順序を変えたもの、（D）応募ページから先の正式フォームへのリンク、（E）短縮URL/追跡URL、（F）無関係・危険・ログイン必須のURLを再現。**A/B/Cで情報や登録候補が欠けず、対応関係が混ざらないこと**、Dは根拠と取得必要性に応じ安全に追跡すること、E/Fでは安全に停止・記録することを契約テストで証明する。
- 以前の修正との食い違いが「リンク先取得だけ1件」「候補化から落ちた」「別ルートでは全件」「報告書の表現誤解」のどれかを確定。推測を事実として扱わない。

## 2. 収集時の網羅性を根本改善する（F1の残課題）
- 取得した公開情報を**後から再解析できる形で可能な限り欠落なく保存**する。新AIで設計済みの `evidence_documents`（migration 115：ローカルのみ、未本番適用）と整合させる。収集時の3,000字、投稿3,500字、link数5、linkMap30、最初の1リンク、取得本文6,000字、保存最大2ページ等を**上流から下流まで**監査。単純な定数引上げだけでなく、どのリンク・文字・ページが失われたかを観測し、可能な限り損失を解消する。
- 全リンクを無条件でクロールするのではなく、初期は**広く深く取得**する。項目との関連性、複数開催回、転載/親リンクの共有をAIが判断できるよう、候補URLの発見と安全なページ取得を分離する。robots・利用条件・SSRF・リダイレクト・アクセス頻度・ホスト別/候補別件数・バイト数・時間・保存容量・停止上限を維持。禁止/認証ページは未確認と記録し、無理に回避しない。
- 原文/出典ID/取得URL/取得時刻/情報範囲/切断・未取得理由/更新版/応募項目ID/ページの本文範囲を保存して適切に再利用する。キャッシュを共有しても項目間の証拠スコープが混ざらないこと。
- 本番収集処理の変更は動作・費用・アクセス負荷に影響するため、**開発環境で実装・ローカル検証まで**。本番反映は新たな承認を要する。

## 3. 画像を一次情報として扱えるようにする（②）
- 現状は画像参照最大4、収集時の画像読み取り情報は新AIに渡せるが、**画像そのものを新AIが直接検証するビジョン経路は未実装**。
- X投稿・公式告知・応募ページの画像について、必要性に応じて取得・安全な保存・ビジョン解析・出典と画像番号/文字領域の対応付けを設計。画像の文言に期間/店/商品/応募単位が記載され、本文には無い例と矛盾する例を用意し、曖昧な読み取りは未確認にする。画像解析の仮説を原文の確認済み事実に昇格させない。
- 取得量・画素数・画像形式・メタ情報・圧縮・著作権/個人情報・トークン費用/コスト上限を評価。既存画像解析との重複課金を避け、取得/解析結果を再利用。**有料ビジョン実行は新たな明示承認まで禁止**。模擬画像読み取り/偽クライアントで経路テストする。
- 画像の有無により、抽選候補/登録案/未確認事項に適切な状態が残り、重要条件を無言で除外しない。

## 4. 調査経験から自律的に改善する構造（③）
ユーザー方針：AIが有用な特徴の組み合わせを自ら発見することを優先し、サイト・販売元・HTML構造・文言・見出し・重要条件の位置・成功/失敗・人の訂正を柔軟に関連付けて次回調査へ活用する。例「LivePocket＋晴れる屋2という文言なら、重要条件は注意事項の後半に多い」は**ヒントの例であり固定ルールではない**。
- PR #104 の `evidence_coverage_stats` と既存の判断理由・レビューから、確実な記録と未確認の仮説を区別した経験を蓄積する設計を評価・実装。単なるホスト別平均では不足。特徴を自動/半自動的に発見し、類似する過去ページ・調査成功/失敗を検索できる形（検索索引/メモリ/RAG等の具体手段はClaude Code自身が比較し選択）にする。
- **記録するだけで終わらず次の調査へ実際に反映する入口**を実装・契約テスト。思い込みの自己強化を防ぐため、引用元、独立gold/人の訂正、バージョンと取得日時、正誤の確信度、仮説の検証結果、適用条件を分離。情報源/ページ構造が変わっても適応できるようにする。
- 重要情報の探索は、学習した優先順位に従って効率化してよいが、**全文の参照可能性と情報欠落検知は維持**。十分な裏付けがない段階では、未確認部分を無断で省略・「記載なし」と判断させない。実験ごとに網羅性・人の修正率・費用・時間・真の正解例との一致を比較し、改善が実証されない最適化は採用しない。
- 自律改善の安全性：新しい特徴/仮説を本番登録ルールや自動削除へ直接反映しない。費用/時間/件数/無限ループ・誤対応・情報漏洩対策、ログからの原文/機密除去、停止・バックアップ・復旧・人の訂正を保持。

## 5. 横断監査と完了基準
- 以前見つかった「cachedToolsの検索配線消失」「AIの既知enumが保存時unknown」「収集3,000字とAI2,500字の二重欠落」「人の修正が別項目へ移動」「画像読み取り未配線」「1MBで取得切れを成功扱い」「12項目超過の無言破棄」等を典型とし、**別経路でも同型の見落としがないか**検査。
- トレースと自動試験は上位入口→実装の収集/解析→保存DB→新AI/登録案→UIまで。長文・複数URL・画像・同名店舗内複数商品・別開催回・並べ替え・古い情報・再取得失敗・並列・API停止・権限の異常系を含む。旧応募/当選/購入/通知/ユーザー別機能非干渉、typecheck/lint/単体/DB統合/E2E/buildを確認。
- 事前に**調査対象・実装済み・検証済み・なお残る制約**を明確に区別し、未検証を解消済みと主張しない。追加有料試験の必要性・上限見積は報告のみとする。
- 報告書 `docs/reports/phase2-post-ui-collector-image-learning.md` に、以前の複数URL修正との整合性（コードとテスト根拠）、失われていた情報の発生箇所・修正、画像経路、経験再利用の実配線、開発テスト、未解決、将来の費用効果をまとめる。UI改修後の最新baseから**未マージPR**を作り、本番への統合は行わない。

**最重要：根拠が不十分なら人に確認を回すことは許すが、情報を見落とした原因がシステム側にある状態を「AIの限界」とみなさない。**
