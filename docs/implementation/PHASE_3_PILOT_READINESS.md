## 2. 本番移行を妨げる重大な欠陥のみ解消（優先順位順）
1. **照合DB取得失敗を重複なしにしない（最重要）**。identity-store.ts loadExistingOpportunities: Supabase の error を確認せず data??[]、catch も空/部分結果扱い。取得結果の完全性と正常な0件を明確に区別。DB障害/ページ欠落は未照合として再開し、正常取得まで新規確定案として扱わない。identity.ts judgeIdentity の候補0件→verified independent を正常な検索の場合に限定。部分取得・通信失敗も同様。AIが意味を決める原則は維持し、新たな意味ルールは追加しない。
2. **照合の再開と既存との重複漏れ**。generate.ts で noTime/budget/judge_failed 等の未照合結果でも processedItems となる。調査結果は再利用し、照合だけ再試行できるようにする。再開した同一候補の完了済み機会も照合対象に含める（現行は同一実行 records.slice のみ、loadExistingOpportunities は同一候補を除外）。候補間の同時実行で後から先の登録が判明する場合も、半自動の確定直前に最新既存データとの照合状態を再確認する。未完了を完了と数えず、時間/費用不足は未照合と明示。既存のキュー・保存を再利用し、過剰な新基盤は作らない。
3. **検索の範囲と確実性**。identity-store の120日/2000・3000件等の上限、DB既定の返却件数/順序、opportunity-identity の上位8件・店舗/商品類似度、選択店舗/商品の切詰めを確認。上限や取得失敗で正しい相手を見落とす危険があるときは、既存索引・ページング・追加検索などの合理的な拡張で必要な相手へ到達できるようにする。全件を常にAIへ投入する必要はない。現在の実データで具体的な弊害を確認し、重大な欠落だけ是正する。未照合の状態を独立確定に置換しない。候補検索は補助、同一性の判断はAI。
4. **評価と本番の費用差**。隔離評価の再開で25円枠が再付与され、36.30円等になっていた。既存の本番通算枠と同じように再開時の累積費用を差し引く。実際の1候補25円での性能・未完了・正しい完結1件の実費を確認。再開上限/候補上限到達時の未完了状態も確定扱いしない。実測は少数の代表例で十分、広範囲の再比較は今回不要。
5. **評価の時点と半自動確定の安全性**。過去の作成日時で絞っても、現在の更新後の抽選・登録案の情報が混ざる懸念がある。利用可能な当時の版/履歴を使い、再現できない場合は過去比較の限界として明記し、新しい時点の独立例で補う。歴史データの全面復元基盤は作らない。identity の overall と対象別判断、照合先ID・予定操作の客観的な矛盾を確認し、誤ったリンク/上書きを人が承認できる形で表示しない。意味の判定を機械的に上書きしない。登録案は自動的に既存抽選を変えない。

## 3. 次の段階を並行して準備：人が確定する登録案の実運用
- 新AIの登録/除外/同一性の提案を、実際に利用者が確認して確定できるUIと処理を既存の登録案レビュー・手動登録/編集・候補管理の部品を活用して準備する。先にUI・安全な実行経路を整える（自動登録を解禁しない）。新規、既存と同じ/結び付け、既存の補足/更新、別機会、除外、未確定を根拠とともに見せる。利用者が修正・承認・却下でき、未完了/未照合と判断の保留を区別する。既存で同じものが登録されていれば追加登録せず、承認した対象にのみ適用する。候補・機会・照合先が古い状態での確定、同時実行や連打による重複、誤った統合、履歴の損失を防ぐ（既存のトランザクション/保護を再利用）。AIに一律の意味判定をさせるための新規ルールは不要。人の確認結果を次の判断に利用できるよう既存のレビュー履歴に記録する。モバイルの実用性も確認。半自動運用開始時の旧方式との役割・競合防止・切替/復帰方法を具体化し、誤って旧・新の二重登録を起こさない。
- 現行運用を止めずに、隔離/テストDBで実案件相当の新規確定、既存リンク、補足修正、独立機会、除外、未照合の扱い、二重確定防止、既存履歴保護の動作を確認。既定OFF、利用者承認前は本番書き込み経路を開かない。必要なら試験的な半自動運用の開始条件と範囲、停止・復帰方法を提案する。データを破壊する操作/自動登録/通知等は本Stageの対象外。利用者が実際に使える段階へ進むことを優先する。
