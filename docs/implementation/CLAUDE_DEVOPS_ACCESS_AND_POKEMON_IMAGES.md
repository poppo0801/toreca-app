## フェーズA：権限阻害の実態診断
1. Claude Codeの現在の実行モード（VS Code/Remote、sandbox、permissions/deny rules、hook、組織ポリシー、CLI実行）、使用可能なgh/GitHub API、Supabase CLI/API/DB接続、Vercel CLI/API、環境変数の有無を**秘密値を表示せず**確認する。
2. 権限拒否の**正確なエラーメッセージ、どの層で拒否されたか**（Claude Code permission、OS、CLI未インストール、ネットワーク、サービス側RBAC、トークン不足）を区別。推測で設定変更や権限回避をしない。
3. 必要な権限だけを表にして、ユーザーによる初回設定が必要なら**操作画面と必要な最小手順**を案内する。管理者トークン/DBパスワード/service-roleをチャットに貼らせない。

## フェーズB：安全な自走経路
- GitHub: gh CLI導入/認証、または既存の安全なGitHub API連携を整備。PR作成・CI確認・承認済みUI専用PRのマージまで。main保護を解除せず、直接pushやforce pushで回避しない。
- Supabase: 適切な管理API/CLI接続、Storageバケット設定、必要なSQL、RLS、オブジェクトアップロードを再現可能なスクリプトに。秘密値はローカル秘密管理・CI secretなどに保存し、git/log/ブラウザへ露出しない。production DBの書換えは対象・バックアップ・復元手順・ロールバックを確認し、今回承認された画像導入範囲だけ実行。
- Vercel: CLI/APIの認証を整備し、プロジェクト/環境（production/preview）を照合してから環境変数設定とデプロイ検証。必要なら再デプロイ。ユーザーが指定した画像フラグだけを変更。
- 自動化: コード変更→branch→PR→CI→承認済み範囲のmerge→Vercel→スモークテスト、Storage/DB変更はバックアップ→dry-run→適用→検証。失敗時停止とロールバック。**破壊的DB変更、広範囲の権限変更、公開状態変更、費用増、秘密情報漏えいの恐れ**は都度ユーザー承認を求める。既存のAI Stage10T/10UやPR #36/#46を本番に混入させない。
- 実行権限は**必要なコマンドだけ**allowlist化し、deny規則・branch protection・人間の承認ゲートを維持。危険な権限回避オプションや強制履歴書換えは使わない。
