# Phase 3 — 本番データでの並行稼働への移行
## 目的・判断
合成R1段階Aの再試験（PR #131、実装 #130）を区切りとし、合成B/C・gold全件再入力・追加の合成精度追求は本番シャドー開始の必須条件としない。現行固定ロジックを維持し、実際の情報を使って自律型AIの発見・解析・検証・判断・費用を比較する。今回の旧1リンク/新全リンク比較は現行固定ロジックとの比較ではない。実運用から学習・改善できる状態を優先する。
## 今回の作業範囲と承認境界
- ユーザーは本番シャドーへの移行方針を承認済み。ただし既存のAI実装PRを無断でmainにマージしないという恒久方針は維持。今回は統合PR・移行計画・稼働準備を一括完成させ、mainへのコードマージ、本番DBへの移行適用、ジョブの有効化、有料本番APIの開始は最終確認用の報告を提出した後の明示承認で行う。運用予算は未承認。R1評価の残額41.42円を本番費用へ転用しない。今回の有料AIは0円。
- 現行本番収集・抽選登録・応募履歴・購入履歴・通知・ユーザーデータを維持する。通常の既存ジョブを停止/変更しない。秘密情報を表示・コミットしない。既存キーの正規の参照経路を使用し、新規キーを増やさない。Windowsでは npm.cmd/npx.cmd。
## 1. 積み上げPRの統合
- #98以降の全積み上げPRの依存・最新head・mainとの差分を実際のGit履歴で確認する（#130 head e0cfbfd、#131 head 40fc6b3 は現時点の参照。#131は報告書のみ）。枝の取りこぼし、未コミット変更、main側の独立した修正、移行番号の競合、古い試験用変更の混入を監査する。
- 最新mainを保全し、統合専用ブランチを作成。既存PRを個別にmainへ順次マージせず、依存を保った統合PRをmain向けに作成する。競合や互換性を自律的に是正。実装の取りこぼしがないことを差分・履歴で示す。実装PRは未マージで終了。
- 本番とのスキーマ差・未適用移行（120〜122等、実際の現状を確認）を精査し、適用順序・後方互換・バックアップ・ロールバック/停止手順を示す。本番への書き込みなし。ローカルで移行のリハーサルと既存機能の回帰検証。ローカル評価データは保全検査の後にテストする。
## 2. シャドーの設計と稼働準備
- 既存のshadow worker/提案保存/読み取り経路/feature flag/ジョブ/管理UI等を調査し、既にあるものを最大限再利用する。新たな大規模な仕組みを無用に追加しない。既定OFF、停止可能、二重起動防止、処理の上限、障害時の現行処理への非干渉を確認。
- 本番の公開情報を使うが、AIの出力は独立の提案・診断・評価領域に保存。抽選の本登録・更新・削除・自動応募・通知・既存履歴変更を一切しない。別ユーザー/世帯のデータ混入防止、RLS/権限、読み取りと書き込み境界、SSRF・外部本文の命令への追従防止、停止スイッチを検証する。運用に必要なシャドー用の保存・ログは明確に区別する。
- 本番データを同時期・同条件で比較できる設計。共通入力での解析比較と、AIが独自に発見した候補の比較を区別し、既存システムを正解とみなさない。独自探索は初期の予算内で段階的に行い、対象地域・商品・重複・根拠・対象範囲を記録する。AIの自律的な探索・再調査・判断の自由度を保ち、店舗固有の固定ルールを増やさない。
- 管理者が現行結果とAI結果、双方のみの発見、保留/除外、差分理由、情報の鮮度・取得時刻、根拠、費用、失敗を確認できるようにする。既存UIで十分なら再利用。人手の全件gold入力を必須にしない。重要な差分や誤りを優先して少量確認する。
## 3. 最小限の観測性と費用安全
- R1で判明した評価時点の不一致は、本番比較では同じ取得・評価基準時刻を記録して解消する。応募単位は実際の応募可能範囲を中心とし、曖昧なら暫定。既存goldを勝手に変更せず、合成評価環境の全面改修は延期。
- 自己修正の試行回数・理由・成否、判断出力の不正の型情報（秘密・原文を不用意に記録しない）、取得・解析・判断の失敗、費用、候補の由来を最低限記録。既存の再試行上限内で安全な復旧、解消不能なら保留。観測の追加が大規模になる場合は最低限に留める。
- 既存の30件/日等の運用上限や費用制御を実装から確認し、シャドーに独立した日次/通算費用・候補数・呼び出し数・検索/取得/時間上限、異常停止条件を適用する。実際のモデル・キー・課金体系・最大予約・現行費用への上乗せを確認し、最初の少量試行の具体的な推奨件数・日数・費用上限を提示する（ユーザー未承認の金額で自動開始しない）。上限が永続化され再起動/多重実行で回避されないことを検証。費用はR1と別管理。
## 4. 最終検証・報告
- 無料で実施可能な型検査・lint・単体・DB統合・E2E・build、統合ブランチのCI、既定OFFとシャドーの非干渉、上限・停止・隔離・モック独立性・失敗時の保全を検証する。合成データのさらなる精度改善を目的とした作業は行わない。重大な安全上の問題のみ根本修正し、その他は本番並行稼働後の課題へ。
- docs/reports に統合PR番号/差分/CI、依存PRの範囲、必要な本番移行・操作順序、既存機能への影響、実際の設定項目・既定値、停止・復旧方法、試行予算案、比較方法、未確認事項、承認後に必要な最小の操作をまとめる。今回の完了条件は「本番で安全に並行稼働を開始できる準備ができ、具体的な承認対象が明確」であり、本番の実行を装わない。既存スマホ通知で完了を知らせる。
