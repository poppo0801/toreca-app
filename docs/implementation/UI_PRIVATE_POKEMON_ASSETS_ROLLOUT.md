ユーザーは151図鑑・相場調査メモ・購入記録のUI改善と、画像の非公開Supabase Storage移行、UI部分のみの本番反映を承認済み。AI情報収集Stage10T/10UおよびPR #36/#46の本番反映は**未承認**。画像入りPR #68はクローズ済み、マージ禁止。旧ブランチ `ui/collection-polish` に実装差分があるが公開リポジトリに画像がコミットされている。画像入りブランチの履歴を新PRに引き継がないこと。

## 最初に実態確認
- GitHubリポジトリの公開状態、現在のmain、本番Vercelのデプロイ元、Supabase認証/RLS/Storage構成、画像素材の**実際の総数と配置**、151図鑑・相場メモの画像参照、旧ブランチとmainの差分を確認。
- 151匹以外も含む**すべてのポケモン公式絵**を対象にする。図鑑番号は4桁ゼロ埋め、`【公式絵No.0001】フシギダネ`、同番号の括弧付き姿違いは括弧なし通常版優先。番号が151を超える画像も処理し、取りこぼし・重複・対応誤りを集計。図鑑・相場メモで同一画像を共用。存在しない画像は安全なプレースホルダー。
- 素材の利用権限・ライセンスはユーザー確認が必要。**非公開配信は著作権上の許諾を代替しない**。権限が未確認の場合、無断再配布を前提に本番配信を進めず、画像なしのUI公開までに留め、未解決事項を明記。

## GitHubに画像を載せない
- `main`から**新規UI専用ブランチ**を作る。旧 `ui/collection-polish` のコミットをmerge/cherry-pickしない。UIのソース変更のみ選択的に移植。private-assets/、public/等の画像バイナリ、元ファイル、base64画像、バックアップを新コミットに含めない。画像ファイルを.gitignoreへ追加。変更差分を確認。
- 既に公開リポジトリへpushされた画像については、PR #68を閉じても公開履歴・キャッシュから消える保証はない。旧ブランチを安全に削除し、公開履歴に残る可能性を確認。必要ならGitHub Supportへ履歴/キャッシュ除去相談。リポジトリの非公開化はユーザー判断が必要な場合、確認を求める。履歴書換え/force-pushを無断実行しない。

## Supabase Storage 非公開配信
- **private bucket** を利用（public=false）。認証済みの許可された家族アカウントのみ読み取り可能にする。単なる「authenticated」全員許可ではなく、既存のトレマネのアクセス制御に合わせて許可ユーザーを制限。Storage RLSまたはサーバー側で検証。匿名アクセス、パス推測、他ユーザーのアクセス、URL共有による漏えいをテスト。
- 画像のアップロードはローカルの元画像から実施。既存Storageのバケット/ポリシーを不用意に破壊しない。ファイル名の日本語/括弧/番号差を正規化し、保存キーは安定した形式（例: `official/0001.webp`）、必要ならmanifestで番号と実ファイルを対応づける。151以外も含む全画像の件数、サイズ、重複、欠損、失敗件数を記録。画像の最適化と容量・費用に配慮。
- Vercel側は**認証付き画像取得API**を推奨。セッションと許可ユーザーをサーバーで検証してからprivate bucketより取得、レスポンスは `Cache-Control: private` 等で共有キャッシュを避ける。署名URLを使うなら有効期限・漏えいリスクを明示。service role keyをクライアントやログへ出さない。認証が切れたら画像を返さない。画像取得時の負荷、スクロール性能、アクセス制限、エラーハンドリングを確認。
- 151図鑑は入手済み白背景・カラー、未入手薄グレー・画像半透明。相場調査メモでは**常に不透明**。共通の画像取得経路を使うが画面別の表示スタイルを混同しない。

## テスト・本番反映
1. 新ブランチに**画像バイナリが無い**こと、Stage10T/AI系変更が無いことをGit diffで検証。build、lint、型検査、単体・E2Eテスト、モバイル画面・画像配信の認証テストを実行。
2. Supabase Storage/RLSの変更・アップロードは対象を限定し、事前にバックアップ・復元手順を確認。既存DBデータは破壊しない。画像素材の利用権限が確認できない場合は、画像アップロード/配信の本番実施を停止し、画像なしUIを先に公開可能。
3. UI専用PR作成→CI確認→安全な場合のみマージ→正規のVercel本番デプロイ→本番スモークテスト。実際に未完了なら完了と報告しない。重大なリスクや必要権限の欠如は停止・報告。
4. 完了報告: 新PR/commit、本番デプロイ、画像総数と対象範囲、認証テスト、費用影響、テスト結果、バックアップ、残課題。
