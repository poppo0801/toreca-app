# Stage 10E 実AI評価：既存APIキー再利用の追加指示

対象：PR #36（`feat/10e-unified-judgment`）。ユーザーは新しいキーを増やさず、**既に設定されているAnthropic APIキーを第1段階の評価に再利用**する方針を承認した。前指示書 `STAGE_10E_REAL_AI_EVALUATION.md` のキー分離条件だけを本書で更新する。**架空19事例・総額30円・1事例2円・開発環境限定・Web検索なし**という承認範囲は不変。

## 作業
1. 最新mainをPR #36の作業ブランチへ取り込む。`src/lib/judgment/real-gate.ts`、`scripts/eval-judgment-real.mjs`、`src/lib/judgment/real-eval.test.ts` と関連テストを確認。
2. **既存の `ANTHROPIC_API_KEY` を評価用に明示的に再利用できる**よう、開発環境限定の明確なオプトイン（例：`JUDGMENT_REUSE_EXISTING_KEY=allow`）を追加する。評価専用 `JUDGMENT_EVAL_API_KEY` の従来経路も維持。再利用時は既存のキーが安全に環境変数で利用可能なことを確認し、秘密値のコピーや新規キー発行を要求しない。**キーの一致拒否を無条件に撤去しない**：再利用を明示許可した場合のみ受け入れる。オプトインなしで一致・代用・未設定なら従来どおり拒否する。曖昧な両キー設定の優先順位を明文化する。
3. `TOREMANE_ENV=local`、`JUDGMENT_REAL_EVAL=allow`、実行ごとの `--confirm=yes`、総額30円・1件2円の上限、モデル/費用見積もり、失敗時の保守的費用計上、秘密情報の非出力、架空データのみの評価を維持。Vercel・本番環境では実行不可。本番DBアクセス・外部ページ取得・本番への反映は禁止。**共有キーであるため、評価用の累積費用記録とAPI側全体の請求額は別物**と報告する。キー共用の漏洩時リスクも明記。
4. 実際のキーが環境に設定済みかは**存在のみ**確認し、値を表示・報告・Gitへ保存しない。設定が足りなければユーザーが追記する設定名だけを案内して停止。すでに設定されていればpreflight→モデル利用可否・上限確認→第1段階の実AI評価を1回実行し、報告書を更新する。評価用の既存キーを誤って上書きしない。
5. ユニット（オプトイン有無、同一キー、両キー、未設定、local以外、予算超過）、DB結合、typecheck、lint、build、CIを実施。失敗は隠さず原因を報告。実AI結果は正解と独立に採点し、誤統合・誤分割・根拠不明・費用・遅延・再判断を報告。実AI未実行なら未実行と明記。
6. 実装・結果は**PR #36に追加**し、PR #36はマージせずレビュー待ち。Stage 10F、本番DB読み取り、実原文のAI送信、第2段階の評価は開始しない。

## 注意
既存キーを再利用する承認は、秘密をチャットやPRへ貼る承認ではない。キーが既に開発環境から読めるなら再入力を要求しない。費用の30円は評価コードが制御する上限であり、同じキーを使う他のプロセスの費用を制限しない。
