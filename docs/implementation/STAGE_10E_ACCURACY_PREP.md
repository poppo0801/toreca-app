# Stage 10E 精度改善・実データ評価準備 指示書

対象: PR #36 `feat/10e-unified-judgment`。参照: `docs/reports/2026-11-21-stage10e-real-eval-results.md`、`docs/AI_REDESIGN_SPEC.md`、`docs/AI_REDESIGN_ACCEPTANCE_PLAN.md`。

## 今回の承認範囲
Stage 10Eの残課題 J01（同一応募権の誤分割2）、J13（独立3商品の誤統合2）を改善し、**実データ評価の実施準備**を進める。既存の架空評価データとローカルのテストのみ使用可。**本番DBの読み取り、実際の抽選原文の取得・外部AI送信、追加の有料API呼び出し、Stage 10F実装、本番デプロイ・機能有効化は今回の指示に含まれない**。それぞれ実施前にユーザーへ明示的な承認を求める。PR #36はマージしない。

## 実施内容
1. PR #36の最新コードと報告書、10E仕様・契約・gold・採点器を確認。mainを取り込む。J01/J13を「なぜ起こるか」入力証拠、プロンプト、出力スキーマ、機会の定義、既存レコードの関係付けまで追跡し、**事例固有の文言やIDをハードコードしない**。
2. 応募機会の定義を明文化：応募フォーム数や商品数ではなく、**独立して応募・当落・購入可否を追跡できる権利単位**。同一企画の別店舗カードが同一応募権を表す場合の同一性と、1回の送信で複数の独立した応募権が発生する場合の分割を区別する。曖昧なら根拠を明示して保留し、誤統合・履歴破壊を避ける。関係 `same` と `same_campaign_other` の判定根拠も明確にする。
3. AIが機会数と各機会の対応関係を一貫して出せるよう、汎用的なプロンプト・契約・検証器を必要最小限修正。**モデルの誤判定を検証器の無理な自動補正で隠さない**。1件の原文に複数応募権があるとき、機会数と機会の詳細が整合しない出力は採用せず安全側に保留。重複判断では系列・店舗・商品・開催回・応募権の証拠を優先し、根拠なしに `same` と断定しない。
4. J01/J13の回帰テストに加え、**未見の新規架空ケース**を作り（類似・逆パターン・境界事例を含む）、正解を先に固定し、モデル入力と分離する。旧19件だけに合わせた改善を避ける。評価の正解に曖昧さがあるJ21は正解を事後変更せず注記を維持。テストは実AIの精度を証明しない旨を明記。
5. 追加費用なしでできる既存保存済みAI出力の再採点・差分分析を行う。ただし新プロンプトの**実AI精度が改善したと主張しない**。未見の実AI再評価が必要なら対象件数・モデル・費用見積もり・停止条件を提示して別承認を求める。
6. **第2段階の実データ評価を実行可能な計画に具体化**：本番DBの読み取り対象（表・列・期間・上限30件・抽出コマンド）、最小権限、マスキングと全件人手確認、外部AI送信対象・保存期間・削除手順、gold作成担当、旧方式との同条件比較、費用上限案（前回50円・1件3円）と承認ゲートを文書化。原文抽出・送信は実行しない。可能なら**架空データのみ**で抽出・redact・漏洩検出・評価フローをテストする。
7. 型検査、lint、単体、DB結合、build、CIを実行。履歴・ユーザー別応募・通知・安全な取得境界・予算制御の回帰を検証。報告書 `docs/reports/2026-11-21-stage10e-accuracy-prep.md` に原因、変更、テスト、未見ケース、残る精度上の不確実性、実データ評価に必要な承認事項を記載。PR #36に追加して**未マージ**でレビュー待ち。

## 完了条件
J01/J13の根本原因と対策がコード・テストで追跡でき、架空データでの回帰を確認できること。実AIによる未見データ精度・実データ比較が未測定である場合は明示すること。本番データ・追加API費用には触れないこと。
