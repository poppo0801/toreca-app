# Stage 10H：AI判断の入力設計・情報取得の改善と再評価

## 背景
Stage 10G（`docs/reports/2026-11-21-stage10g-refresh-preview.md`）では、対象94件、保存原文あり42件、AI再判定28件（費用14.01円）。構造unknown 10/28（短い断片4・一覧投稿の詳細不足4・応募単位不明2）、未解決事項あり28/28、質問80件。自己登録との同一確認16事例と年推定10質問が過剰保留の主因。原文なし52件のうち36件はX/短縮URLのみで取得困難。既存登録との差分はあるが確定更新0件。

## 目的
**人手確認を増やさず、AIが情報を適切に取得・区別・判断できるようにする。** 10Gの28件を同条件で再評価し、unknownと保留の改善効果、費用・遅延、誤統合・誤分割の危険を比較する。今回は本番データの書き込みなし。

## 一括実装・検証
1. `feat/10f-shadow-integration` に最新mainを反映。Stage10E/10F/10Gの判断器・ローカル評価・収集部品を再利用。作業を細かな承認段階に分割せず、実装→テスト→再評価→報告をまとめて行う。
2. **自己登録の区別**：再評価対象自身の既存登録をrelatedな別抽選として渡さず、`currentCase` 等の明示的な自己コンテキストとして入力する。自己照合の疑問を生成させず、別の抽選との関係だけ判定する。入力の識別子・保護情報を外部AIに漏らさない。
3. **保留基準の改善**：応募可否・応募単位・重複・締切に影響する不確実性を優先。日付の年は、掲載日時・現在日時・曜日など根拠が揃い矛盾しない場合だけ推定し、推定であることを記録。根拠不足の日付や重要な応募条件は推測で確定しない。単なる未記載項目を無制限に質問として増やさず、必要なら低重要度の情報不足として集約する。重要な不確実性の隠蔽は禁止。
4. **一覧投稿の分割**：複数店舗・複数抽選を列挙する原文をAIが区別し、独立した応募機会ごとに判断できる入力を組み立てる。1投稿を安易に1応募とみなさず、逆に根拠なく分割しない。元投稿の出典と断片の対応を保持し、引用検証・既存の関係/店舗整合チェックを維持。
5. **詳細ページ取得**：公開httpsページに明示されたリンク・取得可能な公開ページを既存の取得部品で再取得し、追加情報を判断へ渡す。最大60取得、ロボット制限・認証・SSRF防御を維持。X/t.co等のアクセス制限回避やログイン取得はしない。取得不能なら理由を記録し、無限再試行しない。原文のない対象も、取得可能な範囲で改善可能性を評価する。
6. **同一データで比較**：10Gで送信した28件を可能な限り同一スナップショット・同一対象として再評価し、10Gの基準値（unknown 10/28、質問80、高重要度39、保留あり28/28、費用14.01円）と比較。対象や入力の追加情報が変わる場合は、**入力設計だけの改善**と**追加取得による改善**を分けて集計。10Gで除外した2件を無断送信しない。
7. **評価指標**：構造unknown数、未解決質問数と重要度、自己照合質問数、応募単位・重複判定の妥当性、引用検証、店舗関係矛盾、取得成功率、費用、遅延。保留が減っただけで正しいと断定せず、明らかな誤確定・誤統合・誤分割は少数の根拠確認で検出する。正解率が未測定なら未測定と記載。
8. **予算**：既存Anthropic APIキーを使用。公開告知の伏せ字・漏洩検出を再実行し、承認済みのAPI保持リスク受容を適用。初回の実AI評価は最大30対象・90 AI呼び出し・60公開ページ取得・合計50円・1件3円を上限とする。予算が不足したら、得られた範囲で分析し報告する。機密漏洩・本番更新・無限ループ・予算超過は防止。
9. **成果物**：`docs/reports/2026-11-21-stage10h-improvements.md` に実装内容、前後の比較、unknown/保留の残存原因、取得可能性、実測費用、改善の副作用、今後の本番適用・再整理の判断を簡潔に記載。Gitに原文・URL・内部ID・APIキーを含めない。変更箇所のテストを実施し、必要以上の全体テストや確認作業で停止しない。

## 変更範囲
本番DBの更新・統合・削除・アーカイブは行わない。PR #36/#46および他の実装PRを勝手にマージしない。改善した収集・判断コードの本番反映は結果を評価してから決める。既存の応募・当選・購入履歴の保護を維持する。
