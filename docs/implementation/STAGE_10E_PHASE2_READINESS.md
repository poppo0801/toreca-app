# Stage 10E Phase 2 実データ評価：承認前準備

参照: `docs/AI_REDESIGN_10E_PHASE2_PLAN.md`、PR #36 のStage10E実装・評価報告。

## 許可範囲
ユーザーは第2段階の**準備着手**に同意。承認ゲートA〜E（本番DB読み取り・人手確認・実原文の外部AI送信・gold担当・費用/キー）はまだ個別に確定していない。**この指示はA〜Eの実行承認ではない。**

許可: ローカルの架空データでの安全機構・dry-run・評価設計・費用見積もり・比較方式の実装/テスト・承認資料の作成。禁止: 本番DB接続/バックアップ実行（本番へのアクセスを伴う場合）、実原文取得、実原文のAI送信、課金API実行、本番変更、10F着手、PR #36マージ。

## 一括作業
1. 最新mainをPR #36に反映し、既存の `phase2.ts`、テスト、real-gate、費用ゲート、既存抽出方式、実データの保持・削除フローを調査。9Z導入日を履歴・報告書から確定できるなら出典付きで提示する。未確定事項は推測しない。
2. **本番への接続を伴わない**準備コードを実装。列ホワイトリスト、最大30件、読み取り専用、`--execute` と本番確認の二重ゲート、ローカルgitignore、ログ秘匿、伏せ字・漏洩検出・全件人手レビュー必須、未承認時の送信拒否、予算停止、削除記録などを架空データでテスト。実際のDB接続/原文取得は行わない。SQLの読み取り専用性と認可方式の実現可能性を静的に検証し、できない場合は設計上の懸念として明記。
3. 旧方式との比較は、**構造判定のみ**と**項目抽出まで含む比較**を分けて設計し、既存コードを再利用可能か調査。旧方式が課金APIを要する場合は未実行とし、費用を明記。AI評価結果・既存登録結果をgoldに流用しない。
4. 実データのgold作成は、ユーザーが全30件を手入力する前提を置かず、候補・原文・機会・既存関係を**ローカルのレビューUI/ファイルで確認・修正・承認**できる省力化案を設計。ただしAIの提案をそのまま正解にしない。原文・正解のGitコミットは禁止（固定はローカルハッシュ/改変検知などで実現）。
5. 承認ゲートA〜Eの選択肢を、ユーザーが一度で判断できる短い承認票として作成。特に外部送信データの具体的範囲、Anthropic API保持ポリシーの未確認点、既存キー再利用の可否、最大30件/総額50円・1件3円の費用内訳、旧方式の比較を含むか、30日以内のローカル削除、人手レビュー担当、実施順序を明記する。ユーザーの個別承認なしにゲートを通さない。
6. 型検査・lint・単体・DB結合（ローカルのみ）・build・CIを確認。結果と残リスクを `docs/reports/2026-11-21-stage10e-phase2-readiness.md` にまとめ、PR #36へ追加する。**PR #36は未マージ**。

## 完了条件
承認ゲートA〜Eを提示でき、未承認では実データの取得・送信・課金が実行不能な状態。実データ評価の精度・安全性について、実測済みと誤認させない。
