## 1. 最優先：本番機能の横断監査と是正
- 実際の本番コード・デプロイSHA・DB移行/制約/RLS・環境フラグの有効判定（値や秘密を出力しない）・cron/キュー/実行経路/タイムアウト・設定・サービス権限・呼出し元を一覧化し、過去に実装した主要機能が本番で実際に動くかを調べる。開発専用条件、既定OFF、未接続、古いコード、設定不一致、上限/予算で常に発動しない、エラー握り潰しなどを横断的に探す。報告は各機能について「意図した本番状態／実際の状態／原因／修正／実データの動作証拠」を示す。意図的な安全境界と誤った機能停止を区別。テスト用モック、評価用入口、課金許可、登録/削除等の制限まで一括で解禁しない。
- 確認済みの具体例: flag.ts の evidenceCollectStoreEnabled / linkRecheckEnabled / dbHostGateEnabled が proposalPreviewEnabled に依存し本番で必ずfalse。image-intake.ts の imageIntakeEnabled も開発環境限定。proposal-hook.ts の storeCollectedEvidence はその条件で即return。関連DBは既に移行済みだが、本番の最新実態・権限を確認する。特に全文保存、未取得リンクの再調査、画像取得/参照、ホスト共有制御を本番で安全に必要な範囲で稼働させる。専用の本番許可・停止スイッチ・世帯制限・回数/時間/アクセス規約を保つ。既存の開発モック生成は本番で無効のまま。ホスト制御等は必要性を判断し、無条件に全機能ONにはしない。
- collector/run.ts、x-rich.ts、collected-docs.ts、collected-store.ts、link-recheck.ts、image-intake.ts、evidence.ts、source-prefetch.ts、generate.ts、pipeline.ts、research-loop.ts、research-ai.ts、実行台帳・UI・集計を通して確認。全文のWeakMap受渡し、キュー跨ぎ、取得時刻、失敗経路でも証拠が保存されるか、再収集で旧版が消えないか、同じURL別版の時点、画像参照が既存抽出の成功時だけ保存される条件（run.ts imageEvidence）、X本文がキュー投入時12,000字・引用元6,000字で先に切れ、後段で切断が分からない可能性、保存したpost全文がAI側に利用されるかを確認。本文なし/画像だけの告知も漏らさない。保存原文と抽出結果・二次情報を区別。
- 評価と本番の共通経路も再監査。実行入口だけ同じでは不十分。事前取得・保存済み全文の読込、時刻、学習ヒント、画像、検索、モデル/effort、実行時間/予約費用、キュー継続、取得制限の差を明示し、意図しない差をなくす。実際の本番cronで呼ばれたこととテストで呼ばれたことを区別。安全性を維持しつつ、機能有効なのに予算/時間の設計で実質利用できない機能も修正する。時間枠超過や多数機会の処理は耐久キュー/再開/重複防止等で必要分を継続できるか検討。

- 前回の棚卸しは全2,976候補中、原文あり426・全文保存あり26（候補数、過去含む）。リンク先あり22でLivePocketに偏る。過去の無保存と現行の欠落を区別するため、直近の収集（例: 直近7日・新方式導入後・修正後の時期別）と情報形式別に、対象数/取得試行/成功/失敗理由、原文の種類（公式告知・投稿・二次カード）、取得前に把握できた文字数/実取得HTMLバイト/整形本文文字数/保存抜粋/保存全文/AIに実際に提示したユニーク文字範囲・追加read・最終判断の入力、リンク発見/取得/保存/未取得、画像参照/取得/解析を計測する。平均・中央値・範囲・切詰め率・保存率・提示率、失敗の分母と理由を示す。元ページ総文字数が分からない場合は未知とする。単に上限値や重複した文字数を示すだけでは不可。
- 公式原文で取得可能なのに欠落する重要情報（後半の応募条件、発表/購入/受取、複数店舗・商品/受付枠、画像内の文字等）を実案件で追跡し、どこで消えたかを特定。整形で欠落するHTML構造、ページ内リンク、画像参照を保持し、許可された公開情報の意味を失わず保存、再解析に使えるようにする。全文保存と毎回全量をAPIに渡すことは別。長文はAIが必要な箇所に自律的に到達できる構造、実際に読めた範囲と未読の明示を優先。JS/ログイン/終了/robots等は迂回せず制約と代替の公式情報を調査する。画像は既存の安全な保存方針を尊重し、無断で大量の原画像を永続保存しない。本文取得・保存だけならAPI不要。容量、通信、時間、利用規約、プライバシーと現行稼働への影響を確認。

## 3. 判定能力の原因を切り分け、改善を最優先
- 前回の未見の不要保留、地域適合、応募単位、公式ページの選択/詳細への到達、まとめ投稿の複数機会、期間の混同を重点とする。保留が妥当かを独立証拠で分類し、情報元未取得/保存欠落/提示不足/調査AIの行動不足/判断AIの推論不足/検証による拒否/真正な不明/予算・時間等の原因を案件単位で追う。取得・提示済みの証拠を活用できなかった場合、具体的な原文と判断の差を確認。保留を数値上減らすための強制登録や根拠の緩和は禁止。
- 適切な追加調査で解決可能な不明と同一証拠から推論可能な不明、利用者しか知らない不明を区別。AIが公式情報の検索・リンク追跡・画像・所在地照合等を選択し、判断から調査へ戻る能力を実証する。askHuman の自己申告だけで調査/上位を打ち切る設計も検討。明確な応募機会を保留する原因となる検証の過剰制約は根拠を保って直す。複数機会は候補単位だけでなく各応募機会単位で探索・判断・保存する。
- 対象範囲はポケモンカード（BOX・パック・シングル等）およびポケモンカードを含む福袋・セット。フィギュア等カード以外のみ、他TCGのみは除外。混在告知では対象の応募機会/商品を抽出。福袋にカードが含まれるか不明なら公開情報を追加調査し、確定不能を明示。単に「福袋」「ポケモン」という語だけで決めない。これは利用者の確定した方針であり、人に再確認不要。前回のLINE案件等は情報が実際に必要な場合のみ少数依頼。正解入力を開発の前提にしない。

## 4. モデルと推論設定の比較
- APIの調査/判定を別々に比較し、Haiku→Haiku、Haiku→Sonnet、Sonnet→Haiku、Sonnet→Sonnetの構成を必要十分な実案件で比較する。判断モデルの差は同一証拠・時刻・出力仕様・検証で測り、調査モデルの差は同じ初期証拠・ツール・調査条件で得られた追加証拠・最終結果を比較。現在はeffort lowなので、対応する設定を公式仕様で確認した上で、代表的な難案件で推論レベル差も比較。すべての組合せを全件で浪費する必要はない。少数で原因切り分け→有望構成を代表例/未見で検証する。API互換性と費用予約・出力上限・実行時間を整合し、既知のSonnet強制tool_choice不適合を再発させない。
- Haiku優先を目的化しない。Sonnetが広い範囲で有効ならSonnet標準、特定段階だけ有効ならその段階で採用、差が小さいならHaiku、難易度適応方式が有効なら採用。直接Sonnetの方が二重処理より安い場合も比較。精度・保留・全項目・取得証拠・時間・実費・上位切替率/改善率を同じ母数で比較し、通常の月間件数を複数シナリオとして運用費を見積もる。難案件だけの試験を通常運用全体の率とみなさない。恒常的なコスト増を伴う本番標準モデル変更は結果と見積を示して利用者の直接承認を得てから反映。今回の評価実行は承認予算内で自律的に進める。
