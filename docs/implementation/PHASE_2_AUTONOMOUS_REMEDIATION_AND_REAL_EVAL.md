# Phase 2：既知課題の自律的な一括解消・収集上限の継続監査・実AI比較試験

起点：未マージPR #115 `feat/phase2-vision-runtime-safety`（積み上げ #98→#100→#102→#104→#113→#115）。新規実装PRのbaseは#115。最新mainとの互換確認を維持。

## 最重要の開発運用の変更（今回以降の新AI開発に適用）

**Claude Codeが認識している修正可能な課題は、報告だけして終了せず、原因調査→修正→テスト→再監査を自律的に繰り返して解消する。** 1件の修正時には類似の欠陥が別経路・上限・保存・再生・AI入力・UIまで存在しないか横断監査する。実装と検証、問題発見と解消を同じ工程で行う。小さな修正ごとにユーザーへ確認を求めない。既知課題に対し「将来対応」「本番前に要対策」と書くだけでは完了扱いにしない。修正可能なのに残した場合は理由・影響・代替策・停止基準を明記する。

一方、(a)ユーザー以外が確認すべき独立goldの真偽、(b)有料APIの具体的な承認金額、(c)本番DB/Storage/Vercelの変更や本番新AI有効化、(d)第三者サイトの利用規約や権利上の未解決、(e)復元不能な操作は**独断で実施しない**。承認不要な実装・試験・準備は全て先に済ませ、承認が必要な事柄だけ最後に整理して提示する。評価のためにgoldをAI出力から捏造しない。

## 1. PR #115で既知の未解決事項を一括解消

優先的に以下を調査し、開発環境で実装、既存データと最新mainとの互換性を検証する。

1. **未取得リンクの自動再調査**：`linkLedger`/`pendingRecheck`を実際のワーカー再実行・キューへ接続。締切・予算・429等の一時的な未取得を耐久的に記録し、別実行で再取得できるようにする。重複実行防止・指数バックオフ・試行回数/期限/最大件数・ホスト制限・中止・情報鮮度・追加費用上限を設ける。robots拒否/認証必須/危険URLの回避はしない。1回の実行時間に収めるための分割・継続処理、途中で落ちた際の復帰も検証。**収集時に時間切れ→台帳に記録されるだけでは不十分**。再調査された本文が元の候補・項目に正しく戻り、後段AIが再解析できるところまで通す。
2. **収集負荷の全体制御**：現在のホスト別制御はプロセス内のみ。サーバーレス複数インスタンス・複数cronの競合、ホスト別グローバルレート制御・同時接続、429/503対応、DB書込み量、実行時間の上限を合理的に設計・実装。DB持続型キュー/ロック/リース等の選択は自由。デッドロック・リース失効・障害復旧・同時実行数/リクエスト数のテストを含める。外部への実負荷試験は禁止（ローカル/保存データ再生）。
3. **画像の通常の収集からの接続**：PR #115の実ビジョンは評価入口のみ。公開画像の発見・安全取得→解析→結果保存→新AI調査への受け渡しを、今後の実運用可能な経路として完成させる。ただし新AI本番OFFを維持し、本番cron/APIから勝手に有料画像解析を起動しない。開発環境の明示的な承認関門・予算制御を再利用。画像だけにある条件と本文矛盾、取得不能時の未確認、重複課金対策をE2Eで検証。
4. **保存容量・保持期間・掃除**：`evidence_documents`、画像観察、経験・台帳の肥大化、保持期限、個人情報・原文の扱いを監査。回収可能性と履歴保全を両立する保守・クリーンアップ/容量制御を安全に設計・テスト。必要な法的/利用条件の判断が不明な外部画像は無断取得・保管しない。
5. **テストの既知不具合**：`ui-audit`の不合格（無変更mainにも存在する）を原因究明。既存UIに影響せず修正可能なら別途適切に分離して修正。テストを緩めたりskipして合格扱いしない。新規lint警告も解消。
6. **実AIエラーへの耐性**：出力途切れ・構造不正・API停止・認証/上限制限・リトライ時の冪等性・異常な長文/複数URL・他候補の混同・秘密情報を含むログを監査・修正する。

## 2. 上限・切り詰めの「十分性」を継続監査

前回、リンク取得1→24（＋追跡6）、抜粋3,000→6,000字、X本文3,500→12,000字、保存ページ2→30件等へ引き上げたが、**設定値が増えたことは網羅性の証明ではない**。現在のコード・全経路での上限を表にし、実保存済みの長文/多リンク事例と合成ワーストケースで、(1)入力に入った、(2)全文が保持された、(3)AIがreadで必要部分を開けた、(4)未取得/切れを検出して再取得できた、を独立に監査。

- 上限到達率（分母・件数・パーセンタイル・最大）、実際に失われる項目とその段階、未取得の再処理成功率、候補別の証拠網羅性を測定する。実データが少なければ「十分」と断定せず、観測不足を示す。
- 24+6、30ページ、60リンク、画像16、6,000字抜粋、12,000字本文、AI提示14,000字/12,000字、ツールread、上流の隠れた20,000字/サイズ制限、投稿/スレッド/再収集や候補分割/DB列制限を全て確認。
- 上限を固定の十分値と見なさない。必要なら可変ページング・全文保管・逐次read・継続取得・後段への「不足」信号を採用。予算や技術上の限界がある場合には黙って落とさず原因を記録し、自動再取得や確認待ちに回す。未確認を「条件なし」と判断しない。
- **今後の収集・実AIテストごとに同じ監査指標を記録し、閾値超過や情報欠落が発生した場合は自動的に失敗/警告とする回帰テストを組み込む**。単純に最大文字数だけ増やしてAIの入力コストを無制限に増やさない。

## 3. gold（独立正解）と実AI試験を連続で準備・実施

最優先は **R1（複数リンク・旧方式vs新方式）**。保存済みの実投稿から12案件程度を選び、重要な応募機会（店舗×商品×開催回）を網羅できるよう、独立goldを作成するための原文・参照URL・候補解答・根拠位置を**人が短時間で監査しやすい資料**として書き出す。ただしAIの推定結果/旧登録案から正解を無検証で作らない。原文で機械的に確定できる範囲を明示し、不確定な部分は人の確認待ちにする。gold不足なら、比較試験用の人による確認だけを最後に求める。

- 試験ランナーの plan/mock/dry-run を使い、比較条件・実行対象・実行時間・費用と最悪予約・独立gold・評価指標（応募機会再現率、誤登録/混同/無効引用、費用/ターン数）を検証。R1試験後はR2（全文）・R3（画像）・R4（経験ヒント）へ段階的に進む判断資料を作成する。
- **ユーザーは実AI試験へ進む意向を示しているが、具体的な承認金額・関門確認文は未確定**。必要金額をdry-runで確定し、既存の承認ゲート `APPROVE C <総額>JPY` を勝手に代入・模造・回避しない。正しい独立goldと明示的な金額承認が得られた場合だけ、ユーザーが承認した範囲の実AI試験を実行する。上限は既存の60円/1件5円を超えない（さらに小額なら小額を優先）。承認まで他の無課金作業を完了しておく。承認が無ければ**実AIの有料呼出しだけ保留**とし、調査・実装・無課金検証・評価資料・PR作成は完了させる。
- 小標本で「改善を実証」と断定しない。重大な誤登録/異なる店舗の根拠混同が出たら実験を停止・原因追跡・修正・モック再検証を行う。実費の再実行は再承認。R1の結果を事実ベースで報告する。

## 4. 自律実装・レビュー・完了基準

- 実装の途中で明白な課題が発見された場合、修正可能ならその場で改善して再テストする。問題が繰り返し発見される場合、同型の構造欠陥を上流から横断調査する。規模・複雑さ・予算が増す場合でもまず費用ゼロでできる根本対策まで完了する。
- 本番変更・AI系PRのmainマージはしない。DB移行120/121の本番適用、外部サイトへの実負荷テスト、追加の有料API試験は承認対象。PR #115を起点に実装PRを作り、最新mainと統合した環境でtypecheck/lint/単体/DB統合/E2E/buildを確認。
- 完了報告は `docs/reports/phase2-autonomous-remediation-real-eval.md`。①発見した全課題と原因/自己解消の証拠、②上限到達率と全文到達の測定、③再取得/画像/並列制御の実配線、④実AI R1の実施状況（未承認なら未実施と明記）、⑤テスト・未解決制約、⑥次工程の提案をまとめる。**既知の修正可能な課題を残したまま「完了」とだけ報告しない**。
- 報告時には課題を「解消済み」「ユーザーの権限/費用承認が必須」「外部制約による残存」「未発見のリスク」に分ける。未発見リスクがゼロとは主張しない。

## 5. 作業終了時のスマホ通知（追加指示 2026-11-24）

本工程の実装・検証・PR作成が完了した時、または独立goldの確認・有料APIの明示承認待ちで停止する時、**iPhoneへ短い完了／確認待ちプッシュ通知**を送れるよう整備する。今後の全開発工程の恒久ルールは `CLAUDE.md` §4.1 を参照する。

- Claude Codeの既存通知/Remote/hooksなどを先に調査し、実機通知まで確認できる最も簡単で安全な方法を採用する。既存環境で実際の送信が可能なら実装・試験まで行う。
- 端末アプリの導入・通知許可・外部サービスの連携など**ユーザー操作が必須の初期設定**は、必要最小限だけ依頼する。準備できない間は通知の実装・モック検証まで進め、未送信である旨を報告する。
