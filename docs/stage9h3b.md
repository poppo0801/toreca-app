# Stage 9H-3B: 収集処理と自律調査エージェントの統合基盤

開発環境のみ。本番DB・開発DBへのマイグレーションなし。**有料API・実AI・実検索の呼び出しなし（費用 0円）**。監査（`docs/stage9h3a.md`）で分かった原因 — 収集処理と調査が別系統・AIの判断が後段で失われる・入力と判断の履歴が残らない・人間の評価が判断に戻らない — を、共通の基盤で解消する。**今回の完了は、実AIの判断精度が改善したことを意味しない。**

## 1. 実装前の整理: 何が重複していたか・今回どう変わるか
| 責務 | 従来 | 今回 |
|---|---|---|
| 抽出（AIの読み取り） | 本番収集は `record_lottery`、調査は独自の `report_page_findings`（別スキーマ） | 調査の報告も、当選発表の期間・応募単位（店舗選択式・選べる店舗）を持つ。両者の結果は共通モデルで表す |
| 同一抽選・店舗選択式・重複の判定 | 本番は固定の連鎖、調査は独自の台帳 | 判定を**新しく増やさない**。調査の結果は既存の入口（`ExtractedLottery` → `buildDraft` → 応募単位の判定 → 重複 → 登録判定）に合流する |
| 判断の履歴 | 店舗選択式の一部だけ `understanding.trace` | 全項目の「AIの読み取り → 変更 → 理由」を判断履歴に残す |
| 人間の評価 | 評価ツールだけが読む | 評価JSONを置くだけでAIの参考情報になる（参考。正解にしない） |

本番収集の変化: **フラグ無効（既定・本番では常に無効）のとき、動作・保存内容は従来と同一。** 有効時（開発環境で `TOREMANE_ENV=local` かつ `COLLECT_UNIFIED=on`）だけ、AIの入力に参考情報が加わり、判断履歴が候補の下書きに保存される。AI調査の呼び出しは、さらに `COLLECT_INVESTIGATE=on` で、調査機能が接続されているときだけ。

## 2. 共通モデル（案件ファイル）`src/lib/case-model/types.ts`
純粋な型（サーバー・AIの部品を import しない）。項目: 系列・店舗・抽選形態（店舗選択式/店舗別独立/その他）・選べる店舗・商品・応募開始/締切・**当選発表の開始/終了**・応募方法・条件・応募URL・受取方法。各項目に 値・状態（確定／推定／未確認／矛盾／不明／人間確定）・決めた主体（AI／固定／マスター／人間／調査）・根拠（URL・原文・一次/二次・主催者本文/受付表示・取得日時）・別の値。ほかに、情報源の一覧（使った／取得失敗／同一でない／未報告）・人間確定の項目・**未反映情報（`unreflected`。登録候補に欄が無い値・確定していない別の値を黙って捨てない）**・判断の履歴。
- AIの読み取りは**推定**（確定ではない）。確定は固定ロジックが根拠（一次情報・独立した複数の出どころ）で与える。
- 登録候補への変換は既存の抽出形式を経由する（`merge.ts`）。DBの列が無い情報は `unreflected` に保持（DB変更なし）。

## 3. 本番収集経路との接続（`src/lib/server/collector/run.ts`）
| 箇所 | 内容（すべてフラグ有効時のみ） |
|---|---|
| `extractFor` | AIへ渡す入力を記録（`q.aiInput`）。X投稿は投稿者の表示名・プロフィールと過去の人間の判断（参考）を、告知本文と区別して追加（これまで固定ロジックだけが参照していた） |
| `processCandidate`（アカウント特定の直後） | AIの読み取りを案件ファイル化 → 調査が必要か判定 → 必要で、調査が有効・接続済みなら調査を呼び、結果を `buildDraft` の前に合流。以降（店舗選択式の判定・重複・登録判定）は既存の経路 |
| 応募単位の判定の入力 | 調査が見つけた応募単位・選べる店舗を `result.extraction` へも渡す（**統合テストで判明: 渡さないと、調査の判断が既存の応募単位の判定に届かなかった**） |
| 固定ロジックが応募単位を変える2箇所 | 変更の理由を判断の追跡（trace）に記録（従来は記録なし＝黙った上書きだった。フラグ有効時のみ） |
| `stored`（候補の下書き） | `judgment`（判断履歴）を保存 |
| 呼び出し口 | `investigation-hook.ts`（`grouping-hook.ts` と同じ作り: 環境判定のあとの動的読み込み。本番では何もしない）→ `server/agent/case-bridge.ts`（調査対象の組み立て・調査・案件ファイルへの変換。**DBへ書かない**） |

調査の起動条件（`investigationNeeds`）: 取得制限・必須情報の不足・矛盾・系列不明・店舗不明（店舗選択式とも判断できない）・複数店舗の羅列で形態が不明・重複の判断が難しい・根拠が弱い。正常に見える案件は対象外（将来の抜き取り再確認も同じ関数を通す設計。今回は有料実行なし）。**調査機能は既定で未接続**（`configureInvestigation` または `CollectDeps.investigate` で開発・評価が明示的に接続。実AI・実検索は承認制）。接続されていなければ「必要だが未実行（理由つき）」を記録するだけ。

## 4. AIの判断履歴の保存（`judgment`）
`candidates.draft.judgment`（JSON）。内容: AIへ渡した入力の記録（種類・URL・文字数・ハッシュ・**伏せ字にした短い抜粋 1,200字**・画像枚数・参考情報の要素）、AIの読み取りと最終の登録候補（項目と状態）、**差分の判断履歴**（項目・変更／破棄／補完／保留／拒否・前後の値・主体・理由）、固定ロジックの検証の指摘、重複の根拠、使った人間の判断、未反映情報、調査の要否・実行・結果（`reasons`＝調査前の理由／`remaining`＝登録候補が固まったあとに残った理由）。
- 「AIが正しく読んだ値が、どこで変わったか」: 理由の記録がない変更は **「固定ロジックによる変更（理由の記録なし）」** と明示（`silentChanges` で抽出できる）。表記の違い・マスターの正式名称への照合は変更にしない。
- 容量・保持: 判断履歴は最大60件、入力の抜粋は1,200字、参考情報は8件×200字。本文全文は保存せずハッシュと長さで同一性だけを追う。APIキー・認証情報・メール・電話・住所らしき文字列は伏せ字（`redact.ts`）。保持は候補の下書きと同じ（候補の整理に従う）。
- 調査エージェントの結果は、取得したが報告されなかったページ・同一でないと統合しなかった情報源も `decisions` に残る。

## 5. 固定ロジックとの役割分担（調査結果の合流規則 `merge.ts`）
- 読み取りが空の項目: 調査の値で補う（確定以外は「未確認」の注意つき）。
- 読み取りと違う値: 調査が**確定**（一次情報・独立した複数の出どころ）のときだけ置き換える（記録: changed）。確定でなければ置き換えず、食い違いを注意・未反映情報・保留として残し、確認待ちの理由にする。
- 矛盾（conflict）の項目は採用しない（別の値も未反映情報へ）。人間確定の項目は上書きしない（拒否の記録）。当選発表の終了が開始より前の値は採用しない。
- 固定ロジックが持つ役割: 形式・必須項目・原文との整合（引用の実在）・既存データとの衝突・手動編集の保護・SSRF/アクセス制限・費用/回数の上限・DBへの安全な書き込み。AIが担う役割: 情報源の探索・意味解釈・系列/店舗の候補・店舗選択式の判断・同一抽選の判断・追加調査の判断。
- 調査エージェント側の修正（9H-3A の「AI判断が失われる箇所」）: ①当選発表の期間を受理（開始・終了を保持）②店舗選択式を根拠の抜粋つきで報告できる（`applyUnit`）。店舗選択式のとき、店舗の羅列を店舗の値にしない。羅列を店舗として報告しようとすると理由つきで拒否され、`applyUnit` での報告を促す ③取得したが報告されなかったページを検証層が指摘し、記録に残す。
- **未修正（提案のみ）**: LivePocket の主催者本文の一次情報扱い（`tierOfCase`）は変更していない。理由: 主催者が対象の系列かを確認する根拠なしに一次扱いにすると、別の主催者のページで誤って「確定」になる。判断を利用者に委ねる（§8）。

## 6. 人間の評価の利用（`human-knowledge.ts`・`human-knowledge-load.ts`）
`backups/review-answers/*.json`（評価ツールの書き出し）を置くだけで、毎回コピーせずに使われる（`HUMAN_KNOWLEDGE_DIR` で変更可）。抜き出すもの: 系列の別名（正規化で同一になる表記は作らない）・店舗選択式の判断・店舗名の訂正・登録/除外/重複の判断・評価コメント。`usableAsGold=false` の評価は使わない。**参考情報として「過去の人間の判断。今回の告知の記載を優先し、告知に根拠が無いまま当てはめない」と明示して渡す。応募条件・日程は渡さない。確定値の代入には使わない。** 実際の評価30件のファイルから、キデイランド・フルコンプの店舗選択式の判断が取り出せることをテストで確認。
