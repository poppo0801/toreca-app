# Stage 7Q: 抽選重複判定の改善・除外系列管理の修正

## 1. 重複判定（`src/lib/lottery-match.ts` の `findDuplicates`。自動収集・抽選候補の再評価・手動登録・一括登録・登録直後の再確認で共通）

### 店舗の区分（店舗IDが無いというだけで同じ扱いにしない）
| 区分 | 意味 |
|---|---|
| 店舗固定式（fixed） | 特定の店舗で実施される抽選（店舗IDあり） |
| 店舗選択式（select） | 応募時に応募者が店舗を選ぶ抽選（`storeMode=select_on_apply`、仮の店舗「応募時に店舗選択」。GEO など） |
| 通販（online） | オンライン・通販 |
| 店舗未確定（unconfirmed） | 本来の対象店舗が不明（店舗IDなし・選択式でも通販でもない） |

### 店舗の関係（`storeRelation`）
- same: 同じ店舗 / 双方が通販 / 双方が店舗選択式 / **双方が店舗未確定**
- weak: 店舗固定式と店舗未確定（同じ告知か別の店舗か判断できない）
- 別（統合しない）: 別の店舗、店舗選択式と店舗固定式・店舗未確定、通販と店舗

### 判定
| 条件 | 結果 |
|---|---|
| 同じ情報源URL（店舗の関係が「別」でない） | high |
| 系列・商品構成・店舗の関係が same、締切が両方分かる、明確に別の開催回でない | **high**（応募期間・情報元URL・締切日が違っても） |
| 同上で締切が不明 / 同じ店舗で商品の一部だけ共通・同じ締切日 | medium（抽選候補で確認） |
| 店舗の関係が weak、商品構成が同じ、締切が同じ・不明 | medium（抽選候補で確認） |
| 明確に別の開催回（応募期間が重ならない・既存の締切が過ぎていて新しい締切が後 等） | 別カード |
| 店舗が明確に違う独立した抽選 / 商品構成が違う | 別カード |

7P からの変更: **店舗未確定どうしを medium（確認待ち）から high（統合）へ**。店舗選択式と店舗未確定を区別（以前は同じ区分に混ぜていた）。

## 2. 並行処理・DB
- `lotteries.auto_dedupe_key`（7P）: 系列|店舗|商品構成|締切日が同じ自動登録の二重登録を DB が拒否（23505）。**締切日だけ違う同じ抽選は防げない**。手動登録・既存はキーなし。
- **登録直後の再確認（7Q・`dedupe-guard.ts` の `reconcileAutoRegistered`）**: 自動登録の直後に、同じ系列の登録済みの抽選（判定に必要な項目だけ・最新の状態）を共通の `findDuplicates` にかけ直す。重複なら **先に作られた方（同時刻は ID の小さい方）を残し、あとの方をアーカイブして統合**。手動登録は常に残す。どの処理が先に確認しても全員が同じ結果になる（ロック不要）。応募記録がある抽選は統合しない。収集（run.ts）・再評価（reevaluate.ts）の両方に適用。全件取得はせず、同じ系列の抽選と商品明細の2クエリだけ。
- 残るリスク: 2つの処理が、互いの登録のコミット前に両方とも確認を終える極めて短い時間差があると、まれに2件残る（次回の重複判定・整理スクリプトで検出可能）。

## 3. 情報元の統合・保存（`lotteries.merged_sources`・内部データ）
URL・収集日時・収集時の系列名・統合した日時・理由・統合元の候補ID・抽選ID・元データ（系列・店舗・商品・締切・情報源）を jsonb 配列で保持。同じURLは重複保存しない（上限30件）。抽選詳細画面には出さない。統合元の抽選はアーカイブで残るため、別店舗・別開催回と分かった場合は `archived_at` を戻して再分離できる。`scripts/dedupe-lotteries-7q.mjs --restore <バックアップ>` でも復元可能。

## 4. 除外系列（信頼性なし）
### 調査結果（Luruna Card）
- 系列マスター `Luruna Card`（仮登録・2026-11-03 作成）。**系列の除外ルール（collection_exclusions）は保存されていなかった**。除外ルールは `@orikuji`・`@tcgprocojp`（Xアカウント）の2件のみ。
- 11/7〜11/9 に利用者が候補を除外（「信頼性に疑問があるショップ」など）していたが、旧操作（`manualDismissAction`）は候補1件を除外するだけで、系列の除外ルールを作らなかった。そのため同じ系列の次の告知・再確認が止まらなかった。
- 該当系列の抽選 5 件（有効 4・アーカイブ 1）はすべて 11/3〜11/8 の登録で、11/9 の除外指定より前（除外指定後に新たに登録されたものは確認されない）。11/11 06:00 の定期再確認（変更なし）が続いている。
- 系列名の別名の登録はなく、別名による回避は確認されなかった。

### 修正
- `src/lib/collector/chain-exclusion.ts`（純関数）: 系列マスターID → 系列名・別名・表記ゆれ（空白・全半角・大小文字・「通販」等の語を除いた名称）→ 題名の系列名。情報源のアカウントが不明でも適用。
- 適用箇所: 候補の作成前（Web・一覧の題名。X投稿は解析後の系列で判定）、解析の前（公式アカウントの対応づけが除外系列なら AI を呼ばない）、登録前（run.ts・reevaluate.ts）。除外した候補は削除せず `excluded` で残し、理由と除外指定日を記録。
- 「信頼性なし」で候補を除外したとき、系列マスターで確定していればその系列の除外ルールを自動で保存（以前は候補1件のみ）。
- 除外系列の別名で新規マスターを作って回避することを防ぐ（登録前に名称・別名で判定するため、仮マスターも作られない）。
- 除外系列の既存の抽選カードは削除・アーカイブしない（整理スクリプトも対象外）。手動登録は禁止しない。
