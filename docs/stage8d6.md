# Stage 8D-6: 検証結果を受けた自律的な再調査（再調査ループ）

目的: 住所調査AIが、**検証システムの返す具体的な不足の理由**を受けて、追加調査・保留・終了を自分で選べるようにする。検索回数を増やすことは目的ではない。将来の抽選情報収集AIにも転用できる形（検証結果 → 不足 → 文面）にした。
実装済み（開発環境）／評価済み（実API・未知30店舗）／未実装（本番の有効化・`followUps` の環境変数化）を区別して書く。本番には何も変更していない。

## 1. 既存実装の確認（8D-5 時点）
- ツール（読み取り専用6種）と上限（12ステップ・検索4・取得6・15円・90秒・再試行2）は `core.ts`。1回の `runAgent` が1つの `Budget` を持つ。
- 検証（`verify.ts`・`official.ts`）は AI の外側。確認済みは公式の情報源（登録済み／根拠で検証済み）に店舗名と住所があり、閉店・移転・別店舗の疑いがない場合のみ。
- 従来の「追加調査」は、**AI自身が決めた検索**か、利用者の手動の再調査（`retryNote`）だけで、**検証結果がAIへ返ることはなかった**（提出して終わり）。

## 2. 実装（再調査ループ）
流れ: ①AIが提出（submit）→ ②**独立した検証**（`verifyResearch`。同じ基準）→ ③不足があれば、具体的な理由を提出への結果として返す → ④AIが追加調査／保留／終了を選ぶ（同じ会話・同じ予算）→ ⑤再提出 → ⑥再検証して最終結果を保存。
- `core.ts`: `runAgent` に `review`（提出後の検証。AIの外側）と `maxReviews`。提出の呼び出し（`submit_findings`）への結果として検証結果を返す（思考ブロックを含む応答の原本は維持。同じ応答の他の呼び出しは実行しない）。再調査の途中で上限・障害に当たっても、**直近の提出を失わない**（`lastSubmitted`）。
- `followup.ts`（純粋なロジック）: 検証結果から**不足（Gap）**を取り出す。種類: 公式サイトである根拠が不足／住所の番地が不足／店舗名の一致が不十分／別店舗の可能性／情報源同士の矛盾／引用が取得ページに存在しない／地図（国土地理院）の照合が不十分／店舗名はあるが住所の記載がない。公式性の不足には、検証が確認できなかった根拠の種類（店舗一覧との一致・運営会社など）を具体的に返す。**返すのは根拠の種類だけで、検証を通すための引用の加工・抜け道は示さない**。依頼文に外部ページの文面・AIの自己評価は含まれない。
- **再調査しない（保留する）条件**: 確認済み（`sufficient`）／閉店・移転・命令らしき文面・都道府県の相違（`safety_hold`。追加調査では解消できない。人が確認）／補える不足がない（`no_gap`。見つからない等はAIの結論を尊重）／再調査後も同じ不足が続く（`no_progress`）／回数の上限（`max_rounds`）／予算の余力が見込めない（`budget`）。
- **予算（抜け道なし）**: 再調査は同じ会話・同じ `Budget`。追加の上限は無い。`Budget.hasHeadroom`: 残りステップ2以上、費用・トークン・時間が1ステップ平均の1.5倍以上、のときだけ始める（予測で超過するなら始めない）。
- **重複の抑止**: 同じ検索語（空白・全角半角・大文字小文字の違いのみ）・同じURL（`#`・末尾`/`の違いのみ）は、実行せず・検索/取得/費用を消費せずに断る。3回続いたら終了（`maxDuplicates`）。
- `run.ts`: 提出ごとに検証し、`rounds`（提出ごとの状態・不足の種類・再調査したか・終了の理由・その時点の費用/時間）と `submissions`（AIの出力そのもの）を返す。最終の検証は全提出の候補をまとめて行う（取り下げた提出の矛盾の手がかりを失わない）。再調査の途中の障害は、それまでの提出の検証結果を保存し、`reasons` に記録する。**`followUps` の既定は 0（従来どおり）。評価と開発画面は 2。**
- 保存: 新しいマイグレーションは不要（`usage`・`trace` の jsonb に `duplicateCalls`・`followUps`・`review`・`duplicate` を追加）。

## 3. 評価データの保存不具合の修正
- **原因**（実データで確認）: ①実行記録（`real-*.json`）に、AIが見たページの本文が無かった。②再判定は共有のキャッシュ（`cache.json`。URL → 最後に取得した内容。**取得日時・実行IDなし**）から URL で探していた。③そのキャッシュは実行をまたいで上書きされる（8D-5 時点で150件のURLのうち14件が複数の実行で取得されていた）。→ 実行時とは別の時点のページが再判定に混入し、検出もできなかった（P19・R1 の食い違い）。
- **対策**（`evidence-store.ts`）: 実行ごとに**証拠の台帳 `pages-<実行ID>.jsonl`** を新規作成し、店舗・順番・URL・最終URL・取得日時・取得元（通信/キャッシュ）・本文・SHA-256 を追記する。**既存ファイルは上書きしない**（排他的作成。同じ実行IDの結果も拒否）。評価実行のキャッシュも実行ごとに分離（`cache-<実行ID>.json`）。取得日時は `CachedFetcher` が本文と一緒に保存する。再判定は台帳のページだけを使う。AIの提出（`proposals`）も実行記録に全文を残す。
- **整合性の検査**（`verifyLedger`。自動テスト）: 実行IDの混入・本文のハッシュ・連番の連続と重複・取得日時が実行開始以降か・実行記録のページ取得との順序つきの対応。同じURLで内容が違う取得は別の項目として両方残る。実在の実行（`eval/runs/real/`）の台帳も、テストで毎回検査する。
- 過去の評価結果（8D-3〜8D-5 の記録）は書き換えていない。旧記録の再判定は従来のキャッシュ（制約つき）を使う（再判定の出力に出どころを明記）。
- **確認**: 8D-6 の実行を台帳から再判定した結果、30店舗すべてが実行時の判定と一致（差0）。

## 4. 役割分担と独立性
- AIが選ぶ: 調査方法（検索語・取得先・再調査するか）。検証システムが決める: 公式性・住所の一致・店舗の同一性・確認済み・安全上の問題。AIは検証結果を書き換えられない（結果はコードで計算され、依頼文は検証結果から作られる）。基準の変更はコード・テスト・履歴（git）で管理する。
- 8D-6 で `official.ts` の第三者リスト（`THIRD_PARTY`）に `tcg-map.com`・`nansan.com`（商店会）を追加した（**実行前**。評価対象の登録ドメインを見て、地図・商店会サイトを公式にしないため）。

## 5. モック環境での検証（有料APIなし。`followup.test.ts`・`agent-core.test.ts`・`evidence-store.test.ts`）
公式性の根拠不足 → 店舗一覧を追加取得して確認済み／別店舗の行を引用 → 正しい行で再提出して確認済み（店舗名の不一致の解消）／矛盾 → 追加調査しても解消せず保留（同じ不足を繰り返さない）／根拠が十分なら再調査しない（余分な検索・取得・費用なし）／同じ検索語・URLの繰り返しを断り終了（それまでの提出は残る）／実行回数・費用・時間の余力が予測で足りなければ始めない／再調査の途中で上限に達しても提出が残る・API障害でも提出の検証結果を保存／悪意のあるページ（命令らしき文面）は無視され、確認済みにならず保留・依頼文に含まれない・AIの「公式・信頼度100」の主張で判定が変わらない／登録情報は変更されず、書き込みに当たるツールは登録できない／Anthropic接続のメッセージ変換（提出への結果の返却・思考ブロックの維持）。
