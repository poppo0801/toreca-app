# Stage 9H-3E: 複数の調査結果の統合・評価の1抽選1件化・人間評価の取り込み

開発環境のみ。マイグレーションなし。**有料API・実AIの呼び出しなし（費用 0円）**。保存済みの実データ（9F-2・9H-2・9H-3D の評価と調査結果）とモックだけで検証。実AIでの効果は未測定。

## 1. 統合処理（`src/lib/case-model/integrate.ts`。純関数・再現可能）
同じ抽選の複数の情報（収集AIの読み取り・調査エージェントの結果・同じ抽選の別の候補）を、1件の最終候補に統合する。
1. **同一抽選の判定**（`identity.ts` を共通モデルへ移動）: 系列・商品・店舗・応募期間。別の系列・商品・応募期間（14日超の差）・**別の店舗の独立した抽選**は統合しない。店舗が**一方だけ**分かっている候補も統合しない（9H-3Dの誤統合の再発防止。逆向きも）。店舗をまたぐ応募制限・店舗選択欄の記載がある店舗別の告知は、店舗選択式の1件として統合し、各店舗は「選べる店舗」に入れる。調査エージェントの結果は、調べている抽選そのものなので同一性を再判定しない（`sameVerified`）。
2. **項目ごとの根拠の比較**（情報源全体の一律の順位は付けない）: 値ごとの強さ＝確定／一次情報／主催者本文／原文の抜粋／サービス側の受付表示（弱）／根拠のない推定（弱）。同じ意味の値（日時の境界・詳しさ、系列・商品・文面の言い換え）は1つにまとめ、独立した出どころが複数なら強くする。強さの差が大きければ強い値を採用し、近ければ**矛盾として未確認で保持**（応募締切の暫定値は早い方、他は基準の読み取り）。
3. **詳細な応募条件を短い文面に置き換えない**: 同じ内容の文面は最も詳しいものを採用（確定した短い記載を含むだけなら、確定ではなく推定に下げる）。言い換えは文字の2文字組の一致率で同一視。
4. **当選発表の期間**は、開始日だけの候補で終了日を消さない。**商品**は装飾の少ない短い名前に（「MEGA 拡張パック ○○(シュリンクなし)」→「○○」）、**系列**は短い表記に（「イトーヨーカドーネット通販」→「イトーヨーカドー」）。
5. **形式の検証（固定ロジック）**: URLでない応募URL・日時でない値・区分外の応募方法/受取方法は採用せず、理由を項目単位で記録（実データで「抽選受付ページ（URL未取得）」が応募URLに入っていたのを検出）。
6. **導出（推定。確定ではない）**: 店舗選択式・特定の実店舗なら店舗受取（人間の評価の傾向）。
7. **人間が確定した項目は上書きしない**。採用した値・採用しなかった値・統合しなかった候補を、項目ごとに理由つきで記録（`adoptions`・`decisions`・`unresolved`）。

AIと固定ロジックの役割: 項目の読み取り・店舗選択式の判断・追加調査・同一抽選の照合の材料はAI（調査エージェント）が出し、固定ロジックは同一性の保守的な判定・根拠の強さの比較・形式の検証・矛盾の検出・手動確定の保護・記録を担当する。固定ロジックがAIの値を採用しなかった場合は、変更前後の値と理由が必ず残る。

## 2. 収集経路への接続（`run.ts`。`COLLECT_UNIFIED=on`＋`TOREMANE_ENV=local` のときだけ）
- 同じ抽選の別の候補（確認待ち・追跡中。`loadOpen`）を、同じ系列のものだけ集めて統合へ渡す（`from-open.ts`）。調査の結果があれば一緒に統合する。調査をしない・できない場合も、同じ抽選の別の候補があれば統合する。
- **従来の同一抽選の統合（`mergeSides`）とは別に**、統合に参加した確認待ちの候補を「同じ抽選の別の候補へ統合」として除外する（削除しない・理由つき）。利用者に同じ抽選が複数のカードで出ないようにするため。統合に参加しなかった別の抽選の候補は触らない。
- 以前の調査結果の合流（`merge.ts`）も、選択を統合処理に一本化した（別の規則を持たない）。判断履歴（`draft.judgment.integration`）に、統合した候補・採用/不採用・矛盾・統合済みにした候補を保存し、開発用の判断履歴画面で確認できる。
- フラグ無効時は従来と同一（統合・除外・判断履歴なし）。DB変更なし。
