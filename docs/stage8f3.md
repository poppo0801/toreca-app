## 1. 形式不正11回（8F-2）の原因分析
- 8F-2 の実行記録には生の提出を保存していなかったため、**原因は確定できない**（正直な結論）。実行記録から確認できた事実: 11実行はすべて「AIの提出が解析で却下」（API障害・上限停止ではない。停止理由は正常、ステップ・トークンは通常範囲）。
- 有力な原因（コードの読み取りと再現テスト）: 解析が厳しすぎた。共通/相違の項目（`claimedCommon`/`claimedDiffers`）は1項目40文字以内、`missing` は10件以内などで、**1つでも超えると提出全体を却下**していた。実際のAIは、理由を長い文で書く傾向があり（判断理由の記録で確認）、項目に長い文を入れると却下される。`format.test.ts` で、この条件が却下を起こすこと（旧）／補正して受理すること（新）を再現。ただし**実APIで確認するまでは「推定」**。
- 対策（実装済み・テスト済み）:
  1. **解析の補正（`parseGroupingProposalDetailed`）**: 文字数・件数の超過、型の軽微なずれは、切り詰め・補正して受理し、補正の内容を記録する。判断に関わるもの（`action` が不正、相手が81件以上と過大）は却下（保留）。共通の文言（`commonPhrase`）は、300字超なら切り詰めず「無し」にする（切り詰めると「すべての情報源に実在する文言」の検証の意味が変わるため）。内容の検証は従来どおり検証層（固定ロジック）が行うので、補正しても安全性は変わらない。
  2. **形式不正時の再提出（1回まで）**: 却下の理由だけ（正解・内部情報なし）を返し、同じ会話・同じ予算の中で再提出させる。直らなければ保留（自動にしない）。追加調査の回数とは別枠。
  3. **構造化出力（strict）の提出ツール**: `AnthropicLlmOptions.submit.strict`（提出ツールに `strict: true` と `additionalProperties:false` のスキーマ）。**既定は無効**。実APIで効果と互換性（モデルが対応しているか）を測ってから有効にする（`--strict` で A/B 比較）。未検証のまま本番経路では有効にしない。
  4. **応答の安全な記録（`recorder.ts`）**: 各ステップの停止理由・呼んだツール・提出の生の内容・使用量・エラーを `RunRecord.trace` に保存。APIキーらしき文字列（`sk-…`・`Bearer …`）と認証系のキーは伏せる。長い文章は切り詰める。評価データは公開情報のみで個人情報を含まない（結果ファイルは Git 管理外）。
  5. 実行記録に `parseIssues`（補正・却下の内訳）と `followUpKinds`（format／evidence）を追加。
- 安全性: 形式不正でも自動グループ化は起きない（保留）。再提出も検証層を通る。

## 2. 「異なる」「記載なし」「確認できない」の区別（判定ロジック）
- **応募条件**: 条件タグの片方だけに追加の項目がある（例: 一方に `id_check` があり他方に無い）は、従来は「異なる（hard）」。**新: `unstated`（記載なし。条件が異なるとは限らない）＝軽微（soft）**。互いに相手に無い項目がある（食い違い）・論理が異なる場合は従来どおり `differs`（hard）。8F-2 の K11（キデイランド）の見逃しの型。
- 軽微（soft）は従来から「利用者の承認が必要な候補（suggest）」。**自動にはならない**。理由に「記載なし」と明示。
- **確認できない**: 情報源の文章が保存されていない抽選は `sourceTextStored=false` としてAIに示す（異なるのではなく確認できない）。関係の読み方（`legend`）を一覧の結果に付ける。システムプロンプトに3区別（異なる→single／記載なし→missing に書いて候補を提案してよい／確認できない→missing に書く）と、「同じ企画の根拠が全く無いときはまとめない」を明記。
- **変えなかったこと**（既存テストが定める安全側）: 不明（日付なし等）で同じ企画の裏づけが無ければ保留。期間・方式が異なり裏づけが無ければ単独。「記載がないだけ」を根拠にまとめない。8F-2 の K12（店舗未特定・情報源の文章なし・URLが別）は、この方針のため**改善しない**（候補に上がらない）。残る課題として、手動登録にも情報源の文章を保存する・同じイベントIDを検出する、が必要（§5）。
