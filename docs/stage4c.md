# Stage 4C: 抽選情報の自動収集

## 構成
- DB（`20261101000035_stage4c.sql`）: `collection_sources`（収集元）/ `collection_settings`（収集条件・定期実行・X予算）/ `collection_candidates`（候補）/ `collection_runs`（実行履歴。同時に1つだけ running）。RLSは世帯単位。
- 収集処理 `src/lib/server/collector/run.ts`: 収集元 → 告知リンク/X投稿 → 関連判定（ルール）→ AI読み取り（既存 `lottery-extract-service` の共通処理 `extractFromRequest`）→ 収集条件（`lib/collector/conditions.ts`）→ マスター照合（`buildDraft`）→ 重複検出（`findDuplicates`）→ 候補/自動登録。
- Web: `lib/collector/listing.ts` が一覧ページの外部リンク（公式告知・応募ページ・店舗のX投稿）を取り出す。pokeso / トレカ日和 / 汎用のアダプター。0件なら「解析設定が必要」。robots.txt を守り、403/429 は「アクセス制限」と表示して回避しない。
- X: `x-client.ts` が公式API v2（`X_BEARER_TOKEN`）で投稿（本文・日時・画像全件・外部リンク・引用）を取得。まとめサイト経由のX投稿URLは無料の公式oEmbed。
- 画面: 設定 › 抽選情報の自動収集（収集元CRUD・手動実行・条件・費用・候補・履歴）。API: `/api/collection`（ログイン必須）、`/api/cron/collect`（CRON_SECRET）。

## 安全・費用
- X API: 設定で有効化し月額予算を決めるまで1回も呼ばない（既定: 無効・0円）。1投稿 約0.005米ドル（公開情報。見積もり1.2円/件で安全側）。取得前に残り予算を計算し、超える場合は停止。401/402/403/429 は原因を表示。
- AI: 1回の解析上限（既定8件）＋既存の時間/日の上限＋月間予算。上限を超えた分は次回（キュー）。同じURL/投稿IDは再解析しない。
- 自動収集は★管理対象にせず、応募記録を作らず、既存抽選の確定情報を変更しない（重複時は情報源URLの追加のみ）。
- 定期実行はログインが無いため候補作成まで（登録は手動実行か候補画面）。`schedule_enabled` 既定false。

## 定期実行の有効化手順（未実施）
1. `X_BEARER_TOKEN`（Xを使う場合）をVercel環境変数に設定。
2. 設定画面で定期実行・X API・月額予算を設定して保存。
3. Supabase Cron から `/api/cron/collect` を `Authorization: Bearer $CRON_SECRET` で毎時（または日本時間6:00=UTC 21:00）呼ぶ。設定した時刻の世帯だけ実行される。

## 解析待ちの絞り込み（初回収集で溜まる解析待ちへの対策）
- 初回は一覧の情報（リンク・見出し・周辺の文章）をすべて候補として保存する。一覧の表示から読み取れる**締切**（「11/3(火) 20:30まで」「11/6(金)まで」など。時刻が無いものは日付だけで判定し、23:59は補わない）と**都道府県**（「千葉県・LivePocket」）で、締切済み・対象外の地域のものは**AI読み取りの前に除外**する（費用なし）。通販・発送の表示があるものは地域で除外しない。除外した候補には理由を付け、「確認待ちに戻す」で解析できる。
- この絞り込みは収集のたびに、過去に溜まった解析待ちにも適用する（締切が過ぎたものは自動で除外される）。
- 残りは**締切が近い順**に、1回のAI上限（既定8件）まで、4件ずつ並行して読み取る（実行時間の上限60秒の中で上限件数まで進める）。時間が足りない分は次回に回す。
- 取得済みのURL・X投稿IDは再取得・再解析しない（新しい告知だけが解析対象）。サイトがロボット取得を許可していないページは、再試行せず失敗として確定する。
- 画面は「確認待ち（解析済み）」と「解析待ち（AI読み取り前）」を分け、件数は表示件数ではなく全件の数を示す。

## 継続処理・優先順位・差分検出（追加実装）

### 実行基盤
- **Supabase Cron（pg_cron）→ pg_net → Vercel の `/api/cron/collect`**。Vercel Cron は使わない（Hobby の頻度制限を避け、有料プラン変更も不要）。Supabase Cron は Supabase 側の機能で、追加費用はない。
- サーバーレスはレスポンスを返すと処理が止まるため、「1回の呼び出し＝約54秒以内で完結（バッチ処理）」「残りは次の定期起動が引き継ぐ」方式。単発の非同期処理には依存しない。
- 定期ジョブは5分おき（`npm run cron:collect -- --enable`）。解析待ちも再確認も無ければ、DB参照だけですぐ終了する。
- 毎朝6:00（日本時間）の収集: 5分おきの起動のうち、「指定時刻を過ぎていて、今日まだ収集していない」最初の起動で実行する（時刻のずれ・取りこぼしを吸収。Cronの実行時刻には数分の揺れがある）。
- 「今すぐ収集」も同じキューを使う。画面を閉じても、ワーカーが続きを処理する。

### キュー（collection_candidates の job_state）
`pending`(解析待ち) / `processing`(解析中・リース付き) / `completed` / `skipped`(除外) / `retry`(再試行待ち) / `review`(確認待ち) / `failed`(隔離)。
開始・完了日時、試行回数、エラー、次回実行時刻、リース期限、ロック者を保存。
- **原子的な取得**: `claim_collection_jobs`（`FOR UPDATE SKIP LOCKED`）。複数のワーカーが同時に動いても同じジョブを取らない。
- **リース**: 150秒。ワーカーが異常終了しても、リース切れのジョブは次のワーカーが再取得する（試行回数は加算）。
- **再試行**: 15分 → 1時間 → 4時間（指数バックオフ）。3回で `failed`（隔離）。ロボット取得の拒否など再試行しても変わらない失敗は即 `failed`。
- **優先順位**: 締切が6時間以内100／24時間以内90／72時間以内70／それ以降30／不明40（最後尾にしない）＋変更を検出25＋24時間以内の新着15＋待ち時間（6時間ごとに+1、上限60）。同点は締切が近い順。
- **事前絞り込み（費用なし）**: 毎回、解析待ち全体に対して、一覧の表示から締切済み・対象外の地域を除外。

### 差分検出
- 一覧の見出し・周辺の文章を正規化（「あと○時間」「新しいタブで開きます」「アクセス数」等を除く）してハッシュ化し、変化があれば再解析。変化が無ければAIを呼ばない。
- 告知ページ本文も、再確認間隔（既定6時間）ごとに無料で取得して正規化ハッシュを比較（AIなし）。変化があれば再解析、「中止」の表現があれば状態の更新を提案。
- 再解析の結果は既存の抽選と比較し、**更新の提案**（日時・受取方法・状態）として確認待ちに出す。利用者が「更新を反映」を押すと日時等だけを更新（応募・当落・スルー・購入には触れない）。提案後に抽選が編集されていれば反映を拒否する。
- 同じURLで前回の締切より後に新しい応募期間が始まった場合は、別の抽選回として新しい候補（キー `URL#締切日`）を作る。
- X投稿は編集の検出対象外（投稿IDで1回だけ解析）。

### 費用・異常の停止
- ワーカーの1日の上限（既定30件）＋既存のAI利用上限（時間20/日60）＋月額予算。上限に達したら次のAIリクエストを開始しない。
- AI読み取りが5件連続で失敗したら6時間自動停止（画面から解除可）。
- 1回で新規候補が150件を超えたら警告。
- 画面に警告: ワーカー停止（30分）、解析待ちの滞留（2日）、失敗の急増、収集元の連続失敗、定期収集の停止。

### Supabase / Vercel の設定
- `npm run cron:collect -- --url https://<ホスト>/api/cron/collect`（Vaultに保存）→ `--enable`。停止は `--disable`、状態は `--status`。
- 収集条件画面の「解析待ちを自動で解析し続ける」と「定期収集」で、利用者が有効/無効を決める。

## 運用調整（AI上限・予算・統計）
- **日次上限**: 既定100件（日本時間0時に更新）。1回のワーカーは2件のまま、Cron（5分）で順次消化。解析対象が無ければAIを呼ばない。設定画面で変更でき、上限到達時は『今日だけ』150/200件に引き上げられる（翌日0時に通常へ戻る。月額予算が不足なら再開しない）。
- **月額予算**: 既定3,000円（日本時間の月単位）。費用は既存の利用記録（実際の入出力トークン数×モデル別単価×世帯の為替レート）から計算。再試行・画像も記録した分は計上、統計の費用は同じ呼び出しから積算（二重計上しない）。残額が『1回の見込み(約8円)×件数』に満たない分は始めない（並列・反映遅れの安全側）。X APIの料金は別集計。予算・レートは設定画面から変更（アプリ内の停止条件のみ。外部サービスの契約・課金上限は変更しない）。
- **日別統計**（`collection_daily_stats`、日本時間）: 新規発見（通常/初回取込を区別）・更新検出・重複・除外・AI解析（成功/失敗）・実登録・更新反映・確認待ち追加・解析待ち残・トークン・費用。新規発見は候補を初めて保存した時だけ加算（再取得で増えない）。設定画面の『AI費用・日別の統計』（折りたたみ）で30日の推移と日別履歴を確認。
- 運用状況パネル: 本日の新規発見／AI解析と上限／解析待ち／本日の新規登録／今月のAI料金と予算／最終収集成功／最終ワーカー／処理が進んだ時刻。解析待ちがあるのに30分以上処理が進んでいなければ（上限・予算・停止中を除く）警告する。

## 最終調整（自動登録率・仮登録・X統合解析）
- **照合**: 商品は `productKey`（全角半角・大小・記号・MEGA接頭辞・拡張パック等の区分語・セレブレーション/CELEBRATION/CEREBRATION・未開封/シュリンク付きを除く）で比較。確実な一致は正式名称→別名の順。さらに「途中のMEGAだけ違う」「シリーズ名（別商品名として存在する語）を省いた」場合は、該当が1件に絞れるときだけ別名一致にする。種類を特定できない表記（例: 『30th CELEBRATION プレミアムデッキセット』）は自動確定しない。
- **系列**: 古本市場／ふるいちは同じ系列として照合（マスターは統合しない。その店舗が登録されている系列、なければ店舗数の多い系列を選ぶ）。ブックオフ／BOOKOFF、`TSUTAYA Trading Card`・`ブックオフプラス`のように付帯語だけが付いた表記は同じ系列。未登録の系列・店舗・商品は、名称が明確で既存と曖昧に重ならないときだけ仮登録（住所・都道府県は推測しない）。
- **利用者の修正の再利用**: 確認待ちを「編集して登録」したとき、AIの抽出名（マスター未一致）と選んだマスターの対応を別名（chain/store/product_aliases）として記録。一致済み・短すぎる語（3文字未満）・対応が一意でない商品は記録しない。
- **X投稿**: 単件・一括・自動収集・iPhone共有は同じ取得処理（本文＋複数画像＋リンク先本文）。X APIの利用許可・キーがない場合は公開oEmbedで本文のみ。画像のある投稿は『画像未取得』、取得できた画像は枚数を通知に記録。リンク先の本文は本文のみの取得でも統合。
- **根拠の出所**: AIは各項目の根拠に出所（本文／画像N枚目／リンク先）を付ける。画像・リンク先が出所の根拠は本文と照合できないため『原文に見当たりません』としない（未照合）。
- **確認待ち画面**: 理由は『要確認：締切・店舗・商品』に集約し、詳細は展開。主操作は『編集して登録』、情報源リンク、その他（そのまま登録・再解析・除外）はメニュー。一括登録・一括除外は従来どおり。
