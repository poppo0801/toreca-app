# Stage 5I: 抽選カードの整理・当落発表の期間・商品画像の高速化・プロフィールアイコン

UIは CLAUDE.md / docs/ui-design-guidelines.md のルール（メイン面積優先・説明文を増やさない・操作ボタンを増やさない）に従った。AppShellの高さ・Safe Area・固定メニュー・`?diag=1` の診断には触れていない。

## 1. 抽選カード
- **商品名**: 一覧は先頭の1種類だけ（最大2行・長い名前は末尾を「…」）。残りは右に「＋他N種」（N=商品の**種類数**。数量・BOX数ではない）。単一商品は何も付けない（「＋他0種」は出ない）。全商品・数量・商品別の当落は詳細パネルで確認できる。集約は表示だけで、`items`・`itemResults`・`selectedItemId` は変えない。
- **締切の残り時間**（`deadlineBadge` / `src/lib/datetime.ts`）: 詳細カードは右上の小さなバッジ。シンプル表示は「11/6 23:59　あと7日」の行。3日以上=通常（青緑）／3日未満=オレンジ／24時間未満=赤／終了=グレー。時刻つきは分・時間・日で正確に（境目は3×1440分・1440分・60分）。**日付のみの締切は23:59などの時刻を補わず**、日付の差だけで「あとN日」「本日まで」を出す（バッジに「時刻は未確認」のヒント）。締切不明は出さない。受付前は「受付前」、受付終了・中止は文言のみ。カード左端の色帯も同じ段階。
- **都道府県／通販**: 右上は残り時間に譲り、店舗名の隣の小さな丸いチップへ移動（受取方法が発送なら「通販」、店頭なら受取店舗の都道府県。既存ルールのまま）。
- **シンプル表示**: ★・小さな画像・店舗・商品名（最大2行）・締切と残り時間・現在のプロフィールの応募操作。詳細表示より低い。

## 2. 応募状況と応募操作
- **プロフィール別の応募状況は表示専用**（`ApplyStatusRow`）: 「A ✓　B ○　C 当選」のように、プロフィールの色・マークの小さな丸＋状態アイコン。応募済み=✓、未応募=○、スルー=⤼、枠充足=◎、対象外=－、応募不可=✕、要確認=！。当選・落選は文字。色だけに頼らず形・文字でも区別できる。**押しても状態は変わらない**（カードの一部なので詳細が開くだけ）。現在のプロフィールは薄い背景で強調。
- **応募操作は現在のプロフィール専用**（`MyApplyButton`）: 詳細カードは右下、シンプル表示は右端、詳細パネルのユーザー別セクションにも同じボタン。「応募済みにする」→「✓ 応募済み」。解除は確認ダイアログつき。当落が確定した後・購入手続き後は解除できない。スルー中・受付終了などは状態名だけ表示してボタンにしない。
- **サーバー側の確認**: `setApplied`（`lottery-service.ts`）が、操作する人（actor）のプロフィールが担当するアカウントでなければ「他のユーザーの応募状況は変更できません」で拒否する（解除も同じ）。モック保存先も同じ。DB結合テストで確認。
- **複数商品**: 応募・当落の内部データは商品別のまま。応募操作は抽選単位（all / one_win）。「希望商品を1つ選んで応募」（choose_one）の抽選は、商品を選んでから応募済みになり、一覧では「応募済み（選んだ商品のみ）」と表すホバー表記・ラベルになる。全商品へ無条件に応募済みを設定する処理は追加していない。
- **「未確認」の整理**: 一覧から商品ごとのプロフィール＋「未確認」を撤去。発表前の応募済みは「応募済み」だけ。発表日（期間なら最終日）を過ぎても結果が未登録のときだけ「結果未確認」（カードの赤枠・バッジ、ベル、「応募済み」タブの赤丸）。発表期間中は「発表期間中」と穏やかに表示。当落ボタンの「未確認」は「結果待ち」に変更（詳細パネル）。

## 3. 当落発表の期間指定
- **DB**（migration `20261101000028_result_period.sql`、追加のみ）: `lotteries.result_end_date date NULL` を追加。既存の `result_precision/result_date/result_at` は**発表開始**としてそのまま使い、時刻つきの開始も失わない。`NULL` = 従来どおり単一日（既存データは全件このまま）。CHECK: 終了日は開始日（JST）以降。`save_lottery_tx` を再作成（終了日の保存を追加。他は同一）。
- **入力検証**（`lotteryInputSchema`）: 終了日は `YYYY-MM-DD`。開始日が不明のまま終了日は保存できない／終了日が開始日より前は保存できない。
- **フォーム**: 通常は日付欄1つ。「期間で指定」にチェックした時だけ「当選発表の終了日」欄が出る（空いているセルを使うので行は増えない）。期間のある抽選を編集すると最初から開いている。外すと単一日に戻る。
- **表示**: `発表 11/7`、`11/7〜11/10`、時刻つき開始は `11/7 12:00〜11/10`。今年以外は年つき（`2027/1/5`）。詳細パネルは「時刻未確認」の注記も維持。
- **AI解析**（単件・一括とも同じ抽出処理）: ツール定義に `result_end_date` を追加（プロンプト `2026-11-01.1`）。「11月7日から11月10日に順次発表」→ 開始・終了を登録候補へ。終了日が不明・開始以前・開始が不明のときは**推測で補わず期間にしない**（開始以前のときは注意を表示）。年またぎ（12/28〜1/5）は翌年に解釈。
- **ソート**: 発表日順は発表開始日が基準。応募済みタブは「発表日（期間なら最終日）を過ぎて結果未登録」を最上位。
- **通知**: 期間の発表は、開始日（朝／時刻つきなら開始時刻）に「発表期間が始まった」を通知し、**結果の未確認催促は最終日の翌朝**から（期間中は催促しない）。アプリ内のベル・赤丸も最終日を過ぎてから。単一日の通知は従来どおり。**通知Cronは有効化していない。**

## 4. 商品画像の高速化
### 調査（切り分け）
| 項目 | 結果 |
|---|---|
| 保存先 | Supabase Storage 非公開バケット `product-images`（18件） |
| 元画像 | PNG 18件、合計 **6.6MB**、平均 **374KB**（最大468KB）、高さ500px。一覧の表示は高さ約96px＝約5倍の大きさを毎回ダウンロード |
| URL | 画面を読み込むたびに**署名付きURLを再発行**（有効1時間・トークンがURLごとに別）→ ブラウザのキャッシュが効かず、再読込・再訪問のたびに全画像を再ダウンロード。さらに全画像分の署名を発行する往復が毎回のデータ読み込みに入っていた |
| 認証 | Storageの署名URL方式（取得時の認証処理はなし）。ログイン本人の権限で署名 |
| `next/image` | 使っていない（署名URLのため最適化の対象外） |
| 再描画 | カード切替では同じURLのため再取得は起きないが、データ再読み込みでURLが変わると再取得 |
| 遅さの原因 | **通信量（元画像が大きい）と、URLが毎回変わるためのキャッシュ不能**。描画（再レンダリング）は主因ではない |

### 対策
1. **サムネイル**: 高さ288px（表示の3倍）のWebP（透明・縦横比を保つ。元より小さくならない場合は作らない）。新規アップロード時に自動生成。既存18件は `scripts/build-thumbs.mjs`（ドライラン→`--apply`、冪等、元画像は読み取りのみ）で生成。migration `20261101000029_product_image_thumbs.sql`（`product_images.thumb_path`、追加のみ）。
2. **安定URL＋長期キャッシュ**: `/api/product-image/<画像ID>?v=<内容ハッシュ12桁>&s=thumb|full`。ログイン本人の権限（RLS・Storage RLS）で取得して返し、`Cache-Control: private, max-age=31536000, immutable` と ETag（304対応）。画像を差し替えるとハッシュが変わり自動で新しい画像になる。URLを知っていても未ログイン・他の世帯は取得できない（401/404）。署名URLの一括発行が不要になり、データ読み込みも軽くなった。
3. **読み込み方式**: 既存の `loading="lazy"` / `decoding="async"` と幅・高さ・固定枠（画像が来る前から場所を確保）を維持。

### 計測
- **元画像→サムネイル**（実データ18件）: 合計 6,733KB → **423KB（94%削減）**、平均 374KB → 約23KB。
- **初回表示で転送する画像量**（カード18枚分の目安）: 約6.6MB → 約0.4MB。
- **2回目以降**: 以前＝毎回全画像を再取得（URLが毎回違う）／現在＝URLが同一でブラウザキャッシュから（`immutable`。E2Eで再読込後も同じURL・条件つきリクエストが304であることを確認）。
- **未計測**: iPhone Safari/PWAでの体感時間・ネットワークの実測（通信環境に依存）。Storage→サーバーの取得時間は元画像で平均約440ms/件（ローカルPCから）。

### AI解析画像との分離
サムネイル（`thumb_path` / `s=thumb`）は**表示専用**。AI解析へ渡す画像はブラウザで選んだ告知画像（`prepareAiImages`）とサーバー側の安全網（`splitTallImages`）を通り、商品画像テーブル・配信ルートとは経路が別で、縦長画像の高解像度分割（Stage 5H）のコード・テストは変更していない（`tall-image.test.ts` も無変更で通過）。

### 付随して直したもの
- **画像のキャッシュヘッダ**: `next.config.ts` は `/api/*` 全体を `no-store` にしていたため、画像の配信だけ除外（`/api/product-image/*`。認証は配信側）。
- **アップロードの本文上限**: 商品画像のアップロード（Server Action）は既定の1MBを超えると本文超過で失敗していたため、4MBに緩和（画像自体の上限3MBは従来どおり）。
- **応募ボタンの重なり**: 当選タブの購入ボタンの行に重ならないよう、★と応募ボタンはカードの上段の枠の中に配置（E2Eで確認）。
- **AI一括解析の同時実行数**（Stage 5G の不具合・migration `20261101000030`）: `claim_ai_job_items` が、実行計画によっては世帯ごとの上限3件を超えて（4件）取り出すことがあった（DB結合テストが断続的に失敗）。1回だけ評価されるCTEにして上限を厳密に守る。データ変更なし。

## 5. プロフィールアイコン
既存12種（頭文字・星・ハート・いなずま・ほのお・はっぱ・つき・たいよう・おうかん・ほうせき・おばけ・ねこ）のキーと見た目は変更なし。**13種を追加して25種**: とり・いぬ・さかな・うさぎ・かめ・はな・クローバー・おんぷ・ゲーム・ロケット・トロフィー・ゆき・かさ。白線・単色（lucide、既存と同じ線幅）。選択画面は7列のコンパクトなグリッド（4行）。保存済みのプロフィール設定・色はそのまま。
