# Stage 7A: 抽選情報の自動収集改善・確認待ち削減

方針: **応募可能な抽選を見落とさないことを優先**する。不足している情報は不明のまま保持して登録し、追加収集で補う。ただし、誤った抽選への誘導・重複登録・既存データの破壊は防ぐ。DB変更は追加のみ（`20261129000077_stage7a.sql`）。

## 1. 確認待ちの原因分析（2026-11-08・本番の保存済みデータから）
対象: 確認待ち（status=pending）**27件**（保留＝自動再調査 22、要手動確認 1、登録済みへの更新提案など 4）。分類は候補に保存された理由（reasons）と解析結果（draft）から機械的に行った（`scripts/analyze-review-queue.mjs`・読み取り専用）。1件に複数の原因がある場合はそれぞれ数える。

| 原因 | 件数 |
|---|---|
| 系列・店舗の判別失敗 | 17 |
| 受取方法・応募条件の不明 | 15 |
| 応募URL・応募方法の不足 | 13 |
| 情報が少ない（識別困難） | 11 |
| 商品名の判別失敗 | 6 |
| 締切・発表日などの情報不足 | 6 |
| 対象地域外・地域不明 | 3 |
| 複数商品の応募方式が不明 | 2 |
| 複数情報源の内容不一致 | 1 |
| 取得失敗 | 1 |
| その他 | 3 |

- 地域外（豊橋・藤沢・池袋・徳島藍住・ウインクあいち）が確認待ちに入っていたのは、**受取方法が不明だと「要確認」になり、地域外でも除外されない**ため、および店舗名の市区町村名（豊橋・徳島藍住など）から都道府県を判定できなかったため。
- 「再販 30th CELEBRATION」が商品を判別できなかったのは、先頭の【再販】が商品名の整形（ブランド名・シリーズ名の除去）を妨げていたため。
- 系列を特定できないもの（WonderGOO・新星堂・Ganryu店舗 のように複数系列をまとめた告知）は、1つの抽選として登録できない。
- **残っていない情報**: 過去に自動で解決・除外された候補（「1〜2日で約30件増えた」分の内訳）は日別統計に理由の分類が無く再現できない。今回から日別に理由の分類を保存する。

## 2. 自動登録の判定: A / B / C（`collector/attention.ts`）
既存の情報充実度 A〜E（`completeness.ts`）とは別の軸（登録の可否）。不足項目の判定（`isReady`）は共有する。

| 判定 | 内容 | 処理 |
|---|---|---|
| A | 不足も矛盾もない | 通常登録 |
| B | 情報不足・軽微な矛盾（当選発表日／購入・受取期間／受取方法／応募方法／応募条件／店舗・地域の未確認／日付の相違／複数商品の応募方式） | **注意付きで自動登録** |
| C | 抽選として成立するか判断できない | 確認待ち（従来の保留・追跡・要手動確認） |

C にする条件: 系列・商品を特定できない／商品マスター未登録／情報源URLなし／同一抽選か別抽選か判断できない（重複の疑い）／日時が未発表（予告）・締切が不明／受付前（追跡）／系列・店舗・商品の食い違い／締切が2週間以上離れて食い違う（別の抽選の可能性）／「別の抽選」「抽選ではない」等の重大な矛盾／収集条件の対象外。商品名が不明でも無理に架空の商品は作らない。

### 注意情報（構造化）
`lotteries.cautions`（jsonb 配列）に `{code, field, message, values?, at}` を保存する。`code` は自動補完・解除のキー（例: `result_date_unknown` `receive_period_unknown` `receive_method_unknown` `apply_method_unclear` `conditions_unknown` `region_unconfirmed` `store_unconfirmed` `store_select_assumed` `deadline_conflict` `conflict_resultDate` `text_conflict` `mode_unconfirmed`）。`lotteries.confidence`（内部管理）は `official` / `multi_source` / `single_source` / `partial` / `conflict`。`cautions_updated_at` は自動処理による最終更新（手動編集との区別に使う）。

### 表示
- 一覧: 店舗名の行の右端に小さな注意アイコン（`CautionMark`）。NEW・★・応募状態と別の位置で、カードの高さは増えない。注意がない抽選には出ない。
- 詳細: 「確認が必要な点」に項目別の文言（例: 「当選発表日が確認できていません」「締切情報に相違があります。11/10と11/12の情報が確認されています（早い方の11/10を暫定表示しています）」「受取店舗が確定していません」）。
- 注意付きでも、全情報・★・応募済み・プロフィール別の応募管理・当落・購入/受取の記録は通常の抽選と同じ。
- 通知: 不明な日時は推測しない（既存の通知は日時が不明の項目を対象にしない。テストで確認）。注意付きの自動登録は締切が分かっているものだけ（締切不明は C）。

## 3. 地域外の自動除外（`collector/region.ts`・`region-cities.ts`）
- 判定順: 店舗マスターの都道府県 → 住所（都道府県・市区町村）→ 告知・一覧の都道府県 → 店舗名の都道府県名 → 店舗名の市区町村・主要地名。外部APIは使わない。
- 辞書: 47都道府県の市（主要な区・駅名・繁華街名を含む）を静的に持つ。**複数の都道府県に同名があるもの（府中・伊達・中野・大田 等）は曖昧なので載せない**。辞書にない地名は「不明」（除外しない）。辞書は網羅ではない（町村は一部のみ）。
- 除外条件（すべて）: 地域を十分な根拠で特定／対象外／通販・全国応募でない／特定の1店舗の抽選（複数店舗の一覧・店舗選択式・店舗名なしではない）。地域が不明・複数店舗の一覧は地域外と断定しない。店舗選択式は選べる店舗に対象地域の店舗があれば除外しない（従来どおり）。
- **挙動の変更**: 以前は「受取方法が不明」だと地域外でも「要確認」になった。特定の1店舗の抽選で地域が対象外と分かれば、受取方法が不明でも除外する（`conditions.ts`）。
- 除外履歴: 候補は削除せず `status=excluded`。`draft.exclusion`（情報元・日時・都道府県・市区町村・根拠・理由）と、理由に「判定根拠」を残す。除外一覧から確認・戻せる。日別統計に `excluded_region`。

## 4. 情報の食い違い
- 情報源の優先順位は既存（公式サイト > 公式X > Xまとめ > まとめサイト）。優先順位が同じで締切が **2週間以内** に食い違うときは **早い方を暫定採用**し、`state=conflict`・両方の値・注意に残す（`fields.ts`）。公式があれば公式を優先。2週間以上離れる場合は置き換えず C。
- 当選発表日・購入/受取期間は機械的に早い方にせず、採用中の値を保ち相違の注意を追加する。
- 自動補完（`collector/complete.ts` ＋ `server/collector/complete.ts`）: 注意付きの自動登録の抽選に同じ抽選の新情報が届いたら、不足項目を埋めて注意を解除し、公式の締切で暫定値を更新し、新しい相違の注意を追加する。**値のある項目は上書きしない**。最後の更新が自動処理（`cautions_updated_at`）より2分以上後の抽選は、手動編集されたものとして触らない。

## 5. 商品名の整理（`product-name.ts`）
【再販】【予約】などの印・発売日表記・ブランド名の接頭辞を除き、括弧『』内の本体名（括弧の外がブランド名・商品区分だけの場合のみ）を候補にして、既存の商品マスター（正式名称・別名）と**確実な一致のときだけ**紐づける。通常版/特別版・BOX/パックなど商品を区別する語は除かない。一致しなければ新規候補（整理後の名称）として扱う。

## 6. 店舗選択式
- 系列に「店舗選択式を基本とする」設定（`chains.store_select_default`）。マスター管理の系列行メニュー（⋯）から切り替え。初期値: Joshin・トレカキャピタル（ゲオ・エディオンは系列マスターに無いため未設定。登録後にONにできる）。
- 優先順位: 個別抽選の明示 → 応募ページ・告知 → 系列設定 → 既存の安全な処理。**系列設定だけでは確定しない**: 店舗を特定できない抽選のみ、店舗選択式（応募時に店舗選択）で注意付き登録（`store_select_assumed`）。設定がなければ仮の店舗名「店舗未確認」で注意付き登録。応募時の店舗選択・プロフィール別の応募店舗（Stage 6N）は変更なし。

## 7. 収集結果の分析
`collection_daily_stats` に `registered_caution`（注意付き登録）・`excluded_region`（地域外除外）・`review_reasons`（確認待ち理由の分類ごとの件数）。既存の動作状況 > 日別の統計に統合（30日の要約に注意付き・地域外・主な確認待ち理由）。通常登録・確認待ち・重複・除外・収集件数は既存の項目。AI費用・X API予算の管理は変更なし（再評価・判定はAIを呼ばない）。

## 8. 既存の確認待ちへの適用
`runReevaluation`（既存。Stage 4C）に新判定を組み込み。処理: ①バックアップ（`npm run backup`）→ ②判定のみ（`STAGE7A_REEVAL=plan`）で件数と内容を確認 → ③実行（`execute`）。候補の変更前の状態は `draft.reeval.before` に残り、復元できる（`restoreReevaluation`）。登録済み・除外済みは対象外なので再実行しても二重登録しない。応募・当落・購入・受取の記録は変更しない。運用スクリプト: `tests/ops/stage7a-reeval.ops.test.ts`。
