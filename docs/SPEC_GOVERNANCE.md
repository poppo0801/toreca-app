# トレマネ 設計仕様の管理ルール（ChatGPT・Claude Code共通）

更新日: 2026-11-19 / 状態: 運用案（PRレビュー中）

## 目的と役割
- ユーザー: 要望と仕様の最終決定。Claude Codeへの実装指示を直接渡す。
- ChatGPT: 要望の整理、既存仕様との整合確認、採用された仕様の文書更新案をGitHubのPRとして作成。コード変更や本番反映は原則担当しない。
- Claude Code: 承認・反映された仕様を参照し、コード実装・テスト・変更履歴の更新を行う。
- GitHubの `main` にマージされた設計文書を仕様の正本とする。会話・メモリ・個別Stage報告は参照資料であり、無条件に正本へ昇格させない。

## 既存文書を活用する（重複する正本を作らない）
| 文書 | 役割 |
|---|---|
| `docs/PRODUCT_VISION.md` | 最上位の目的・AI主体の開発思想。実装状況やロードマップの古い記述は別途更新対象 |
| `requirements.md` | 採用済みの機能要件。初期設計の記述が残るため、新しい正式決定との照合が必要 |
| `architecture-decisions.md` | 技術判断の理由と制約。製品要件・最上位目的を変更する根拠にはしない |
| `docs/UI_UX_GUIDELINES.md` / `ui-spec.md` | UIの原則／初期画面仕様。現行UIと不一致の箇所は確認する |
| `docs/ARCHITECTURE.md` / `supabase/migrations/` | 構成の説明／実DBスキーマ。実装状態の確認にはコードとマイグレーションを使う |
| `docs/DEVELOPMENT_LOG.md` | 重要な判断・変更理由・未解決の矛盾 |
| `implementation-plan.md` / `docs/stage*.md` | 開発計画／Stageごとの実施結果。古い計画は現行の約束とみなさない |
| `CLAUDE.md` | Claude Codeの作業手順・参照先。詳細仕様の重複転記を避ける |

## 仕様変更の手順
1. ChatGPTとの会話で、提案・検討中・正式採用を区別する。曖昧な内容を勝手に採用扱いしない。
2. 採用した変更について、影響する既存仕様・競合・未実装事項を照合する。
3. ChatGPTが文書変更のPRを作成する。変更理由、旧仕様との差、未解決事項をPRに記載する。
4. ユーザーがPRを確認・マージする。Claude Codeはマージ済み文書を基準に実装する。
5. Claude Codeは実装後に、実装済み／テスト済み／本番反映済み／未検証を分けて記録する。PR未反映の仕様を実装済みと書かない。
6. 決定の変更は旧決定を無言で消さず、`docs/DEVELOPMENT_LOG.md` に日付・理由・参照を残す。

## 衝突した場合の判断
- 明示された最新のユーザー決定を優先する。ただし変更の影響を説明し、正本に反映してから実装する。
- 目的・仕様と既存コードが食い違う場合、コードを『正しい仕様』とみなさず、実装上の差異として記録する。
- 資料同士の矛盾が解決できなければ、推測で上書きせず未解決として報告する。
- 安全上の制約（費用、秘密情報、応募・当選・購入履歴の保護、復元可能性）は維持する。ただしAIの調査・判断を不必要に妨げる固定ルールは見直す。

## 現時点で確認された整備課題（未確定のものを断定しない）
- `CLAUDE.md` のStage説明が長大で、最新の進捗を探しにくい。参照索引への整理が必要。
- `docs/PRODUCT_VISION.md` にはStage 8D時点の『構想』『未着手』が残る。Stage 9系の実装・検証状況との照合が必要。
- `requirements.md`・`implementation-plan.md`・`README.md` に初期フェーズの記述が残る。歴史的内容と現行仕様を区別する。
- Stage 9Uの報告では調査対象の多様化・保留再調査は改善したが、通常収集中のAIによる名称・応募方式判断は未接続。本番成果・正確性は未検証。PR #5/#6 のマージ・本番反映状況を都度確認する。
- この文書は運用ルールのみを定める。既存の採用済み機能仕様を一括変更しない。
