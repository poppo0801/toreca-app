状態: **計画のみ（未承認・未実行）**。本番DBの読み取り、情報元の再取得、AI実行、現在の抽選・候補への変更は、ユーザーの個別承認までコード上も実行しない。計画の部品（`src/lib/judgment/refresh/refresh-plan.ts`）は純関数で、**更新・統合・削除を実行する関数を持たない**（テストで確認）。
前提・参照: `docs/reports/2026-11-19-existing-lottery-recheck.md`（9W）、`docs/reports/2026-11-19-full-recheck-9x.md`（9X）、`docs/reports/2026-11-19-9x-data-fixes.md`、`docs/AI_REDESIGN_10F_SHADOW_ROLLOUT.md`、`docs/AI_REDESIGN_10E_PHASE2_APPROVAL.md`。

## 1. 目的と対象の定義
- 目的: その時点の「全情報」タブと「抽選候補」に表示されている現行の抽選を、新方式（AI判断）と固定ロジックで再判定し、**重複・系列の別名・店舗別/商品別/開催回別の分け方・古い情報・取得不能**を整理するための、差分プレビューを作る。既存の応募・当選・購入記録は変更しない。
- 対象（過去の実施と同じ定義。`scripts/plan-recheck-9x.mjs`・`analyze-screen-9x.mjs`）:
  - **全情報タブ相当**: アーカイブされておらず、★（要チェック）でなく、応募記録がなく、受付中または期限不明の抽選。
  - **抽選候補**: 確認待ち（review）で、応募受付が終了していない候補。判定は画面と同じ `src/lib/collector/closed.ts`。
  - 画面の件数はプロフィール別（自分の応募・スルー設定）で変わる。**世帯全体の集計は画面の件数と一致しない**（9Xの再現でも43件は再現できなかった）ため、対象一覧は「その時点のDBの条件」で作り、画面の件数との差を報告に併記する。

## 3. 対象の選択・除外（`selectTargets`。決定的）
- 除外: アーカイブ済み・応募受付終了（理由つきで一覧化）。
- 優先順: 保護のないもの → **保存原文があるもの**（再取得なし）→ 情報元が取得可能な種類（公開ページ・まとめサイトの一覧）→ 識別子順。X・短縮URLのみの情報元は後回し（取得不能が多い実績）。保護ありは調査は可能だが提案が限定されるため後回し（除外はしない）。
- 件数: **初回は最大30件**（パイロット）。残りは `deferred` として件数だけ報告。2回目以降は、初回の結果を見てユーザーが範囲を決める（既定の上限は100件）。

## 4. 情報元の再取得と再判定の方法
1. **保存原文を最優先**（9Zの `last_good.evidence`。再取得なし・Webアクセスなし）。新方式のシャドー（`ShadowController`）に、承認済みの伏せ字本文を渡して構造・機会数・関係を判断し、旧方式の保存結果との差分を出す。
2. 保存原文がない対象は、情報元が**公開ページ**または**まとめサイトの一覧**の場合のみ再取得（既存の取得部品・ロボット制限の尊重・SSRF防御つき。**制限・ログインは回避しない**）。X・短縮URLは取得しない（取得不能と記録。利用者が告知文を貼り付ける運用で補う案は別途）。
3. 再取得の結果は新たな保存原文として扱わない（この試験では書き込まない。ローカルの作業ファイルのみ）。
4. Web検索を伴うAI調査は、**費用が大きい（約5.6円/件）ため初回に含めない**。必要になった対象だけを、承認を得て追加する。

## 5. 判定の観点（新方式＋固定ロジックの差分）
| 観点 | 見るもの |
|---|---|
| 重複 | 同一の応募権を表す複数の抽選・候補（同一系列・同一商品・同一期間）。新方式の `same` と、固定ロジックの重複検出（high/medium）の差 |
| 系列の別名 | 系列名の表記ゆれ（既存のマスター・別名と照合。**固定の例外規則を積まない**） |
| 店舗別 / 店舗選択式 | 選択肢内の店舗ごとのカードは同一の応募権の重複表示の可能性（K03/J01の知見）。選択肢外の店舗は別 |
| 商品別 | 商品ごとに独立した応募・当落か（`per_product`/`multi_independent_per_submit`の区別は送信単位） |
| 開催回別 | 第1回・第2回などは別の応募権（`per_round`）。1つの既存カードが複数回のうち1つに対応する場合は、組み合わせ単位で見る |
| 古い情報 | 締切超過・受付終了の表記、更新の提案 |
| 取得不能・情報不足 | 確認不能（成功扱いしない）／情報不足（未確認項目）を分けて数える |
**新方式の保守的な `unknown` は、誤統合より安全として許容**（H06/K03）。差分は「疑い」であり、正解ではない。

## 6. 履歴保護と提案の扱い（`classifyProtection`・`allowedActions`・`buildPreview`）
- 保護の分類（強い順）: **確認不能**（保護ありとして扱う）→ **応募・当選・購入の記録／保護コード**（`lottery_history_blockers`）→ **人が確定した項目** → **★管理中** → なし。
- 保護あり・不明の対象に出せる提案は、**残置・保留・人への確認・関連づけのみ**。更新・統合・削除の提案は出さず、`ask_human`（人の確認事項）に落として理由を残す（黙って捨てない）。
- 提案の種類: 残置（keep）／保留（hold）／人への確認（ask_human）／関連づけのみ（link_only）／更新案／統合案／削除案。**案は提案であり実行ではない**。
- 応募済み・当選・購入記録、人が確定した値は、いかなる段階でも自動変更しない（既存の履歴保護・`decideAutonomousOp`・`protectionUnknown` と整合）。

## 8. 復元手段・バックアップ
- 実行前に `npm run backup:full`（完全バックアップ。`docs/RESTORE.md`）。直近のバックアップ（24時間以内）を確認。
- 変更を行う段階（R2以降）は、9Xのデータ修正と同じ方式: dry-run→`--execute`、**変更前の行を保存したファイル**（`backups/…/before-*.json`）と `--restore` で元に戻せる。応募・購入の記録がある対象は中止。
- 判断履歴（`case_judgments`）は追記専用。統合は元の抽選・履歴を消さない形（提案のみ・アーカイブ）を優先し、**物理削除はしない**（削除案は「アーカイブ」の提案として扱う案。要承認）。
- 誤統合・誤削除が見つかった場合: 変更前の保存ファイルから復元／完全バックアップから該当表を復元。

## 10. 実施すべきタイミング（推奨条件）
次の**すべて**が整ってから R1（差分プレビュー）に進む:
1. **実データ評価（S3）で、新方式の挙動が許容範囲**: 保存原文での新旧比較（構造・保留・誤統合/誤分割の疑い）を人が確認し、重大な問題がない。→ これが R1 の前提（新方式を整理に使ってよいかの判断材料）。

3. PR #36・#46 のレビューと、本番反映の方針が決まっている（新方式の判断を整理に使う前に、検証・保護の改善が反映されていること。反映は別承認）。
4. 収集が安定している時期（自動収集の直後・停止中でなく、応募締切が集中する時期を避ける。件数の変動が小さい）。
**事前にR0だけを実行して、保存原文の割合・対象件数・除外・保護の分布を見ることを推奨**（読み取り専用の書き出し。ゲートAと同種の本番DB読み取りの承認が必要）。
