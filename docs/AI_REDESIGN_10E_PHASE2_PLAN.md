# Stage 10E 第2段階（保存済み実原文の評価）実施計画

状態: **計画のみ（未承認・未実行）**。本番DBの読み取り・実原文の取得・外部AIへの送信・追加の有料API呼び出しは、この文書の承認ゲートを通るまで一切行わない。準備部品（`src/lib/judgment/eval/phase2.ts`）は純関数で、**架空データだけ**でテスト済み（`phase2.test.ts`）。
前提: `docs/reports/2026-11-21-stage10e-real-eval-results.md`（第1段階）、`docs/AI_REDESIGN_ACCEPTANCE_PLAN.md`、`CLAUDE.md` §5（本番に作用する入口は `npm run prod -- scripts/<名前>.mjs … --yes-production` のみ・dry-run既定）。

## 1. 目的と範囲
- 目的: 架空事例では測れない**実原文での精度**（構造・機会数・関係・誤統合/誤分割・根拠）と、旧方式との同条件比較を測る。10Fへ進む判断材料にする。
- 範囲: 保存済みの実際の抽選原文 **最大30件**。新規のWeb取得・再取得はしない。本番データの**変更はしない**（読み取り専用）。

## 2. 本番DBの読み取り（承認ゲートA）
- **対象表・列（これ以外は読まない）**: `collection_candidates` の次の列のみ。
  - `id`（連番への置換用。外部へは出さない）、`created_at`、`status`
  - `last_good -> 'evidence' ->> 'text'`（保存された原文）、`->> 'fetchedAt'`、`->> 'via'`、`->> 'origin'`、`->> 'hash'`、`->> 'url'`
  - **読まない**: `household_id` 以外の個人に紐づく表（`applications`・`profiles`・通知・メモ・`draft` の人手の入力・ユーザー名義など）。`household_id` は絞り込みにのみ使い、出力に含めない。
- **期間**: 9Z導入後（原文の保存が始まって以降）に保存されたもの。具体的な開始日は、承認時に `docs/reports` の9Z導入日で確定する。
- **件数の上限**: 30件（層別。下記）。原文なし（取得不能・未保存）は最大3件。
- **抽出コマンド案**（実装は承認後。dry-run既定・件数と層の分布だけを表示し、`--execute` で原文をローカルへ書き出す）:
  `npm run prod -- scripts/extract-judgment-phase2.mjs --limit 30 --since <9Z導入日> [--execute] --yes-production`
  - 実行前に `npm run backup:full`（読み取りだが、運用手順に従う）。接続先の project ref を確認。
  - **読み取り専用トランザクション**（`SET TRANSACTION READ ONLY`）で、上記の列だけを `SELECT`。書き込み・更新・削除・マイグレーションは行わない。
  - 出力先は **Git管理外のローカルのみ**（`eval/real-data/`。`.gitignore` に追加済み）。コミット・PR・チャット・ログに原文を出さない。
- **最小権限**: 既存の運用用の読み取り経路（`npm run prod`）を使い、新しい権限・鍵・サービスを作らない。AIの経路から本番へ接続しない（AIのツールは読み取り専用のみという原則を維持）。
- **層別の選び方**（`selectStratified`・決定的）: 店舗選択式／店舗別独立／商品別独立／複数機会／系列名のゆれ／締切変更／取得不能。層の付与は、**固定ルールでなく人が確認時に付ける**（AIの出力や旧方式の判定を層の根拠にしない）。

## 3. 伏せ字・漏洩検出・全件の人手確認（承認ゲートB）
1. `redact`（キー・認証情報・メール・電話・郵便番号つき住所）を適用。
2. **伏せ字の後**に `detectLeaks`（メール・電話・郵便番号・住所らしき並び・氏名ラベル・9桁以上の数字・カード番号らしき並び・トークンつきURL・キー・SNSハンドル）。**1件でも検出された原文は除外**（または人が修正して再検査）。
3. **人が全件を全文目視**して「外部へ送ってよい」と記録（`reviewedIds`）。**記録のない原文は送信不可**（`needs_human_review`）。規則で日本語の氏名・住所を完全には拾えないため、この確認が必須で、自動検出だけで送信可としない。
4. 外部へ出すのは、連番（`seq`）・層・伏せ字後の本文のみ。元の `id`・URL・取得日時・世帯・応募情報は出さない。
5. 漏れが1件でも見つかった場合は、その原文を除外し、検出規則を見直して全件を再検査する（漏れ率を報告書に記録）。
- 架空データでの検証: `phase2.test.ts`（検出・選定・送信可否の流れ）。

## 4. 外部AIへの送信（承認ゲートC）
- 送信先: Anthropic API（モデル `claude-haiku-5-5`）。**Web検索なし**。送信対象は §3 で `ready` になった原文のみ。
- **保存期間**: 評価結果（AIの出力・採点）と原文のローカル写しは、**評価完了の報告から30日以内に削除**（案）。Anthropic側の保持はAPIの規約に従う（要確認事項として承認時に提示）。
- **削除手順**: ①`eval/real-data/` と `eval/runs/judgment-10e/` の該当ファイルを削除 ②削除したことと件数を報告書に記録 ③Gitに入っていないことを確認。
- キーの扱い: 第1段階と同じ関門（`real-gate.ts`・開発環境限定・`--confirm=yes`）。**実データ評価では専用キーを分ける案を推奨**（共用キーは漏洩時の影響が評価以外に及ぶため）。

## 5. 正解（gold）の作成（承認ゲートD）
- **担当**: ユーザー（または、ユーザーが指名した人）。実原文を読んで、構造・機会数・各機会の店舗/商品/日程・既存抽選との関係を記入する。AIの出力・旧方式の登録結果は正解にしない。
- 入力ファイル（原文）と正解ファイルを**分離**し、正解はAIに渡さない。**AIを実行する前に正解を確定・コミット相当で固定**（事後変更しない。曖昧さは注記で残す）。
- 判断できない原文は「検証不能」とし、精度の分母に入れない。作成者・確認日を記録。

## 6. 評価方法
- 第1段階と同じ指標・同じ採点基準（構造・機会数・項目・関係・誤統合/誤分割の別集計・根拠・費用・遅延・再判断）。プロンプトは評価前に版を固定（`JUDGMENT_PROMPT_VERSION`）。**評価後にプロンプトを調整して同じ30件で再評価する場合は、過学習を避けるため、調整前後を明記し、別の保留分で確認する。**
- **旧方式との同条件比較**: 同じ原文で、(a) 構造判定のみ（費用なし）、(b) 旧の自動収集の抽出（項目抽出）。(b) は旧抽出を実行する部品が**未実装**のため、実装と追加費用の承認が必要。(b) を行わない場合、比較は構造判定のみとし、旧方式の総合精度は「未測定」と記載する。

## 7. 費用上限案と承認ゲート
- 新方式: 30件 × 最大3回 × 約0.28円 ≒ 最大 約25円（実測: 第1段階の最終実行は1件あたり約0.22円・1回で完了）。旧抽出の比較: 30件 × 約0.3円 ≒ 約9円（概算・(b) を行う場合）。
- **上限案: 総額50円・1件3円**（前回案を維持）。内訳の目安: 新方式 ≤ 35円、旧抽出比較 ≤ 15円。合算で超過しないよう、評価コードが事前予約で制御する（共用キーの場合、API側の請求額は別途Consoleで確認）。
- **承認ゲート（それぞれ、実施前にユーザーの明示承認が必要）**
  - A: 本番DBの読み取り（対象・件数・期間・抽出コマンド）
  - B: 伏せ字・検出・全件の人手確認の方法（確認担当の割り当て）
  - C: 外部AIへの実原文の送信（Anthropic）と保存期間・削除手順
  - D: gold作成の担当と期日
  - E: 費用上限（総額50円・1件3円・旧抽出の比較を含むか）とキーの扱い（専用キーを分けるか）
- 全ゲートの承認が揃うまで、本番へはアクセスしない。1つでも欠ければ実施しない。
