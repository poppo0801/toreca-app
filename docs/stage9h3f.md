## 3. 3方式の比較環境（`tests/helpers/threeway.ts`）
同じ抽選（候補の集まり）を、同じ初期の読み取りから3方式で処理する。
| 方式 | 内容 |
|---|---|
| A 従来 | フラグ無効の従来経路（調査なし・統合なし） |
| B AI調査＋従来の統合処理 | 調査結果を従来の合流規則（`legacy-merge.ts`）で反映。同じ抽選の別の候補は統合しない |
| C AI調査＋統合処理 | 9H-3Eの統合処理。同じ抽選の別の候補も統合 |
- **BとCは同じ調査結果**: 調査はCで1回だけ実行し、Bは保存した結果を再生する（調査の回数が1を超えたら中止）。統合処理による差分だけが測れる。他の方式の途中結果を流用しない（各方式の前にテスト用データを消去）。
- 比較指標の材料: 方式ごとの最終候補・確認待ちのカード数（同じ抽選が何枚に分かれたか）・判断履歴・調査の全記録（入力・検索語・結果URL・ページの抜粋・AIの報告・費用）。
- 動作確認（モック・実Supabase・有料AIなし。`tests/stage9h3f.integration.test.ts` 3件）: ①LivePocket＋Xの抽選: BとCが同じ調査結果の店舗選択式・選べる店舗・当選発表の期間を反映し、Cだけが別の候補（Xの応募開始）を統合して確認待ちが1枚になる。調査は1回 ②店舗ごとの独立抽選は統合されない ③通常抽選は3方式で同じ。
- **従来経路にも同じ抽選をまとめる処理がある**（動作確認でAのカードが1枚になった）。Cの優位は、実データで測る（過大な期待をしない）。
