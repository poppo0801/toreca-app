## 3. 新旧AI比較の評価基盤
構成・出力形式・評価7項目は [../eval/README.md](../eval/README.md)。要点:
- 入力18件（`cases`）・正解（`gold`、**システムに渡さない**）・既存データの断面（`context`）・調査用資料（`corpus`）・出力（`runs`、Git管理外）に分離。入力側に正解のキーが混ざると `validate` が失敗。`runSystem` は正解を読まず渡さない（テストで確認）。
- 正解に、判断に必要な条件（conditions）・情報源と権威（sources）・確定できない項目（unresolvable）・調査で解決できる項目（missingResolvable）・登録禁止（mustNotRegister）・許容する決定（allowedDecisions）を記録。
- 採点: 正確性・情報不足の解決率・重複判定（適合率・再現率・誤った重複扱い）・人手修正の推定・処理時間・API回数と推定費用・誤登録/誤更新/推測で作った項目。基準線（全件を人手確認）で動作確認済み。採点器の自己検証テスト14件（満点・基準線・無謀なシステム・欠落・差分の向き）。
- **AIの実接続はしていない。** 既存AIの基準値は未計測（8D-2 で既存AIのアダプターを作り最初に測る）。18件は回帰検知用の規模で、統計的な比較には足りない。

## 4. Git・Vercel の安全対策
| 項目 | 確認結果（2026-11-11） |
|---|---|
| `dev` ブランチで開発 | はい（ローカルのみ。push していない） |
| `main` への push → 本番デプロイ | **確認済み**: Vercel の Production Branch は `main`、Git 連携（`source: git`）で、直近のデプロイはすべて `main` 由来 |
| Preview の接続先 | Preview・Development の環境変数は 0 個 → 本番DBの URL・鍵を持たず、本番DBには繋がらない（アプリは未設定ならエラー停止）。プレビュー作成の有無: 過去に非 `main` のデプロイは無し |
| GitHub ブランチ保護 | **未設定・この環境からは設定不可**（`gh` 未導入・認証なし。リポジトリは公開のため無料の保護機能が使える）。無理な操作はしていない |
| 端末側の防止（実装） | `.githooks/pre-push`: `main` への push を拒否（`TOREMANE_ALLOW_MAIN_PUSH=1` でのみ許可）。`core.hooksPath` 設定済み。Claude Code の設定で `main` への push・`TOREMANE_ALLOW_MAIN_PUSH`・`--mirror`・`--delete` を禁止 |
| CI を本番反映の条件にする | CI は push(main)・PR で起動するが、Vercel は CI を待たずに `main` の push でデプロイする（待つ設定なし）。**GitHub の `main` ブランチ保護（PR必須・`check` 合格必須）が最も確実**: これで `main` へは CI 合格後のマージでしか入らず、本番デプロイも CI 合格後になる。`vercel.json` の変更（Ignored Build Step 等）は、本番デプロイの挙動を変えうるため今回は行わない |
- フックの注意: この端末の `git push` にのみ効く。他の端末・GitHub 上の操作は止まらない（だから GitHub 側の保護が必要）。

### 利用者の操作（GitHub、1〜2分）
GitHub → リポジトリ → Settings → Branches（または Rules → Rulesets）→ `main` に対して: "Require a pull request before merging" と "Require status checks to pass"（`check`）を有効にし、必要なら "Do not allow bypassing"。設定後は、`dev` → PR → CI 合格 → マージ、の流れで本番に反映される（マージの瞬間に本番デプロイが走る）。
