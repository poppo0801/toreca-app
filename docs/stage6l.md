## 0. 下部メニューの位置（6K の訂正）
- **6K の説明は誤り。** 6K は「standalone で入れ物を `100lvh` に固定する」としたが、実機で下半分が隠れた。診断（入れ物の矩形・色付きの帯の実験）の結果、真因は `appleWebApp.statusBarStyle: "black-translucent"`。iOS 18.4.1 のホーム画面アプリでは描画できる範囲が `innerHeight`（793）で止まり、下 59px には要素を描けない（暗幕もダイアログも 793 で止まる）。
- 対策: `statusBarStyle: "default"`。画面がステータスバーの下から始まり、高さ 793 が画面に収まる。ステータスバーの色は `theme-color` が決めるため、`ThemeColorMeta` が head の `theme-color` を監視してアプリのテーマに合わせ続ける（Next が画面遷移ごとに書き直すので一度きりでは戻る）。
- 診断UI・実験ページ・`viewport-gap` は削除済み。**戻さないこと**（`black-translucent` に戻すと再発する）。

## 1. 店舗なしでの抽選登録
- 系列は必須、店舗は任意。空のときは `lotteries.store_id = NULL`（ダミーの店舗は作らない）。DB: `store_id` の NOT NULL を解除し、`save_lottery_tx` の店舗の解決を変更（migration 20261121000065。既存の行は変更しない）。
- 内部の区別: 保存された抽選の `store_id = NULL` は「意図した店舗なし」。自動収集の下書きでは、空の店舗は「未読取（要確認）」で、意図して店舗なしにしたものだけ `noStore: true`（`assessCompleteness` が読み取り漏れとして扱わない）。
- 表示: 店舗名を補完しない。通販は従来どおり受取方法（発送）で「通販」。統計は系列ごとの「（店舗なし）」にまとめる（`win-rate.ts`）。プロフィールの対象範囲は系列の対象・除外だけで判定（店舗単位の指定には当てはまらない）。
- Excel 取り込み: 店舗の列が空でも取り込める（空でない店舗名が照合できないときは従来どおりエラー）。

## 2. コレクションの長押しドラッグ
- 原因: 並び替えのたびに React が `<li>` の DOM ノードを移動（再挿入）しており、ブラウザが CSS アニメーション（順次フェードイン `card-fade`・光沢の `::after`）をやり直していた。さらに、`card-fade` は先頭24件にだけ付く条件で、順位が24をまたぐとクラスの付け外しでもフェードが再生された。
- 対策: DOM の順序は動かさず、見た目の順序だけ CSS の `order` で変える（ドラッグ中はノードが作り直されない）。フェードインは一覧を作り直した直後（1.1秒）だけ。入れ替わるカードの移動は 0.62秒の減速、離したときに持っていたカードも 0.42秒で収まる。
- お気に入り順の保存・他の表示での一時並び・縦スクロールとの共存は従来どおり。実機の指の操作感は未確認。

## 3. AIによる不足情報の補完
- 操作: 抽選の編集画面 →「AIで情報を補完」→ 画像を追加（複数可）→「読み取る」→ 項目ごとの候補を確認 →「選んだN件をフォームに反映」→ 通常の「保存」。
- 補完（空欄・未設定・日付のみ→同じ日の日時）は初めから選択済み。食い違う項目（既存と異なる日付・区分・店舗など）は「食い違い」と現在の値・原文の抜粋を表示し、初期は選択なし。文章（応募条件・本人確認・発表方法）は置き換えず追記。反映先はフォームの入力値のみで、保存は利用者が行う。
- 画像で読めない項目は候補にならない（推測しない）。反映した項目と読み取り元は、メモの末尾に1行で記録（出典）。
- 費用: 既存の `/api/lottery-extract` を通るので、時間・日の上限と `ai_extraction_logs` の記録に計上される。画像は既存と同じ前処理（縦長の分割・縮小・合計4MBまで）。
- 画像と一緒に、対象を特定する短い手がかり（系列・店舗・商品名）だけを送る。既存の日付・条件は送らない（AIが既存値をなぞって「一致」にしないため）。

## 4・5. ★・スワイプの退出アニメーション（共通）
- `apply-exit.tsx` の `begin → ok/fail`。★は 0.32秒の待機 → 0.32秒で横へスライド → 0.28秒で下が詰まる。スワイプは指で既に動かしているので待機なし、画面外まで滑ってから詰まる。右スワイプは右へ、左は左へ。
- 保存の成功と待機の経過がそろってから退出する。保存後もそのタブに残るカード（絞り込みで残るなど）は退出しない。失敗したら退出を取り消し、カードを元に戻す。
- 6L の途中で見つかった不具合: スワイプの `run` が成功しても失敗扱いを返し、退出が毎回取り消されていた（単体テストで検出して修正）。

## 6. 4タブの重複排除
- 優先順位: **当選 → 応募済み → 要チェック → 全情報**（`tabOf` / `inTab`）。同じ抽選は1つのタブにだけ出る。
  - 当選: 表示対象ユーザー（既定は本人＋紐づくサブ）に当選記録がある
  - 応募済み: 表示対象ユーザーに結果待ちの応募があり（通常の抽選）、当選でない
  - 要チェック: ★で、当選・応募済みでない
  - 全情報: 上のどれでもない
- 例外: 継続抽選・招待制販売は「継続中の抽選」に分けるため応募済みタブに含めない。退出アニメーション中のカードは分類が変わっても今のタブに残す（`keepIds`）。他のユーザーの応募は、表示対象ユーザーに入らない限り本人の分類を変えない（既定）。「全ユーザー」に切り替えると他のユーザーの応募も反映（1抽選＝1枚）。
- 件数・赤丸・新着は同じ判定を使う。全情報の絞り込みの「要チェック外」は不要になったので廃止（「スルーのみ」は残す）。

## 8. 系列の別名
- DB（`chain_aliases`）と照合（`matchChain`）は以前からあり、6L で系列の登録・編集画面に別名の入力を統合。正式名称と別名は同じ系列IDで、統計・応募履歴も同じ系列として集計される。
- 照合ルール: 全角半角・大小文字・空白を無視（`normalizeAlias`）。同じ系列の正式名称・別名の重複は取り除く。**他の系列の正式名称・別名と同じ別名は保存を拒否**（自動で確定しない）。DB は世帯内で正規化した別名が一意。
- 既存データ（本番・読み取りのみ）: 「ハレツー通販」（仮登録）と「晴れる屋2」が別系列。`npm run merge:chains -- --from ハレツー通販 --into 晴れる屋2` のドライランでは、店舗1・抽選1・アカウント3が移動でき、応募ルール・条件の衝突はなし。**統合は実行していない**（実データの変更なので利用者の判断）。

## 9. 優先収集メモの廃止
- 画面（＋登録の左のメモアイコン、登録フォーム、メモ一覧）・登録/取り下げ/再調査の操作を削除。メモのテーブル（`collection_memos`）と既存のメモは**削除しない**。
- 引き続き動くもの: 既存の調査中メモの照合（`runMemoPass`。既存の抽選 → 収集候補 → 参考URL の順。参考URLの内容は収集候補として解析待ちに入る）。X ブックマークの取得は通常の収集候補として追跡され、情報不足は保留・再調査（hold）で継続追跡される。
- 新しいメモは作れない。メモが全て終了したら `runMemoPass` とテーブルは次の段階で整理できる（それまでデータは残す）。
