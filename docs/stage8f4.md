# Stage 8F-4：抽選グループAIの実用性改善（自律的な根拠の収集・情報源の保存・実データ評価の整備）

状態: 開発・モック・保存済みデータでの検証まで完了。**新しい有料API評価は未実施（承認待ち）**。本番DB・本番データ・main・デプロイには触れていない。マイグレーション100は**開発DBのみ**で作成・検証（本番未適用）。本番ではAI判定は引き続き無効。

## 1. 評価基盤の問題の修正（評価データの誤りとAIの誤判定を区別する）
- **M05**（8F-3）: 評価ハーネス（`eval-world.ts`）が既存グループの系列を固定値にしていた不具合を、8F-3 の評価後に修正済み。8F-4 では `exclusions.json`（評価から除くケースを、種類 `harness_defect`／`data_error` と理由つきで宣言。凍結した入力・正解は変更しない）に登録し、**集計から除外して別に報告**する。保存済みの提出（AIの add_to_group）を修正後の検証層でやり直す（replay）と single→auto に変わる＝AIの判断は妥当だった（評価側の不具合）。
- **評価ケース・正解・判定ロジックの分離**: 入力（`cases*.json`）・正解（`gold*.json`）・ページの台帳（`pages*.json`）・除外（`exclusions.json`）・判定ロジック（`src/lib/agent/lottery-grouping/`）はすべて別ファイル。凍結ハッシュ（cases・gold・pages）を実行時に照合。台帳に正解の説明文が混ざっていないこともテストで固定。
- **反復は独立した件数ではない**: 集計に `caseLevel`（ケース単位。全回で同じ区分なら stable、違えば unstable）と `independentCases` を追加。「正しい自動グループ化」は、実行数ではなく**独立したケース数**で報告する（8F-3 の「8実行」は2ケース）。
- **個別例外処理は作らない**: 新しい判定・取得の仕組みは、特定の店舗・サイト専用の規則を持たない（識別子はどのサイトにも共通の「イベントID／キャンペーンID」の形のみ）。

## 2. AIの追加調査・再判定（自律性の向上。上限は維持）
- **新ツール `compare_evidence`**（固定ロジックの比較。read_internal）: 2つの抽選の「共有する情報源URL・同じイベントID・共通の長い文言・情報源の文章の有無」を返す。**検証層が最終判断で使うものと同じ事実**（AIの主張ではなく事実が判断に使われる）。
- **新ツール `fetch_source_page`**（read_external・`consumes: fetch`）: 抽選に**登録されている情報源URLだけ**を取得（登録外のURL・X/Twitter・短縮URLは取得しない）。既存の安全な取得（SSRF対策・robots.txt・サイズ/時間・取得間隔）を再利用。**取得部品を渡さなければツール自体が登録されない**（本番の既定）。取得部品は開発環境（`TOREMANE_ENV=local`）かつ `GROUPING_FETCH=allow` のときだけ作る（テストで固定）。取得上限は既定4回（同じ予算の中。重複した取得は断る）。取得した本文は外部由来のデータ（命令は実行しない・検出したら自動にしない）。
- **イベント同一性の検証**（検証層・固定ロジック）: 取得したページ（HTML全体から抽出）・URLの識別子を、対象と**すべての相手**で比べる。共有→強い裏づけ（`event_id`）／別の値→「別のイベントページ」（軽微。自動にしない）／**同じIDと別のIDが混在→矛盾として保留**（自動にも候補にもしない。追加調査も求めない＝人が確認）。同じ種類のIDが3種類以上あるページ（関連イベントのリンク等）は、そのページ自身のIDが分からないため使わない。
- **追加調査の指示を具体化**: 不足している根拠の種類（情報源の文章が無い抽選・取得できるURL）を特定して `fetch_source_page`／`compare_evidence` を促し、**「調べて根拠が見つかれば提出／確認できなければ missing に書き、結論を無理に変える必要はない」**と明記（8F-3 で追加調査が候補を保留へ後退させた傾向への対策）。同じ状況の繰り返し・上限は従来どおり打ち切り。
- **過去の保留・単独を無条件に維持しない**: 判断の記録キーに**根拠の状態の署名**（保存済みの文章＋取得したページ）を含める。情報源が増えると署名が変わり、過去の保留・単独を再評価する。同じ状況なら再実行しない（取得・AIの繰り返しなし）。取得を保存できない環境でも、取得前の状態のキーを併せて記録し、毎回再調査しない。
- 安全の維持: 自動の必須条件（全項目一致＋独立した裏づけ＋信頼度）は不変。手動で分けた組・却下は、根拠が増えても再グループ化しない（DBテスト）。取得したページの命令らしき文面は自動にしない。取得失敗・上限・API障害でも自動にならない。

## 3. 情報源の保存（マイグレーション100・開発DBのみ）
- 表 `lottery_source_snapshots`: 元のURL・リダイレクト後URL・**情報源の種類**（x_post／web_page／candidate_text／manual_note）・**保存の経路**（collector／manual／grouping_fetch）・題・**取得した本文の要点（最大4000文字）**・本文ハッシュ・抽出した**識別子**・**取得日時**・**保持期限（既定180日）**。同じ抽選・URL・本文は1件（一意制約）。RLS: 世帯のメンバーは読み・追加のみ（更新・削除不可）。保持期間の削除は `purge_expired_source_snapshots`（service_role のみ）。
- 保存しないもの: 個人情報・認証情報・ページ全文（要点のみ。キーらしき文字列は伏せる）。
- 使い方: AIが取得したページを保存し、次回の判定の入力（情報源の文章）に使う。**原文が無い過去データも正常**（行が無いだけ）。表が無い環境（本番など）では、保存は何もせず読み込みは空（互換。テスト済み）。判定の記録（提案）の `evidence` に、**判断の根拠（basis）・参照した情報源（URL・取得日時・ハッシュ・識別子）・開始時点の署名**を保存し、後から追跡できる。
- 収集・手動登録について（正直に）: 自動収集の情報源の文章は従来どおり収集時の候補の下書きから読む（変更なし）。手動登録の抽選は、**グループ判定の際にAIが登録済みのURLを取得して保存する**経路で補う（開発環境）。登録画面での原文の貼り付け・収集時の自動保存は未実装（本番の表が無いため。本番導入の工程で検討）。
- UI（最小）: 候補の「根拠の詳細」（既定で折りたたみ）に、判断の根拠の箇条書きと「確認した情報源（ホスト名・件数）」、裏づけの種類「同じイベントID」を追加。iPhone幅（390px）で横はみ出しなしをE2Eで確認。
