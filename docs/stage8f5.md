# Stage 8F-5：抽選グループ化の定義修正と判定ロジックの再構築

状態: 開発・モック・保存済みデータでの検証まで完了。**新しい有料API評価は未実施（承認待ち）**。本番DB・本番データ・main・デプロイには触れていない。マイグレーションの追加なし（8F-4 の 100 は開発DBのみ・本番未適用のまま）。本番ではAI判定は引き続き無効。

## 1. 旧定義と新定義（正式仕様）

| | 旧定義（8F〜8F-4） | 新定義（8F-5） |
|---|---|---|
| グループ化の意味 | 「同じイベント（同じ応募枠）」の店舗違い | **同一系列の複数店舗で、同一商品・同一応募期間・同一応募条件・同一抽選方式の抽選が、それぞれ独立に実施されている**ものを、一覧で1つにまとめる |
| 目的 | 同じ企画の把握 | 似た抽選カードが大量に並ぶのを防ぎ、一覧を見やすくする |
| 自動の必須条件 | 全項目一致＋**同じ企画の独立した裏づけ**（同じキャンペーン・同じ情報源URL・同じイベントID・共通の企画文言） | 全項目が**確認できたうえで**一致＋店舗が別で特定＋店舗固定＋応募条件の一致を確認できる根拠。**裏づけ（イベントID・URL・キャンペーン・企画文言）は必須でなく、信頼度の補足** |
| イベントIDが異なる | 別のイベント＝自動にしない／混在は矛盾として保留 | **判定に使わない**（店舗ごとに別でも拒否しない）。同じIDでも内容が違えば対象外 |
| 期間・条件・方式・数量・商品が異なる | 同じ企画の裏づけがあれば「承認候補」 | **対象外（単独）**。同じキャンペーン・同じ企画名でも、別の抽選としてまとめない |
| 別のキャンペーンID | 対象外 | 拒否せず、利用者の確認（候補）。自動にしない |
| 店舗選択式 | 項目の違いとして扱う | **対象外**（事前の絞り込みでAIも呼ばない）。「対象店舗の中から1店舗のみ応募」等の記載・タグ `one_store_only` がある登録も、自動にせず候補止まり |
| 同一店舗の重複 | 単独 | 単独（理由に「グループ化ではなく重複管理の対象」と明記） |

不変の原則: 各店舗の抽選は独立のまま。応募状況・応募URL・当選結果・通知・履歴は店舗別。グループ化・解除は表示だけで、元の抽選データを統合・削除しない（DB結合テストで確認）。

## 2. 判定ロジックの修正（`src/lib/agent/lottery-grouping/`）
- **AIと固定ロジックの分離は維持**。AIは調査して提案し、区分（auto／suggest／hold／single）は検証層（`verify.ts`）が事実で決める。AIの自己評価・「共通」の主張は信用しない。
- 区分の決定: ①店舗が同じ・店舗選択式・商品が重ならない → single ②商品の一部だけ共通・数量/期間/方法/条件/方式の相違 → single ③核心（商品・応募開始/締切・店舗・応募条件）が不明 → 補足の裏づけがあれば suggest／無ければ hold ④周辺（発表日・受取方法など）の不明、条件の記載なし・文面の違い、別キャンペーンID、店舗選択式の疑い → suggest ⑤すべて確認できて一致 → auto。
- **情報不足を一致とみなさない**: 応募条件が両方とも未登録（タグも文面も空）の「同じ」は、全件に情報源の文章があるときだけ確認できたとみなす（無ければ候補）。不明は常に「確認できない」であり「一致」ではない。信頼度も、未登録の条件は半分しか加点しない（合計100点配分に再設計）。
- **表記揺れ・略称**: 商品の登録が別でも名称が正規化後に同じなら同じ商品（固定ロジック）。名称が一方に他方を含み（略称の可能性）、AIが「商品は共通」と判断した場合は、一致とせず**候補（確認が必要）**。末尾1文字だけ違う別商品・構成が違うものは別の商品。
- **どれに入れるか決められない**: 内容が完全に一致する別の既存グループが他にもあれば、自動にしない（候補）。追加先の所属の間で内容が一致しない（旧定義で作られたグループなど）ときは保留（勝手に追加しない）。
- イベントID・共有URL・キャンペーン・企画文言（`strongSignals`）は**補足の裏づけ**として保持（信頼度の加点・根拠の表示）。8F-4 の情報源の保存・`compare_evidence`・`fetch_source_page`・判断の根拠（basis）は再利用。AIの追加調査は、**調べれば解決しうる不足（不明・記載なし）だけ**を対象にし、相違は再調査しない。指示文に「イベントIDや応募URLが店舗ごとに違うことは、まとめない理由にならない」と明記。上限（回数・費用・時間）は不変。
- AIの指示（system prompt）・モックAI（careful は全項目一致の別店舗だけを提案）を新定義に更新。
- 手動グループ化の候補（`suggestGroupMates`）から、同一店舗と店舗選択式を除外。ラベルは「同じ企画の可能性」→「条件が同じ」。

## 3. 安全性
- 禁止事項の維持: 異なる条件の自動統合なし（hard の相違は single）／店舗別情報の更新なし／手動解除・却下した組を再びまとめない／根拠のない自動確定なし（確認できない・命令らしき文面・AIの主張の食い違い・実行の途中終了・自動が無効の設定・手動グループへの追加は、すべて auto にならない）／無制限の調査なし。
- **定義の版（`GROUPING_DEFINITION = "def8f5"`）を、判断の記録キー（単独・保留）に含めた**。旧定義で記録された単独・保留は、新定義で一度だけ再評価される。手動で分けた組（`lottery_group_events`）・却下／解除済みの提案は別の記録なので、再評価でも再びまとめない（DBテストで確認）。
- **旧定義で作られた既存グループ・候補の安全な再評価（読み取りのみ）**: `auditGroupingState`（`lottery-grouping-service.ts`）と `auditGroup`（`audit.ts`）。既存グループの所属を新定義で比べ（consistent／needs_review／inconsistent）、承認待ちの候補を現在の検証層でやり直す（区分が変わったものを指摘）。**自動では解除・変更・却下しない**（手動で作ったグループは利用者の意思として変更しない旨を案内）。AIを使わないため費用なし。移行は、この結果を利用者が確認して店舗ごとに外す・却下する方式（無条件に移行しない）。
