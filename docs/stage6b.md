# Stage 6B: X投稿の収集・画像解析の正常化と自動補完

## 1. @pokecayoyaku が候補0件だった原因

**確定した原因（コード＋実DBで再現）**: X投稿の題名を `text.slice(0, 80)` で切っていた。投稿は絵文字（⚡📅🎯＝サロゲートペア）が多く、80文字目が絵文字の途中に当たると**孤立サロゲート**になり、JSONとして不正になる。候補は**97件を1回の一括保存**で送っていたため、1件の不正な文字列でバッチ全体が失敗した。さらに保存結果の `error` を検査していなかったため、「投稿97件を取得、新しい候補0件」と**成功として記録**され、`x_since_id` も進んだ（＝97件は以後取得されない。約119円の取得が成果なし）。

- 再現: `tests/stage6b.integration.test.ts`「原因の再現」。孤立サロゲートを含む1行を混ぜた一括保存は、正常な行も含めて全件失敗する（実Supabase）。
- 現在の @pokecayoyaku（11/5 13:05 以降）は6件が候補化されている（偶然、切断位置が絵文字に当たらなかった）。
- 当時の97投稿の個別の中身（画像の有無・引用の有無・関連判定の結果）は**記録なし**（投稿本文を保存していなかった。保存失敗のため候補もない）。97件の構成別の内訳は復元できない。

**他に確認した点（原因ではなかったもの）**
| 観点 | 確認結果 |
|---|---|
| X APIは画像情報を返しているか | 返している（`attachments.media_keys`＋`includes.media`）。現在の候補6件のうち5件に画像URLがある |
| 画像URLの取得・解決 | `pbs.twimg.com` の photo のみ対象（動画は対象外のまま） |
| 画像がAIへ渡るか | 渡る（`enrichXPost`）。ただし**取得できた枚数・AIへ渡した枚数が記録されていなかった**（今回記録する） |
| 関連性判定が画像付き投稿を落とすか | 本文にポケモンカード/抽選の語が無い画像だけの投稿は、`judgeRelevance` が通らず**落ちる設計だった**（今回修正） |
| 引用投稿 | 取得フィールドに引用元の展開が無く、引用元の本文・画像は**常に欠落**していた（今回修正） |
| 長文投稿 | `note_tweet` を取得していないため、280文字超は途中までだった（今回修正） |
| 受付前という理由の除外 | 収集条件が「受付中のみ」で、応募開始前の抽選は除外されていた（3件）。本番の設定を「受付前も含める」に変更（§6） |
| 重複判定が過剰か | 過剰ではない（重複は同一店舗・商品・締切、または同一URLのみ） |

## 2. 変更内容

### X収集（`run.ts`、`x-relevance.ts`、`save-rows.ts`）
- 題名などの切り詰めは `safeSlice`（サロゲートペアの途中で切らない）に変更。DBへ送る行は `deepClean`（NUL・孤立サロゲート除去）を通す。
- 候補の保存は `saveCandidateRows`: 一括保存→失敗したら1件ずつ。**結果の失敗を検査**し、失敗があれば収集元を `error` として記録する。
- **各段階の件数を記録**（`XFunnel`）: 取得／画像付き／引用付き／リンク付き／解析対象（本文・画像・引用・リンク別）／対象外（他TCG・関連なし・古い）／新規保存／保存失敗。収集元ごとの取得結果（`collection_source_attempts.message/detail`）と収集結果に残る。
- 関連判定（`judgeXPost`）: 本文のキーワードだけで画像付き投稿を落とさない。本文が短い（画像中心）または抽選の語がある画像・引用・リンク付きの投稿を解析対象にする。他のTCGが主題・無関係な長文・30日以上前の投稿は解析しない（有料AIを無条件に使わない）。
- 新しいXアカウントの初回取得は直近14日に絞る（`start_time`）。引用元の読み取りは課金の見積りに数える。
- 画像が情報の中心の投稿で画像を1枚も取得できなかったときは、本文だけで有料のAI解析をしない（再試行）。

### 画像・引用元・リンク（`x-client.ts`、`x-posts.ts`、`x-rich.ts`）
- 取得フィールドに `note_tweet`、`referenced_tweets.id`（引用元の本文・投稿者）、`referenced_tweets.id.attachments.media_keys`（引用元の画像）を追加。引用元の本文・画像・リンクもAIへ渡す。返信・リポストは従来どおり取得しない（大量取得を避ける。まとめアカウントの紹介は引用で行われるため）。
- 画像は **見つかった／取得できた／AIへ渡した** を別々に数え（`ImageStats`）、解析後の草稿に残す。画像から読み取れた項目（根拠の出典が「画像N枚目」の項目）も `extractedFromImage` として残す。

### 取得済みX情報の保持・再利用
- 解析後の草稿に `xpost` を保存: 投稿ID・投稿者・日時・本文（4,000字まで）・画像URL・リンク・引用元・取得日時・取得経路・画像の扱い・画像から読み取れた項目・解析に回した根拠。
- 再解析（手動・保留・本文更新・再評価）は `rebuildQueued` が保存済みの投稿を使い、**X APIで再取得しない**。保存・再利用は**取得から30日以内**に限る（`XPOST_REUSE_DAYS`。X APIの利用条件に配慮し、期間を限定。それを過ぎたら再取得）。
- 保存済みの画像URLがすべて取得できない（期限切れ等）ときは、1回だけX APIで投稿を取り直す（予算の範囲内）。

### 公式Xアカウントと系列・店舗（`x_account_links`、`x-accounts.ts`）
- 既存に同等の機能は無かったため新設（`x_account_links`。RLSは世帯メンバーのみ）。role: `official_store`（店舗が必須）／`official_chain`（系列のみ。店舗は確定しない）。**まとめアカウント（収集元のXアカウント）は登録できない**（紹介元であり実施店舗ではない）。
- 登録は利用者の明示操作のみ（API: `POST /api/collection` の `linkXAccount`／`unlinkXAccount`）。自動では確定しない。
- 使い方: AIが告知から系列/店舗を読み取れなかった項目**だけ**を補い、二次情報（`secondary`）として明示する。告知の系列/店舗が対応先と異なるときは上書きせず注意を出す。

### 抽選予告（`stage.ts`）
- 段階を `open`（受付中・詳細確定）／`upcoming`（受付前・詳細確定）／`teaser`（予告・詳細未発表）／`partial` に分類して草稿に保存。受付前という理由だけでは除外しない（詳細が確定していれば通常の登録、未発表は再調査として保留）。通常の発売予告など抽選でないものは、従来どおりAIが「抽選告知ではない」と判定して除外する。

### 既存処理の修正
- `preferredAltFor` の未接続: `altPlanFor`（`sources-health.ts`）を収集に接続。応募サービス/ドメインが robots で拒否され、一覧文章による代替が2回以上成功し失敗を上回り、直近7日以内に失敗が確認されている場合は、**同じ制限URLへ再アクセスせず最初から代替で読み取る**。7日を過ぎたら取得を試し直す（制限の解除に気づくため）。この経路では失敗日時・失敗回数を更新しない（`recordAltSuccess`）。
- `hold.ts` の固定値: `failKind`（候補の `fail_kind`）、`altTried`（草稿の `viaList`）、`important`（優先収集メモ）を実値で渡す。再試行回数・間隔（内部管理）は変更なし。
