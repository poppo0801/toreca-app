# Stage 6C: 抽選予告の追跡・重複整理・X画像解析の精度検証

## 1. 抽選予告の自動追跡

### 設定の整理（既存の意味は変えない）
- 「現在応募可能のみ」(`status_mode=open`) は、通常の収集・登録対象を制限する設定のまま。
- 新設定 **「受付前の抽選予告も追跡する」**（`collection_settings.track_upcoming`、**既定ON**、画面: 自動収集 → 収集対象・条件 → 受付前の抽選予告）。
  - ON: 現在応募可能のみでも、受付前の抽選を**破棄せず追跡候補として保持**する（`evaluateCandidate` の新しい判定結果 `upcoming`）。**応募可能として登録・表示はしない**。受付が始まり、通常の登録条件を満たした時点で、通常の自動登録に移行する。
  - OFF: 従来どおり「まだ応募開始前です」で除外。
  - 「受付前も含む」(`open_or_before`): 従来どおり、詳細確定の受付前抽選は通常条件で登録。

### 受付状況の分類（`stage.ts`）
受付中（詳細確定）／受付前（詳細確定）／抽選予告（詳細未発表）／一部判明／受付終了。「抽選と無関係」は AI の判定（抽選告知でない）と、**抽選の文言検査**（`hasLotteryWording`: 抽選・当選・応募・エントリー・申込）で扱う。抽選の文言が無い予告・一部判明の告知（新商品の発売予定・入荷予定など）は、抽選予告として追跡せず除外する。AI のプロンプトも更新（予告は true、発売日だけの告知は false、画像間の矛盾は不明にして warnings）。

### 追跡の方法
- 追跡の条件: 抽選の文言がある・**具体的な系列がある**・受付前または詳細未発表（`wantTrack`）。系列が無い予告は追跡しない（通常の保留）。
- 既存の保留機構（`triage=auto_retry`）を使い、候補の `draft.tracking`（開始日時・最終更新・受付開始予定・情報源・更新履歴・関連候補）を保持する。保持する情報は、系列・店舗・商品・元投稿URL・発見日時・受付開始予定・判明している条件・不足情報（reasons）・次回調査予定（`next_run_at`）。不明な項目は推測しない。
- **追跡中は、保留の回数・締切の近さを理由に要手動確認へ移さない**（`decideHold` の `tracking`）。商品マスター未登録・矛盾は追跡中でも利用者の判断。続報が60日以上ない予告だけ自動で終了（履歴は残す）。
- **受付開始が近いほど再確認の間隔を短縮**: 7日超12h／7日以内6h／48h以内2h／開始日以降30分（`trackingIntervalMs`）。
- 同じ内容の AI 再解析はしない（既存の本文ハッシュ・一覧ハッシュ・保存済みX投稿の再利用をそのまま使う）。追跡の再確認（`runHoldPass`）は無料の再照合のみで、`judge()` は追跡中の予告を除外・AI再解析・手動確認に回さない。

### 続報の照合・更新（`tracking.ts`、`processCandidate`）
- 新しい候補が解析されたとき、追跡中の予告のうち **系列（ID・または「通販」「オンライン」を除いた名称）・商品（ID・または照合キー）が一致し、店舗は双方が分かっていれば同じ**ものを探す。**一意に決まれば同じ抽選の続報**として、予告の候補の追跡情報・履歴を引き継ぐ。**複数に一致して決められないときは統合せず、関連候補として保持**（`tracking.related`）。商品と締切日だけの一致では統合しない。
- 結果に応じて、元の予告の候補を整理（削除しない）: 正式登録→「重複（同じ抽選）」で登録した抽選に付け替え／追跡継続→「続報の候補へ統合」（excluded。復元可）／登録済みの抽選と同じ→重複。
- **更新履歴**（`diffTracking`）: 受付開始日・応募締切・応募URL・応募条件・店舗が判明／日時の変更／対象商品の変更を、**情報源URLと日時つき**で保持。正式登録時は `promotedAt`・`promotedLotteryId` を記録。
- 手動修正の保護: 候補の画面に手動編集は無く、登録済みの抽選への反映は従来どおり「更新の提案」（確定情報は自動で書き換えない）。系列の抽選条件（Stage 5R・手動のみ）は AI が変更しない。告知から読んだ条件との**違いを草稿に表示**（`conditionDiff`）。

### 登録条件
受付前の抽選も、既存の商品マスター照合・登録条件（`isReady`）を維持。商品マスターに無ければ商品確認待ち。必要情報が不足する予告は登録しない。日時は推測しない。画像・本文の矛盾（`矛盾|食い違`）は自動登録せず、要手動確認。

## 2. 重複判定の強化（`lottery-match.ts`）
- 系列は ID または「通販・オンライン・公式」等を除いた名称で同一視（駿河屋／駿河屋通販）。
- **店舗名「オンライン」「通販」は販売形態**として扱い、店舗が未確定でも、オンライン同士・同じ系列・同じ商品・同日締切で同一と判定。実店舗の抽選とは同一にしない。
- 情報源の同一性（`urlIdentity`）: X投稿は投稿ID（投稿者名が違っても同じ）、Googleフォームはフォームの識別子、その他は検索条件を除いたURL。
- 商品と締切日だけが一致する別の店舗・別の系列は統合しない（テストで検証）。

## 3. 既存重複の整理（`scripts/dedupe-lotteries.mjs`）
既定は調査のみ（dry-run）。`--execute` でバックアップ（`backups/dedupe-6c-*.json`）を取って実行、`--restore <ファイル>` で復元。整理の条件: 残す側以外が、自動登録・手動修正なし・★管理でない・応募/当落/購入/スルー/例外/通知/優先収集メモの記録なし。1つでも当てはまれば統合せず要判断。処理: 情報源URLを残す側へ統合→不要な抽選に紐づく候補を「重複」として付け替え→不要な抽選をアーカイブ（物理削除なし）。
