## 1. 日時解析の是正（共有実装 `time-tokens.ts`）

確認画面・gold検証・採点が同じ実装を使う。**不正・曖昧な時刻は補正せず捨てる**（`invalid` に記録）。

| 入力 | 扱い |
|---|---|
| `24:00`・`24時` | 有効（翌日0時。日付またぎは採点側で前日24:00と翌日00:00を同一視。goldが00:00のときだけ） |
| `24:01`〜`24:59`・`25:00`・`23:60`・`99:99` | **不正**（補正しない） |
| 午前/午後 0〜11時 | 有効。午前0時=00:00、午後0時=12:00、午後11時59分=23:59 |
| 午後13時・午前13時 | **不正** |
| 午前12時・午後12時 | **曖昧（正午か午前0時か）のため採用しない**（不正扱い） |
| 12:00 AM / 12:00 PM | 00:00 / 12:00。13:00 PM・0:30 AM は不正 |
| 全角（２３：５９）・「23時」「23時59分」 | 有効。「約10時間」は時刻にしない |
| 「受付時間 10:00〜20:00」「当選発表 12:00」「営業時間」 | **応募締切の時刻と認めない**（`deadlineTimeTokens`：締切・〆・期限・応募/受付…まで の文脈の時刻だけ。「当選発表」等の後ろは別項目として切り離す） |

- 原文に時刻があるだけでは、goldの「応募締切時刻」にできない：確認画面と `validateGold` の両方で、**根拠の引用の「応募締切」の文脈に書かれた時刻**だけを許可（最終判断は人）。
- 回帰テスト：`time-tokens.test.ts`（5群）、採点（表記ゆれ・日付またぎ・母数0・年）、gold検査、確認画面の検査。

## 3. 費用管理（正確な区分）

**重要な事実：関門（real-gate）・CallBudget の総額/1件の上限は、1回の実行（プロセス）ごとに作り直される。** したがって「総額60円」は**1回の実行の上限**であり、段階・再実行・合成/実投稿をまたいだ**通算上限ではない**（これまでの説明は不正確だった）。

| 項目 | 内容 |
|---|---|
| 期待費用（無課金の再計算） | 合成 A・B・C（各4案件・8回）各 約12.5円、実投稿4案件（8回）約8.3円。合計の期待 **約45.7円** |
| 最大予約（1回あたり3.6円） | 4案件8回で 3.6×8 = **28.8円**（完走を保証できる最小の承認総額の目安）。**「上限20円」は完走保証ではない**（期待12.5円に収まる見込みだが、途中停止ありうる） |
| 承認額の例 20+20+20+15=75円 | 各実行を**別々に承認**する場合の合計であり、60円の内枠ではない。別々の承認は通算で60円を保証しない |
| **新規：費用の通算台帳**（`spend-ledger`） | `--program-cap-jpy=<円>`（**利用者が指定・既定値なし**）。実行前に台帳（ローカル `spend-ledger.local.json`）を読み、①この実行の承認総額が通算上限を超える ②（通算上限−確定・予約済み）を超える ③同じ段階の二重実行（意図した再実行は `--rerun-stage`、費用は加算）④終了の記録が無い実行がある、のいずれかなら**開始前に拒否**。終了した実行は**実費**、未終了（異常終了を含む）は**承認額の満額**を使ったものとして保守的に数える。単体テスト5件（段階をまたぐ通算・75円の例が最後の段階で拒否される/実費が低ければ通る・二重実行・未終了） |
| 台帳の保証の範囲 | **この入口（`compare-phase2.mjs run`）に対してのみ**。別の入口から直接APIを呼ぶ操作、Anthropic側の利用上限・請求とは連動しない。台帳ファイルを人が書き換えれば回避できる（ローカルの運用上の安全弁で、仕様より強い保証は主張しない） |

**初回の上限・停止条件（初回＝合成の段階A：価値の高い4案件×2アーム=8回）**
- 1回の承認総額：**28.8円以上**で完走保証（例：30円）。1案件上限：**5円**（関門の上限）。通算上限：利用者が指定（例：60円）。
- 停止条件：総額/1案件の予算到達・残額が最小予約（1.2円）未満・画像1案件4枚・取得30件・全体120分・401/403/429は即停止（再試行しない）・連続3案件の通信/出力不備で停止・実行ロック（二重起動拒否）・台帳（通算）。誤登録・他店舗の混入が1件でも出たら停止して原因修正。

- 段階を重ねる場合、各段階の承認総額が通算上限の「内枠」になるのは、台帳が**実費**で残額を計算するため（実費が期待どおりなら60円内で収まる見込みだが、実費が高い場合は後の段階が拒否される）。

初回の実行コマンドの形（`<…>` は利用者が確定。AIは値を入れない）：

```
npm.cmd run db:check
node scripts/r1-readiness.mjs
node scripts/compare-phase2.mjs plan --experiments=links --dataset=synthetic --case-limit=4 --total-jpy=<承認総額> --per-case-jpy=<1案件上限>
node scripts/compare-phase2.mjs run --experiments=links --dataset=synthetic --case-limit=4 --approved-total-jpy=<承認総額> --approved-per-case-jpy=<1案件上限> --program-cap-jpy=<通算上限> --confirm="<利用者が入力する承認文>"
```

- 段階B：`--case-from=4 --case-limit=4`、段階C：`--case-from=8`。実投稿：`--dataset=real`（`--case-limit` なし）。
- 実行前に `plan` の `feasibility`・`ledger`・`evaluation` を確認し、`readiness` のブロッカー0を再確認する。
