## 1. 調査結果（通常収集の処理経路）
| 項目 | 結果 |
|---|---|
| 正式な経路 | `src/lib/server/collector/run.ts`（指示書の `src/lib/collector/run.ts` は誤記）。`processQueue` が候補ごとに AI抽出（`extractFor`）→ `processCandidate`（判断・保存・自動登録）。判断の確定・保存は `processCandidate` の内部（`finish(...)`／登録）で行われ、戻り値は `Outcome`（usedAi/registered/aiFailed） |
| 旧方式の実値 | ①**応募単位**: AI抽出の `applyUnit`（store_select / store_independent / per_product / single / unknown）②抽出した商品数 `items.length` ③重複検出 `findDuplicates` の結果（既存の抽選ID・level=high/medium）④特定した系列ID。**「応募機会の数」という単位は旧方式に無い**（候補1件＝抽選1件の登録単位）→ 実値が取れないため常に null |
| 実行寿命 | `processQueue` は1回の関数実行（最大60秒、`ctx.timeLeft()`）の中で動く。サーバレスでは応答後の fire-and-forget は完走を保証できない。→ 有効化を**開発環境のみ**とし、開始は旧方式の保存直後（並行）・待機は全候補の処理後に1回（残り時間−3秒、最大25秒で打ち切り） |
| 訂正 | 10Fの最初の実装では「商品別（per_product）は旧方式が表現不能」としていたが、収集のAI抽出は `per_product` を表現できる（固定の形態判定 `judgeForm` だけが表現できない）。**表現不能は開催回別・1送信複数独立のみ**に訂正し、旧の応募単位を比較に使うよう変更 |
| 既存のPhase2承認票との整合 | gold（D）を必須にしていたため、10Fの方針（30件のgoldを前提にしない）と不整合。→ 承認を3つに整理（§5） |

## 3. 通常収集の不変性（どう確認したか）
ローカルDB（RLS適用下）の統合テスト `tests/stage10f-shadow-wiring.integration.test.ts`（実際の `processQueue` を、AI・外部サイトはモックで実行）。同じ名前の候補を、**設定だけ変えて1件ずつ**処理し（処理後に候補を削除して事前状態を揃える）、旧方式の結果を突き合わせた。
| シナリオ | 旧方式の戻り値・保存内容（status/job_state/理由/ai_calls/triage/原文ハッシュ/draft）・各表（抽選・応募・候補・判断履歴・通知）の増減 |
|---|---|
| シャドーON（モックの新方式） | **OFFと同一**。判断履歴の増減0。記録1件（非機微） |
| 新方式が例外／不正出力／ハング（100msで打ち切り） | **OFFと同一**。失敗の状態は記録される |
| 本番設定（VERCEL）／緊急停止／OFF／モデル未設定 | **OFFと同一**。新方式は1回も呼ばれず、記録なし |
- 静的検査: `run.ts` は `judgment/shadow` に直接触れず、接続口（`shadow-hook`）だけを経由。接続口はDB・ネットワーク・実AI・書き込み系のメソッドを含まない。
- **同じ原文**: シャドーが見た原文のハッシュ先頭が、旧方式が `last_good.evidence` に保存した原文のハッシュ先頭と一致することをテストで確認。
- **非機微**: 記録に、原文・URL・候補ID・世帯ID・店舗名を含まないことをテストで確認。
- **待ち時間**: モック（即答）で旧方式のみ 113ms／シャドーON 89ms（単発の実測。差は計測のばらつきの範囲で、有意な増加は観測されず）。新方式が実AIで秒単位かかる場合、全候補の処理後の待機（最大25秒）が加わる。**1件ごとの旧方式の処理時間には影響しない**設計だが、実AIでの実測は未実施。
