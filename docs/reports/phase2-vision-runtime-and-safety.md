## 2. 画像解析を実際のAPIへ接続できる状態にする

### 2.1 全体の流れ

```
収集時の画像参照（imageRefs）・画像の読み取り（imageReadings）
  → analyzeImages（image-evidence.ts）
       ├ 収集時の読み取りがある画像 → 再利用（課金なし）
       ├ 保存済みの解析結果（同じモード・期間内）→ 再利用（取得も解析もしない）
       └ それ以外 → VisionClient（注入）
              ├ モック: vision-mock.ts（取得・検査は実と同じ経路 → 固定表の読み取り）
              └ 実:    vision-real.ts（取得 → 検査 → 分割 → 費用の予約 → Anthropic → 検証・伏せ字）
  → 本文との照合（一致 / 矛盾 / 画像のみ / 未確認）→ 観察の注記（仮説・原本未照合）→ AI調査 → 登録案
  → evidence_image_observations（解析結果・失敗理由・ハッシュ・費用。原本の画像は保存しない）
```

### 2.2 画像の安全な取得（`src/lib/server/images/image-fetch.ts`）

| 対策 | 実装 |
|---|---|
| 許可されたプロトコル | http(s)のみ。標準以外のポート・認証情報つきURL・内部名（localhost・.local 等）を事前に拒否 |
| SSRF | 既存の `safeFetch` と同じ防御を、バイナリ用の `safeFetchBytes` に適用。接続の直前にDNS解決し、**全アドレス**を検査（ループバック・プライベート・リンクローカル・メタデータ・CGNAT・予約・マルチキャスト・IPv6射影を拒否）。リダイレクトは1回ずつ手動で辿り、毎回同じ検査（最大3回。内部アドレスへの誘導・無限ループは拒否） |
| robots・利用条件 | 取得前に robots.txt を確認（ホスト別に10分キャッシュ）。禁止なら画像のリクエストを送らない。**Xの投稿の添付媒体の配信元（pbs.twimg.com）だけは対象外**（既存の `fetchXImage` と同じ扱い。投稿に添付された媒体として公開されているもの） |
| 認証・私的URLの回避 | 個人用パス（mypage・login・account・order 等）・署名つき/期限つきURL（X-Amz-Signature・token・expires 等）・Xのページ（x.com・t.co）は取得しない。401/403は「ログインや権限が必要」として停止（回避しない）。Cookie・認証ヘッダーは送らない |
| Content-Typeと実バイトの検証 | 申告の種類が許可リスト（PNG・JPEG・WebP・GIF）に無ければ拒否（SVG・HTMLを拒否）。**実バイトの先頭**で形式を判定し、申告と一致しなければ `spoofed_type`（偽装レスポンス）として拒否 |
| 上限 | サイズ 5MB（モデルAPIの上限に合わせる）・ピクセル数 80Mピクセル（`sharp` の `limitInputPixels`＝展開爆弾対策。圧縮すると小さいが展開すると大きい画像も拒否）・時間 12秒・リダイレクト 3回 |
| 加工 | EXIFの向きを反映・長辺 2,000px 超は縮小（形式は保つ）。アニメーションGIFは加工しない。縦長は既存の `splitTallImages` で分割（最大3枚まで解析） |
| 負荷 | ホスト別の間隔・同時接続・バックオフ・実行の総量（§3）に統合。再試行は通信失敗・タイムアウト・5xxだけ1回（4xx・robots・429は再試行しない） |
| 失敗の分類 | `invalid_url / private_url / blocked / robots / auth_required / not_found / rate_limited / http_error / timeout / network / unsupported_type / spoofed_type / too_large_bytes / too_large_pixels / corrupt / too_many_redirects / not_attempted`。例外にせず分類して返す |

テスト（`image-fetch.test.ts`・12件）は、ローカルの一時サーバーに、正常・偽装（PNG申告でHTML）・実体の形式違い・SVG・展開爆弾（10000×9000の単色PNG）・6MB超・壊れたファイル・EXIF回転・長辺超過・404/403/429/5xx・内部アドレスへのリダイレクト・無限リダイレクト・robots禁止・遅延を返させて検証した（外部アクセスなし）。

### 2.3 AIへの接続（`src/lib/judgment/xsource/vision-real.ts`）

- **正式API**：既存の依存（`@anthropic-ai/sdk`）の `messages.create` に、`image` ブロック（base64の画像バイト）＋ツール `submit_image_readings`（強制）を渡す。既存の書き起こし（`image-transcriber.ts`）と同じ方式。画像の中の文章は命令ではなくデータ（システムプロンプトで明示）。個人情報は読み取らない・出力も `redact` を通す。
- **読み取る項目**：応募期間・応募開始・応募締切・当選発表・対象店舗・対象商品・応募単位（店舗選択・商品ごと）・購入条件・受取方法（＋その他）。各読み取りに `field・text（見えたとおりの原文の抜粋）・region（画像内の位置の説明）・uncertainty（確度）` を付ける。画像ID（`IMG<番号>-<内容ハッシュ8桁>`）で、複数画像のどれかを区別する。
- **仮説の扱い**：画像の読み取りは**原文の事実ではない**。引用の根拠にならず（引用は本文の実在を検査する）、観察の注記としてAIに渡す。画像だけにある情報は「画像のみの情報（AIの読み取り・原本と未照合・事実として確定しない）」と明記。
- **キーを持つだけでは呼べない**：クライアントは**許可証（RealRunTicket）が無いと生成できない**（例外）。許可証は、承認済みの関門（`checkJudgmentRealRun`：開発環境・許可フラグ・開発専用キー・承認額・確認文）＋ローカルSupabase を通った評価入口だけが発行する（既存の仕組み）。画像の呼び出しは、調査・判断と**同じ `CallBudget`** で回数・費用を予約してから行う。静的テストで、収集・画面・server action・登録案の生成部が `vision-real`・`image-fetch` を読み込まないことを確認。
- **停止条件**：401/403・429は**即停止**（以降の画像を呼ばない・再試行しない）。通信エラー・出力の途切れは「解析失敗」として残し（読み取れなかった扱い。**画像の内容を「無い」にしない**）、再試行しない（次回の実行で再解析できる）。1実行あたりの最大画像数（既定8）・1画像あたり最大3分割・予約が残額に収まらなければ呼ばない。同じ画像の二重実行は進行中の結果を共有。単価が不明なモデルは呼ばない。
- **費用の見積**：入力トークンは画像1枚あたり `幅×高さ÷750`（長辺1568pxに縮小される前提で最大1,600）＋指示 1,100・出力上限 1,200。Haiku 5.5 で **1画像あたり最悪 約0.1〜0.2円**（`estimateVisionRunCostJpy`）。`preflightRun` に画像の予約（1件あたりの枚数×最悪費用）を加え、1件の上限が不足すれば警告する。
- 監査イベント（`vision_call / vision_done / vision_skip`）にはホスト・件数・費用だけを出し、画像データ・URL全体・キーを出さない（テストで確認）。

### 2.4 本文・画像の照合

| 状態 | 意味 | 扱い |
|---|---|---|
| `confirmed_by_text` | 本文（・リンク先）でも確認できる | 注記に残す |
| `conflict` | 日付が食い違う（月日の集合で比較。年またぎの誤判定を避ける） | **矛盾・未確定**として残し、どちらも確認済みにしない |
| `image_only` | 画像だけにある情報 | 「原本未照合」の注記。**重要情報の唯一の情報源でも黙って除外しない**（登録案は排除されず、引用の根拠にもならない） |
| 未確認 | 取得・解析できなかった画像 | **理由つき**（期限切れ・robots・ログイン・過大・偽装・上限・停止など）で残し、「画像に重要な条件が書かれている可能性がある」と明記 |

- 既存の安全な登録検証（引用の実在・識別・権限・履歴保護）は変更していない（画像の読み取りは引用の根拠にならないため、検証層を弱めない）。
- 画像から読み取れなかった項目（応募期間・店舗 等）は「画像に書かれていない、とは断定しない」として注記する。

### 2.5 再利用・鮮度・費用制御

- 保存（`evidence_image_observations`・migration 121）：候補×画像URL×**モード（mock/replay/real）**×内容ハッシュ。**モックの結果を実解析として再利用しない**（読み出しもモード別）。
- 鮮度：解析結果は7日間は取得せず再利用。7日を過ぎたら**画像を取り直し**（無料）、内容ハッシュが同じなら再利用（有料の解析を重ねない）・違えば（同じURLで画像が差し替えられた）再解析して別の行として追記。
- 失敗の保存：再試行しても同じ結果になる理由（robots・期限切れ・過大・偽装・不正・private）は保存し、3日間は再取得しない。通信・タイムアウト・上限・停止は保存せず次回再試行。
- 同じURLの画像が複数ある場合（投稿と引用元の重複）は1回だけ解析（重複課金なし）。
- 費用：`CallBudget`（回数・費用）・`preflightRun`（画像の予約を含む）・1実行の最大画像数・停止/二重実行防止（ロック）を、既存のリアルAIの関門・評価入口（`real-run.ts`）に統合。

### 2.6 モックでの通し検証（実API・実ネットワークなし）

`tests/phase2-vision-runtime.integration.test.ts`（DB統合・4件）：取得→検査→解析入力→根拠/未確認→保存→AI調査→登録案。
- 条件が画像だけにある案件：「画像のみ・原本未照合」が観察に入り、登録案は排除されず、画像の文言は引用の根拠にならない。保存には画像データ（base64）が含まれない。
- 失敗：期限切れ・偽装・robotsは保存して再取得しない／タイムアウトは保存せず再試行。理由が観察に出る。
- 鮮度：期間内は取得も解析もしない／期間超過で取り直し、ハッシュ同一なら解析しない／差し替えは再解析。モックの行は real では見えない。同じURL2回は解析1回。
- 権限：構成員だけが読める・他世帯は読めない・利用者は書けない・更新できない。

### 2.7 画像の保存期間・著作権・個人情報・容量（比較と方針）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A 原本を保存 | 取得した画像をStorage等に保存 | 後で再解析・原本照合ができる | **著作権（店舗・公式の画像の複製保持）**・容量・個人情報の混入・保存期間の管理が必要。利用条件の確認が重い |
| **B 読み取り結果だけ保存（採用）** | 読み取りの短い抜粋（≤300字×20件）・位置の説明・ハッシュ・寸法・費用だけ。原本は保存しない | 著作権・容量・個人情報のリスクが小さい。再解析は画像を取り直して（無料）ハッシュで同一性を判断 | 画像が削除・差し替えられると原本照合できない（その場合は「未確認」） |
| C 保存しない | 毎回取得・解析 | 保存のリスクなし | 重複課金・再現性なし |

- 採用：**B**。読み取り結果は `redact`（メールアドレス・電話・住所等の伏せ字）を通して保存する。容量は1行最大20KB（DB制約）・1画像1行。
- 保存期間：候補の削除に連鎖して削除される（外部キー `on delete cascade`・リハーサルで確認）。**候補が残る間は保存される**ため、期限切れの掃除（例：失敗・解析不能の行は180日で削除）は未実装＝**未解決事項**。
- 画像の公開URLは `image_url` に保存する（https・500字まで）。署名つき・期限つきURLは取得・保存しない。
- 著作権・利用条件：取得は公開されている画像に限り、robots.txt を守り、個人利用の範囲で、解析のためだけに一時的にメモリへ読み込む。再配布・表示はしない。**法的な判断ではなく、方針の比較**。サイトごとの利用規約の確認は未実施（実運用前に必要）。

## 3. 複数URL取得の実運用上の負荷と安全性

### 3.1 構造（投稿単位 ＋ 実行全体）

| 層 | 上限・制御 | 実装 |
|---|---|---|
| 投稿単位（#113） | リンク最大24（同一ホスト16）＋深さ1の追跡6・90秒・1ページ 120,000字・画像 MAX_IMAGES | `link-plan.ts`・`x-rich.ts` |
| **ホスト別（新）** | 取得開始の間隔 1.5秒・同時接続 1・連続失敗2回で停止・429/503は指数バックオフ（Retry-After尊重・3回で停止） | `fetch-control.ts` の `HostThrottle` |
| **全体の同時接続（新）** | 4 | 同上 |
| **実行の総量（新）** | リクエスト 600・転送 200MB・画像 120・締切（収集ワーカーの残り時間。Vercelの実行時間60秒のうち収集は約54秒） | `RunFetchBudget`（`processQueue` の開始時に用意） |
| **締切・中止（新）** | 投稿の90秒と、収集の残り時間の**早い方**で新規の取得を止める。残り8秒を切ったら中止 | `x-rich.ts` の取得ループ |

- ホスト別の制御は**投稿・実行をまたいで共有**（プロセス内のシングルトン）。サーバーレスで複数インスタンスが同時に動く場合の**インスタンス間の共有はできない**（未解決事項）。
- 取得しなかったリンクは**必ず台帳（`linkLedger`）に理由つきで残る**：`host_suspended / deadline / time_limit / backoff_beyond_deadline / budget_requests / budget_bytes / budget_images / cancelled / over_total_limit / over_host_limit` 等。無言で捨てない。
- **再調査の経路**：上限・時間・制限・一時的な通信失敗が理由の未取得リンクは `pendingRecheck(ledger)` で取り出せる（本当に取得できない robots・ログイン・短縮・X・不正とは区別）。AIの入力には「未取得（上限・時間・制限のため。再調査で取得できる）」と明記し、画面の通知にも件数を出す。再解析（再実行）のたびに投稿のリンクは再び取得対象になる。**未取得を自動で再キューする処理は未実装**（収集の挙動を変えるため、利用者の判断が要る。未解決事項）。
- 取得範囲を縮めていない：1投稿の上限（24＋6）は#113のまま。取得できたページの全文保管と後段AIへの到達は維持。

### 3.2 負荷の再生・見積（実際のURLには接続していない）

保存済みのリンク構造とモックの応答で、`x-rich-load.test.ts`（7件）が次を検証した。

- 10投稿×24リンク（8ホスト）が同時に走っても、ホスト別の同時接続は1・全体は4以下・同じホストへの開始間隔は1.5秒以上。実行の総量（120）を超えた分は `budget_requests` で未取得として台帳に残り、240リンク全てが台帳にある。
- 429が続く遅いホストはバックオフの後に停止し、他のホストは取得を続ける。403は2回で停止（回避しない）。
- 遅いホスト（1ページ20秒）は、締切を超えると取得せず `deadline` で残る。中止（収集の時間切れ）は `cancelled` で残る。
- 制御なし（単件解析・従来の呼び出し）は従来どおり動く。

**見積**（`estimateLoad`。1ページ平均 0.15〜0.3MB・画像 0.35〜0.5MB・応答 0.8〜1.2秒と仮定。実測ではない）：

| シナリオ | リクエスト | 転送 | 取得の下限時間 | 最も多いホストへのリクエスト | 保存量（全文の10%が本文として残ると仮定） |
|---|---|---|---|---|---|
| 通常（30投稿・平均5リンク・画像2・追跡1・12ホスト） | 240 | 46MB | 約48秒 | 20 | 約2.6MB |
| 多め（60投稿・平均10リンク・画像3・追跡2・15ホスト） | 900 | 206MB | 約203秒 | 60 | 約14MB |
| 最悪（60投稿・上限の24＋6・画像4・8ホスト） | 2,040 | 629MB | 約612秒 | 255 | 約53MB |
| 集中（40投稿・同じ公式サイトへ20リンク・2ホスト） | 960 | 198MB | **約720秒**（ホスト別の間隔が支配） | 480 | 約17MB |

- 「多め」「最悪」「集中」は、1回の収集ワーカー（約54秒）では取りきれない。**実行の総量（600リクエスト・200MB）と締切で自動的に打ち切られ、残りは理由つきで未取得になる**（上の台帳）。収集は複数回のワーカーで少しずつ進む設計のため、未取得分は次の実行で取得される（再キューの自動化は上記のとおり未実装）。
- DB容量：全文は取得できたページごとに最大120,000字（約360KB）。通常で2〜3MB／回、最悪で約53MB／回。`evidence_documents` は追記専用・同じ内容は保存しない（冪等）ため、再取得で増えるのは内容が変わったときだけ。**保持期間・容量の上限（古い全文の整理）は未実装**（未解決事項）。
- 課金推定：URL・画像の取得は無料（通信量のみ）。有料なのはAI（調査・判断・画像）。画像は1枚あたり約0.1〜0.2円（Haiku・最悪）。

### 3.3 Vercel等との整合

- 収集ワーカーは `maxDuration=60` のうち約54秒を使う（`cron/collect`）。`RunFetchBudget.deadlineAt` はこの残り時間から決まり、投稿の90秒より先に打ち切る。進行中の1リクエスト（最大10秒＋robots 5秒）の分として、残り8秒で新規取得を止める。

### 5.3 独立gold（採点の独立性）

- `validateGold`：**人による確認（by=human・日時・根拠）・根拠の場所と原文の引用・合言葉（canary）が必須**。根拠の出所が AI出力・旧方式・モック・登録案に見えるものは拒否。重複・形式不正も拒否。
- gold は採点の関数だけが読む。AIへ渡す入力・観察に gold の合言葉が混ざっていないことを `assertNoGoldLeak` で検査（テストで、混入すると検出されることを確認）。
- **モック・台本・再生の結果は精度として主張しない**（`claim=pipeline_check_only`）。実AI（mode=real）の結果だけが `accuracy`。
- gold の作成は人が行う：`gold-template` で、案件の入力の要約だけの記入用の下書きを作る（AI出力を含めない）。
- 採点：機会（店舗×商品）を gold と対応づけ、店舗・商品・締切・応募単位・URL・登録の判断を採点。**誤登録**（登録すべきでないものを登録）・**他の機会のページにしか無い引用の混入**・**本文に実在しない引用**を重大な指標として数える。登録案が根拠の引用と正しい項目に紐づくかは、引用が自分の機会のページ/投稿にあるかで検査する。

### 5.4 合否基準

- **重大な指標が baseline より1件でも悪化したら、他が改善していても不合格**（総合点で相殺しない）。
- 主指標が「見込む改善幅の半分」以上改善し、案件ごとの比較で悪化が改善を上回らなければ合格。
- gold の件数が実験ごとの必要件数に満たなければ **inconclusive**（重大な悪化が無いことだけ言える。改善は主張しない）。必要件数は、有意水準5%・検出力80%・設計効果1.5（同じ案件内の機会の相関）で算出：

| 実験 | 見込む改善幅（仮定） | 合格の最小改善 | 必要な gold の案件数（目安・1案件3機会） |
|---|---|---|---|
| links | 30ポイント | 15ポイント | 76 |
| text_depth | 15ポイント | 7.5ポイント | 322 |
| image | 15ポイント | 7.5ポイント | 322 |
| hints | 8ポイント | 4ポイント | 1,154 |

  見込む改善幅は**実測前の仮定**。効果が小さい実験（hints）は、現実的な件数では改善を統計的に言えない。その場合は「重大な悪化なし」の確認と、案件ごとの差・費用・ターン数・ヒントの命中率の記述に留める。（**案件ごとの符号検定**（両側・正確確率）を実装した。勝負が8件以上で p<0.05・主指標が最小改善以上・悪化が改善より少なければ、gold が必要件数に満たなくても「小標本の合格」とする（効果の大きさの推定は不確かと明記）。links のように旧方式が構造的に取りこぼす実験は、10件前後でも合格しうる。重大な悪化があれば常に不合格）

### 5.5 実行前の計画（dry-run・無課金）と停止条件

`node scripts/compare-phase2.mjs plan` が、件数・アーム・API呼び出し数（調査・判断・画像）・期待費用・最悪の予約・承認文・停止条件・gold不足の警告を出す。実行（`run`）は、**承認額・確認文 `APPROVE C <総額>JPY`・開発専用キー・関門・事前検査・独立goldの検証・計画の費用が承認額内**のすべてが通らなければ起動しない（金額・確認文に既定値なし）。

停止条件：総額/1案件の予算（CallBudget・予約の事前検査）・画像枚数・最大取得回数/時間・認証/利用上限の即停止・連続失敗で停止・実行ロック（二重起動を拒否）・協調的な中止。誤登録の防止：登録案は評価用のローカルDBにだけ保存（本番・利用者の登録には作用しない・人が確定した情報・履歴は変更しない）。
