## 2. B2: 実世界の公開ページを安全に調べる（§1）
### 実装（再利用を優先・新しい生fetch/プロキシなし）
- `live-fetch.ts`（開発限定）: 既存の `fetchRespectingRobots`（SSRF・DNS解決後の全アドレス検査・サイズ/時間の上限・Cookie/認証なし・**robots.txt**）を、**リダイレクトを1回ずつ自分で辿り、毎回 robots と安全検査を通す**形で呼ぶ。同一ホストに最低1.5秒の間隔・2回続けて失敗したホストは停止・1実行の取得数の上限・X/t.co・`mypage/login/account/cart/order/member` のパスは取得しない・401/403・ログインが必要な短いページ・robots禁止は**停止（迂回しない）**。`TOREMANE_ENV=local` ＋ `JUDGMENT_LIVE_FETCH=allow` が無ければ生成できない。通常の画面・収集・cron から読み込まれないこと（静的テスト）。
- **明示モード**（混ぜない）: `replay_saved`（厳密な旧基準。保存に無いURLは取得不能＝評価の制約）／`live_public`（開発限定。取得の経路が裏付けられたときだけ同じページと数える: URLの正規化一致、または取得ページの題名・受付枠が正解の店舗を名指しし、対応の検査が mismatch でない）。
- 失敗の層（`classifyB2Layer`）: 検索に正解ページが無い／AIが選ばなかった／取得できない（終了・制限）／検索を使わない／検索を介さず到達／別ページ／成功。**終了イベントの404・ロボット制限をモデル能力の失敗に数えない**。
- **検索候補の再生**: 過去のB2結果にはURLが保存されていなかったため（ホストのみ）、**無課金で再生できる検索資産は無い**。次回の実評価から、検索結果（題名・URL）を事例ごとにローカル限定の出力へ保存する（`B2CaseRow.searches[].hits`）。今回の「候補→実ページ」は、**保存済みの応募ページURLを候補として与えた再生**であり、**AIがWeb検索で発見した実測ではない**（`candidate: saved_url（候補として与えた。検索による発見ではない）` と明示）。

## 3. A/C・根拠の実在と意味対応（§2）
### 人が確認できる比較資料（ローカル限定・Git管理外）
- `eval/real-data/xsource-10y-review.{json,md}`: **1事例1行**（A 12件＋C の gold 3件）。構造化ページの受付枠（名称・状態・価格・「項目: 値」・注意書き）・旧方式の読み取り（受付枠数）・元の文言・AIの結果（判断・検証・保留理由・項目ごとの根拠の種類）・正解の有無・確認すること、を並べる。
- **今回までのAの評価ではAIの候補値・引用を保存していなかった**ため、AI側は「値は未保存」と明示される。次回の実評価から候補値・引用（160字まで・ローカル限定）を保存する（実装済み）。
- 採点: **独立した正解（gold）がある事例だけ**。A 12件は gold **0**＝採点せず「正解なし・要確認点」を列挙（受付枠が複数＝応募単位の確認、検証通過≠正しさ、観察とされたが値が本文に逐語で無い項目、等）。C は gold 3件（採点対象3件）。**gold が10件に満たないため正答率は出さない**。
- gold を増やす具体案: 根拠メモの無い6件（`human_unit_no_basis`）に、利用者が公開ページ等の根拠を書くと 9件。あと1件で10件。以前のAIへの「正しい」評価3件・判断不能17件は gold にしない。

### 検証通過の意味
- A再試験の検証通過9件は正答率ではない。観察とされた68項目のうち、値が本文に**逐語**で現れたのは32件（47%）。値の書式変換・導出か、根拠からは導けない値かは**人が確認する必要がある**。検証層は引用の実在しか見ない設計で、これは**弱点として明記**する（基準を緩めてはいない）。

### 別指標（誤統合・誤分割・過剰保留・根拠のない確定）
- `scoreAgainstGold` に **誤統合（misMerge）・誤分割（misSplit）**を追加（既存の `overHold`・`unsupportedAssertion` と別に数える）。gold のある事例だけ。自動の本登録は既定にしない。**現在は gold 3件のため値の一般化はしない**。

### 本文抽出（pageText）の回帰
- 構造（plain／`<main>`＋nav・footer／スクリプト・エンティティ／属性内の「>」）で、題名・受付枠が本文に残ることをテスト。**`<header>`/`<aside>` の中に受付枠がある構造は、既定の整形（メニュー・フッター等を除く）で消える**ことを発見 → `pageTextChecked`: 構造として認識できた語（題名・受付枠・項目の値）が本文に無ければ、除かない整形に切り替え、それでも欠けるものは `textLoss` に残し、**そのページを根拠にした observed 項目は保留（`page_text_loss`）**・AIにも注意を表示。**保存済みの実ページ12件では欠落0**。引用の実在チェックは弛めていない（テスト済み）。

### 調査出力の途切れ（max_tokens）
- 原因候補: 出力スキーマの上限が大きい（観察10件×240字・不明6件×最大300字 等）。対策（**mock検証のみ。実AIで直ったとは主張しない**）: スキーマの上限を絞り（観察6・推論4・不明4・引用/本文160字・反対仮説2・判断の項目12）、`max_tokens` を 1,800→3,000、プロンプトに「簡潔に」を追加。`stop_reason=max_tokens` は失敗として理由を記録（テスト済み）。最悪値の保証はスキーマだけではできない（出力が上限に達すれば途切れる）ため、**途切れの再発頻度は有料の実測が要る**。

## 4. 費用の事前検査（§2・§4）
- `preflightRun`（課金なし・純関数）: 総額・1件・調査/判断/検索の予約・関門の1件上限・最悪費用を、**実AIのクライアントを作る前に**検査する。3つの real テスト（A・B2・C）が呼ぶことを静的テストで確認。Stage 10X で実際に起きた2つの失敗設定（総額¥5＋予約¥3+¥3、1件¥1＋予約¥0.6+¥0.6）を**拒否**することをテスト。
- 実費が予約を超えた場合: **実費で計上し、`overruns` に記録、残りが無ければ以降の呼び出しを開始しない**（テスト済み）。
- **保証の限界（正直な制約）**: API費用は呼び出し後にしか確定しない。予約が「1回の最悪費用（入力12,000トークン・出力3,000トークンで約¥0.41）」以上なら1回で予約を超えない。調査・判断の予約は¥0.6で上回る。**検索（web_search）は1回の問い合わせで複数メッセージになりうる**ため、`AnthropicWebSearch` に `maxMessages`（既定3＝従来どおり。評価では1）を追加し、検索の最悪費用を約¥1.9に抑えて予約¥2.5で覆う。予約が最悪費用より小さい設定は警告（保証なし）。承認額の絶対保証は、予約が最悪費用以上の設定でのみ成立する。
- **1件の追加費用が上限を超えたとき**: その事例は上限で停止し（`CaseBudget`）、判断が必要な予約が残らなければ判断も呼ばず `budget_cost` で保留。次の事例は新しい1件上限で開始し、全体の上限は共有する。
- 入口（`xsource-10x.mjs`）: 1件の最小値（A・C ¥1.5、B2 ¥4.5）未満は拒否（確認済み）。**今回もCの実AI再試験は行っていない**。
