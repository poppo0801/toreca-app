- **一般の画面・server action・cron・収集の接続口から実AIは動かせない**（許可証＋静的テスト）。環境変数だけ・本番にある秘密キーだけ・画面操作だけでは有料AIは起動しない。
- 限定運用の準備: 人のレビューの再利用（修正値を再評価の入力に）・再評価の差分表示・集計（候補・レビュー・修正・費用・解決率）・**本番限定プレビューの許可判定の設計（未接続・既定OFF・即時OFF・誤起動試験つき）**を整備。

## 2. 実AIの通し経路（§1）
### 2.1 呼び出し経路と稼働入口
| 区間 | 実装 | 状態 |
| --- | --- | --- |
| 起動入口 | `scripts/proposal-real.mjs plan\|prepare\|run` → `src/lib/server/proposals/proposal-real.real.test.ts`（評価入口。ローカルDB以外には接続しない） | `run` は承認が無ければ拒否（承認額・確認文 `APPROVE P <総額>JPY`・1件上限の最小値）。**実際に拒否されることを確認**。`plan`/`prepare` は無課金で実行済み |
| 許可証 | `real-gate.ts`: 関門（承認額・確認・開発専用キー・開発環境）＋ローカルのSupabase＋非Vercel でなければ発行しない | 発行できるのは `real-run.ts` だけ（静的テスト） |
| 実行 | `real-run.ts` の `runRealProposals`: 事前検査 → 全体 `CallBudget`＋項目ごと `CaseBudget` → 候補ごとに `generateProposalsForCandidate`（mode=real） | 台本クライアントで統合テスト済み |
| 調査・判断 | 既存の `ResearchAgent`/`RegistrationJudge`（実AI版）＋検索（`AnthropicWebSearch`・メッセージ1通に限定）＋ページ取得（保存ページの再生 → 開発限定の実取得 `live-fetch`） | 実AIでの動作は**未検証** |
| 保存・レビュー | 既存の `registration_proposals`（mode=real・モデル・費用・停止理由を記録）・追記専用のレビュー・候補詳細のUI | 実DB・E2Eで確認 |
- 実AIの依存は**注入**（クライアントは呼び出し側が作る）。既定は費用ゼロのモック。`mode=real` は許可証が無いと生成しない（画面・server action・収集 hook・環境変数だけでは不可。許可証の偽造（同形のオブジェクト）も拒否: 統合テスト⑤）。
- **入口の分離（静的テスト）**: 許可証の発行を import できるのは `real-run.ts` のみ／`real-run`・擬似クライアント・本番プレビュー判定は非テストのコードから読み込まれない／候補の画面・操作・hook・`run.ts` は `real-run`・AIクライアント・`AnthropicWebSearch` を読み込まない／登録案系のコードは SDK・APIキーを扱わない／評価入口は関門 → クライアント生成の順・ローカルDB以外に接続しない。
- **本番の候補・本番DBに実AIを実行しない**: 許可証の発行条件（ローカルのSupabaseの接続先）と、評価入口のDB接続の検査（ローカル以外は例外）の二重。

### 2.2 費用の予約・停止・監査（実装と、保証の限界）
- **事前検査**（`preflightRun`）: 総額・1件・調査/判断/検索の予約・関門の1件上限・最悪費用。通らなければ**1回もAIを呼ばない**（テスト: Stage 10X の失敗設定・検索の予約不足）。
- **予約→計上**: 全体 `CallBudget`＋項目ごと（`CaseBudget`）。実費が予約を超えた場合は実費で計上・`overruns` に記録し、残りが無ければ次を呼ばない。
- **停止条件**（統合テスト④）: 認証エラー(401/403)・利用上限(429)は**即停止**（再試行しない）／5xx等が連続3候補で停止／予算が尽きたら停止／協調的な中止／**二重起動はロックで拒否**（実行後はロックを残さない）。クライアントは `maxRetries=0`。
- **監査ログ**（`onEvent`・`eval/real-data/proposal-real-audit.jsonl`・Git管理外）: 候補は短いハッシュ・件数・費用・理由コードだけ。**原文・URL・キー・投稿全文を含めない**（テストで確認）。失敗は握りつぶさず `role:reason` で分類して集計。
- **保証の限界（誇張しない）**: API費用は呼び出し後にしか確定しない。「予約が最悪費用以上」の設定でのみ**1回の呼び出しで予約を超えない**。したがって実行全体の最悪値は「承認の総額＋最後の1回分の最悪費用（調査/判断 約¥0.41・検索 約¥1.9）」であり、承認額ちょうどの絶対保証ではない。請求の実額は Anthropic Console で確認する（評価コードの計上値とは別）。
### 2.3 収集 hook の見直し
- 旧: 3秒の `Promise.race` は内部処理を止めなかった。新: 超過したら**協調的な中止フラグ**を立て、残りの項目は処理しない（実行中の1項目は完了まで待つ）。**無言で握りつぶさず**、分類コード（`timeout_stop_requested`・`generate_<reason>`・`error:<名前>`）だけを記録（原文・IDなし）。**hook は mode=mock 固定で実AIは渡さない**。キュー化・リース/冪等再試行は、実AIの評価入口（手動起動・ロック・`input_hash` の冪等）で代替し、**収集経路には実AIを載せない設計**にした（実AIを収集に載せるときの前提は §7）。
### 2.4 A/B1/B2/C と今回の通し試験（P）の区別
- 既存の評価（A: URL既知・B1: 入力リンク（AIなし）・B2: 自律発見・C: 独立gold）は、そのまま別指標として維持。
- **P（収集候補経路）**: 保存済みの実在の公開投稿・公開ページ（`eval/real-data/`）から、収集と同じ構造の候補（42件: 10S 30件＝短縮URL未展開・LivePocket 12件＝項目自身のリンク＋保存ページ）をローカルDBへ入れ（`prepare`・実行済み・無課金）、同じ入口を通す。**検索経由の到達**（`pages[].viaSearch`）を、URLが最初から与えられたものと区別して記録（既知URLを渡しただけの再生を「自律発見」と数えない）。到達＝正しいとは限らず、gold がある事例だけ別に採点（誤統合・誤分割・過剰保留・根拠なし確定は独立指標）。
- 登録案の項目名は、人が確定した値と照合できるよう英語のキー（store/product/deadline/apply_unit）を指示（実AIでの遵守は未検証）。値の導出（`support`）・引用の実在は従来どおり別に記録。保留を増やすための基準の追加・検証の緩和はしていない。

## 3. 人間確認つき限定運用の実装準備（§2）
- **人の修正の再利用**: レビューの「修正して承認」の値を、再評価のとき**人が確定した値（protectedFields）**として調査・判断の入力に渡す。AIは変更できず、食い違いは人への確認（検証層）。入力のハッシュに含めるため、修正が変わると新しい版になる（旧版・レビューは残る）。**保存した人の判断を次回の入力に使うだけで、モデルが学習したのではない**（統合テスト⑥: 判断の入力に人の値が渡る・却下/保留は渡らない）。
- **再評価後の差分表示**: レビューした版と現行の版の主要項目（店舗・商品・締切・応募単位）の変化を「再評価で変わった点（前回 v1・現行 v2）」として表示。人のレビューは消えない（E2E・390pxで確認）。
- **集計（フィードバック記録）**: 候補一覧の上に1行（開発用・フラグON時のみ）: 候補・登録案・レビュー済（修正あり/却下/保留）・解決率・費用。定義を固定（`proposal-summary.ts`）: 解決率＝（修正して承認＋却下）／登録案、修正率＝修正して承認のうち1項目以上を人が修正したもの。**閾値は作っていない**（ベースライン測定後）。モードの表示（モック／再生／実AI＋「実AIが作成した登録案です（正しさは未検証）」）。
- 承認と実際の抽選登録の分離は維持（承認はレビュー記録のみ。lotteries・応募・購入・通知・既存履歴に書かない。DB結合・E2Eで確認）。
### 本番限定プレビューの接続設計（実装済みの判定・**未接続・本番では有効化しない**）
`src/lib/server/proposals/prod-gate.ts`（純関数・テスト5件・非テストからの import なし）。**すべて**が揃うときだけ許可、既定OFF: ①本番の実行環境（`VERCEL_ENV=production`）②スイッチ2つ（`PROPOSAL_PROD_PREVIEW=on`・`PROPOSAL_PROD_APPROVED=yes`）③緊急停止なし（環境変数・**DB側の設定。DB側は再デプロイ不要で即時OFF**）④対象世帯が許可リストにある⑤**専用の日次予算**がある・未超過⑥**専用のAPIキー**があり他機能のキーと別の値⑦自動登録・通知は常に false。**誤起動の試験**: ローカル/プレビュー環境では本番用スイッチが全部ONでも拒否／ローカル用の許可（`flag.ts`）は本番・ホスト型DBでは常に拒否。
- 本番で動かすには、(a) この判定を呼ぶ入口と DB設定表（新しい migration）の実装 (b) 専用キー・予算の用意 (c) **別の明示承認**が要る。今回は実施しない。
### データ最小化・保存期間・古い証拠・個人情報
- 登録案は原文・URL全体を複製せず、ホスト名・項目自身のリンク・値・引用（160字まで）・理由コードのみ。レビューのメモは300字まで。監査ログは内容を含めない。実AIの評価結果（`eval/real-data/`）は Git 管理外。
- **保存期間・古い証拠の扱い（提案。未実装）**: 登録案は現行の版＋レビューした版を保持し、締切を過ぎて一定期間（例: 90日）経過した候補の旧版は、集計だけを残して削除する（`shadow_purge` に準じた service_role 専用の関数。**本番適用は別承認**）。再評価では、取得日時が古いページ（`fetched_at`）を AI に「古い可能性がある証拠」として明示する（現在は取得日時を渡している）。個人情報は redact を通してから AI へ渡す既存の仕組みを維持。

- **安全（合否の前提）**: 登録案テーブル以外への書き込み0・総額上限内・キー/原文の漏出なし・停止条件が機能（想定外の再試行なし）。1つでも外れたら限定運用に進まない。
- **測る指標（別々に記録）**: 完走率・停止理由／項目ごとの費用と時間／**URLなしの項目で検索経由に到達できた率**（`viaSearch`・到達≠正しい）／引用の実在と値の導出（`support`）／gold 3件の応募単位（採点可能数3＝**一般化しない**）／過剰保留・根拠なし確定・誤統合・誤分割（gold のある事例のみ）。
- **次へ進む判断**: ベースラインの数値と、**人が登録案を全件レビューした結果**（修正率・却下率・解決率）を見て、**閾値は利用者が決める**。gold を増やした再測定（§4・GOLD手順）が、一般化の前提。
