## 1. 「最初の1リンクのみ取得」の事実関係（実コードで確認）
| 段階 | 実コード | 結果 |
|---|---|---|
| ① 発見 | `x-posts.ts` の `linksOf`（entities/note_tweet の全URL）、`linkMap`（最大30） | **全件発見できていた** |
| ② 項目への対応付け | 10M `linkMap`・10S `item-links`・10W `link-evidence`・`link-scope` | **正しく動いていた**（以前の複数URL改善はこの層。今回のテストでも不変） |
| ③ 本文の取得 | `x-rich.ts` の `enrichXPost`: `[...post.links, ...quoted.links].find(外部)` | **最初の外部リンク1件だけ取得**（根本原因） |
| ④ 原文の保存 | `evidence.ts`: linkedPages 最大2件・各3,000字、links 最大5件、text 3,500字、imageRefs 4件。`run.ts` の投稿スナップショットも links 5件・text 4,000字 | 取得できても欠落（さらに `extractPageText` の既定 20,000字が隠れた上限） |
| ⑤ 下流 | `build-input.ts`: 保存リンク先ページを先頭2件に限定。`generate.ts`: 切り詰めを定数（3,000字）で判定 | 2件目以降の本文は新AIの調査入力に届かない |

- **導入経緯**: `.find` による1件取得は Stage 4C 最終調整（`204fba2`「X統合解析」）で入った。複数URL改善（10M〜10W）より前で、後の改善は「対応付け」の層に限られ、**取得の層には及んでいなかった**。つまり PR #104 報告書の「最初の1件のみ取得」の指摘は正しく、「対応付けの改善が壊れた」わけではない（別の層の未解決）。
- **影響経路**: 単件・一括・iPhone共有・自動収集のX投稿はすべて `makeXRichFetcher`／`enrichXPost` を通る（`x-check` の cron も同関数）。全経路共通。旧方式・新AIの再生もこの保存結果を使うため、2件目以降の応募ページの条件は**収集時の根拠に一切入らなかった**。
- **失われていた場所**: ③取得（2件目以降）→④保存（3,000字・2件・5件）→⑤下流（先頭2件）。①②では失われない。
- 同型の見落とし確認（横断監査）: 新AIが使う調査ツールのリンク表示（15件/40件）は**AIへの表示上限であって取得上限ではない**ため欠落には当たらない（ただしリンクが多い応募ページでは要注視。§7）。非X（Webページ）経路は1ページを取得し、先のリンクは新AIの調査ツールが辿る設計で、1件だけ取得する同型の欠落はない。

|---|---|---|

| 選別 | `planLinkFetches` | 取得するもの（既定 24件・同一ホスト16件）を決め、**選ばなかったものは理由つき**（X投稿・未展開の短縮URL・不正・危険（認証情報つき/IP/ローカル/非標準ポート）・件数上限）で残す |
| 取得 | `x-rich.ts` `enrichXPost` | 選ばれたリンクを全て取得（robots・SSRF・サイズ・時間は既存の `fetchRespectingRobots`、1投稿90秒の上限）。ログイン画面は回避せず `login_required`、短すぎる本文は `too_short`。**深さ1**: 応募案内の文言のリンク（応募・申込・フォーム 等）だけ、1ページ3件・合計6件まで追跡（`depth=1`・`fromUrl` を記録） |

| 台帳 | `linkLedger` | 発見した全リンクの結果（fetched/failed/blocked/login_required/too_short/skipped＋理由・字数・切れ）を `last_good.evidence.linkLedger` に保存 |
| 保存（行） | `evidence.ts` | linkedPages 2→30件、抜粋 3,000→6,000字（`fullChars`・`truncated`・`depth`・`origins` を保持）、links 5→60、imageRefs 4→16、text 3,500→12,000字、投稿スナップショット 4,000→12,000字 |

## 3. 画像の一次情報化
- `src/lib/judgment/xsource/image-evidence.ts`（純関数＋注入されるビジョン）。
- **再利用**: 収集時に画像番号つきの読み取りがある画像は再利用し、ビジョンを呼ばない（重複課金なし）。画像番号が不明な読み取りは、画像が1枚のときだけその画像の読み取りとして扱う（複数枚で全画像を解析済みにしない）。
- **解析**: 読み取りの無い画像だけ、注入された `VisionClient`（既定は無し）で解析（上限4枚）。解析結果は `evidence_image_observations`（migration 119）に保存して再利用（モードごと。モックの結果を実AIの結果として再利用しない）。失敗・上限超過は保存せず再解析できる。
- **仮説の扱い**: 画像から読んだ内容は原文の事実へ昇格させない。本文・リンク先の日付と**一致→「本文でも確認」**、**食い違い→「矛盾・未確定（どちらも確認済みとしない）」**、画像のみ→「画像のみ・原本未照合」。読めない・失敗・上限超過・未解析の画像は「内容を確認できていない（無いのではなく未確認）」として観察に残る（重要条件を無言で除外しない）。
- 配線: `generate.ts` が解析結果の注記を新AIの調査入力（観察。引用の根拠にはならない）に渡す。**実ビジョンのクライアントは作っていない**（有料のため別途の明示承認）。
- 未実装: 画像そのもの（バイト）の取得・縮小・ビジョン実装（取得量・画素数・著作権/個人情報・トークン費用の評価は §7 の費用見積）。画像内の文字領域の座標対応は、領域の記述（`region`）の保持までで、原本画像との照合は未対応（原本を保存していないため）。

## 4. 調査経験を活用する自律学習
- `src/lib/judgment/xsource/experience.ts`。**固定ルールを持たない**。
- **特徴の発見**: ページの候補特徴を広く記録（ホスト・URLの形・長さの桁・受付枠数・関連イベント数・画像有無・リンクの深さ・頻出語）。どの特徴が有用かは固定せず、経験の蓄積から**逆文書頻度つきの類似度**で決まる（「LivePocket＋晴れる屋2」のような組み合わせの関連は、コードに書かれず経験から現れる）。
- **記録**: 調査ごとに、重要条件（観察として登録され、引用が本文に実在するもの）が**本文のどの相対位置にあったか**の分布を `investigation_experiences`（migration 119・追記専用）へ。原文・URLは保存しない。検証の強さを区別: `human`（人の確認。レビューで `approve_with_edits` したとき、直さなかった項目の引用だけを正しい位置として追記・直した項目は `failed_fields`）／`gold`（独立した正解）／`ai_unverified`（AIの観察のみ）。
- **次の調査への実配線**: `generate.ts` が過去の経験を読み、`tools.readHints` → 研究ループが長文ページ（12,000字超）の取得時にヒントを `hintSpans` として付け、AIの入力に「過去の類似ページの経験から最初に見る価値がある位置（仮説）」として出す（`research-ai`）。モックでも実AIでも同じ経路。
- **信用しない仕組み**: ①`ai_unverified` は重み0.15で、**検証済み（human/gold）の実効重みが2未満ならヒントを出さない**（AIの出力だけの自己強化を防止。`withheld` に理由）②類似度が低い経験・古い経験（半減期120日）は効かない ③位置に偏りが無ければ出さない ④ヒントは**位置の優先だけ**で、全文・目次・条件語の周辺・read は変わらない。ヒント範囲に無いことを「記載なし」としない旨をAIに明示 ⑤経験は支持数・検証重み・理由つき。
- **改善の実証**: `evaluateHints`（最初の提示範囲に重要条件が入った割合のヒント無し/あり比較）と `shouldAdopt`（評価点20以上・改善5pt以上）。`learn:false` の対照群で、ヒントなし・経験の追記なしで比較できる。実データでの改善は**未実証**（実験は未実施。§7）。
- 権限: 人の確認由来（`human`/`human_review`）の経験だけ、世帯の構成員が自分の世帯へ追記できる。AI由来・gold は service_role のみ。更新・削除不可。

## 7. 未解決・制約・次の実AI試験案
**未解決・制約**
- 実AIでの検証は未実施。ビジョン解析の実クライアントは未実装（有料）。画像のバイト取得・縮小・保存方針（著作権・個人情報）は未設計。
- 収集時リンク先取得の拡大（最大24件＋追跡6件）は、本番の収集の負荷・費用・時間に影響する。有効化の前に、ホスト別のアクセス間隔の設定・実測が必要。収集時の全文保存は本番では動かない（115 未適用・フラグ）。本番で動かすまでは、行の抜粋（30件×6,000字）と台帳のみが残る。
- 経験の効果は未実証。評価点20以上・改善5pt以上で採否を決める仕組みはあるが、実データがない。経験は世帯ごと（世帯間では共有しない）。
- 新AIの調査ツールのリンク表示上限（15/40件）は、リンクの多い応募ページで応募フォームが表示から漏れる可能性がある（取得上限ではない）。要観察。
- 深さ1の追跡は応募案内の文言のリンクだけ（意味判断ではなく目印）。誤追跡・見落としの率は未測定。

**次の実AI試験案（承認が前提。費用は見積のみ）**
1. 複数リンクの再生評価: 保存済みの複数店舗投稿（実データ数件）を、実AIで①リンク1件のみ（旧）②全リンク（新）で調査し、登録案の欠落・混同・人の修正率を比較。1項目あたり既存の見積（約1〜3円）× 項目数 ×2条件 ≒ 上限 数百円。
2. 画像ビジョン: 画像に条件が載っている投稿 10〜20件で、ビジョン有無を比較（読み取りの正誤は gold と照合）。1枚あたり数円〜十数円の見込み。画像上限4枚・総額上限を設定。
3. 経験の効果: 検証済み経験が20件以上たまってから、ヒントあり/なしで同じ長文ページ群を調査し、`evaluateHints` で判定。費用は調査と同程度。
