## 1. 独立goldの確認画面（開発専用）

### 1.1 使い方（ユーザー操作は最小限）

1. `.env.local` に `GOLD_REVIEW=on` を1行追加（`TOREMANE_ENV=local`・ローカルのSupabaseの設定が前提。本番・Vercel・未設定では画面は404）。
2. `npm run dev` で起動してログインし、`/dev/gold-review` を開く（ナビには出ません。URLを直接開く）。
3. 12ページを1つずつ確認する（iPhone幅でも、PCでも操作できます）:
   - 「公式ページを開く ↗」で別タブに公式ページを開き、原文と照らす（画面にも保存した原文を表示。検索・位置移動つき）。
   - 機械抽出の候補は**未確認**の枠で表示されます（「候補を入力欄へコピー」しても確認にはなりません）。
   - 店舗・商品・応募締切・応募単位・根拠の引用を入力し、**項目ごとに「確認した」にチェック**。引用はページの本文にあることがその場で検査されます。
   - 「公式ページを開いて確認した」にチェックし、確認の基準（何をどう確認したか）を書いて「確認済みにする」。
   - 複数の受付枠・商品・店舗があるページは「除外する」（理由つき。複数機会の試験の対象にできる理由が区別されます）。
4. 全て確認済み／除外になったら「R1用のgoldを書き出す」→ `node scripts/compare-phase2.mjs r1-build` → `plan`。**未確認・要再確認が1つでも残る間は、書き出せず、有料試験も実行できません**。

### 1.2 設計と安全

| 要件 | 実装 |
|---|---|
| 通常UIへ混入させない | ナビ・設定から誘導しない／静的テストで、gold確認のコードが他の画面から参照されないこと・収集・AI・登録案のコードを読み込まないことを検査 |
| 本番で使えない | `goldReviewEnabled`: ローカル開発（`TOREMANE_ENV=local`）・ローカルのSupabase・`GOLD_REVIEW=on`・Vercelでない、が全て揃うときだけ。画面は404・操作は拒否 |
| 未確認の明示・推測で補わない | 機械抽出の候補は「未確認・正解ではありません」の枠。確認済みにするには、**項目ごとの確認5つ＋公式ページを開いた確認＋根拠の引用がページの本文に実在＋確認の基準**が全て必要（一括承認の設計は無い）。締切・応募単位は「確認できない」を明示する場合のみ空にできる |
| AI・旧方式・登録案・モックの流用禁止 | 確認の基準にそれらを示す語があれば拒否。画面・保存は、AIの出力・登録案のテーブルを一切読まない |
| 版・日時・根拠・訂正履歴 | 確認時に**ページの版（HTMLのハッシュ）**・確認日時・確認者（利用者IDのハッシュ）・基準を記録。ページの内容が後から変わると**自動で「要再確認」**。履歴（保存・確認・除外・再確認・取り込み）を残す |
| 1ページに複数枠 | 「除外」＋理由（受付枠が複数・商品が複数・店舗が複数 ほか）。別試験（複数機会）の対象にできる理由を区別して保持 |
| 保存・消失防止 | Git管理外のローカルファイルのみ。原子的な書き込み＋書き込みごとのバックアップ（30世代）。壊れた保存ファイルは黙って空にせず、エラー（バックアップから復元）。エクスポート／インポート（取り込み時に**ページの本文・版で再検査**し、改ざん・別の版は「要再確認」へ） |
| 認可・入力検証 | ログイン中の利用者のみ。サーバー操作は全て入力を検査（zod・長さ・列挙）。公式ページのリンクは検査済みの https のみ・`rel=noopener noreferrer`。Next.js のサーバーアクションの同一オリジン検査 |
| R1・ランナーとの連携 | 確認済み/除外から `r1-gold-pages.local.json`（既存の `r1-build` が読む形式。確認したページの版が基準に残る）を書き出す。`r1-build` と比較試験の `run` は、確認の保存があって未完了なら拒否 |

### 1.3 検証

- 単体 9件（有効条件・項目ごとの確認の強制・引用の実在・AI由来の基準の拒否・版の変化→要再確認・除外・バックアップ・インポートの再検査・R1への連携）。
- E2E（390px・PC）1件: 一覧→詳細→**チェック無しの確認は拒否（項目ごとの指摘）**→引用の実在表示→項目ごとに確認→確認済み→未完了の間は書き出し不可→PC幅で一覧と詳細が並ぶ→除外→書き出し→再確認で書き出し不可に戻る→390pxで横にはみ出さない。画面キャプチャ: `test-results/gold-review-*.png`（Git管理外）。

## 2. 実投稿の複数リンク不足の原因調査（経路別）

### 2.1 切り分け

| 経路 | 調査結果 |
|---|---|
| 保存済みの実投稿30件（10S） | **項目単位の抜粋**（一覧の項目12件＋公開ページ18件）。投稿全体ではないため、リンクが1つなのは構造上当然。複数リンクの「投稿」の資料ではない |
| **過去の抽出（extract・実投稿30行）** | **X API経由の実投稿18件＋oEmbed 1件。うち16件が複数リンク（2〜10件、合計95の短縮URL）**。投稿URL（実在）・本文・取得日時はある。**短縮URLは未展開・リンク先の本文は保存されていない**（旧スキーマは本文だけを保存） |
| 収集（API経路）の現行コード | 全リンクを取得・保存する（#113〜）。ただしAPIの `linkMap`（短縮→宛先）が無い保存では展開できない |
| **収集（公開oEmbed経路）の現行コード** | **発見した不具合**: 短縮リンクの展開を先頭3件で無言に打ち切っていた（4件目以降は消え、台帳にも残らなかった）。上限12件・時間20秒・3並列に広げ、**展開できなかった短縮リンクは「展開できなかった短縮リンク」として本文に残り、台帳に理由つき（短縮URL）で記録**。契約テストで確認 |
| 本番のデータ | 触れていない（本番の読み取りも禁止） |

→ 結論: 「実データが無い」のではなく、**実の複数リンク投稿16件の本文はあるが、短縮URLの展開先とリンク先の本文が保存されていない**。展開と取得には、第三者サイト（t.co・店舗サイト）への実アクセスが要る。

### 2.2 実装（実行は許可待ち）

- `real-posts-scan`（ネットワークなし）: 上記の候補を数え、候補一覧（ローカル・Git管理外）を作る。**実測**: 30行・Xの投稿19・複数リンクの投稿**16**・短縮URL**95**・1投稿あたり最大10。
- `real-posts-expand --allow-network`（**第三者サイトへの実アクセスを伴う。利用者の許可が必要。実行していない**）: 短縮URLごとに展開（公開のリダイレクト先を読むだけ。**短縮URL→宛先の対応を保つ**）→取得してよいリンクだけ（SNS・短縮・危険・不正は除外）をrobots.txt・SSRF対策・ホスト別間隔（1.5秒）・総リクエスト数の上限（既定150）つきで取得→出所つきの案件にする。ログイン必須・robots拒否は回避せず、理由を報告に残す。本文が2ページ未満なら案件にしない（実例が揃ったふりをしない）。無課金（有料のX API・検索は使わない）。
- 見積: 短縮URL 95件の展開＋リンク先の取得で最大150リクエスト・約5分（ホスト別の間隔による）。

### 2.3 合成と実投稿の分離

| | 合成（`synthetic_lp`） | 実投稿（`real_post`） |
|---|---|---|
| 内容 | 実在のLivePocket 12ページを、合成した投稿文に組み合わせる | 実在のX投稿＋リンク先の保存済みの本文 |
| ファイル | `cases/gold.synthetic.local.json` | `cases/gold.real.local.json`（出所つき） |
| 出所の検査 | — | 投稿URL（実在の形式）・取得日時・取得元（`saved_public` / `user_supplied` のみ）・複数リンク（展開済み2件以上・本文2ページ以上）。合成案件のIDは拒否 |
| 結果の主張 | **実AIでも精度として主張しない**（`structure_check_only`）。ページの重複・サイトの偏り・独立性不足のため | 実AIの結果だけが精度の根拠になりうる（件数が少なければ断定しない） |

ランナーの各結果に `dataset` と `claim` を記録する。`real-validate` で実投稿のデータセットを検査（未作成なら「実例が揃っていない」と明示）。

## 3. 情報の上限・全文参照の追跡

- 既存の上限監査（`limits-audit`）に加え、**読み飛ばしの切り分け**を追加。gold の重要条件（根拠の引用）が、次のどの段階で失われたかを、比較試験の各アームで測る:
  `not_collected`（未収集）→`not_stored`（保存に無い）→`not_in_ai_input`（AI入力に無い）→`in_input_unread`（入力にあるが読まれていない＝読み飛ばし）→`seen_wrong`（読んだが誤判断）→`seen_ok`。
- 計測の保存: `evidence_coverage_stats` に、文書の識別（URLのハッシュ）・**AIの入力に出ていた区間**・**readした区間**（字位置。原文・URLは保存しない）を追加（migration 120。未適用のため版を変えず編集）。`coverageStatsOf` が記録し、`compare-run` が gold の引用の位置と突き合わせる。
- 検証: 単体（各段階の判定・集計）＋DB統合（旧方式は2件目以降のページが `not_collected`、新方式は全て収集・保存・AI入力に届き、短いページは全文が提示範囲に入る）。比較試験の結果（`readAudit`・`limitAudit`）に毎回載る。
- 上限到達率・p50/p95/最大・未取得の再取得回収は、前工程の `coverageReport`（比較試験の各結果に含まれる）で継続。**実AIでの実測は R1 で行う**（現状はモック。AIの `read`/`fetch`/`search` の行動を、実AIの試験で初めて測る）。重要条件の未読を「記載なし」としない扱い（提示範囲の明記）は従来どおり。

## 6. 残存・ユーザーの判断が必要なこと

**ユーザーの権限／承認が必須**
1. **gold確認（人）**: `/dev/gold-review` で12ページ（§1.1）。
2. **R1の金額承認**: `plan` の見積を見て、総額と確認文を決める。
3. **実投稿の短縮URL展開とリンク先取得の許可**: `node scripts/compare-phase2.mjs real-posts-expand --allow-network`（無課金・約150リクエスト・robots/SSRF対策つき）。許可があれば、実投稿のR1（`--dataset=real`）の準備が進められる。実投稿のgoldも、同じ確認画面の方式で人が確認する必要がある（今回の画面は、保存済みの12ページ用。実投稿のページ用への拡張は、案件が確定してから）。
4. 本番へのDB移行（120〜122）の適用・新AIの本番有効化。

**未発見のリスク（ゼロとは主張しない）**
5. 確認画面は、ローカルの1ユーザー・1ファイルの運用を想定（同時編集の競合制御は無し。保存の都度バックアップは取る）。
6. 実投稿の短縮URLが、保存から日数が経って失効している可能性（展開できない場合は理由を報告に残す）。
7. 実AIの読み飛ばしの実測は未実施（R1で初めて測る）。
