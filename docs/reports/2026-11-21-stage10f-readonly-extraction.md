## 2. バックアップ接続先の安全性（最優先で実施）
**問題**: 既存の `backup:full` は `supabase db query --linked` を使うが、Supabase CLI 3.2.0 のヘルプには `--remote` と「既定はローカル」しか記載がなく、`--linked` が本番に向くか不明だった。
**調査**: 過去の実行ログでは、`--linked` 使用時の完全バックアップが 2026-11-19・11-20 に成功し、行数も本番規模（19,375〜21,249行）だったため、実際は本番に向いていた可能性が高い。ただし根拠は状況証拠で、確認はされていなかった。
**修正**（推測に頼らない方式）:
1. 読み取りクエリは `--remote=<プロジェクトref> --read-only` で接続先を**明示**（`scripts/lib/backup-target.mjs`・`scripts/full-backup.mjs`）。
2. **CLIが表示する接続先（Target行）が、期待する ref を含み、ローカルを示さないこと**を毎回検証し、確認できなければ中止（fail-closed）。ローカルの表示に案内文として本番refが含まれていても拒否する。
3. ダンプ（`db dump --linked`。`dump` サブコマンドでは `--linked` が正規のフラグ）とクエリの件数が大きく食い違えば（別のDBを見ている疑い）中止（許容: 合計差が max(100, 全体の2%)）。
4. 抽出CLIのバックアップ確認を、**実際の保存先**（`%USERPROFILE%\TorecaBackups\full` と `BACKUP_DIR2`）の `tcg-full-*.tcgbak2`（1MB以上・24時間以内）に修正（以前は存在しない `backups/` を見ていた）。
5. 接続先確認コマンド `scripts/check-prod-target.mjs`（`select 1` のみ・データは読まない）を追加。
**実際の確認結果**:
- `npm run prod -- scripts/check-prod-target.mjs`: CLIの接続先表示が **本番プロジェクト（ref が既知の本番ID・リンク先・設定のURLと一致）・production** であることを確認（`--remote=<ref>` が実際に本番へ向き、認証も通る）。
- `npm run backup:full`（修正後）: **成功**。DB 117テーブル・21,638行、認証ユーザー1、Storage 727ファイル（30.2MB）。本体 172.7MB（`tcg-full-20261121-…`）を **C: と D: の両方に保存**し、保存前に復号と全ファイルのSHA-256照合を実施（スクリプトの検証）。ダンプとクエリの件数検査も通過。
- 残る限界: 今回のバックアップの**復元演習は未実施**（直近の復元演習は 2026-11-19。復元手順は `docs/RESTORE.md`）。他のスクリプト（`cleanup-fake-stores`・`cron-setup`・`cron-collect`・`sql-exec`）にも `db query --linked` が残るが、今回の範囲外で未変更（`--linked` が無視された場合の既定はローカルで、本番を誤って変更する方向のリスクではないが、意図どおり本番に向くかは未確認）。
