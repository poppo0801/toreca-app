## 0. 結論（先に）
- **経路は実際に動く**（開発環境・費用0）: 通常収集が保存した候補（本文・親リンク・収集時の linkMap・linkedPages）→ 新AI（10U〜10Yの調査ループ。調査・判断は注入）→ **登録案を `registration_proposals` に保存** → 候補の詳細画面で **人が「保留／修正して承認／却下」**。DB結合テスト7件・単体17件・E2E（390px）で、操作・関数の呼び出し元・データの変化を確認した。
- **承認は「新方式の登録案へのレビュー記録」で、抽選は登録されない**。lotteries・applications・purchases・通知・候補の状態は一切変わらないことを、DB結合テストとE2Eで確認した。自動登録・通知はしない。
- **AIは「費用ゼロのモック（実AIではない）」と保存済みページの再生で動かした**。**実AIで検証済みなのは、既存のStage 10Xの評価だけ**（今回は有料AI・X API を呼んでいない）。実AIの判断精度は未証明のまま。
- **限定運用を始められるか**: ①本番の合流（機能OFF）は準備できている（要・利用者の承認）。②限定的な人間確認プレビューは、**実AIの接続（承認済みの関門つき）と一度きりの有料実測が前提**で、モックのままでは実用的な価値が出ない。→ 今の答えは「**段階①は進められる／段階②は有料実測の承認待ち**」（§6・§8）。
- **変更したこと**: DBは新規 migration `114`（追加のみ・**ローカルのみ適用・本番未適用**）。収集の旧方式のコードは**1か所の呼び出しを追加しただけ**（既定OFF・フラグが無ければDBにも触れず待たない）。

### 収集の構造が正しく渡ること（DB結合テスト・実DB）
- 複数店舗の一覧投稿: 項目ごとに登録案ができ、`source_urls` は**項目自身のリンクのみ**。親の共通リンクは `link_hosts` に出所 `parent_card`（対応未確認）としてホスト名だけが残り、**取得にも根拠にも使われない**。別店舗のページを取り違えない（新宿→新宿、渋谷→渋谷）。
- URLなし／短縮URL未展開／親の共通リンクだけ／取得不能＋調査AIの例外: いずれも**項目は候補に保持**され、`url_status` と未確認事項（`unknowns`）が残り、応募単位は `unknown`（推測しない）。
- 応募単位: AIの出力をそのまま運ぶ（列挙に**完全一致**するときだけ採用。名前一致・系列別の固定ルールは足していない）。店舗選択式／店舗別独立／同じ店舗・商品の別項目（→「同じ応募機会の可能性」を示すだけで統合しない）をテスト。
- 公開ページ・検索抜粋・原文は**データとして扱う**（調査ループの既存の仕組み）。モックは本登録（register）を返さない。

## 3. 登録案の保存と人のレビュー（§2）
### 既存資産の評価（`shadow_opportunities` を使わなかった理由）
`shadow_opportunities`（10N/10P）は「複数の情報源を同じ応募機会にまとめた**旧新比較のプレビュー**」（キー=クラスタID・旧方式との比較・判断のプレビュー）。**①項目ごとのリンクの出所・根拠の種類・引用の導出、②モデル・費用・停止理由、③人のレビュー状態、④元候補・投稿ID・項目番号による追跡**が無く、人の判断の保持（再評価で上書きされない）の構造も無い。用途が違うため、**開発ブランチの migration 案 `114`** を作った（本番適用禁止）。既存の `shadow_*` には触れていない。
### migration 114（追加のみ・ローカルのみ適用）
- `registration_proposals`: 候補ID・`proposal_key`（候補・投稿・項目番号のハッシュ。再評価で不変）・版・`input_hash`・項目ごとの値/根拠の種類/引用/出典/導出（`support`）・応募単位・未確認事項・ページ（ホスト・対応の検査・本文欠落）・同じ機会の可能性・モード（mock/replay/real）・モデル・費用・停止理由・取得/判断時刻。**原文・URL全体は複製しない**（ホスト名と項目自身のリンクだけ）。
- `registration_proposal_reviews`: **追記専用**（更新トリガ・権限なし）。保留／修正して承認／却下・修正した項目（AIの値とは別に保持）・メモ・レビューした版・本人名義。
- RLS: 閲覧は世帯の構成員。**登録案の書き込みはサービス権限のみ**・削除権限なし。レビューは構成員が本人名義で追記だけ。
- 重複防止: 現行の版は応募機会候補ごとに**1つだけ**（部分ユニーク索引）。同じ入力の再生成は**増えない**（冪等）。入力（取得したページ）が変わったときだけ新しい版を追加し、古い版に `superseded_at` を付ける（古い版の内容は更新不可＝トリガ）。
- **人のレビューは `proposal_key` に紐づき、再評価で版が変わっても残る**。AIが上書き・削除する経路・権限は無い。古い版へのレビューは拒否（`not_current`）。再評価で内容が変わったことは画面に「再確認してください」と出る。
### 画面（既存の候補確認UIへの非破壊的な統合）
- 抽選候補の**詳細**の中に折りたたみ「新AIの登録案（プレビュー）N件」を追加（一覧には出さない・管理画面は増やさない）。項目ごとに 店舗/商品/締切/応募単位＋根拠の種類（観察/推論/不明）＋**値が根拠から確認できない場合の警告**＋未確認事項＋モード（「モック（実AIではない）」）＋保留／修正して承認／却下。「承認は記録だけで、抽選は登録されません」と明示。実際の登録は従来の「確認・登録」のまま。390pxで横スクロールなし（E2Eで確認・スクリーンショットあり）。
### 既定OFFと誤設定の防止
- 有効条件: `TOREMANE_ENV=local` ＋ `PROPOSAL_PREVIEW=on` ＋ **接続先がローカルのSupabase（127.0.0.1/localhost）**。Vercelでは常に無効。**本番DB（ホスト型）に繋がる環境では、フラグが立っていても動かない**（誤設定だけで有効にならない）。自動生成はさらに `PROPOSAL_AUTO=on`。
- 停止・再開・費用ゼロ: フラグを外せば全て停止（画面・生成・レビュー・収集の接続口）。データは残り、フラグを戻せば再開。費用は常に0（実AIを呼ぶ経路が無い）。ローカルDBの削除・再起動後も、登録案はDBに残る（リハーサルで確認済みの復元手順の範囲）。

## 4. AI判断の実用的評価の準備（§3）
- **引用の実在と値の導出を分離**: 各項目に `support`（引用に逐語／本文に逐語／書式変換で一致／見つからない／値なし）を保存・表示し、`proposalMetrics` が検証通過数と導出の内訳を別に集計する。**「検証通過」は正答率ではない**（Stage 10X のA 9/12 も同様）。今回の保存済みAの結果にはAIの値が残っていないため、遡って導出率は出せない（次回の実評価から値・引用を保存する実装は Stage 10Y で済み）。
- **誤統合・誤分割・未発見・過剰保留・根拠なし確定は独立指標**（`scoreAgainstGold` に misMerge/misSplit を追加済み・gold がある事例だけ採点）。AIの旧出力・検証通過を正解扱いしない。
- **gold の増やし方（人のレビュー手順）**: `scripts/gold-worksheet-10z.mjs`（読み取り専用）が、根拠メモなし6件の原文・人が指定した応募方式・確認すべき点をローカル限定のワークシートに出す。利用者が原文・応募ページ・出典で確認し、**どのページのどの記載か**をメモ（6文字以上）に書くと gold になる。現状 gold 3／10。**十分に揃うまで精度は断定しない**。AIは回答を書き換えない。
- B2: 実ページ取得モード（Stage 10Y）はそのまま。**検索は呼んでいない**（有料）。検索結果が与えられた再生は「候補与件の再生」であり、自律発見の成功とは報告しない。
- 予算ミスの防止: Stage 10Y の `preflightRun`（総額・1件・調査＋判断の予約・検索・関門の上限・最悪費用）と実費超過の記録・停止をそのまま維持。**API請求の絶対保証は誇張しない**（予約が最悪費用以上の設定でのみ成立）。出力途切れ（max_tokens）の改善は**mockのみの検証**で、実AIで直ったとは主張しない。

## 6. 本番導入の三段階（準備のみ・本番変更なし）
本番へ合流（main へのマージ）すると **Vercel が自動デプロイ**する。以下はすべて独立した承認が必要。
### 段階①: バックアップ → 本番DB移行 → 旧アプリ互換の確認 → 新コードの本番合流（**機能OFF**）
1. 本番の適用状況の確認（`release-db.mjs plan`）。**記録が食い違う**（11/19の記録は106まで適用済み／指示書は098＋104のみ）。確定は本番を読む承認の後。
2. `npm run backup:full`＋復元演習（`docs/RESTORE.md`）。
3. 移行（`release-db.mjs approve` → `apply`）。未適用の移行: **107**（CHECK緩和・既存行は満たす・元に戻すには旧制約の再追加が必要）、**108**（`cases`・`case_judgments`・`case_id` 列・`judgment_engine`・`lottery_history_blockers`・**テスト世帯掃除関数の差し替え**）、**109〜113**（`shadow_*`・RLS・追記専用・既定OFF）、**114（本Stage）**（登録案・レビュー）。099〜106 が未適用なら併せて。いずれも追加のみ・後方互換（リハーサルで旧アプリ＋新DBが動くことを確認）。**DBを先、コードの合流を後**。
4. PR #84 を main へ（CI通過後）。続けて #86 → #88 → #89 → #90 → #92 → 本PR（base を main に付け替え）。**この時点で `PROPOSAL_*`・`SHADOW_*` の環境変数は設定しない**（本番DBでは本機能は動かない設計）。Supabase Cron に `/api/cron/shadow` を登録しない。
5. スモーク確認（ログイン・抽選一覧/詳細・応募・当落・購入・相場・図鑑・画像・通知）。ログイン後の本番画面は利用者の確認が必要。
### 段階②: 限定的な人間確認プレビュー（明示承認後・自動登録なし）
- 前提: 実AIの接続（承認済みの関門 `checkJudgmentRealRun`・`preflightRun`・開発/専用キー・上限）と**一度きりの有料実測**（§8）。現在のコードは本番でプレビューを有効にしない（ローカルDB限定）。本番で行うには、別のコード変更（フラグの接続先条件の見直し）と専用の承認が必要で、**今回は行わない**。
### 段階③: 精度と費用が認められた後の自動登録／通知の切替（別承認）
- 独立 gold ≥10 での精度・誤統合/誤分割/過剰保留の指標・費用の実績・人のレビューの実績を見て判断。**今回の実装は自動登録・通知を一切持たない**。
### ロールバック
コード=合流コミットの `git revert`（履歴は書き換えない）＋ `vercel promote`。DB=追加のみのため戻さない（旧コードは新構造と両立）。機能OFFで戻らないもの: 107の制約緩和・108の関数差し替え・追加された列/表（未使用のまま残す。`drop` は安易にしない）。最後の手段=完全バックアップからの復元（データ喪失を伴うため利用者判断）。

## 8. 次の判断: 「本番作業」か「安全な有料実測」か
