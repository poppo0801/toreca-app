## 2. 今回直した不具合・制約

1. **締切の時刻が採点対象外**（ご指摘の問題）: goldは日付（YYYY-MM-DD）のみで、採点も月日だけの照合だった。
   - gold に任意の `applyEndTime`（HH:MM）を追加（人が入力した場合のみ。AIは補わない。日付が無ければ不可・形式検査あり）。確認画面に時刻入力（`gold-applyEnd-time`）を追加。
   - 採点に `deadlineTimeAccuracy`（goldに時刻がある機会だけ。「23:59」「23時59分」「23時」を同一視）と `deadlineYearAccuracy`（AIの出力に年があるときだけ。年なしは対象外、別の年は不一致）を追加。単体テスト4件。
   - **今のgoldは時刻が未入力のため、時刻の採点は0件（対象外）のまま。** 時刻を測るには、人が該当ページを開き直して時刻を入力する必要がある（既存の確認済みデータは変更していない）。
2. **実投稿R1が、goldの無い案件にも費用をかける設計**だった（14案件のうち10件は採点不可）。実行・計画の対象を「goldのある案件」だけに限定（期待費用 72.6円 → 8.3円）。

## 3. 評価上の制約と改善案

| 制約 | 影響 | 改善案 |
|---|---|---|
| gold件数が少ない（合成12・実投稿4／必要目安 76〜102） | 「重大な悪化がないか」は見られるが、**改善の合否は inconclusive になりうる**。合成の「合格」はモックでも出るため精度とは言えない | 実投稿の未確認57ページを、ページ数の少ない投稿から確認して増やす（確認が済んだ投稿だけが案件になる） |
| 締切の時刻・年がgold/採点に弱い | 23:59か否か等の誤りを検出できない | 上記の対応済み。時刻は人が該当ページに追記 |
| 実投稿が livepocket.jp のみ | 他サイトへ一般化できない | 他サイトの実投稿を収集運用で追加（HTMLと取得対象外の宛先も保存） |
| 合成12案件は LivePocket 構造の検証用 | 精度の主張に使えない（`structure_check_only`） | 結果の報告では合成と実投稿を分けて表示（実装済み） |
| 1サイト・小標本のため再現率の差は不確か | 誤登録・他店舗混入の「1件でも出たら停止」が主な判定 | 重大指標（誤登録・混入・無効引用）を最優先で判定 |

## 4. 実AI評価の実行計画・費用・承認

- 対象実験: **links（先頭1リンク（旧）vs 全リンク（新））**。使用モデル Haiku 5.5（既存の保存済み実測平均: 調査ターン0.163円・判断0.148円）。
- 実行案（推奨の順）:
  1. **合成R1**: 12案件×2アーム。期待 約37.4円。
  2. **実投稿R1**: gold 4案件×2アーム。期待 約8.3円。
  合計の期待 約45.7円。
- 費用上限（関門）: 総額60円・1案件5円。停止条件: 総額/1案件の予算到達・画像1案件4枚・取得30件・全体120分・401/403/429は即停止・連続3案件の不備で停止・実行ロック。誤登録は評価用ローカルDBにのみ保存（本番・利用者の登録は変更しない）。
- **承認文（利用者が決める。AIは入力しない）**: 例 `APPROVE C 60JPY`（総額60円・1案件5円）。別々に実行する場合は、合成 `APPROVE C 50JPY`、実投稿 `APPROVE C 15JPY` のように、期待費用に余裕を持たせた額を指定できる（実行直前に `plan` が再計算する）。
- 実行コマンド（承認後・利用者の指定値で）: `node scripts/compare-phase2.mjs run --experiments=links --approved-total-jpy=<円> --approved-per-case-jpy=<円> --confirm="APPROVE C <総額>JPY"`（実投稿は `--dataset=real`）。
- 実行前に実機で未確認の点: 実AIでの読み飛ばし・誤登録の実測は未実施。
