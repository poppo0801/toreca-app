## 1. 実投稿16件の安全な復元

### 1.1 実行前の静的レビュー（実アクセスの実装とURL先の検証）

前回の `real-post-capture` を、実行前に次の観点で点検し、**実行前に全て修正**した（修正後の動作は、模擬のWebでの単体テスト7件＋実測分布に合わせた再生2件で確認）。

| # | 発見した問題 | 影響 | 修正 |
|---|---|---|---|
| 1 | 総リクエストの数え漏れ: 予算が数えるのは短縮URLの展開とページ取得だけで、**robots.txt・リダイレクトの各ホップを数えていなかった**（`fetchRespectingRobots` は呼ぶたびに robots を取得し、既定で最大4回リダイレクトを辿る） | 「最大150リクエスト」を超えうる | `safeFetch` に `beforeRequest`/`onResponse` を追加。**実際のHTTPリクエストの直前**に上限を検査し、送る前に止める。内訳（展開・robots・ページ・リダイレクト・ホスト別）とバイト数を報告 |
| 2 | リダイレクトの各ホップが、ホスト別の間隔・robots の対象外だった（別ホストへ誘導されると間隔なしで接続） | サイトへの負荷・robots 違反 | リダイレクトを**自分で1ホップずつ**辿り、各ホップで URL検査→間隔（1.5秒）→robots→取得 |
| 3 | robots.txt をページごとに取得し直していた | 無駄なリクエスト・負荷 | ホスト別に1回だけ取得してキャッシュ（取得も数える） |
| 4 | 展開先が **http** だと、短縮URLの展開に成功しても無言で捨てていた | 取り違えではないが「展開失敗」と区別がつかない | 取得せず、理由 `insecure_http` を残す（回避しない） |
| 5 | t.co が 301 ではなく **HTML（meta refresh）** で返す場合に、展開失敗になる | 展開率の過小評価 | meta refresh・location.replace の宛先を読む（解決専用。本文は取得しない） |
| 6 | 短縮URL→宛先の対応を順序で推定していた（展開失敗・除外があるとずれる） | **リンクの取り違え** | 短縮URLごとに展開し、対応を保持。取得できたページの対応だけを `linkMap` にする |
| 7 | 危険ホストへの接続: リンクの選別（SNS・短縮・危険・不正）→`safeFetch` の SSRF 検査（内部IP・メタデータ・ポート）の2層。ホップごとにも検査 | — | テストで、メタデータアドレスへのリダイレクトが模擬のWebにも届かないことを確認 |
| 8 | 同じ内容の2ページを2応募機会と数えうる | 応募機会の水増し | 取得したページの本文ハッシュで同一内容を検出し、案件には**内容の異なるページだけ**を入れる |
| 9 | 取得の順序: 投稿の順で、予算が尽きると後ろの投稿が丸ごと未処理 | 完成する案件が少ない | **リンクの少ない投稿から先に**処理（予算内で完成する案件を最大化） |

t.co は短縮リンクの解決専用（最初の Location を読むだけ）。**t.co の robots.txt は「ルートを許可しない」設定（disallows_root）だった**ため、これは記録として報告する。解決専用の利用（宛先URLを知るだけで、t.co 上の本文を取得しない）は指示書で許可された範囲であり、アプリ本体の既存の短縮URL展開と同じ使い方。**利用条件に疑義があれば、以降はこの解決を止める**（今回は、指示書の範囲で1回だけ実施）。

### 1.4 重要なリンクが失われた段階の調査

- 失われたリンク: ①予算切れ（展開5件・ページ未取得5件）②取得対象外 12件（分類の内訳は未記録）。**発見・展開・安全取得・本文化・保存・入力・AI の各段階**のうち、今回の損失は「発見→展開」の予算（意図した上限）と「取得対象の選別」だけ。HTML本文化・保存では、ページ（68）の欠落なし（取得できたページは全て本文化に成功）。
- 取得対象外12件の内訳が不明だった点は**今回の不備**として、次の取得から記録する（宛先のホスト名と分類）。
- 合成・モックで実例不足を埋めたことを、実例取得の成功とは主張しない（実投稿は実投稿、合成は合成）。

## 4. 上限・読み飛ばし・性能の監査

- 上限の表・測定は #118 の `limits-audit`（上限の一覧は報告書 `phase2-autonomous-remediation-real-eval.md` §2）を維持し、**実投稿68ページの実測**を加えた（§1.2: 6,000字超 18ページ=26%・12,000字超 0・最大 11,704字）。24+6リンク・30ページ・20,000字統合入力・120,000字・read・画像の上限に、実投稿は達していない（実投稿の最大: 1投稿あたり短縮URL 10件・ページ 11,704字）。**観測が単一サイトのため、これらの上限が十分とは断定しない**。
- **実測の形に合わせた再生**（架空の内容。件数・字数の分布だけを使う）: 単一ホストへの集中・取得対象外の宛先・予算切れで、総リクエストが150を超えず、少ない投稿から完成し、間隔1.5秒が守られることを確認。
- AIの `fetch/read/search` とgoldの根拠位置の照合は、#120 の読み飛ばしの切り分け（未収集〜読んだが誤り）で稼働（無料テストで確認済み）。goldが無い実案件では、人未確認の条件語候補を代理にできる設計だが、**精度・正答率は主張しない**。
- 独立機会の同一性（同じ系列の異店舗・同一店舗の別開催回・誤統合・誤分割）は、採点の契約テストで確認（#1）。AIが自分の根拠ではないURLから引用する事故は、引用の混入率（他の機会のページにしかない引用）として計測し、検証層（引用の実在・識別）が従来どおり。通知・ユーザーの応募履歴の保護は、既存の回帰テスト（人の修正は再評価で上書きされない等）が全て合格。

## 5. R1の準備と、夜に人が行う操作

### 5.1 自動の準備状況判定

`node scripts/r1-readiness.mjs`（無課金・読み取り専用。`--full` で型検査・lint・単体・DB統合・buildも実行）。判定する項目: 接続先がローカル／ローカルDBに移行120〜122／最新mainとの競合／承認に関する環境変数が事前に設定されていない（偽造防止）／gold確認の状態（LivePocket・実投稿）／goldの独立性・AI入力への混入／費用の事前検査（最小・最大予約・最悪の1回）／実測指標。現在の結果: **ブロッカー＝gold確認の未完了のみ**（人の操作待ち）。承認前に動かせる検査（型検査・lint・単体・DB統合・E2E・build・移行の適用/ロールバック/再適用・最新main互換性）は全て合格（§6）。

### 5.2 夜に必要な操作（最小）

1. `.env.local` に `GOLD_REVIEW=on` を1行追加 → `npm run dev` → ログイン → `http://localhost:3000/dev/gold-review` を開く。
2. **タブ「LivePocket 12ページ（合成R1）」**: 12ページを順に確認（公式ページを別タブで開いて、店舗・商品・締切（年を含めて）・応募単位・引用）。確認・除外・保留のたびに次のページが開く。全て済んだら「R1用のgoldを書き出す」。
3. （任意・推奨）**タブ「実投稿のリンク先」**: ページの少ない投稿から先に確認（投稿の全ページを確認した投稿だけが案件になる）。まず先頭の6投稿（計14ページ）。済んだら「実投稿のgoldを書き出す」。
4. `node scripts/compare-phase2.mjs r1-build`（合成）→ `node scripts/r1-readiness.mjs` → ブロッカーが無いことを確認 → `node scripts/compare-phase2.mjs plan` の見積を見て、**金額（総額・1件）と確認文 `APPROVE C <総額>JPY` を決めて指定**。実投稿のR1は `--dataset=real`（`real-validate` → `plan`）。

### 5.4 費用（実行直前に再計算）

R1（links・12案件・2アーム・各3項目）の期待費用は**約37.4円**（保存済みの実測平均: 調査ターン0.163円・判断0.148円。使用モデル Haiku 5.5）。最大予約: 1件あたり最小1.2円〜最大3.6円・1回の最悪0.585円・関門の上限は総額60円・1件5円。**固定の承認額ではなく、実行直前に `plan` と `readiness` が、対象件数・モデル料金・最大予約額・呼び出し数を再計算して表示する**。停止条件: 総額/1案件の予算・画像枚数・最大取得回数/時間・認証/利用上限の即停止・連続失敗・実行ロック。**金額の明示承認が無い限り、有料の実行はしない**。R1は小標本（案件12）であり、改善を断定しない。誤登録・他店舗の混同が1件でも出たら停止・原因修正・無料の回帰試験（再実行は追加承認）。

## 6. 実測指標（長期の完成度）

主観的な点数（40点・72%）は実測値として使わない。`measured-metrics.ts` が、次の12項目を、**測れたか（値・分母・状態）を明示して**集計する（`readiness` が表示）: 短縮リンクの展開率／応募機会の再現率／誤登録率／誤統合・誤分割／1機会あたりの実費／独立goldの対象数／未確認の割合／再調査の回収率／AIの根拠参照率／繰り返し誤り／既存履歴の保護違反／実AI試験の数。**モック・合成の結果は、再現率・誤登録率・費用に入れない**（実AIの結果だけ）。

現時点の実測: 短縮リンクの展開率 **94.1%（n=85）**。それ以外は未測定（実AI・gold確認が未実施）。

## 8. 残存リスク・未実施

**ユーザーの権限／承認が必須**: gold の人による確認（夜）／R1の金額承認／本番へのDB移行（120〜122）／R2〜R4の有料試験・本番移行。

**外部制約**: 実投稿は livepocket.jp のみ（サイトの偏り）。t.co の robots.txt は解決専用の利用でも「ルートを許可しない」設定（今回の1回の実施は指示書の範囲内。以降の追加取得は、利用条件の確認を含めて利用者の判断が要る）。取得対象外12件の宛先は今回は未記録。HTML未保存のため、受付枠などの構造は今回の取得分には無い。

**未発見のリスク（ゼロとは主張しない）**: 実投稿の取得は1回・単一サイトで、取得の失敗の理由（robots・403・JS・ログイン壁）の実例が無い（模擬テストでのみ確認）／確認画面は1ユーザー・1ファイルの運用で、同時編集の競合制御は無い／実AIの読み飛ばし・誤登録の実測は未実施。

## 9. 次の工程

1. gold確認（夜）→ `r1-build` → `readiness` → 金額承認 → R1（合成）実行 → 事実ベースの報告。
2. 実投稿の少数案件のR1（確認が済んだ投稿だけ）。他の系列・店舗・応募形式の実投稿の追加（収集の運用で蓄積。HTMLと取得対象外の宛先も記録）。
3. R1の結果を見て、R2（全文）→R3（画像）→R4（経験ヒント）→未知店舗/系列の発見力・登録精度・自己改善・運用費用の評価へ。
