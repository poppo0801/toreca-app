# Stage 10R 報告書: 自由なAI推論・ヒントの適用検証・応募先ページの実取得

## 0. 結論（先に）

- **本番DB・PR #36/#46のマージ・本番デプロイ・cron有効化・既存データの書き込みは行っていない。** ローカルのプレビュー・評価まで。マイグレーションの追加なし（未適用は 108〜113 のまま）。
- 参考知識を「結論の推奨」から**判断観点（ヒント）**へ作り替え、AIが**採用・反論・無視・再解釈**できる構造にした。ヒントの採否は判断・検証に影響しない（テストで固定）。未想定の方式（`other`）も提案でき、暫定候補として保持する。
- **偏りの検証（実測）**: 店舗選択式への集中は、**ヒントが原因ではなかった**。ヒント無しでも 12件中 6件が store_select（関連ヒントありは 7件）。一方、**無関係なヒントを混ぜると結論が 7/12 件変わった**（AIは30回「無視」と答えたのに、結論は one_form_one へ動いた）。**ヒントの選択（関連するものだけを少数渡す）が誘導を防ぐ要で、プロンプトでの注意だけでは防げない**。
- **応募先ページの実取得**: 15回取得して、成功 4（LivePocket・親投稿に付いていた展開済みリンク）、失敗 11（項目の短縮URL t.co は **すべて robots で拒否**。回避しない）。成功した4ページは、**全て別の店舗のページで、この項目の根拠にできなかった**（対応検査で 9件の対応づけが全て scope_mismatch）。**応募先ページから直接の根拠は得られていない**（0/12）。
- 対応検査を入れる前の再推論では「直接の根拠 9件・one_form_one 9件・欠落つき候補 2件」と出たが、**別店舗のページを項目に誤って結びつけたもの**で、採用しない。検査で防げたことを実測できた。
- 最終（同一の51機会・55項目）: 除外 38・確認待ち 12・暫定候補 1・自動登録 0。**応募単位の不明を解消しても自動登録は増えない**（他の阻害要因を §6 に分解）。
- **人の確認は 0件**。推論の変化を正解率とは取り違えない。

## 2. 偏り検証（同じ12件・同じ入力。ページ観察なし）

| B 関連ヒントのみ | 7 | 3 | 1 | unknown 1 | 全て low |

- ヒントの採否: B では adopted 1・他は未使用に近い（選ばれるヒントが少ない）。
- ユーザー提供の経験則（架空の対立仮説ケース 10件・テスト用途。**実測の正解率に混ぜない**。「望ましい方向」は私の設定）:

## 3. 応募先ページの取得（実測）

10Qで取得が0件だった原因: 保存済みの一覧項目に応募リンクが付いていなかった。10Rでは、保存した親投稿の展開済みリンクと、項目の短縮URLを辿った。

| 項目 | 結果 |
| --- | --- |
| 取得回数 | 15（上限 60） |
| 成功 | **4**（親投稿のリンク: livepocket.jp。公開・robots許可） |
| 失敗 | **11**（項目の短縮URL（t.co）。**全て robots**。回避しない） |
| 応募先ページの観察が得られた対象 | 9/12（親投稿のリンク経由） |
| **この項目の店舗に対応するページ** | **0/12**（対応づけ 9件が全て scope_mismatch） |
| 直接の根拠として使えた | **0** |

- 原因: 親投稿に付いていたリンクは**親投稿の全項目に共通**で、実際には**特定の1店舗のページ**だった。他の店舗の項目に当てはめると誤る。AIも「ページは別店舗の関連」と観察する場合があったが、**別店舗のページから one_form_one を導く推論が出た**（検査前の再推論で9件）。→ `pageMatchesItem`（ページの文面に項目の店舗名が現れるか）で対応を検査し、対応しないページは根拠として渡さない。
- 取得の安全: 既存の安全な取得（SSRF・robots・リダイレクト・サイズ・時間・間隔）を使用。ログイン・CAPTCHA回避・応募送信なし。取得できない場合は「未確認」で、推測で埋めない。
- 改善の見込み: 項目ごとの応募先は、**収集時にXの投稿データから短縮URLの展開結果（`linkMap`）を保存**する（実装済み・新規収集分から）ことで、t.co を辿らずに得られる。旧データでは取得不能。
