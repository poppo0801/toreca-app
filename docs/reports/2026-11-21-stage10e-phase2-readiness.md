## 3. 静的検証できたこと／設計上の懸念
- **SQLの読み取り専用性**: 静的検査で書き込み・複数文・他表・禁止列を拒否することをテストで確認（11パターン）。ただし静的検査は**文字列の検査**であり、DB側の保証ではない → 実行時は `--read-only`（DB側強制）も併用する設計。**接続コードの実装後に、読み取り専用が実際に効くことをローカルDBで確認する必要がある**（未実施）。
- **認可方式の実現可能性**: 既存の `npm run prod` 経由・運用用接続の再利用で実現可能（新しい権限・鍵は不要）と判断。ただし本番への接続は一切試していないため、**接続・権限は実機で未確認**。
- 懸念1: `last_good.evidence.text` は保存時に伏せ字済みだが、日本語の氏名・住所は規則で拾いきれない → 人の全件確認を必須にしている。懸念2: 評価時のプロンプトに含めるのは本文のみで、URL・IDは送らない（コード上の実装は評価実行コードの接続時に確認）。懸念3: 費用見積もりの旧抽出単価（約0.3円/件）は過去の概算で未実測。

## 4. 費用
- 新方式（30件）: 1回の最悪 約0.55円×最大3回＝1件 約1.65円 → **最悪 約49.5円**。典型は 約0.2〜1.0円/件（r3・r4の実測）→ 約12円（見積もり）。前回計画の「約0.28円×3回」は過小だったため訂正。
- 総額50円・1件3円の案: 旧抽出（約9円・概算）を含め新方式に35円を配分すると、**新方式の最悪は21件までしか保証できず**、最悪時は後ろの事例が予算停止で未実行になる（未実行として報告する）。構造のみの比較なら新方式に50円を割り当てられ、最悪でも30件に収まる。
