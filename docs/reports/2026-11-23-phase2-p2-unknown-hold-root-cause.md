## 1. 最優先: 検索ツールの配線不具合（再現・確定・修正）
### 1.1 コードの経路（P2 の実行時に存在した状態）
`proposal-real.real.test.ts` → `runRealProposals` → `generateProposalsForCandidate`（`tools.search` に検索を設定）→ **`runXPostReplay` が `cachedTools(a.tools)` を `runResearch` へ渡す** → `cachedTools` は `now` と `fetchPage` だけを返していた（**`search` を返さない**）→ 調査ループの `searchAvailable: !!args.tools.search && L.maxSearches > 0` は常に **false**。
### 1.2 再現（修正前）
`src/lib/judgment/xsource/root-cause-p2.test.ts`（偽の検索プロバイダーを注入した `runXPostReplay` の通し）を修正前に実行: **4件中3件が失敗** — 調査AIに届く `searchAvailable` が **false**（期待 true）、`cachedTools(...).search` が **undefined**、検索の実行が **0回**（期待 1回）。検索なしの経路（OFFのまま）の1件だけが通った。
### 1.3 修正と回帰防止
- `cachedTools` が `search` を引き継ぐ。**同じ投稿内の同じ検索語（空白・全半角の違いを除く）は2回実行しない**（2回目は費用0。有料検索の重複防止）。検索ツールが無ければ従来どおり OFF。上限（`maxSearches`）・予算の予約・重複禁止・結果の安全化（`makeSearchTool`）は調査ループ/ツール側のままで、**予算が小さいときは検索を実行しない**ことも確認。
- 回帰テスト: 単体4（再現・OFFのまま・キャッシュ・上限/予算）＋**DB結合（real-run → generate → ループの実際の通し経路）**: 検索が実行され、検索結果のページへ進み、登録案に `viaSearch=true`・停止理由 `…|searched:1`・検索を含む費用が残る。検索ツール無しは `search_not_offered`、提示されたがAIが使わない場合は `offeredNotUsed` として**区別して記録**。
### 1.4 影響範囲と、なぜ見逃したか
- 影響: 収集候補の経路（Phase 2 の `proposal-real`）。**Stage 10X の B2 の評価ハーネス（`evaluateB2`）は `runResearch` を直接呼ぶため影響を受けておらず、B2 で検索が4/4実行された事実と整合する**。
- 見逃した理由: Phase 2 の統合テスト・P2 の事前確認は、検索を渡さない経路か、`runResearch` 直呼びで検証しており、**検索を渡した `runXPostReplay` の通しがテストに無かった**。P2 では「検索ツールは使える状態（コードで確認）」と記述したが、**確認したのは `runResearch` 内の式であり、`cachedTools` を経由した実際の値ではなかった**（誤り）。
- 観測の限界: P2 実行時のAI入力（プロンプト）のログは保存していない。**`searchAvailable=false` だった事実は、コード経路と再現から確定**であり、実行時の直接観測ではない。今後は `searchOffered` を調査結果（登録案の停止理由 `search_not_offered`／`searched:N`）として**事実として記録**する。
### 1.5 「検索を常に実行する固定ルール」にしていない／無駄打ちの対照
- 検索するか・何を検索するかは**AIが判断**する（固定の実行ルールなし）。**URLが与えられている項目では検索しない**よう調査の指示に明記（無駄打ちの抑制）。**上限は1回/項目・同じ検索語は実行しない・予算の予約**がコード側の安全弁（最悪値: 1項目あたり検索約¥1.9）。
- P2 後に追加した「検索が使えるなら先に検索」の指示が過剰検索を生むかは、**実AIでのみ確認できる（未検証）**。次の測定で `search.used`（URLあり項目の実行数＝0が期待）を記録する（§9）。
