## 0. 要約（結論）

1. **現行は「固定ロジックが骨格・AIは1回の抽出だけ」の構造**。本番で動く収集は、1告知＝AI1回の読み取り（`record_lottery`）の結果を、約15種類の固定ロジックが連鎖して加工・判定し、登録の可否まで決める。9H系の「調査エージェント・判断履歴・統合」は、**本番ではフラグにより無効**（`COLLECT_UNIFIED`・`COLLECT_INVESTIGATE` が未設定）。9Hで作った自律的な仕組みの大半は、通常の収集経路に入っていない。
2. **店舗選択式の誤判定の主因は、AIの判断より後ろの固定ロジック**。`run.ts` の複数の固定の分岐（`detectStoreSelect` ほか）が、AIの応募単位（`apply_unit`）と無関係に形式を書き換え、しかも**「店舗選択式へ寄せる一方向」の補正しかない**（選択式→独立への補正がない）。反対に、店舗を特定できない告知は「店舗なしの固定カード」として登録され、後から同じURLの店舗選択式カードが別に作られる。本番データで **同じ情報源URLに「店舗選択式」と「店舗なしの固定」が併存する組を4組確認**。
3. **重複判定は複数経路で、別々の基準を使う**（候補のキー・`findDuplicates`・DBの一意キー・事後整理・結合）。見逃しの主因は「店舗の表現（固定／選択／未確定）が違うと別扱い」「商品・系列のIDが無いとキーが作れない」。誤統合のリスクは「同じ店舗・同じ商品なら期間が違っても高確度」「同じURLだけで高確度」。
4. **系列の同一性は、3種類の正規化（`chain-normalize.ts`・`lottery-match.ts` の旧辞書・DBの `norm_name`）が別々に存在**し、判定不能なときは**仮登録の新規系列を作る**。本番は系列101件のうち**61件が仮登録**（抽選142件＝57%がそれらに属する）。別名の登録は13件・合併履歴は5件のみ。
5. **AIに必要な情報が渡っていない例**: 一覧カードから店舗名「とれじゃらす別館」まで分かっているのに、系列が空で「系列を確実に特定できません」として保留（本番のpending 67件中26件）。
6. **9Zの原文保存は、現状は再調査（reeval）でしか使われない**。通常の収集の解析・重複判定・再確認には、まだ使われていない。

## 3. AIプロンプトと固定ロジックの役割

**AIに渡すもの**: X投稿＝本文＋引用元＋添付画像（縦長は分割）＋リンク先本文。URL＝ページ本文のみ（ページ内の画像は読まない）。取得制限時＝一覧カードの文（二次情報）。**9Hの文脈（アカウントのプロフィール・過去の人間の判断）は `withCtx` が本番で無効のため渡らない。**

**プロンプトの要点**（`ai/provider.ts:57-`）: 告知に書かれたことだけを記録・推測しない／日付は年月日時分を別々に（年は補わない）／商品名は表記どおり・数量は別項目／系列と店舗を分ける／命令文はデータとして扱う／根拠の原文（80字以内）を `evidence` に／1件の抽選として複数画像をまとめる／プレゼント企画は非抽選／矛盾は `warnings` へ。

**AIの出力スキーマの特徴（問題に関わる点）**:
- 店舗は **スカラー1つ**（`store_name`）。複数店舗の告知は「1件1店舗」にしか構造化できない。複数店舗は `selectable_stores`（配列）と `apply_unit`（`store_select`／`store_independent`／`per_product`／`single`／`unknown`）で補う設計。`apply_unit` の説明は「『1店舗のみ応募可』の記載だけで店舗選択式と断定しない」。
- `single` は「その他」に、`per_product`/`unknown` は**判断なし**に写像される（`understanding.ts:44`）＝AIの判断が使われない。
- 抽選の**同一性**（既存と同じか）はAIに聞いていない。固定ロジックのみ。

**固定ロジックが判断する範囲**: 事前の関連・地域・期限／マスター照合／**応募形式の確定（AIを上書きし得る）**／重複／完全性の等級／登録可否／再調査の間隔。AIの自己評価（confidence）は登録可否に使わない（設計の安全原則）。

## 4. 優先課題の根本原因と実例

### 4-0. データと限界
- 使用データ: 本番の読み取り専用スナップショット（`backups/masters-9h3s/snapshot-prod-2026-11-19T11-44-38`）。抽選249件（有効220）・候補2,359件・系列101・店舗188・商品55。**9Xのデータ修正（11/19 11:44）直前の状態**。
- 限界: ①候補には **AIへ渡した入力本文は保存されていない**（9Z以前）。「情報源」は候補の `title`/`queued.card`/`context` と情報源URLまでしか辿れない ②`draft.input` が「AIの抽出＋固定ロジックの加工後の入力」で、**加工前のAIの生の出力は保存されていない**ため、どの段階で変わったかは `understanding.trace`（79件のみ）や各種の注記・`summary` から**推測**する ③本番の収集設定・環境変数は読んでいない（フラグの有効/無効はコードとデータの痕跡から判断）。

### 4-1. 【最優先】店舗選択式の誤判定

#### (a) 現行の判断の仕組み（コード確認済み）
1. AIが `apply_unit` と `selectable_stores` を返す（`provider.ts:159-160`）。
2. `decideApplyUnit`（`understanding.ts:52-74`）: 手動の分類が最優先。AIが答えなければ固定の `judgeForm` の結果。AIの答えがあっても、**固定ロジックが「構造の根拠あり・高信頼・AIと不一致」なら固定が上書き**（記録は残る）。
3. `judgeForm`（`lottery-form.ts:118`）: 正規表現のシグナル（`SELECT_FIELD`「店舗を選択…」、`PER_STORE`「店頭にて応募…」、系列知識の制限文言＝`cross_store_limit`）。両方ヒットは「未確認」。
4. `run.ts:859-896` の**固定の書き換え**:
   - 分岐A: `store_select` と確定したら `select_on_apply`（店舗はプレースホルダ）へ。
   - **分岐B（`run.ts:873`）: 店舗が特定できていなければ、`detectStoreSelect`（`store-select.ts`）が1つでも当てはまれば選択式にする。AIの `apply_unit`・手動の分類・`judgeForm` を見ずに実行される**。パターンは `judgeForm` より緩い（例: `応募(時|の際).{0,10}(店舗|店)`）。トレカキャピタルは系列名だけで強制選択。
   - 分岐C: 店舗を1つ特定できても、`judgeForm` の店舗選択欄シグナル（知識・手動・店別ページの情報なしで再実行）があれば選択式へ。
   - 9H-3Gの推定（フラグ有効時のみ・本番は無効）、`decideRegistration` の `storeSelectDefault`（系列の既定）による強制（`attention.ts:187`）。
5. **選択式から独立への戻す補正は、収集・統合・整理（9F-6）・AI統合（`consolidate_lotteries`）のいずれにも無い**（すべて「固定→選択式」の方向）。
6. 複数店舗名が1つの店舗名になったものは `looksLikeMultipleStores` で確認待ち（C）に止める（`attention.ts:153`。語尾が「店/館」で区切りが `、,・/` のものに限る）。

#### (b) 誤分割・複数カードが起こる段階
- **構造的な要因**: 1回のAI呼び出し＝1カード、店舗は1つだけ。複数店舗のまとめ投稿は「最初の店舗」の固定カードになり、**店舗別の別投稿がさらに別カードを作る**（別々の候補が別カードを作るだけで、1つの告知を分割するコードは無い）。
- **自己強化**: 最初に誤って店舗別カードができると、`hasSiblingStorePages`（`understanding.ts:79`）が「同系列・同商品で別店舗・別URLの抽選あり」と見て `perStorePages` を立て、2件目を「店舗別独立」と補強する。
- 後から選択式と分かっても、**既存の「店舗なし固定」カードは自動では選択式カードに統合されない**（統合は手動、または手動のAI再調査＝`consolidate_lotteries`）。

### 4-3. 【第3優先】系列の同一性

- **正規化の仕組み（3系統）**: ①`chain-normalize.ts`（NFKC・法人格・「通販/オンライン」語尾の除去・同義語辞書9件・独立系列＝イオン系の4種を先に判定。部分一致では寄せない）②`lottery-match.ts` の旧辞書（別表で内容が少し違う）③DBの `norm_name`（`save_lottery_tx` 内の正規化）。**3つの基準が一致する保証はない**（影響は推測）。
- **照合**: AIの系列名 → `matchChain`（完全一致／別名／**部分一致で比率0.75以上なら選択**／語尾付き＝別名／類似度0.7は候補のみ）→ `resolveMasterAndLearn`（確認済み／AI推定の別名・読み・複合名。曖昧は候補）。X投稿は表示名・プロフィール・URLから系列を補正（`identifyPostAuthor`・`corroborateIdentity`）。
- **新規系列の作成条件**: 上記で特定できないとき、`save_lottery_tx` が**仮登録（`is_provisional=true`）の新規系列を作る**（`norm_name` 一致がなければ）。登録判断の「C: 系列を確実に特定できません」は **AIが系列名を空で返した場合**にだけ止める。AIが何か系列名を返せば、未登録でも注意付きで自動登録され、仮系列が増える。事例: 「トレカステーション」は注記「未登録の系列」で自動登録された。
- **データ**: 系列101件中**仮登録61件**（抽選142件＝57%）。別名13件・合併履歴5件。正規化後の同名・部分一致の重複ペアは、イオン系の1組のみ（独立系列として意図的）。つまり**表記揺れによる系列の分裂は、この時点では目立たない**（重複系列の証拠は薄い）が、仮登録が多く、確認・整理の運用が追いついていない（**問題は「分裂」より「未確認の系列が大量に確定扱いに近い状態で使われている」点**）。
- **AIと固定ロジックの役割**: AI＝系列名を文字列で抽出するだけ。同一性の判断は固定（辞書・類似度・別名）。AIに「この名称は既存のどの系列か」を判断・調査させる経路は、9H-3S/9H-3S-3（名寄せ・名称判定）として存在するが、**手動の再評価画面経由で、通常の収集には接続されていない**。
- **系列で保留になる実例（本番pending 67件中26件）**: AIが系列を空で返した候補。例: 一覧カード「とれじゃらす別館 11/22 20:00まで 大阪府…」（t.coの応募ページ。取得制限→一覧カード文から読み取り）で、**AIは店舗「とれじゃらす別館」・大阪府・商品はマスターと一致したが、系列は「判断できない」**と空欄。固定ロジックは「系列が空」で確認待ちに止めた。店舗名から系列を推論するのは、AI（または店舗マスターに既にある店舗名から固定で）できる情報だが、どちらも行われなかった（原因の特定は推測）。

### 4-4. その他の課題

**商品名の誤取得（原因）**:
- AIの商品名は表記どおり。固定の `splitProductName`（装飾・日付・店名の除去）→`matchProduct`（型番→名称キー→別名→部分一致で**比率0.75以上なら採用**）。`productKey` が「MEGA」「拡張パック」を除去するため、**別商品が同じキーに潰れる**恐れ。型番の正規表現（`[A-Z]{1,5}\d{1,3}`）が商品以外の語に当たる恐れ。
- 9H-3S の `master-identity/product-identity.ts` は型番・数字・版・BOX/パックの食い違いを別商品とする**より厳密な基準**だが、収集の照合（`matchProduct`）とは**別系統**で、二重の基準が存在する。
- データ: 候補の商品照合 `exact` 1,163／`alias` 46／`code` 5／**`partial` 176／`none` 356**。`none` の多くは他TCG（除外対象）だが、`partial` には「ポケモンカードゲーム 30th CELEBRATION カードセット 抽選販売」→マスターなし（告知の語尾「抽選販売」が商品名に混入）のような例がある。商品名に「購入権」「購入券(抽選)」「抽選販売」といった**販売形態の語が混入**して照合に失敗する傾向（例: 「…ハドウシーカー BOX 購入権」→ `partial`・マッチなし）。確認済みのマスター商品は55件のみで、未登録商品が `PRODUCT_UNREGISTERED` として**常に人間へ回る**設計も、確認待ちの増加要因。

**情報不足で候補が本登録に進めない原因**（本番pending 67件の理由＝系列26・店舗17・受取方法10・取得制限8・通販7など）:
- 「確認待ち（C）」の条件は、系列・店舗・商品の未特定、重複疑い、矛盾、締切の14日超の食い違い等（`attention.ts`）。この多くは**固定の関門**で、AIが追加調査して解消する経路が本番に無い（9Hの調査は無効）。
- 再調査は「同じ入力を再解析」「30分〜24時間間隔の再評価（最大6回）」が中心で、**新しい情報源を探しに行かない**。締切が24時間以内なら調査せず人間へ。
- 自動登録の中身: 自動登録171件のうち、ランクC=66・A=59・B=17・E=4。**店舗が不明のまま自動登録**＝52件（`missing: 店舗`）。つまり「店舗不明」は、片方では止められ（pending 17件）、片方では通っている（52件）＝**条件が一貫していない**（系列や商品の特定状況の組み合わせで決まる）。

**正しい情報源URLがあるのに読み取りきれない原因**:
- X・t.coは取得できない（9X: 確認不能55件中52件）。本文は初回のX API取得時にしか手に入らず、**原文を保存していなかった**（9Zで保存を開始）。
- URL入力では**ページ内の画像を読まない**（画像に応募期間が載るページ）。LivePocket等は応募サービスの表示と主催者本文が別（プロンプトに注意書きあり）。
- 取得制限（robots）では一覧カード文（二次情報）に落ちるため、**全項目が「二次情報から補った」注記**になり、日付などが空欄になる（上記の例では「告知が途中で切れている可能性」「応募開始日・当選発表日などは読み取れませんでした」）。

## 6. 改善方針の比較（今回は方針を確定しない）

### 案A: 現状維持（運用で補う）
- 内容: 現行構造のまま、確認待ち・併存カードを人が整理。
- メリット: リスク最小・既存の使い勝手を維持。
- デメリット: 併存・仮系列・形式未記録が増え続ける。人手の負担が残る。
- 想定効果: 変化なし。

### 案B: 部分改善（固定ロジックの整合化・AIへの情報追加）
候補（組み合わせ可）:
1. **応募形式の判断を1か所にまとめる**（`decideApplyUnit` を唯一の決定点にし、`detectStoreSelect`・系列既定・推定は「入力シグナル」に格下げ。手動が常に最優先）。**選択式⇄独立の双方向の補正**を持たせる。
2. **店舗が特定できないカードを作らせない**（店舗なし固定は確認待ちか「応募時に店舗選択」候補に。または原文からAIが再確認）。
3. 重複判定の基準を統一し、**店舗の表現が違っても同じ情報源URL・同じ企画なら重複候補として提示**（誤統合を避けるため自動統合はしない）。
4. 系列: 店舗名から系列を補う（店舗マスター・同URLの既存カード）／正規化を1系統に統合。
5. AIの入力に、同系列の既存カード・店舗一覧・保存済み原文を追加。
- メリット: 既存構造を保ち、段階的・低リスク。上記の実例の多くに直接効く。9Zを活用しやすい。
- デメリット: 約15工程の固定ロジックの整合化は広範囲で、回帰テストが重い。個別の正規表現は増えやすい（例外の積み上げ）。
- リスク: 判断の移動で既存の自動登録の挙動が変わる。誤統合・誤分割のバランス調整。
- 想定効果: 併存カードの新規発生の大幅減（事例1〜4型）。系列の保留の一部の解消。AI費用は小増。

### 案C: 構造的な再設計（抽選の「案件」を単位にAIが判断する）
- 内容: 収集は「情報源の取得・原文の保存」まで、**判断は案件（同一抽選）単位でAIが担当**し、既存カード・店舗・系列・原文を見ながら「同じ抽選か／応募形式／登録すべきか／不足は何か」を判断（9H-3B〜3Eの案件ファイル・統合の設計を本番へ）。固定ロジックは「検証・安全（形式・手動値の保護・費用上限・履歴）」に限定。
- メリット: 複数投稿・複数店舗・LivePocket等の「構造」を、一貫した1つの判断で扱える。重複・形式・系列の判断の重複実行が解消。AIの自律性が最大。
- デメリット: AI費用と遅延が増える。実装・移行が大規模。判断の再現性・説明の仕組みが必須。
- リスク: 誤判断が自動登録に直結（検証層・保護の設計が要）。移行期は二重運用。**9Hの実AI評価では精度向上が人間評価待ちで未確定**（改善効果は未証明）。
- 想定効果: 理論上最大。ただし根拠となる実測が現時点で乏しい（9H-3K〜3Lの評価は小規模）。
