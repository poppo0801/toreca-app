## 1. 要約
- **一覧の焦点**: 一覧投稿から、対象案件に関係する項目だけを判断へ渡す方式に変更。10Hで「機会10個に展開」「4個に展開」「3個に展開」だった対象が、対象に即した 1〜2 機会になった。特定できない2件（登録に店舗が無い／同一内容の項目が並ぶ）は、**推測で結び付けず判断しなかった**（理由を記録）。
- **出力途切れ**: 一覧を小さな塊（最大6項目）に分けて抽出した4件の長い一覧（計78項目）は、**すべて完走**（失敗0・再分割の発動0）。10Hでは最長の一覧が途切れて失敗していた。分割失敗時に半分に割って再試行する仕組みも実装（単体テストで確認。実運用では発動せず）。
- **暫定ラベルとの比較**（AIが原文のみから独立に付けた17件・人の確認なし）: 構造が一致 **10/10**（10H: 6/10、誤り3→0）、対象の機会数が一致 **11/11**（10H: 6/11）、特定不能とラベルした2件は推測せず（10H: 誤って確定した件は0だが、機会を過大に出力）。**ただし焦点ロジックの2か所をこのラベル集合の結果を見て修正したため、開発用の集合での数値であり、独立した検証ではない**（§5）。
- **費用**: 追加 **¥25.13**（上限50円）／AI呼び出し 59回（上限90）／公開ページ取得 13回（上限60）。
- **取得品質**: 保存原文の `links`（X投稿内の展開済みリンク）に公開ページが多数あることが判明。10Hは使っていなかった。取得して再判断すると、6件中3件で改善（不明→確定、高重要度の質問の減少）、悪化なし。

## 5. 暫定ラベルとの比較（精度の主張はしない）
- **ラベルの作り方**: 保存された公開告知の原文だけを読み、既存の登録値・AIの出力を見ずに、AI（Claude Code）が独立に付けた（17件: 構造・対象の機会数が確定できるもの10〜11件、特定不能/曖昧2件、判定不能3件、部分的1件）。**人の確認はしていない**ため、「正解」ではなく暫定ラベル。ラベルと原文の対応は、Git管理外（`eval/real-data/gold-10i.json`）に保存し、原文・IDは含まない。
- 結果（10H → 10I）: 構造の一致 6/10 → **10/10**（誤 3→0、判断不能 1→0）。対象の機会数の一致 6/11 → **11/11**。特定不能・曖昧（2件）は、10Iは判断せず／高重要度で保留。判定不能とラベルした3件（本文が断片）は、10H・10Iとも unknown か高の保留。
- **限界（重要）**: 初回の10I実行ではラベルとの一致が 構造9/10・機会9/11 で、焦点ロジックの2つの不具合（先頭8文字が同じ別項目を巻き込む、登録商品が複数でも1項目に絞る）が見つかり、**ラベル集合の結果を見て修正した**。したがって上記は開発用の集合での数値で、未知のデータでの精度ではない。ラベルは17件と少なく、AI作成で人の確認がない。**正解率は主張しない**。確認できたのは「ラベルと矛盾する確定が出ていない」「特定不能な対象を推測で確定していない」まで。
- 新しい未知の一覧（別の件）での検証と、人による少数ラベルの確認が、限定運用の前に必要。

## 6. 収集原文・画像の取得品質の調査
**保存原文が短い原因**（保存済み179件。件数のみ）:
- 取得方法: X公式API 107・X埋め込み 19・公開ページ取得 41・一覧カード 2。文字数の中央値は X API 240／X埋め込み 171／**公開ページ取得 107**。120字未満は 公開ページ取得 22/41・X API 9/107。公開ページ取得の本文が短い（ページ本体ではなく、一覧の要約・見出し・「応募する」等のボタン周辺しか保存されていない例が多い）のが主因。
- 保存上限3,500字に達したものは0件（上限が原因ではない）。
- 「画像・添付・詳細はこちら・アプリで確認」等の参照を含む原文が 22/179。
**既存の保存情報にある取得可能性**（今回の書き出しで初めて確認）:
- `links`（X投稿内の**展開済み**リンク）が 92/179 件にあり、そのうち公開httpsの外部ページが 87件（主に LivePocket 87、ポケモンセンターオンライン 21 など）。**10Hは使っていなかった**。X・t.coだけでなく、投稿に載っていた公開の応募ページを直接取得できる。
- 画像: 70/179 で画像を取得済み（`imageStatus=fetched`）、1件が一部のみ。画像から読んだ内容は保存原文の本文に入っていない（抽出時のAIが画像を読んでも、後の再判定には渡らない）。
**今回実装・実測した低リスクの改善**: 保存原文のリンクを取得候補に加えた（既存の取得部品・robots尊重・SSRF防御・X/短縮URL除外・漏洩検出。新たな外部サービス・有料APIなし）。対象10件のうち、取得できたのは6件（成功8ページ・漏洩検出で除外5ページ・失敗0）。再判断（6件）の結果: 不明→確定 2件（店舗選択式など）、高重要度の質問が減った 2件、悪化 0。費用 ¥4.70。ただし**リンク先の取得で、応募ページの個人情報らしき記載を拾う検出が5ページで作動して除外**（安全側）。
**実装しなかった（別Stage・要判断）**: ①収集時に告知本文・詳細ページ・**画像から読んだ文字**を原文として保存（収集側の変更。画像の再解析は費用・著作権・取得元の配慮が要る）②X・短縮URLのみの36件は引き続き取得不能。取得できたと見なしていない。

## 7. 未解決の問題
1. 保留はほぼ減っていない（質問 66→64）。応募開始日・当落発表日の欠落（原文に無い）と応募単位の不明が主。取得（保存リンク・詳細ページ）で減らせるのは一部。

3. 長い一覧の抽出で、同一内容の項目が集約される可能性（別店舗の取りこぼし）。

5. 画像由来の情報が再判定に渡らない（収集側の改善が必要）。

## 8. 限定運用へ進めるか
- **進めてよい範囲（提案）**: 書き込みなしのシャドー運用（新方式の判断を記録するだけ）で、一覧の焦点・保存リンクの取得を試す。出力の完走・誤った機会の混入防止は確認できた。
- **進めない**: 登録・更新・統合・削除への反映。正解データでの精度測定（人が確認した少数ラベル、未知の一覧での検証）が未了。
- **次の順序**: ①人が確認する少数のラベルを作り、未知の一覧の対象で焦点ロジックを検証 ②収集時に保存リンクと詳細ページ本文を残す収集側の改善（別Stage・本番反映は別承認）③保留の質の確認（応募の可否・単位・締切に関わる高だけが残っているか）。
