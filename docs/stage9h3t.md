# Stage 9H-3T: 自律型AIの判断・調査・修正能力の強化

9H-3S 系（本番へ反映済み: main=edfd3a8・DB 106適用・`REEVAL_AI=on`）を引き継ぎ、①重複マスターの実整理 ②取得困難な情報源への代替調査 ③通常収集と再調査の判断の共通化 を進めた。**本ステージの変更は別ブランチ `stage9h3t`（別PR）。本番は未変更**。

## 1. 重複マスターの実整理（`merge_master`）
- 追加: `src/lib/server/master-identity/merge-service.ts`（マイグレーションなし）。
  - 統合元は**仮登録**のマスターだけ（人が確定した正式なマスターは動かさない）。統合先は非表示でない既存マスター。
  - 付け替える参照は、系列＝抽選・店舗・別名／商品＝抽選の商品行・別名だけ。購入・応募アカウント・ルール・コレクション・ボックス等の参照が1件でもあれば対象外（`unsupportedReferences`。既存の統合機能で人が実行）。統合先に同名の店舗がある場合も何も変更しない。
  - 応募・当選・購入の履歴は抽選IDで結びついたまま変わらない（付け替えるのは抽選が指すマスターだけ）。統合元は非表示（物理削除しない）、統合元の名称は統合先の別名（由来=AI・状態=推定）に残る。
  - **元に戻せる**: 移した行のID・統合元/先の名称を項目の `before_state` に記録（＝統合前後の対応関係）。取り消しは「今も統合先を指している行」だけを戻す（その後に利用者が変えた行には触れない）。
- 適用の条件（`reeval-service.ts`）: 確信度 high（確認済みの別名・表記揺れの一致）、または**AIが調べて同一と確認**（verdict confirm）したものだけ。音の近さだけの候補（`master_candidate`）は、AIが同一と確認したときに初めて統合の項目になる。
- AI再調査（`reeval-ai-run.ts`）: `merge_master`（medium）を名称判定の対象に加え、AIが同一と確認した重複候補を統合項目へ。コジマ⇔ノジマのような音の近い別会社は、AIが別と判断して統合されない。
- 画面: `/settings/reevaluation` に「仮登録の重複マスターを正式なマスターへ統合」の行（25件ずつ適用・全体を元に戻す）。

## 2. 取得困難な情報源への代替調査
- 既存の調査エンジンはAIが検索語・調査先を選ぶ（9H-1）。不足していたのは「取得できないと申告して終える」ことへの検証。
- 追加: `case-investigator/alternatives.ts`。AIが「続けられない」と申告したとき、**検証（AIの外側）が一度だけ**、取得できなかった情報源を具体的に示して代替の探索を促す（検索語・順序は指定しない／アクセス制限の回避・認証の迂回・推測での補完を禁じる）。
- 結果に `alternatives`（取得できなかった情報源・理由、代わりに到達できた情報源の層・種類・状態、根拠として採用された数、確認できなかったこと）を保存。画面の「AIの調査結果」に表示。
- 実AIの検証で、AIは検証の促しを待たずに自分で代替を探索していた（X取得不可→検索→まとめ記事・公式ニュースを取得）。ただし**ふるいち×ハドウシーカーの応募構造は確認できず（不明のまま）**。公式ニュースは別商品の告知で、まとめ記事は同一性を確認できなかった。

## 3. 通常収集と再調査の共通化（現状）
共通になったもの:
- 名寄せ・別名の学習・重複判定は同じ純関数（`master-identity/`）と同じ永続化（`alias-service`）。`saveLottery`（手動・自動収集・自律型AI）の共通入口が、AIが学習した別名・統合結果をそのまま参照する（結合テストで、統合後に「GIRAFULL」と観測した名称が新しい仮登録を作らず統合先へ解決されることを検証）。
- 店舗所在地は店舗マスターへの蓄積（再調査）を、通常収集の地域判定が参照する。応募構造の判定は同じ評価関数（`assessForm`）・調査エンジンを使う。
未接続のもの（残課題）:
- 通常収集の**実行中**にAIで名称を判定する経路（再調査の経路のみ）。収集が保留した名称（関連候補）を、再調査が後から調べる流れで補っている。
- AIの調査を定期実行に組み込むこと（費用が発生するため承認が必要）。
