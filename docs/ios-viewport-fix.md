# iPhone表示不具合・多重反応の修正（Stage 5I と 5J の間の別工程）

**実機（iPhone 15 Pro / iOS 18.4.1 のホーム画面PWA）では未確認。** 下の「事実」はコード・テストで確かめたこと、「仮説」は実機の診断で確かめる必要があること。診断モード（`?diag=1`）は実機で確認できるまで残す。

## 1. 下部メニュー・ボトムシートの表示欠け

### 事実（コードで確認）
- 前回の補正（c5c2910）は、`100vh − innerHeight` を `--vp-gap` として **起動・復帰・最初の `touchstart` の瞬間に1回だけ**測り、下部メニュー・ボトムシートの `bottom` を `−gap` にして下へ下げていた。
- 実機の診断（innerHeight=793 / 100vh=852）は「起動直後は表示領域が低く、操作すると直る」という状態を示す。表示領域は**イベントを伴わずに後から直る**ことがあるため、測った後に直ると `--vp-gap=59px` だけが残る。このとき `bottom: −59px` で、メニューとシートの**下側59pxが画面の外**に出る（再現テスト: `--vp-gap` を残すとメニューが表示領域の下端より下へはみ出す）。
- 既存の診断の判定（`verdict`）は、メニューが下端より**下**にはみ出す状態を検出できなかった（上に浮く場合だけ検出）。
- ボトムシート（`ui/sheet.tsx`）は同じ `--vp-gap` を使い、さらに**キーボードの高さを考慮していなかった**。`position: fixed` はレイアウト上の表示領域の下端に置かれ、iOSではキーボードが出てもこの領域は縮まない（`visualViewport` だけが縮む）ため、入力中は下側（保存・破棄ボタン）がキーボードの下に入る。

### 修正（共通部品側）
1. `useViewportGap`（AppShell）: 起動・復帰（pageshow / visibilitychange）・向き変更・resize・visualViewport・touchstart/touchend・focusin/focusout の後、**4秒間フレームごとに測り直す**（値が変わったときだけ書き換える。無条件の再描画はしない）。表示領域が直れば `--vp-gap` は自動で外れる。
2. `--kb-inset`（新規）: `innerHeight − visualViewport.height − offsetTop`（ピンチ拡大中・小さな差は0）。ボトムシートの `bottom` を `−vp-gap + kb-inset`、最大高さを `− kb-inset` にして、保存・破棄ボタンをキーボードの上に出す。**抽選登録だけでなく共通の `Sheet` すべてに効く**。
3. 下部メニューの背景を下へ40ぶん延長（`::after`）。表示領域が一時的に低くても、メニューの下に黒/空白の帯が見えない。
4. 診断の強化: 判定に **C（メニューが下端より下にはみ出し）** と **D（位置は正常だが、下側を別要素が覆っている＝`elementFromPoint`）** を追加。`--kb-inset`、開いているシートの下端と表示領域の差（`sheetGap`）、focusin/focusout の時点記録を追加。

### 仮説（実機で確認が必要）
- 「メニューの位置は正常に見えるのに下半分が黒く覆われる」は、**上記の古い補正が残った状態（C）**が有力。ただし、DOM上は正常でWebKitの描画だけが隠れる場合（D）は、PCのテストでは再現できない。
- 起動直後に「メニューが上に浮く」のは、起動直後の表示領域の高さの問題（A）で、補正が効くかは実機次第。補正が効かなくても、背景の延長で下に空白は出ない（メニュー自体は約59px上に出る可能性は残る）。

### 実機での確認手順
1. ホーム画面のアプリを開き、URLの代わりに設定画面などから診断を開始（またはSafariで `…/lotteries?diag=1` を開いてから、ホーム画面のアプリを再起動）。
2. 起動直後（触らない）に右上の「診断」→ コピー → 貼り付けて共有。以降、次の時点でも同じことをする: ①起動直後 ②最初のタップの後 ③数時間ぶりの復帰直後 ④登録フォームを開いて入力欄をタップ（キーボード表示中）⑤キーボードを閉じた直後。
3. 読み方: `→ C:` と出れば古い補正が残っている、`→ D:` と出れば別要素が覆っている、`→ A:` は起動直後の浮き。`navCoveredBy` と `sheetGap`（負の値＝シートが下端からはみ出し）も見る。
4. 実機で直ったことを確認できたら、診断（`useDiagEnabled` と設定内のスイッチ）を外す。

## 2. 多重反応

### 事実（コードで確認）
- **設定（表示切替など）の保存に競合があった**: `saveSettings` は即座に画面へ反映したあと、サーバーの保存・全データ再取得が終わると**その時点の「一時的な値」を無条件に外していた**。遅いときに続けて押すと、1回目の保存が終わった時点で2回目の結果が外れ、画面が1回目の値へ戻り、2回目の完了でまた変わる（＝遅れて何度も切り替わる）。また、保存が到着順に処理される保証もなかった。
- 二重登録されたイベントリスナーはなかった（click と touch の両方を処理している箇所はなし。`touchstart` はAppShellの測定とドラッグ用の `pointer` のみ）。シートのハンドルとミニバーは pointer/click をそれぞれ別の用途で使っており、重複していない。
- 保存・応募・購入済みの一部は、状態の更新前に続けて呼ばれると二重実行されうる箇所があった（登録フォームの保存、購入済み/手続き済みボタン）。

### 修正
- `saveSettings`: 一時的な値を ref で積み重ね、**保存を1件ずつ順に実行**し、**最後の保存が終わったときだけ**サーバーの値を取り直して一時的な値を外す。途中で巻き戻らない（テスト: 保存中の2回連続操作）。
- 表示切替・フィルター・凡例・マトリクス切替のボタンに**300msの連続操作ゲート**（ボタンごと。アプリ全体の一律のタップ禁止はしない）。
- `useBusy`（実行中の再呼び出しを ref で確実に止める）を、応募済み操作・購入済み/手続き済みボタンに適用。登録フォームの保存は `savingRef` で二重送信を防止（サーバー側は既存の冪等性: 応募は抽選×アカウントで一意、購入済みは1件のみ生成）。

### 未確認
- 実機でのタップの二重発火（イベント自体が2回届く状況）の有無。ログ取得用の診断は追加していない（コード上、二重登録は見つからなかった）。
