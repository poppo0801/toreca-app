# Stage 9H-3S: マスター自律学習・既存抽選の一括再構築

目的: 系列・商品の同一性判定を共通の仕組みにして、収集するほど精度が上がる（別名を根拠つきで自律学習する）知識基盤を作り、その基盤で既存の「全抽選」「抽選候補」「重複マスター」を整理できる状態にする。個別の系列名・商品名に依存する固定ルールは足さない。**本番は未変更（最終承認後に反映）。有料AI・Web検索は未実行（費用0円）。**

## 2. 実装（追加のみ。マイグレーション `20261224000106_stage9h3s.sql`）
- **共通の名寄せ `src/lib/master-identity/`**
  - `names.ts`: 名称の分解（括弧・区切り・空白・販売チャネル語）。複合名称は**全部の部分が同じマスターに当たるときだけ**その系列とする（部分一致では寄せない）
  - `resolve.ts`: `resolveName(kind, name, masters)` → matched／ambiguous／candidate／none。正式名・別名（確認済み／AI推定）・複合名称・表記揺れ。非表示のマスターへは寄せない。同じ名称が複数に当たれば寄せない。独立管理の系列（イオンオンライン等）は寄せない
  - `product-identity.ts`: 商品の署名（型番・数字・版の語・BOX/パック）。**食い違えば名称が似ていても別商品**。購入券・抽選・シュリンク・再販・ゲーム名は装飾（再販は商品として同一でも抽選は別なので `resale` を別に返す）。数量・入数は識別に使わない
  - `learning.ts`: 別名の学習判断（add_alias／hold_candidate／none）。根拠＝人の選択／公式情報／独立した複数の情報源／確認済みの名称の組み合わせ（複合）
  - `duplicates.ts`: 重複マスターの検出（確定した組＋根拠が足りない候補）。統合先は「仮登録でない→参照が多い→古い」
  - `display.ts`: 表示名（略称→導入前の別名→正式名称）
  - `reeval-plan.ts`／`snapshot.ts`: 一括再評価の計画（純関数）
- **サーバー** `src/lib/server/master-identity/`: `alias-service.ts`（名前解決＋学習の永続化。`saveLottery` から呼ぶ）、`reeval-service.ts`（計画の保存・段階適用・元に戻す・競合回避）
- **画面**: 設定 > データの整理（一括再評価）`/settings/reevaluation`。マスター編集に「略称」欄。別名一覧に「AI推定」の印
- **DB**: `chain_aliases`／`product_aliases` に `source`・`status`・`evidence`・`seen_count`、`chains`／`products` に `short_name`、`master_alias_candidates`、`master_reeval_batches`／`master_reeval_items`（RLS・service_role）。既存データは変更しない

## 3. AIによる別名の自律学習
1. 未知の名称 → 2. 既存の正式名・別名と照合（複合名称・表記揺れ込み）→ 3. 一意に決まれば既存マスターへ紐づけ（仮登録を作らない）→ 4. 根拠が十分なら別名を追加（`source=ai`・`status=inferred`・根拠つき）→ 5. 足りなければ関連候補（`master_alias_candidates`）として保持（同じ名称は件数だけ増える）→ 6. 次回以降の照合・重複判定で再利用。
通常の別名追加に人の承認は要らない。ただし:
- 人が確定した別名（`confirmed`）・正式名は上書き・削除しない（追加のみ）
- **AI推定の別名だけを根拠にした一致からは、別名を増やさない**（誤統合の自己強化の防止）
- 別のマスターの名称・別名と衝突するときは追加せず、衝突として保持
- 名称が近いだけでは追加しない。短すぎる名称・一般語は学習しない
- 影響の大きい統合（独立マスター同士）は、既存の統合機能（影響のプレビュー・履歴・復元）で利用者が実行

## 4. 略称の分離
| 役割 | 内容 |
|---|---|
| 正式名称 | マスターの基準 |
| 別名 | 同一性判定・検索・AI学習（表示には使わない） |
| 略称（`short_name`） | 利用者が設定する表示専用。商品・系列。AIは変更しない。長さ40文字まで |
一覧など狭い画面（現状は「継続中の抽選」）は略称を優先、未設定なら正式名称。詳細・編集・購入履歴は従来どおり正式名称。
**既存データの移行**: 別名を略称へ機械的に移していない。従来「別名の先頭」を表示していた画面は、略称が未設定の商品に限り、**導入前の別名（`source=legacy`）の先頭**を従来どおり表示する（AI学習の別名は表示に使わない）。利用者が略称を設定すれば、そちらが優先。Excelの取り込み列「略称」は従来どおり別名の列（互換性のため変更していない。残課題）。

## 6. 一括再評価の仕組み
- **計画**（何も変更しない）: `master_reeval_batches`／`master_reeval_items` に、対象・処理・リスク・理由・根拠を保存。進捗は項目ごとの状態（proposed／applied／skipped／failed／reverted）
- **適用**: 区分ごと・1回25件（最大100）。適用の直前に、対象が今も保護されていない・状態が計画時と同じことを再確認（★や応募が付いていれば適用しない）。同じ項目は二重に適用しない（一意制約＋状態）。失敗しても他の項目に影響しない。通常の収集（従来・自律型）の実行中は適用しない
- **差分**: 適用前後の状態を項目に記録（`before_state`／`after_state`）。抽選の非表示は除外記録（理由・日時・操作者）も残る
- **元に戻す**: バッチ全体（または項目単位）。抽選は非表示を解除、候補は適用前の状態へ（この再評価で除外したものだけ）
- **保護**: ★／応募・当落／通知・ルール・メモ等の参照／確認済み／人が登録・確認した抽選。タブではなくDBの実態で判定。物理削除はしない
- **マスター統合**: 提案のみ。既存の統合機能で利用者が行う（参照の付け替え・履歴・プレビュー）

## 8. 本番反映の手順と復元方法（承認後）
1. `backup:full`（24時間以内）→ `release-db.mjs plan`（未適用: `20261224000106_stage9h3s.sql`。追加のみ）→ approve → apply → PRマージ → デプロイ確認 → `check-release-9h`（件数不変）。**DB→デプロイの順**（新コードは新しい列・表を使う／旧コードは使わない追加のみの移行）
2. 反映直後に変わること: `saveLottery`（手動・自動収集・自律型）の名寄せが新しくなり、複合名称・表記揺れ・商品の装飾が既存マスターに寄る。**既存データは変わらない**
3. 一括再評価は反映後に、利用者が `/settings/reevaluation` で「計画を作成」→ 内容を確認 → 区分ごとに25件ずつ適用（最終承認の後）
4. 復元: 非表示にした抽選・除外した候補は、画面の「すべて元に戻す」（項目単位も可）。別名の学習で増えた別名は、マスター編集で削除できる（`source=ai`・`status=inferred` で区別）。マスターの統合は既存の統合履歴から。移行は追加のみなので、DBは戻さない。完全バックアップ（`docs/RESTORE.md`）
