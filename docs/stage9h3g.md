## 2. 店舗選択式の推定（`case-model/form-inference.ts`）
優先順位: ①今回の一次情報 → ②今回の複数の情報源 → ③同じ系列・同じ応募方式の過去の確認済みの実績 → ④系列の一般的な傾向。
- **確認済み**: 今回の告知（構造の検査・AIの読み取り・LivePocketの構造解析）に根拠がある。
- **推定**: 今回は確認できないが、実績・傾向から可能性が高い。③は同じ応募方式の実績（人間の評価が複数ならば信頼度「中」）、④は「低」。応募方式が不明（X投稿のみ）のときは、同じ系列の実績を使う。
- **不明**: 判断材料が無い／今回の記載が食い違う。店舗が分からないだけ・「1店舗のみ応募」の制限だけでは店舗選択式と断定しない。
- 今回の告知が店舗別の独立した受付を示すときは、傾向を使わず（`priorOverridden`）、今回を優先する。通販・店舗を持たない抽選は対象外。手動の分類は触らない。
- 反映（`action`）: 店舗が特定できていない → `apply`（推定の店舗選択式として登録候補にする。登録の形に反映）。店舗が特定できている → `propose`（登録の形は変えず、確認候補の警告のみ）。**推定だけで、独立抽選の削除・統合はしない**。`apply` は確認が必要（`conflict` 扱いで自動登録されない）。
- 記録（スキーマ変更なし）: `understanding.trace`（【推定】・優先順位・信頼度・根拠）・`draft.warnings`・`secondary`。確認済みと推定は文面とtraceで区別。
- 判断材料: 人間の評価（`formPriorsFromHuman`。系列は表記揺れを正規化、応募方式は情報源のホストから）＋系列の傾向の辞書（`typical_store_select`、`strength=history|general`）。人間の評価由来の実績があれば、辞書の実績は二重に数えない（`combinePriors`）。**評価JSONは `backups/review-answers/` に置くだけで収集が読み込む**（既存の仕組み）。新しい系列も、評価に店舗選択式の修正が1件あれば同じ仕組みで使える（辞書の追記は不要）。
- 辞書の追加: GEO（一般・基本）、ファミマオンライン（一般・基本）、トレカステーション（実績1）、イオンキッズリパブリック（実績1）。いずれも参考情報で、固定ルールではない。

## 3. LivePocket（`collector/livepocket-structure.ts`）
公開ページの本文から、主催者本文・チケット種別・申込フォームの説明・応募条件・対象店舗・店舗選択の有無・複数店舗の応募制限・受取の指定方法を調べ、A（店舗選択式）／B（店舗別独立）／C（不明）／conflict に分ける。単語だけでなく構造の組み合わせで判断し、**制限の文言だけではCのまま**。確認できなかった項目は `missing` に残す。ログイン・応募操作はしない（本文を読むだけ）。調査エージェントの指示文にも、A/B/Cの区別・確認項目・「傾向だけで店舗選択式と報告しない」を追加した。

## 4. 系列マスター連携（`case-model/chain-resolve.ts`）
登録済みの系列（正式名・別名・表記揺れの正規形）を優先 → 人間が確定した別名 → 一致しなければ名前は変えず、似た名前の候補を注意で示す。部分一致では寄せない（イオン／イオン九州／イオンキッズ…、ゲオ／ゲオマートを誤統合しない）。系列名の解決は店舗選択式の判断と独立。

## 5. 収集経路への接続
`server/collector/run.ts`: 系列名の解決（入口）→ 既存の店舗選択式の判定のあと、推定を適用（`unifiedMode().judgment` のときのみ）。LivePocketのURLなら本文の構造解析をtraceに残す。フラグ無効時は従来と同一（結合テストで確認）。
