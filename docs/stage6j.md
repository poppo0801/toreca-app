# Stage 6J: プロフィール別の抽選管理・UI高速化・iPhone不具合の構造的修正

Stage 6I（Xブックマーク連携）は完了扱いで、今回の対象外。

## 1. プロフィール別の抽選管理
### 表示範囲
| タブ | 表示範囲 |
|---|---|
| 全情報 / ★管理対象 | 世帯で共通（サブの対象系列制限は従来どおり。応募状況・スルーなどの個別情報は共通化しない） |
| 応募済み / 当選 | **現在のユーザー＋紐づくサブ**（サブ自身は本人のみ。他のメイン・紐づかないサブの履歴は混ぜない） |

例: A(メイン)・B(メイン)・C(サブ→A に紐づけ) → A は A＋C、B は B のみ、C は C のみ。

### メイン／サブの紐づけ
- DB: `profiles.main_profile_id`（`20261119000063_stage6j.sql`。追加のみ）。複合外部キー `(main_profile_id, household_id)` で**同一世帯のみ**。紐づけ先が消えたら NULL（`on delete set null`）。
- トリガー `profiles_link_guard`: ①サブだけが紐づけを持てる（メインにすると自動で外れる）②紐づけ先は同一世帯のメインだけ（サブ同士・自分自身は不可。メイン→メインは持てないので**循環は起きない**）③紐づくサブがいるメインはサブにできない。
- 画面: 設定 → ユーザー管理 → 編集。サブのとき「紐づけ先のメインユーザー」（同一世帯の有効なメインから選択。未紐づけも可）。一覧に「→ A」「未紐づけ」を表示。メイン側には紐づくサブを表示。
- 紐づけの変更・解除は応募・当落・購入・受取の履歴に影響しない（履歴は応募アカウントの所有プロフィールに残る。統合テストで変更前後の行が完全一致することを確認）。

### カード・操作
- 応募済み: ユーザーごとに行を分け、アイコン＋名前で誰の記録かを示す（自分だけのときは従来表示）。当選: 当選したユーザーごとに1行（アイコン・名前・期限・記録ボタン）。カードは抽選ごとに1枚（A と C が同じ抽選に応募しても重複しない）。詳細カードの応募状況（ApplyStatusRow）は従来どおり全員分の状態を表示。
- 当落・購入・受取の記録は**必ず応募の所有プロフィールの行に保存**される。メインが紐づくサブの記録を操作するときは、その行・確認ダイアログに「Cの記録として」と明示する。スワイプでの記録は従来どおり**現在のユーザー自身の記録だけ**（サブの記録は行内のボタンで操作）。
- サーバー: サブユーザーは自分の記録だけ操作できる（`ownerScopeError`）。サブの対象系列制限（`subScopeError`）は維持。
### 件数・通知・統計
- タブ件数・赤丸（未対応）はタブの表示範囲と一致。赤丸はタブ内の未対応を示すだけで、**通知の送り先設定には触れない**（メイン画面にサブの履歴が出ても通知先は増えない）。
- タブ件数＝カード数。応募実績・当選率は従来どおりユーザーごとの応募数から計算（`selectLotteries` は集計に使っていない）ので二重計上しない（テストで確認）。

## 2. 起動時の収集結果ポップアップ
- 対象は**固定ID**: `collection_settings.result_notice_profile_id`（同一世帯のプロフィールのみ。表示名を変えても対象は変わらない）。移行時に、表示名が「はとむぎ」の有効なプロフィールが世帯内に**ちょうど1人**のときだけそのIDを設定した（本番で設定されたことを確認）。NULL なら表示しない。
- 判定はサーバー（`getRunNoticesAction(profileId)`）。対象外のプロフィールには何も返さず、ベル・設定画面の履歴は従来どおり。
- ボタンは「確認する」「閉じる」の2つだけ。「確認する」は要手動確認の一覧（`/settings/collection#manual`）へ直接移動。
- 速度: ①「確認済み」の記録（サーバー処理）を、ボタン操作後ではなく表示時に行う（操作後に走らせると、サーバー処理の完了待ちで画面遷移が遅れる）②ポップアップは即座に閉じ、`router.push` で移動 ③移動先に `loading.tsx` を追加し、サーバーの集計中も即座に画面が切り替わる。**計測結果は §7**。

## 3. 自動収集候補の操作
- 「要手動確認」→「編集して登録」: 収集候補の一覧を経由せず、**対象候補の編集フォームを直接開く**（`EditRequestProvider`。解析済みの内容を反映／キャンセルで元の画面／登録後は一覧を更新）。
- 左右スワイプ（`SwipeRow`。要手動確認・収集候補）: **右＝編集フォーム／左＝その候補を除外**。縦スクロール優先（横が縦の1.8倍以上のときだけ横と判定）、一定距離で確定、離すと流れて消える。除外は確認・Undoなし、即座に一覧と件数から外れ、保存に失敗したら行を戻してエラー表示。候補は物理削除せず（`status=excluded`）、収集元の除外ルールは作らない。連続操作を妨げる待機なし（行ごとの短いアニメーションのみ）。
- 収集候補: 10件/ページ（15件に切替可）、前へ/次へ・「n / N ページ」。ランク絞り込み・並び順を維持し、変えたら1ページ目へ。編集・除外後は今のページに留まる。全件を一度に描画しない。

## 4. その他のUI
- コレクションの光の演出: 周期を短縮（上位ティア 6秒→SAR/UR 3秒・SR 3.8秒。走る時間は周期の約25%）。元画像の色は変えない（静止時は何も乗らない／触れた位置にだけ）。**画面外のカードは演出を止める**（IntersectionObserver）。動きを減らす設定では従来どおり停止。
- 抽選管理タブの赤丸: タブ名の**左**（文字に重ねない・全タブで同じ配置）。表示条件は従来どおり。

## 5. iPhone 下部メニュー
原因分析・構造・未確認事項は [stage6j-viewport.md](stage6j-viewport.md)。要点: 過去の対応はすべて「`position:fixed` のメニューを測定値で補正する」同じ構造の上の修正で、iOS の一時的な値の食い違いに対して補正が残る／効きすぎるのどちらかになった。現在は画面全体を固定の入れ物（`fixed inset-0` の縦flex）にして、スクロールを `main` の中だけにし、下部メニューを入れ物の最下段に置いた（測定・補正・タイマーを廃止）。**実機未確認。**

## 6. 起動時の黒画面
### 調査結果（事実）
- 本番のHTML応答の時間（`curl`、サーバー東京リージョン）: **コールドスタート時 約2.0秒／ウォーム時 約0.19秒**。しばらく使っていないあとの最初のアクセスで、サーバー関数の起動に約2秒かかる。これが「2〜3秒の黒画面」のうち**サーバー側**で説明できる部分（最初のHTMLが届くまで、iOSは何も描画できない）。
- アプリ側のロード画面（`SplashScreen`）は最初のHTMLに含まれ、JavaScriptやデータを待たずに表示される（`Suspense` のストリーミング）。つまりHTMLが届いてからの黒画面はない。HTMLが届く前（iOSのプロセス起動・WebViewの準備・通信・サーバー起動）は、Webアプリ側では描画できない。
### 対策（実装）
- **iOS の起動画面（`apple-touch-startup-image`）**を追加（11機種相当 × ライト/ダーク = 22枚、計約0.8MB。`scripts/build-startup-images.mjs` で生成）。ホーム画面アプリの起動からHTMLが届くまでの間、黒（または白）の代わりにロゴ入りの画面（ロード画面と同じ背景・ロゴ）を出す。
### 切り分け
- OS側: iOS のプロセス起動・WebViewの準備（アプリでは変えられない）。サーバー側: 関数のコールドスタート（約2秒）— 起動画面で見た目の黒画面は無くせるが、時間そのものは短縮していない。アプリ側（HTML到着後）: ロード画面が即時表示されるため黒画面は発生しない構造。
### 未確認
- iPhone 実機での黒画面の有無・時間。起動画面は端末が**ホーム画面に追加した時点**で保存することが多く、既にインストール済みのアプリは**一度削除して追加し直す**と反映される場合がある。サーバーのコールドスタートそのものの短縮（常時起動など）は行っていない。

## 7. 計測結果（実Supabase＋ローカル本番ビルド、Chromium のモバイルエミュレーション。iPhone 実機の値ではない）
| 項目 | 結果 |
|---|---|
| 「確認する」押下→ポップアップが閉じる | 約30ms |
| 押下→URLが要手動確認へ変わる | 約45ms |
| 押下→最初の画面（読み込み表示）が出る | 約50ms |
| 押下→要手動確認の一覧が表示される（サーバーの集計を含む） | 約1.4秒 |
| 起動（ローカル）: HTML到着 / 最初の描画(FCP) / ロード画面 / 抽選管理の画面 | 約6ms / 約40ms / 約75ms / 約0.9秒 |
| 本番の最初のHTML到着（コールドスタート時 / ウォーム時） | 約2.0秒 / 約0.19秒（`curl`） |

- **修正前の遷移時間は計測していない**（古い実装を再現して測っていない）。利用者の報告は「数秒」。修正前に遅れうる原因は、ボタン操作の直後に「確認済み」の記録（サーバー処理）を走らせていたこと、移動先の画面がサーバーの集計を終えるまで切り替わらなかったこと。修正後は、記録を表示時に行い、移動先を即座に切り替える（読み込み表示を先に出す）ため、体感の遅れは約50msになった。一覧が表示されるまでの約1.4秒は、サーバーが候補や統計を集計する時間（遷移前後で同じ処理）。
- スワイプ: 指を離してから行が流れて消えるまでは約0.14秒（アニメーション）。除外の保存は消えた後に非同期で行う。
- 黒画面（HTML到着まで）はサーバーのコールドスタート（約2秒）が主因で、ローカルでは再現しない。起動画面で見た目の黒画面は無くせるが、時間そのものの短縮は行っていない。
