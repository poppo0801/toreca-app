# Stage 9A: 抽選情報収集の自律化（情報不足でもまず登録する）

開発環境のみ。本番DB・本番データには触れていない。マイグレーションの追加なし。新しい有料API評価は実施していない（費用の発生なし）。収集処理（`src/lib/server/collector/`）の挙動を変えるため、**本番へ反映すると自動収集の挙動が変わる**（§7）。

## 1. 現状の収集システムの分析（コードと既存の調査文書から）
一次資料: コード（`collector/`・`src/lib/collector/`）、`docs/auto-collection-audit.md`（2026-11-05 本番の読み取り調査）、`docs/stage7a.md`（2026-11-08 本番の確認待ち27件の分析）。**今回、本番データは読んでいない**（本番に作用する作業の入口は利用者の端末のみ）。以下の本番の数値は上記文書の引用で、今日の値ではない。

- **構成**: 収集元（まとめサイト一覧・X公式API・店舗公式Xの対応づけ・ブックマーク・優先収集メモ）→ 候補（`collection_candidates`）→ キュー（`claim_collection_jobs`。優先順位: 締切が近い・新規・変更・ブックマーク）→ AI解析（1日の上限約30件・予算ガード）→ 固定ロジックの判定（マスター照合・地域・商品・重複・`isReady`/`decideRegistration`）→ 自動登録／保留（自動再調査）／要手動確認／自動除外。AIは「告知の読み取り」、固定ロジックは「登録の可否・重複・地域」を担う。
- **見逃しの区別**: ①収集できていない（取得制限・robots・JS描画・X投稿の取得失敗＝`auto-collection-audit` §8.3）②収集できたのに登録されていない（確認待ち・保留・除外）。②の主因は、文書 §1（7A）の分析では「系列・店舗の判別失敗 17／受取方法・応募条件の不明 15／応募URL・方法の不足 13／情報が少ない 11／締切・発表日の不足 6」（27件・複数計上）。7A で、受取方法・応募条件・店舗・発表日などの不足は「注意付きの自動登録」になった。
- **今回特定した、方針（情報不足でもまず登録）と食い違う点**:
  1. **応募締切が不明・受付前・日時が未発表（予告）の告知は、必ず確認待ち（追跡）**になっていた（`attention.ts` の C 条件）。抽選として認識できても、利用者の一覧に出なかった。
  2. **続報で日時が分かっても自動補完できない**: 既存の抽選の締切が未確認だと、同じ店舗・同じ商品でも「応募締切が不明なため同一か判断できません」（`lottery-match.ts`）で人の判断待ちになった。
  3. **手動編集の保護に不具合**: 情報源URLの追記（`appendSourceUrl`）が「自動処理の印（`cautions_updated_at`）」を更新するため、手動で編集された抽選でも、その後の自動補完が手動の値を上書きできてしまう状態だった（手動編集の検出が無効化される）。
  4. 登録済みの抽選への**補足投稿（応募条件だけの投稿）が補完先を見つけられない**（補完先が確認待ちの候補だけだった）。
  5. 受取方法・応募方法が、既存と続報で食い違っても、登録済みの抽選では相違が記録されなかった。
  6. 応募締切が未確認の抽選の情報源の**再確認の優先順位**が、他と同じ（古い順）だった。
- **変更しなかったもの（調査のみ）**: 情報源の追加探索（検索・巡回）、X投稿の画像解析・外部リンクの追跡の拡張。既存の仕組み（画像解析・リンク先取得・ページの再確認・robots 尊重）は維持。

## 2. 実装した改善
| 項目 | 内容 |
|---|---|
| 登録方針 | 締切が不明・開始前・日時が未発表でも、抽選の告知と認識できれば**注意付き（B）で登録**。不明な日時は推測せず、構造化した注意 `deadline_unknown` として保持（`attention.ts`）。 |
| 登録しないもの | ①抽選・応募の文言が無い告知 ②**憶測・未確定の表現**（「〜の模様」「噂」「詳細不明」など。`isSpeculative`）で日時もない告知 ③日時が不明のまま**告知から21日超**（終了済みの可能性。`STALE_UNKNOWN_DEADLINE_DAYS`）④従来どおり: 系列・商品が特定できない／商品がマスター未登録／情報源なし／重複の疑い／収集条件の対象外／重大な矛盾。これらは確認待ち（自動再調査）に残る。 |
| 自動補完 | 続報で応募締切・応募開始が分かれば既存の抽選を補完し、`deadline_unknown` を解除（`planCompletion`）。値のある項目は上書きしない。受取方法・応募方法の食い違いは上書きせず相違の注意に残す。 |
| 続報の同一判定 | 「締切が未確認で自動登録された（注意あり・30日以内）抽選」と、同じ店舗・同じ商品の続報は同一とみなして補完（`lottery-match.ts`）。確定した締切がある抽選・店舗が違う場合・古い場合は従来どおり人の判断。 |
| 補足投稿 | 補完先を、確認待ちの候補に加えて「最近自動登録した抽選」から探す。一意に決まるときだけ、応募条件が**未登録のときだけ**補う（`autoCompleteConditions`）。決まらなければ関連候補として記録（同じアカウントというだけでは統合しない）。 |
| 手動編集の保護 | `appendSourceUrl` が、すでに手動編集された抽選では自動処理の印を更新しない（不具合の修正）。 |
| 再調査の優先順位 | 既存の「情報源ページの再確認」（`recheckPages`）で、`deadline_unknown` の抽選の情報源を先に確認する（優先順位: 重要情報が不足している抽選）。上限（1回の件数・時間）は従来どおり。 |

固定ロジックと自律の分担: 登録の可否・重複・補完の規則は固定ロジック（`decideRegistration`・`planCompletion`・`findDuplicates`）。AIは告知の読み取りと追加調査の材料の取得。AIが無制限に呼ばれる構造ではない（1日の解析上限・再確認の件数・時間の上限は変更なし）。

### 守られているもの（テストで確認）
応募・当選の記録・通知設定は変わらない（補完は日時・方法・条件の列だけを更新。応募の記録を実際のスキーマで作成して不変を確認）。手動で編集された抽選は補完されない。別店舗・別企画は統合しない（店舗不明の続報は、どの抽選か決められないため統合せず確認待ち）。取得制限・robots は回避しない（変更なし）。

## 3. 情報不足でも登録できる範囲
| 不明な項目 | 登録 | 注意 |
|---|---|---|
| 応募締切・応募開始（抽選の文言あり・告知から21日以内・憶測表現なし） | する | `deadline_unknown` |
| 当選発表日・購入/受取期間・受取方法・応募方法・応募条件 | する | 従来の注意（7A） |
| 店舗 | する（系列設定により店舗選択式／未設定） | `store_unconfirmed` 等 |
| 系列・商品（マスター未登録を含む）・情報源URL | しない（確認待ち） | — |
| 抽選かどうか不明／憶測の表現／重複の疑い／重大な矛盾 | しない | 自動再調査 |

画面: 既存の注意アイコン・詳細の「確認が必要な点」を使う（新しい画面・ボタンなし）。締切が不明な抽選は、一覧では締切の文字を出さず（注意アイコンのみ）、詳細では「—」。通常の一覧（全情報）に表示される（単体テストで確認）。通知は日時が不明の項目を対象にしない（既存）。

## 4. 自動補完・再調査の仕組み
登録後、①収集の続報（同じ店舗・商品の告知）→ 既存の抽選を補完 ②情報源ページの再確認（内容の変化を検出→再解析→補完）、`deadline_unknown` の抽選は優先。確認できなかった項目は不明のまま保ち、保留の再調査は既存の間隔（30分→2h→6h→12h→24h・上限回数）で無駄な繰り返しをしない。一度確認した値は、取得失敗や情報不足では消えない（値のある項目は上書きしない）。

## 5. 評価（実データ・再構成・架空の区別）
- **実データによる改善前後の比較は、今回はできていない**: 候補（確認待ち・保留・除外）の保存データは本番にのみあり、開発環境には無い。本番の読み取り分析は、利用者の端末から既存の読み取り専用スクリプト（`scripts/analyze-review-queue.mjs`）で行える（→ §8）。**発見率・登録率・誤登録率・重複率・項目別の抽出精度は、推測では算出していない**。
- **方針の適合確認（架空）**: `eval/collection-9a/scenarios.json`（17件・架空）と `src/lib/collector/stage9a.test.ts`。expected は方針の文言だけから決め、old は 7A 時点の判定。結果: 17件すべてが方針どおり。旧方式で登録 3件 → 新方式 8件（変わったのは、日時が未発表・不明・受付前だけが理由で確認待ちだった5件。登録→保留に変わったものは0件。保留すべき9件は保留のまま）。**これは精度ではなく、方針への適合の確認**。
- **統合テスト（架空データ・DB）**: 締切不明の登録／続報での補完・二重登録なし／応募記録の不変／手動編集の保護／憶測・文言なしの非登録（`tests/stage9a.integration.test.ts`）。旧方針を前提にしていた 6C・6D のテストを新方針に更新した。

## 6. 費用・時間の見積もり
新しい有料API評価はしていない。AI解析の回数は、変更によって増えない（解析の入口・1日の上限は不変）。むしろ、日時が未発表で保留→再調査していた候補が、保留の再解析を繰り返さず登録されるため、再解析の回数は減る方向（**未測定**）。再確認（無料の取得）は、優先順位を変えただけで件数の上限は不変。

## 7. 本番へ反映する前に（本番に影響する変更）
- 収集の判定が変わる（日時が不明・予告・受付前の告知が、確認待ちではなく注意付きで登録される）。**一覧に表示される抽選が増える**。誤登録の増加の有無は、実データで未検証。まず本番の読み取り分析（§8）で、現在の確認待ちのうち登録に変わる件数を見積もることを推奨。
- 追加のマイグレーションなし。戻す方法: コードのみの変更のため、前のコミットへ戻せる。登録された注意付きの抽選は、既存の「除外」で退避できる（応募・購入履歴は保持）。
- `docs/PRODUCTION_ROLLOUT_8D.md` とは別系統（8F はグループ化。9A は通常の収集）。

## 8. 残るリスク・次にまとめて進められる改善
1. **本番の読み取り分析（利用者の端末）**: 確認待ち・保留・除外の現状を、新方針で再判定した場合の件数（読み取りのみ）。実データでの改善前後の比較・発見率・誤登録率の算出はここから。
2. 店舗不明の続報が、店舗不明の既存抽選と「店舗が確定している抽選と未確定の抽選」の判定で確認待ちに残る（誤統合を避けるため）。系列・商品・時刻が一意に決まるときの自動統合は、実データで検証してから。
3. 登録済みの抽選の**変更告知（締切の延長など）の自動反映**は未実装（現状は更新の提案＝人の承認）。差分・根拠の保存、復旧、手動編集の保護を備えた形で設計できる。
4. 情報源の追加探索（AIが調査対象を選ぶ）、X投稿の画像解析・外部リンクの追跡の拡張。費用と上限の設計が必要（有料API評価は承認制）。
5. 日時が不明のまま長く残る抽選の自動整理（現状は21日超の新規は登録しない。登録後に日時が出ない抽選の扱い）。
6. iPhone 実機は未確認。画面の変更なし（既存の表示を使用）。
