# トレマネ：自律型AI移行・継続改善の基本方針

- 制定：2026-11-20
- 状態：ユーザーが明示的に採用した長期基本方針
- 適用対象：トレマネの情報収集・解析・登録・再調査・名寄せ・重複判定・学習・運用・評価
- 想定配置：`docs/AI_AUTONOMY_PRINCIPLES.md`

## 1. 最終目的

既存の情報収集・管理機能を可能な限り活用しながら、判断の主体を分散した固定ロジックから、根拠を参照し自律的に調査・照合・判断できるAIへ移す。単なる「AI化」ではなく、従来より高い情報収集力・正確性・運用効率を、同等以下の費用で実現することを目指す。

## 2. 変更時の原則

1. **慎重さと大胆さを両立する。** 既存の実装や暫定ルールの維持自体を目的にしない。構造上の問題には大胆に手を入れる。一方、実績のある機能、データ、利用者の判断、応募・購入等の履歴、安全対策を不用意に失わない。
2. **AIを総合判断の主体とする。** 抽選の応募機会の同一性、店舗選択式か店舗別独立か、重複、系列・商品の同一性、追加調査の必要性を、複数の情報源・既存データ・過去の判断を踏まえて一貫して扱う。固定ロジックの相互上書きや店舗別の例外規則の積み増しを避ける。
3. **固定ロジックは有効な用途に残す。** 安価で確実な前処理、キャッシュ、取得制限の尊重、データ整合性、根拠の検証、費用上限、アクセス権、履歴保護、復元可能性などを担わせる。AIに任せること自体を目的化しない。
4. **既存資産を再利用する。** 9H系の案件ファイル・調査エージェント・統合・判断履歴、9Zの原文保存、既存の名寄せ、収集元、通知、地域判定、費用制御などを棚卸しし、再利用可能なものを活用する。ただし実装済みと本番稼働中を混同しない。
5. **実測に基づき移行する。** 新旧方式を同条件で比較し、必要に応じてシャドー運用・段階的切替・ロールバックを使う。保守的すぎるために改善を止めず、未検証の変更を無条件で本番適用もしない。

## 3. 使うほど精度と効率が向上する仕組み

- 一度取得した原文・取得日時・取得経路・情報源の信頼性・抽出結果・根拠・判断履歴・人間の訂正・重複や誤判定の原因・調査の成否・費用を、必要な範囲で蓄積する。
- 次回以降の収集・解析・照合・追加調査にそれらを検索・再利用し、同じ調査や誤判定を繰り返さない。
- AIが情報源別の成功率、判定の誤り、処理時間、費用を分析し、より良い探索順序・参照情報・判断手順の改善案を発見できる構造を目指す。
- **保存するだけでモデル自体が自動学習するわけではない。** 検索・参照、フィードバック、評価、改善案の検証・採用を組み合わせ、運用上の継続的な改善を実現する。
- AIによる自己変更や判断基準の更新には、評価・バージョン管理・費用上限・異常時停止・復元手段を設ける。重大なデータ変更や安全上の権限拡大をAIが独断で行わない。
- 保存容量・個人情報・著作権・保管費用を考慮し、原文・要約・構造化データ・統計の使い分け、保存期間、重複排除、圧縮、削除基準を設計する。

## 4. 成果の評価

新旧方式を、少なくとも次の観点で比較する。

- **収集力**：有効な抽選の発見数・発見率・速報性・見逃し
- **正確性**：応募単位、店舗選択式、重複、系列、商品、日付、根拠の正確性、誤統合・誤分割
- **完結率**：確認待ちの滞留、追加調査による解消、登録までの時間
- **費用効率**：AI/API/取得・保存費用、正確な登録1件あたりの費用、手動修正工数
- **継続改善**：過去の証拠の再利用率、同種誤りの再発率、調査成功率の推移
- **機能維持と安全**：既存機能の回帰、応募・当選・購入履歴、利用者確定情報、予算超過、無限ループ、情報漏洩、復元性

単にAI呼び出し回数や登録件数を増やすことを成功としない。改善が実証できない機能は再評価するが、費用・安全・性能の合理的な根拠なしに挑戦を止めない。

## 5. 仕様管理・開発時の適用

- 本文書を長期基本方針の参照先とし、`CLAUDE.md` に短い必読指示を設ける。関連作業では `docs/PRODUCT_VISION.md`、`docs/SPEC_GOVERNANCE.md`、`docs/CURRENT_SPEC.md`、`docs/DECISION_REGISTER.md`、`docs/ACTIVE_ROADMAP.md` と併せて確認する。
- 既存コードの動作を、ユーザーが採用した仕様そのものとみなさない。文書とコードが異なる場合は、設計意図・実装事実・差異を区別する。
- 個別のStage報告や古い履歴が本方針と矛盾する場合、ユーザーの最新の明示決定と仕様管理規則に従って整理する。
- 設計・実装案を提示する際は、本方針との整合、既存資産の再利用、機能後退の可能性、費用・安全・保存の影響、検証方法を明示する。
- 本文書の基本方針を変更する場合は、ユーザーの明示的な承認を得て、決定台帳と仕様の正本を整合させる。

## 6. Stage 10Bで判明した移行上の前提

2026-11-20の調査では、9H系の中核機能は本番で有効化できないコード上の制限があり、通常収集の判断主体は固定ロジックであると報告された。`CLAUDE.md` には古いStage記述と現状の不整合が残る。これらは今後の設計・移行計画で解消対象とする。ただし本方針は特定の実装方式や段階番号を固定するものではない。

## 7. 自律の回復（2026-11-27 利用者の明示決定。§1〜§5 を具体化する）

経緯: Phase 3 の実測で、保守的な固定の検証・調査と推論の制限（思考が働かない呼び出し方、候補全体45秒の締切、語彙による意味判定、ページの有無による除外の停止など）が、AIの正しい判断を失わせていたことが分かった。利用者は「保守的な設計、固定検証、調査・推論の制限は利用者の希望ではない」と明示した。以後、次を恒久方針とする。

1. **AIが総合判断の主体。** 探索、情報の取捨選択、調査の方法・順序・継続、複数の応募機会の理解、情報源の信頼性と意味、登録・除外・保留、名寄せ、重複、判断の再検討は、原則としてAIが担う。
   - 店舗固有の規則や、語彙・閾値による意味判断を増やさない。
2. **プログラムの役割を限定する。** プログラムが担うのは次に限る。
   - 取得・保存・ツールの実行
   - 客観的な整合（引用の実在、時刻・数値・対象IDの整合）
   - 権限、費用と暴走の防止、人の確定値と履歴の保護
   - 固定の規則をAIへの手がかりにする場合も、絶対条件にしない。AIが根拠をもって異なる結論を出せるようにする。
3. **制約は存在するだけで正当化されない。** 採用できるのは、実測で必要性・利点・機会損失を説明できる制約だけとする。
   - 先に代替案（再開、非同期化、根拠の再調査）を検討する。
   - 暫定の制約には、理由・適用範囲・解除条件・見直しの時点を明示する。
   - 性能に関わる制約を追加・変更したら報告に書く。重要な制約を無断で恒久化しない。
   - 利用者が示した実例・仮説を、固定の規則にしない。
4. **ある制約を別の固定規則に置き換えるだけの改善は、改善とみなさない。**
5. **性能を優先し、実測し、必要最小限の費用最適化を行う**（この順序）。
   - 以前の低コストの目標（§1 の「同等以下の費用」を含む）を、性能を犠牲にする絶対条件にしない。
   - モデル・推論・調査の能力は、費用と精度の実測で選ぶ。
6. **実行環境の上限は、1回の実行の外枠として扱う。調査全体の締切にしない。**
   - 時間・予算に達したものは「未完了・再開待ち」とし、情報不足の保留や除外と混同しない。
   - 後半の機会だけ思考・調査を削る設計にしない。
7. **評価だけで緩和して本番は旧い制約のまま、という状態を作らない。** 本番シャドーでも、AIが十分に調査・推論・判断できる構造にする。
8. **権限は分けて扱う。** AIの調査・推論・意味判断の自由度と、本番データへの変更権限は別に扱う（§3 の自己変更の制限は維持）。新AIの本登録・変更・削除・応募・通知は、別の承認による。
9. **区別を守る。** 利用者の要望、技術上の事実、開発者が決めた暫定措置を区別する。保守的な制約を利用者の仕様とみなさない。
   - 古いStageの暫定制約・仕様が本節に反する場合は、本節を優先する。履歴は改変せず、失効・置換を明記する。
